# SuDuo 客户端源码运行（macOS / Windows）

> 一句话：使用者在 Mac（Apple 芯片 / Intel）或 Windows 10/11 上克隆仓库，装好 Node 和 pnpm 后执行 `pnpm install` 和 `pnpm start`，就能自动构建、启动本机服务并打开浏览器。｜最后更新：2026-10-02
>
> 同批需求：[开源与商用授权](开源与商用授权-需求.md)、[云端私有化部署](云端私有化部署-需求.md)、[产品中英双语](产品中英双语-需求.md)、[官网](官网-需求.md)。相关在办：[遗留 token 文档漂移](文档漂移与runtime事件噪音-需求.md)（README 里的访问令牌说法已失效，两边改 README 时要对齐）。

## 需求描述

客户端由本机服务（`client/server`，只听 127.0.0.1）和它托管的前端组成，模型调用交给工作区锁定版本的 Codex CLI。安装包和签名暂缓（用户 2026-10-02：「client 就让他们自己运行先」「我们后面再沟通打包的问题吧」），所以使用者要从源码运行。

现状：

- **Linux / WSL**：有 `pnpm install:m1`（构建 + 注册 systemd 用户服务），官方全链路测试 gate-c 依赖它。
- **Windows**：有 NSIS 安装器代码（暂缓发布），没有源码运行的说明。
- **macOS**：只有开发联调脚本 `dev-local.sh`，它会把云端和客户端一起拉起，不适合普通使用者。
- 生产方式启动要手动 `pnpm build`，再带环境变量运行 `pnpm --filter @suduo/client-server start`，然后自己打开浏览器。

本需求给 Mac 和 Windows 提供一条统一、可重复的路径：

1. **一条命令启动**：`pnpm start` 自动判断是否需要构建、启动服务、打开浏览器；已经在跑就直接打开浏览器。
2. **环境自检**：缺 Node、版本不对、原生模块没装好、Codex 没登录时给出明确的下一步。
3. **版本信息**：显示本机版本与所连云端版本，不一致时提示。
4. **中英文快速开始文档**：Mac 和 Windows 各一份从零开始的步骤，以及更新方法。

## 二、背景与目标

**目标对齐**：使用者是团队里的工程师（会用终端、会装 Node），不一定熟悉 pnpm 工作区。他照着快速开始，十五分钟内从零跑起 SuDuo：克隆、装依赖、`pnpm start`，浏览器自动打开工作台，在设置里填上团队云端的地址，注册登录，选本机工作目录，从需求开工。模型账号用他自己的 Codex 配置，SuDuo 不经手。以后更新是 `git pull` 再 `pnpm install` 和 `pnpm start`。

**模拟示例（Windows 11）**：

```
PS> winget install OpenJS.NodeJS.LTS          # 或从 nodejs.org 下载 24.x
PS> npm install -g pnpm@10.25.0
PS> git clone https://github.com/Im-Sue/suduo-workbench.git; cd suduo-workbench; git checkout v0.7.0
PS> cd client; pnpm install
PS> pnpm start
  SuDuo 0.7.0 · Node 24.10.0 · Codex 0.159.2
  首次运行，正在构建（约 1–2 分钟）…
  ✓ 本机服务已启动：http://127.0.0.1:8787
  ✓ 已在浏览器中打开
  按 Ctrl+C 停止。

（第二天再次运行，服务已在跑）
PS> pnpm start
  ✓ SuDuo 已在运行，已在浏览器中打开
```

- **背景**：
  - 本机服务已经会自动使用工作区锁定的 Codex（`node_modules/.bin/codex`），也会自动建数据目录。
  - Windows 安装器的启动器（`client/scripts/dist-win/templates/launcher.mjs`）里已经有「探测是否在跑 → 拉起 → 等就绪 → 开浏览器」的逻辑，可以复用。
  - 自检脚本 `pnpm run doctor` 已有 Windows 分支。
  - 设置页「关于」已显示本机版本与 Codex 版本。
  - macOS 默认数据目录目前是 `~/.local/share/suduo`（沿用 Linux 习惯），不符合 Mac 惯例。
- **目标**：
  1. Mac（Apple 芯片 / Intel）与 Windows 10/11 x64 上，`pnpm install` + `pnpm start` 即可使用。
  2. 常见环境问题都有明确提示，不需要看源码排查。
  3. 更新路径清楚，本机数据跨版本自动迁移。

## 三、讨论与决策

### 讨论：Windows 最低版本

- 用户最初要求 Win7 起步。Claude 说明了三个独立障碍：客户端运行时 Node 24 不支持 Win7；Win7 最后能装的 Chrome / Edge 是 109 版，而界面使用的 Tailwind v4 需要 Chrome 111 以上；Win7 早已停止安全更新。
- **最终决策（用户 2026-10-02「可以」）**：Windows 10 / 11 x64 起步。

### 讨论：macOS 范围

- **决策**：Apple 芯片与 Intel 都支持（用户原话）。受 Node 24 官方二进制限制，最低 macOS 13.5；Intel 机型大致是 2017 年及以后的 Mac。

### 讨论：Linux / WSL 客户端

- 它是项目最早的安装方式（`pnpm install:m1` + systemd 用户服务），gate-c 在 Ubuntu 虚拟机里依赖它。
- **决策**：保留脚本供开发和 gate-c 使用；对外文档不列为支持平台。`pnpm start` 在 Linux 上顺带可用，但不承诺。

### 讨论：要不要做开机自启 / 常驻

- **决策**：不做。`pnpm start` 前台运行，关掉终端或按 Ctrl+C 即停止。常驻、自启和托盘图标留给以后的安装包。

### 讨论：Mac 默认数据目录

- **决策（Claude 推荐，随本需求确认）**：macOS 默认改为 `~/Library/Application Support/SuDuo`；Windows 保持 `%LOCALAPPDATA%\SuDuo`；Linux 保持 XDG 目录。设置了 `SUDUO_DATA_DIR` 的不受影响。在源码公开之前改：目前没有外部使用者，不需要迁移旧目录（用户本机联调用的是独立数据目录）。

## 四、功能 / 范围

### 4.1 `pnpm start`：一条命令启动

| 项 | 说明 |
|----|------|
| 做什么 | 在 `client/` 下执行：① 检查 Node 版本（≥ 24.10）与依赖是否已安装；② 产物不存在或源码比产物新时构建；③ 探测本机端口：已经是 SuDuo 在跑 → 直接打开浏览器；被其他程序占用 → 报错并说明怎么换端口；空闲 → 启动服务；④ 等待就绪（超时给日志位置和自检命令）；⑤ 打开默认浏览器；⑥ 前台运行，Ctrl+C 优雅停止 |
| 参数 | `--port <端口>`、`--no-open`（不开浏览器）、`--rebuild`（强制重建）；也认现有环境变量（`SUDUO_PORT`、`SUDUO_DATA_DIR`、`SUDUO_REQUIREMENTS_SERVICE_URL` 等） |
| 日志 | 控制台精简输出；完整日志写到数据目录下的 `logs/` |
| 平台 | macOS 13.5+（arm64 / x64）、Windows 10/11 x64；PowerShell 与 cmd 都能用 |

### 4.2 环境自检

| 项 | 说明 |
|----|------|
| 做什么 | `pnpm start` 启动前做快速检查，失败时给一句话原因和下一步；完整检查仍用 `pnpm run doctor`，并确认它在 Mac 与 Windows 上都能跑通 |
| 覆盖 | Node 版本不符；没执行 `pnpm install`；SQLite 原生模块加载失败（给出重装或安装编译工具的办法）；锁定版本的 Codex 不在；Codex 没有可用的模型配置或登录（提示执行 `pnpm exec codex login` 或编辑 `~/.codex/config.toml`）；端口被占用 |
| 原则 | Codex 怎么配由使用者自己决定（用户原话：「他们自己配置」），SuDuo 只检查、只提示，不代填、不读取密钥 |

### 4.3 版本信息与云端版本比对

| 项 | 说明 |
|----|------|
| 做什么 | 启动横幅打印 SuDuo、Node、Codex 版本。设置页「关于」在现有本机版本、Codex 版本之外，加「云端版本」（来自云端健康检查，见[云端私有化部署](云端私有化部署-需求.md) §4.6）。两边版本不一致时，在「关于」和连接设置处显示提示：「本机 0.8.0，云端 0.7.0，建议使用相同版本」 |
| 原则 | 只提示，不拦截（ADR-0004） |

### 4.4 更新

| 项 | 说明 |
|----|------|
| 做什么 | 文档写明：`git fetch --tags && git checkout <新标签>` → `pnpm install` → `pnpm start`（自动重建）。本机数据库随启动自动迁移 |
| 降级 | 不支持把本机数据库降回旧版本；文档写明降级前先备份数据目录，降级后从备份恢复或重建 |

### 4.5 快速开始文档（中英双语）

| 项 | 说明 |
|----|------|
| 做什么 | README 的「快速开始」改为面向使用者：系统要求 → 安装 Node 与 pnpm（Mac：官方安装包 / Homebrew / mise；Windows：官方安装包 / winget）→ 克隆并检出发布标签 → `pnpm install` → `pnpm start` → 配置 Codex → 连接团队云端 → 选择本机工作目录。另附常见问题：原生模块编译失败、端口占用、公司代理、Codex 登录 |
| 开发者内容 | 开发联调（`dev-local.sh`、gate、mise）移到 `CONTRIBUTING.md` 或独立的开发文档，不放在使用者路径上 |
| Windows 安装器 | README 不再把 setup.exe 作为主路径；代码保留，标注「暂未发布」 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 正式支持 macOS 13.5+（Apple 芯片、Intel）与 Windows 10/11 x64 | Linux / WSL 仅供开发与 gate-c，不对外列出 |
| R2 | 只使用工作区锁定的 Codex 版本 | 沿用现状（`resolvePinnedCodexBin`），避免用户全局 Codex 版本与协议不一致 |
| R3 | 本机服务只听 127.0.0.1 | 沿用现状，不提供改监听地址的参数 |
| R4 | SuDuo 不写入、不读取用户的模型密钥 | Codex 配置由使用者自己完成 |
| R5 | 版本不一致只提示不拦截 | ADR-0004 |
| R6 | 端口被其他程序占用时不强占、不杀进程 | 报错并说明 `--port` 用法 |

- 不做安装包、签名、公证、自动更新（用户明确暂缓）。
- 不做开机自启、后台常驻、托盘图标。

- 不支持 Windows 7 / 8、32 位 Windows、Windows on ARM（后者未验证）。
- 不改现有 Linux 安装脚本（`install:m1`）的行为。

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |
|------|----------|
| Windows 下源码运行的数据目录与（暂缓的）安装器版是否冲突 | 已定：源码运行默认改为 `%LOCALAPPDATA%\SuDuo\data`，与安装器版共用一份本机数据 |
| 验收设备 | 已定（用户 2026-10-02「我有win11没有intel mac」）：Apple 芯片 Mac 用本机；Windows 11 用用户的电脑，Claude 提供逐步验收清单，用户执行并回报结果；Windows 10 与 Intel Mac 没有设备，交付时标为「未实机验证」。可选补充：用 GitHub Actions 的 Windows 与 Intel macOS 托管运行器跑一次「安装依赖 → 构建 → 启动 → 健康检查」冒烟（Intel macOS 运行器届时是否仍提供，实施时核实） |
| `pnpm start` 的「是否需要重建」判断 | 已定：产物缺失、或任一源码 / 依赖清单比上次构建标记新时重建；`--rebuild` 强制重建 |
| 是否用浏览器「应用窗口」打开（无地址栏） | 倾向默认用系统默认浏览器的普通标签页；应用窗口模式留给以后的安装包 |

| 实施中发现的缺陷（已修） | 没有设置 `SUDUO_CODEX_HOME` / `CODEX_HOME` 时，本机服务把 Codex 的配置目录默认成仓库里的 `client/.codex`（不存在），Codex 启动即退出。改为 Codex 自己的默认目录 `~/.codex`（`defaultCodexHome()`），与自检、Linux 安装脚本一致。联调栈与 gate-c 一直显式设置 CODEX_HOME，所以此前没暴露 |
| 版本比对的落地 | 本机服务测试云端连接时带回云端健康检查里的版本；「关于」显示云端版本，与本机不同时给出提示；「需求服务」的连接测试结果也带上云端版本 |

## 十四、Windows 11 验收清单（用户在自己的电脑上执行）

每一步记下「通过 / 不通过」，不通过时把命令行输出或截图发回来。

**准备**

1. 安装 Git for Windows（<https://git-scm.com/download/win>）和 Node.js 24（<https://nodejs.org/> 下载 v24 的 Windows 安装包）。
2. 以管理员身份打开 PowerShell，执行 `corepack enable pnpm`；然后关掉，用普通 PowerShell 继续。
   - 预期：`node -v` 显示 v24.x，`pnpm -v` 显示 10.25.0。

**安装与首次启动**

3. `git clone https://github.com/Im-Sue/suduo-workbench.git`，`cd suduo-workbench\client`，`pnpm install`。
   - 预期：安装成功，没有 better-sqlite3 编译错误。
   - 仓库目前是私有的，克隆时按提示登录 GitHub。
4. `pnpm start`。
   - 预期：第一行是版本横幅；随后「首次运行，正在构建」「构建完成」「本机服务已启动：http://127.0.0.1:8787/」，默认浏览器自动打开工作台。
5. 在资源管理器打开 `%LOCALAPPDATA%\SuDuo\data`。
   - 预期：里面有 `suduo.sqlite` 和 `logs\suduo.log`。

**使用**

6. **设置 → 关于**。
   - 预期：显示 SuDuo 与 Codex 版本，以及许可一行。
7. **设置 → 模型服务**里配置模型账号，或在另一个 PowerShell 窗口的 `client` 目录下执行 `pnpm exec codex login`。
8. 在「会话」里选一个本机临时文件夹新建会话，发送「只回复 Windows turn ok」。
   - 预期：流式输出，并转为完成。
9. （有可访问的云端时）**设置 → 需求服务**填入地址，点测试连接。
   - 预期：显示「连接正常 · 云端 x.y.z」。
   - 然后注册、建项目、建需求、从需求开工。

**停止与重启**

10. 在运行 `pnpm start` 的窗口按 `Ctrl+C`。
    - 预期：出现「SuDuo 已停止」；再访问 http://127.0.0.1:8787 打不开。
11. 再次 `pnpm start`。
    - 预期：不再重新构建，几秒内启动。
12. 保持它运行，在另一个窗口的 `client` 目录再执行一次 `pnpm start`。
    - 预期：提示「SuDuo 已在运行」，并打开浏览器，不会启动第二个实例。
13. `pnpm run doctor`。
    - 预期：Node、pnpm、Codex CLI、SQLite 原生模块各项为 PASS。
