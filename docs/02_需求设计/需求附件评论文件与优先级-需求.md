# 需求附件回归本义、评论可带文件、需求优先级

> 一句话：需求详情里的「材料与确认版」改回单纯的「附件」，按时间倒序平铺、用途由人决定；评论可以带文件；需求加优先级，看板和列表按优先级排序。｜最后更新：2026-10-07（用户确认，开始实施 S1）

## 需求描述

需求详情目前有三处与团队实际用法不符：

1. **「材料与确认版」的定位不对。** 它要求把附件「发布」成一个不可修改的确认版，作为产品向开发交接的正式动作；没进过确认版的文件被归到「其他材料」。团队实际的用法要简单得多：附件就是需求的额外存储，定稿的 PRD、第三方资料、需求资料、截图、压缩包都放这里，怎么用由人决定。
2. **评论只能写字。** 讨论时想贴一张截图、附一份文件，只能先传到附件区，再在评论里说「见附件 xxx」，附件区也因此被随手的文件塞满。
3. **需求没有优先级。** 看板和列表只按最近更新排序，团队看不出哪条更急。

本需求做三件事：附件区回到「按时间倒序的一张平铺列表」，停止发布新的确认版；评论框可以附文件，文件只属于这条评论；需求加「优先级」属性，看板每一列和列表都按优先级排序。

## 二、背景与目标

**目标对齐**：

- **附件**：需求详情里的区块就叫「附件」。所有文件按上传时间从新到旧排成一列，最新的在最上面，没有「确认版 / 其他材料」之分，也没有「发布」按钮。读的人（人或 Codex）从上往下读：新旧内容重复时以新的为准，不重复的互相补充，拿不准就在评论里提出来。系统不规定每个文件的用途，也不提供置顶。以前发布过的确认版不删，收在附件区底部「历史确认版」里，只能查看。
- **评论文件**：评论框可以粘贴截图、拖入或点选文件，和文字一起发出。文件只挂在这条评论下面，不进附件区，也不占附件额度。觉得某个文件应该长期留存时，点「存为附件」把它复制到附件区。
- **优先级**：每条需求有一个优先级，分「紧急 / 高 / 中 / 低」四档，没设置时是「无优先级」。新建时可选，详情里随时可改。看板卡片和列表行上显示图标。看板每列、列表都按优先级从高到低排，同一档里再按最近更新排；也可以切回只按最近更新排。

**模拟示例**：

```
产品小王在 REQ-42「导出报表」上：
1. 把 PRD v1.pdf、竞品截图.png、接口文档.zip 拖进「附件」
   → 三个文件出现在附件区，按上传时间从新到旧排（没有「发布确认版」这一步）
2. 把优先级设为「高」
   → 看板「待开发」列里 REQ-42 排到所有「中」「低」「无」的前面
   → 活动时间线出现「小王 把优先级从 无 改为 高」
3. 开发小李在评论里粘贴一张报错截图，写「导出按钮点了没反应」，发送
   → 评论下面显示截图缩略图，点开看大图；附件区不变
4. 小王修订后上传 PRD v2.pdf
   → v2 排在附件区最上面；小李从上往下读，v1 里与 v2 重复的部分以 v2 为准
5. 小王觉得小李那张截图要长期留存，在评论里点截图的「存为附件」
   → 附件区最上面多了「报错截图.png」，上传人是小王；原评论不变
6. 小李从 REQ-42 开 Codex 会话
   → 需求卡写着「优先级：高」，附件列表最新的在前；模型查评论时能看到那张截图并打开查看
```

- **背景**：
  - 确认版由「PM 需求前置闭环」（2026-08 交付）引入，用来把「发布」做成对开发有约束力的交接动作。实际使用中，团队不按这个流程走，反而被「确认版 / 其他材料」的两分法和「发布」按钮困扰。
  - 房间消息已经能带文件（先上传、发消息时带上），评论还不行。
  - 需求的属性目前只有状态和负责人；「UI/UX 产品化重设计」明确把优先级留到后续。
- **目标**：
  1. 附件区只有一种东西：附件，按时间倒序，用途由人定。
  2. 评论可以带文件，文件跟着评论走，不污染附件区。
  3. 需求有优先级，看板和列表按优先级排序。
  4. Codex 会话里看到的信息与界面一致：附件最新在前，评论文件可见，需求卡带优先级，不再出现「确认版」概念。

## 三、讨论与决策

### 讨论 1：「确认版」怎么处理

- 备选：甲「只改名」，区块叫附件，确认版保留但收进菜单；**乙「停用确认版」**，界面只剩附件列表，不能再发布，历史数据只读保留；丙在乙的基础上给附件加分类标签。
- **最终决策：乙**（用户 2026-10-07「你的推荐我基本认可」）。甲会让「两套东西」的困惑留着；丙由系统预设分类，和「用途由人决定」相矛盾。
- 附带决策：**不做置顶**（用户：「不需要置顶的操作暂时」）。时间倒序已经让最新的资料在最上面，阅读约定是「重复以新的为准，不重复互为补充，有疑问再提」。
- 历史确认版：**保留只读**，收在附件区底部（推荐项，用户认可）。

### 讨论 2：评论里的文件算谁的

- 备选：**A 只属于这条评论**；B 同时进附件区。
- **最终决策：A**，另提供「存为附件」（用户认可推荐）。附件区是人有意整理的地方，评论里随手贴的截图不该把它淹没；B 还会占用每个需求 100 个附件的额度。

### 讨论 3：优先级的档位与排序

- 档位：**无（默认）/ 紧急 / 高 / 中 / 低**（用户认可推荐）。默认用「无」而不是「中」：默认「中」会让没人设置的需求全是中，这个标记就没了意义。
- 改优先级**不算改需求内容**：和负责人一样，改它不让需求的正文版本号递增。正文版本号用来告诉会话「需求内容变了」，改优先级不应触发这个提示。
- 排序：**需要按优先级排序**（用户 2026-10-07）。看板每列和列表都按「紧急 → 高 → 中 → 低 → 无」排，同一档按最近更新排。
- Codex 发评论时带文件：**本期不做**（用户认可推荐）。

## 四、功能 / 范围

### 4.1 附件区

| 项 | 说明 |
|----|------|
| 做什么 | 需求详情的「材料与确认版」区块改名「附件」，所有未删除的附件按上传时间从新到旧平铺；去掉「确认版 / 其他材料」分组、「发布确认版」按钮与版本切换菜单 |
| 每行内容 | 文件类型图标、文件名、上传人、上传时间、大小；操作：预览（图片看大图，PDF、文本等按现有方式）、下载、删除（删除前确认，沿用现有文案里的「无法恢复」提示） |
| 上传 | 不变：拖入区块、页面粘贴截图（光标在评论框里时除外，那时截图进评论）、点选上传；每个文件独立进度、失败单独重试 |
| 能传什么 | 允许的文件类型放宽到与房间文件一致：在现有文档、图片、zip 之外，加上 rar、7z、tar、gz、tgz 压缩包，mp4、mov、m4v、webm 视频，log、yaml、yml 文本，bmp、avif、heic 图片。单个文件 300 MB、每个需求 100 个附件的上限不变 |
| 速览抽屉 | 附件概要同样按从新到旧显示前 5 个，去掉「确认版 · 第 N 版」徽标 |
| 历史确认版 | 这条需求发布过确认版时，附件区底部多一行「历史确认版（N）」，默认收起；展开后可逐版查看文件清单、发布人与时间，可下载文件（发布说明仍在活动时间线里）；没有发布、编辑入口。从没发布过的需求不显示这一行 |
| 时间线 | 以往「发布了确认版 · 第 N 版」条目与发布时附带的说明照常显示；上传、删除附件的条目不变 |

### 4.2 评论可带文件

| 项 | 说明 |
|----|------|
| 怎么附 | 评论框旁的「添加文件」按钮点选；把文件拖到评论框；在评论框里粘贴截图（只进评论，不会同时传成附件） |
| 能附什么 | 文件类型与附件相同（见 4.1），因此任何评论文件都能「存为附件」 |
| 发送前 | 评论框下方列出待发文件：名称、大小；可移除。此时文件还没上传 |
| 发送时 | 点发送后才逐个上传，每个文件显示进度；全部传完再发出评论。上传途中输入框只读；途中再加的文件留到下一条。某个文件上传失败时评论不发出，可重试或移除后再发；已传好的文件重发时直接复用，不重复上传。若发评论被拒、查下来文件已经挂在评论上（上次其实发出去了、只是响应没回来），界面说明「刚才这条评论其实已经发出」并刷新活动，不再重复发 |
| 能发什么 | 正文和文件至少有一样：只有文件、没有文字的评论也可以发 |
| 怎么显示 | 时间线里的评论正文下方：图片显示缩略图，点开看大图；其他文件显示类型图标、名称、大小，可预览（规则同附件）或下载 |
| 存为附件 | 每个评论文件有「存为附件」：把它复制成这条需求的一个新附件，上传人记为操作的人；原评论不变。同一个文件可以重复存（每次都是新附件） |
| 不能做的 | 评论本来就不能编辑、删除，评论里的文件同样不能单独删除 |

### 4.3 需求优先级

| 项 | 说明 |
|----|------|
| 档位 | 紧急、高、中、低，外加默认的「无优先级」 |
| 显示 | 图标加文字（紧急用醒目颜色）；看板卡片、列表行只显示图标，悬停显示文字；「无」在卡片上不显示图标 |
| 设置 | 新建需求时可选（默认「无」）；详情右栏属性、需求速览面板里可改 |
| 记录 | 每次修改记审计，活动时间线显示「X 把优先级从 高 改为 紧急」 |
| 筛选 | 需求页筛选条加「优先级」，可多选档位（含「无」） |
| 排序 | 看板每一列、列表的每个状态分组默认按优先级从高到低排，同一档按最近更新从新到旧排；排序方式可切回「最近更新」，选择记在本机 |
| Codex | 需求卡和查需求的工具输出带上优先级；Codex 不能修改优先级 |

### 4.4 Codex 会话里的变化

| 项 | 说明 |
|----|------|
| 附件 | 需求卡与查附件的工具按上传时间从新到旧列出；查附件工具的说明里写明阅读约定：内容重复时以较新的为准，不重复的互为补充，拿不准就提出来 |
| 评论文件 | 查评论的工具列出每条评论的文件（名称、类型、大小、编号），模型可用查看附件的工具打开它，规则与附件相同 |
| 确认版 | 「查看确认版 / 拉取确认版 / 发布确认版」三个工具撤下；需求卡不再提确认版。房间里共享的 Agent 同样撤下前两个。已经开着的旧会话不会重新领取工具清单，模型仍可能调用这三个工具，统一回复「确认版已停用，附件请用查附件工具查看」。活动与评论里以往「发布了确认版」的记录作为历史事实照常描述 |
| 优先级 | 需求卡与查需求工具带上优先级 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 附件区按上传时间从新到旧排 | 详情、速览、Codex 需求卡与工具输出一致 |
| R2 | 不能再发布新的确认版 | 新版客户端的界面与 Codex 都没有发布入口；历史确认版只读 |
| R3 | 历史确认版的数据不删、不改 | 版本里的文件即使对应附件被删，仍可从历史确认版里下载（沿用现有的版本文件保护） |
| R4 | 评论文件只属于这条评论 | 不出现在附件区，不计入附件数与附件上限 |
| R5 | 单条评论最多 10 个文件，单个文件不超过 300 MB | 单个文件上限与附件、房间文件一致 |
| R6 | 评论正文和文件至少有一样 | 只有文件的评论合法 |
| R7 | 评论文件在点发送时才上传；「已上传但评论最终没发出」的文件留在云端，不自动清理 | 发送时才上传，让这种遗留只出现在「上传成功后评论发送失败、用户又放弃重发」时，极少。自动删除存储对象属于 ADR-0004「不可逆字节损失」红线，不由系统自行执行（用户 2026-10-07：「如果太麻烦就先不清理吧」） |
| R8 | 「存为附件」生成一个新附件 | 计入附件上限（每个需求 100 个）；上传人为操作人；与原评论文件互不影响 |
| R9 | 优先级五档：紧急 > 高 > 中 > 低 > 无，默认无 | — |
| R10 | 改优先级不让需求正文版本号递增 | 同负责人；会话里的「需求自上次以来有变化」不因它触发 |
| R11 | 按优先级排序时，同一档按最近更新从新到旧 | 看板每列与列表每个状态分组一致 |
| R13 | 附件与评论文件允许同一份文件类型清单 | 即房间文件的清单；部署时仍可用环境变量覆盖 |
| R12 | 不新增任何拒绝式守卫 | 两人同时改优先级，后改的生效，时间线里能看到谁在什么时候改了什么（ADR-0004） |

## 六、边界 / 不做项

- 不做附件置顶、分类标签、附件说明文字。
- 不删除历史确认版数据，也不把它们迁成普通附件。
- 不做评论编辑、删除，也不做评论文件单独删除。
- 不让 Codex 发带文件的评论（以后再说）。
- 不让 Codex 修改优先级。
- 房间消息的文件能力不动。
- 「我的工作」「概览」以及其他页面里出现的需求条目，本期不加优先级显示与排序；概览统计不加按优先级的口径。
- 不做截止日期、标签、父子需求。

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |
|------|----------|
| 旧版客户端（0.8.x）连新版云端 | 云端保留确认版的读写接口：旧客户端仍能发布，发布的版本在新界面的「历史确认版」里可见；旧客户端看不到评论里的文件（只看到正文），也看不到优先级。技术设计给出具体处理 |
| 新版客户端连旧版云端 | 云端不支持时，隐藏优先级、评论文件入口，附件区照样按时间倒序显示（技术设计确定判断方式） |
| 未发送的评论文件是否清理 | 已闭环：改为点发送时才上传，遗留极少；遗留的不清理（R7，用户 2026-10-07 确认） |
| 附件允许的文件类型 | 已闭环：放宽到与房间文件一致（R13，用户 2026-10-07：「放宽到和房间文件一致」） |
| 排序方式切换记在哪 | 记在本机浏览器（个人偏好），不记云端 |

## 九、数据（草案）

- **需求**：新增「优先级」属性，取值 `urgent / high / medium / low`，无优先级为空；属于元数据，不参与正文版本号。
- **评论文件**：新实体，挂在评论上：编号、所属需求、所属评论（发送前为空）、文件名、类型、大小、sha256、上传人、上传时间。
- **附件、确认版**：表结构不变；确认版只读。
- **审计**：新增「需求优先级变更」动作，改前改后为 `{ priority }`。

## 十二、交互 / 流程

```
评论带文件：
  选 / 拖 / 粘贴文件 → 列进待发（还没上传，可移除）
     → 点发送 → 逐个上传（显示进度；失败的可重试或移除）→ 全部传完 → 发出评论（正文 + 文件编号）
     → 评论出现在时间线，文件挂在下面
  没点发送就离开 → 什么都没上传
  上传成功但评论没发出 → 重发时复用已传好的文件；彻底放弃时这些文件留在云端（不自动清理，见 R7）

存为附件：
  评论文件 ⋯ → 存为附件 → 附件区最上面出现同名文件（上传人 = 我）→ 时间线记一条「上传了附件」
```

## 十三、风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 旧会话里模型还会调用已撤下的确认版工具 | 中 | 调用失败、说法生硬 | Codex 续接旧会话时不会重新下发工具清单，所以三个名字保留专门的「已停用」回复，指向查附件工具；新会话不再挂这三个工具 |
| 旧客户端看不到评论文件，只看到正文 | 中 | 只发了文件的评论在旧客户端显示为空 | 云端给只有文件的评论生成兜底正文（例如「[附件] 报错截图.png」），技术设计确定 |
| 按优先级排序改变了分页方式 | 中 | 列表翻页错位或重复 | 技术设计里把排序字段纳入游标，补测试 |
| 历史确认版和附件的关系让人困惑 | 低 | — | 历史确认版默认收起，只在发布过的需求上出现 |
| 平铺后以前进过确认版的附件也能删了 | 中 | 删了附件，历史确认版还能不能下 | 能：版本保存了自己的文件引用，存储层对被版本引用的文件不做物理删除（现有保护，必须保留） |

## Claude 解读

三项都是让需求详情更贴近团队的实际用法：附件只是存储，用途和阅读顺序交给人（时间倒序 + 「新的为准、不重复互补」的约定）；评论里的文件属于讨论本身，不混进附件区；优先级是团队排序的依据，看板和列表都按它排。确认版这条交接流程整体退场，只留历史数据供查看。

---

## 歧义点

无遗留待用户拍板项。已闭环：确认版停用并保留只读历史（乙）、不做置顶、评论文件只属于评论并可存为附件、优先级五档默认「无」、按优先级排序、Codex 发带文件的评论本期不做（均为用户 2026-10-07 确认）。移交技术设计：新旧版本兼容的判断方式、未发送文件的清理时长、只有文件的评论在旧客户端的兜底正文。

## 保真差异

相对原话的归纳与新增：

- 原话 2 只说「改文案和定位」，本文落实为停用确认版写入口、保留历史只读，是用户确认后的方案。
- **主动新增「排序方式可切回最近更新」**：仲裁者是使用者自己；拿掉它，最坏结果是想看最近动态的人只能按优先级看；人能恢复（筛选或看活动）。成本很小，保留现有习惯，故加入。
- **主动新增「查附件工具里写明阅读约定」**：约定原文来自用户第二段话，只是让 Codex 也按同一规则读；不加的最坏结果是模型自行判断新旧，人能在对话里纠正。
- **主动新增「只有文件也能发评论」「单条评论最多 10 个文件」**：均为容量与体验细节，不是一致性守卫；10 个上限的拿掉最坏结果是单条评论过长，人能拆开发。
- **主动新增「附件允许类型放宽到与房间文件一致」**：依据原话「截图、压缩包各类型的文件」，现有附件清单只有 zip 一种压缩包。
- **「未发送文件自动清理」撤回**：首轮分析里提过、用户认可过，但它要系统自动物理删除存储对象，属于 ADR-0004 红线。用户提出「真实发评论再触发真实上传」，采纳为点发送时才上传，遗留的不清理（R7）。
- 「存为附件」的上传人记为操作人：仲裁者是操作人自己；记成原评论作者的最坏结果是附件区上传人与实际操作人不符。
- 本需求不引入锁、版本校验、幂等表或 409 拒绝。
