# 多 Agent 接入与本机工具服务

> 一句话：成员可以用自己电脑上已登录的 Codex、Claude Code，以及 GitHub Copilot CLI、Gemini CLI、Cursor CLI、OpenCode、Qwen Code、Kimi Code 等 ACP Agent 开工；时间线、审批、权限档位、需求工具、房间共享对所有 Agent 一致；需求工具改由 SuDuo 本机 MCP 服务提供。｜最后更新：2026-10-08（用户确认，开始实施）
>
> 母需求：[v3 规划](v3-多AI工具与多Agent协作规划-需求.md) 的第一阶段（P1）。技术设计（P1 + P2 合并）：[多 Agent 接入与协作-技术设计](../03_开发计划/多Agent接入与协作-技术设计.md)。
>
> 术语：界面上的「讨论」在代码与 ADR-0009 里叫「房间」；「房间任务」指在讨论里 @ 共享 Agent 产生的只读任务。
>
> 决策：[ADR-0014](../06_决策记录/ADR-0014-多Agent接入架构-原生协议加ACP-统一会话模型.md)（接入架构）、[ADR-0015](../06_决策记录/ADR-0015-会话工具改由SuDuo本机MCP服务提供-对所有Agent一致.md)（工具层）、[ADR-0016](../06_决策记录/ADR-0016-AI账号凭据边界-只驱动官方CLI由用户自行登录.md)（凭据边界）。

## 需求描述

SuDuo 现在只能用 Codex。海外开发者最常用的 Claude Code、团队已经付费的 GitHub Copilot、免费额度大的 Gemini CLI、能接任意模型的 OpenCode 都接不进来；成员要么换工具，要么离开 SuDuo 干活。

本需求让 SuDuo 能驱动成员本机已安装、已登录的多家编码 Agent：

- **Codex**：保持现有接法（捆绑锁定版本，ADR-0007）。
- **Claude Code**：通过 Claude 官方 Agent SDK 驱动用户本机的 `claude`。
- **ACP Agent**：通过 ACP 协议接 GitHub Copilot CLI、Gemini CLI、Cursor CLI、OpenCode、Qwen Code、Kimi Code，后续加一家原则上只加一条配置。

所有 Agent 在 SuDuo 里的体验一致：从需求开工、时间线、审批坞、权限档位、需求工具、房间共享都一样，只是能力多少不同，缺的能力不显示。需求工具从 Codex 独有的 dynamicTools 改为 SuDuo 本机 MCP 服务，所有 Agent 共用。

## 原话（verbatim）

> 「需求：当前系统智能支持codex cli，集成的llm或者ai能力太弱，你下载一下tutti（tutti.sh），深度分析一下它是如何集成多ai工具的。」（2026-10-08）
>
> 「1. 我们应该也要复用本机登录的cli为先。这个需要做什么申请吗？
> 2. claude code和acp同时一起做
> 3. 这个你按照项目的长期发展、最优优化方案进行处理」（2026-10-08）

## 二、背景与目标

**目标对齐**：

- 设置里新增「AI Agent」：列出 SuDuo 支持的 Agent，显示每家在本机的状态（就绪 / 未安装 / 需要登录 / 版本过低），给出安装命令、登录入口和条款链接；SuDuo 不替用户登录、不碰凭据。
- 开工时选 Agent（默认记住上次的选择），会话上标明用的是哪家；模型与推理强度的选项来自该 Agent 自己。
- 权限统一为四档：只读 / 写前询问 / 自动 / 完全访问，每家 Agent 按自己的机制落实；某家做不到的档位在选择器里说明。
- 时间线、审批坞、中断、图片输入、Skill 对所有 Agent 一致呈现；Agent 没有的能力不显示。
- 需求工具（读需求、评论、附件、结论笔记、房间历史，发评论须确认）对所有支持 MCP 的 Agent 可用。
- 房间里可以共享任意已就绪的 Agent；房间任务固定只读。
- 现有 Codex 会话与房间历史照常可看、可续接。

**模拟示例**：

```
工作室 Lotus Labs：Duc 用 Codex（ChatGPT 订阅），Minh 装了 Claude Code，Tuan 只装了 Gemini CLI（免费额度）。

1. Minh 打开 SuDuo → 设置 → AI Agent：
   Claude Code   就绪（2.x，已登录）
   Codex         就绪（SuDuo 自带 0.159.2）
   Copilot CLI   未安装  [复制安装命令] [查看官网]
   Gemini CLI    需要登录  [在终端中登录]
   每张卡下方：服务地区与使用条款以官方为准 [链接]
   Minh 把默认 Agent 设成 Claude Code。
2. Minh 在 REQ-88 点「开工」→ 开工对话框里 Agent 默认是 Claude Code，权限「写前询问」，
   模型列表来自 Claude Code → 开工。
3. 会话页标题旁显示「Claude Code」。它读需求（调用 SuDuo 需求工具）、改了 3 个文件；
   要跑测试命令时，审批坞弹出「Claude Code 想运行 pnpm test」[允许] [本会话允许] [拒绝]。
4. Claude Code 起草了一条进展评论，调用「发评论」工具 → 审批坞出现确认卡，Minh 看过内容后确认，
   评论发到 REQ-88。
5. Tuan 在终端执行 `gemini` 完成 Google 登录，回到 SuDuo 点「重新检测」→ 就绪；
   他用 Gemini CLI 开工 REQ-90，时间线、审批坞、需求工具和 Minh 的完全一样。
6. Duc 在项目讨论里点「共享我的 Agent」，选 Codex；项目经理 Linh 在讨论里 @ 它提问 →
   Codex 在 Duc 电脑上只读分析，回答挂在话题下（和现在一样）。
   Duc 也可以改为共享 Gemini CLI，体验相同。
7. Minh 打开上周的 Codex 会话：时间线、改动、审批记录都在，继续发消息照常续接。
```

- **背景**：见母需求 2.1、2.2 与 ADR-0014 背景。
- **目标**：
  1. 支持 Codex、Claude Code，以及 ACP 首批六家（GitHub Copilot CLI、Gemini CLI、Cursor CLI、OpenCode、Qwen Code、Kimi Code），其中至少四家通过真实冒烟。
  2. 所有 Agent 的会话体验一致；需求工具与房间共享对所有 Agent 可用。
  3. SuDuo 不读、不存、不转发任何 AI 凭据（ADR-0016）。
  4. 现有会话、房间历史与 Codex 体验不退化。

## 三、讨论与决策

| 决策点 | 结论 | 依据 |
|---|---|---|
| 接入通道 | Codex：app-server（现状）；Claude Code：官方 Agent SDK 在本机服务进程内调用；其余：ACP | ADR-0014 |
| Claude 为什么不用 ACP | 社区的 Claude ACP 适配包在 Tutti 那里踩过补丁、用量显示错误、新会话启动失败；SDK 是官方库，审批回调、hooks、中断、续接都齐 | ADR-0014 否决方案 |
| 凭据 | 只驱动官方 CLI，登录走官方流程，SuDuo 只用 CLI 自己的状态命令判断是否登录 | ADR-0016 |
| Claude 订阅登录 | 只提示、不限制：Agent 面板与首次开工时提示「用量与使用方式适用你与厂商之间的条款；SuDuo 不读取、不保存你的凭据」，同时给出 API Key / 云厂商凭据的用法；不标「试用」 | 用户 2026-10-08 拍板；ADR-0016 第 9、10 条 |
| 工具层 | 本机 MCP 服务，按会话签发令牌；Codex 老线程保留 dynamicTools 直到自然结束 | ADR-0015 |
| 会话模型 | SuDuo 契约自有的条目模型，字段以 Codex 条目为基线；其他 Agent 翻译成同形条目 | ADR-0014 第 3 条 |
| 权限档位 | 四档：只读 / 写前询问 / 自动 / 完全访问；部署方上限 `SUDUO_MAX_APPROVAL_MODE` 继续生效 | ADR-0014 第 4 条 |
| 安装 | 不替用户安装（Codex 仍随 SuDuo 捆绑）；只检测并给出官方安装命令 | 本需求 R4 |
| 默认列表 | Claude Code、Codex、GitHub Copilot CLI、Gemini CLI、Cursor CLI、OpenCode、Qwen Code、Kimi Code；本机已就绪的排在前面 | 母需求 D2 |

## 四、功能 / 范围

### 4.1 AI Agent 面板

| 项 | 说明 |
|----|------|
| 做什么 | 设置新增「AI Agent」分组：列出支持的 Agent，每家一张卡：名称、接入方式（官方接口 / ACP）、本机版本、状态、默认标记、操作 |
| 谁用 | 所有成员 |
| 怎么触发 | 打开设置；首启向导「连接 Agent」一步；开工对话框里的「管理 Agent」链接 |
| 前置条件 | 无 |
| 预期结果 | 接入方式显示「官方接口」或「标准协议」（悬停说明：通过开放的 Agent Client Protocol 连接）。状态取值：**就绪** / **未安装** / **需要登录** / **版本过低**（显示最低版本）/ **检测失败**（显示原因）。操作：复制安装命令、在终端中登录（打开系统终端并执行官方登录命令）、重新检测、设为默认、查看官网与条款。Codex 显示「SuDuo 自带」。状态在打开面板、点重新检测、以及会话里遇到登录失效时刷新 |

### 4.2 开工选 Agent

| 项 | 说明 |
|----|------|
| 做什么 | 需求开工、项目会话、新建会话的对话框里加「Agent」选择；会话列表与会话页标明 Agent |
| 谁用 | 所有成员 |
| 怎么触发 | 点「开工」或「新建会话」 |
| 前置条件 | 至少一家 Agent 就绪 |
| 预期结果 | 默认选上次用的（没有则用设置里的默认）；只能选就绪的 Agent，未就绪的灰显并说明原因与修复入口；同时选权限档位、模型与推理强度（选项来自所选 Agent）。会话建成后 Agent 固定，不能中途换（换 Agent = 新会话） |

### 4.3 统一的会话体验

| 项 | 说明 |
|----|------|
| 做什么 | 时间线、审批坞、中断、图片输入、Skill、用量显示对所有 Agent 一致 |
| 谁用 | 所有成员 |
| 怎么触发 | 正常使用会话 |
| 前置条件 | 会话已建 |
| 预期结果 | 时间线显示同样的卡片：消息、推理摘要、命令执行（命令、输出、退出码）、文件改动（diff）、工具调用、网页搜索、计划、子 Agent、系统提示。审批坞的选项来自 Agent（例如 ACP 的「始终允许」、Claude 的「本会话允许」），按钮文案统一。Agent 不支持的能力（图片、计划、推理摘要、用量、Skill、模型切换）在界面上不出现，而不是点了报错 |

**权限档位**：

| 档位 | 对用户的含义 | 说明 |
|---|---|---|
| 只读 | 只看不改：可以读文件、搜索、联网查资料，不改文件、不运行会改东西的命令 | 房间任务固定此档；PM 自己问代码也可以用 |
| 写前询问 | 改文件、运行命令前先问你 | 现「询问」档 |
| 自动 | 在工作目录内自动改文件、运行常规命令，越界时才问 | 现「自动」档 |
| 完全访问 | 不再询问 | 现「完全访问」档；受 `SUDUO_MAX_APPROVAL_MODE` 限制 |

某家 Agent 做不到某档的精确语义时，选择器里写出实际效果（例如「此 Agent 的只读由 SuDuo 拒绝写入请求实现」），做不到的档位灰显并说明。

### 4.4 需求工具对所有 Agent 可用

| 项 | 说明 |
|----|------|
| 做什么 | 现有 `suduo_*` 需求工具（读需求、读评论、列附件、看附件、读写结论笔记、发评论、读房间历史、搜房间、看房间文件）改由 SuDuo 本机 MCP 服务提供 |
| 谁用 | 需求会话、项目会话、房间任务里的 Agent |
| 怎么触发 | Agent 自己决定调用 |
| 前置条件 | Agent 支持 HTTP MCP（Codex、Claude Code、多数 ACP Agent） |
| 预期结果 | 工具清单与现在一致（房间任务不挂写工具）；时间线上显示为「SuDuo 工具」卡片；**发评论**仍弹确认卡，确认后发出、拒绝则告诉 Agent「用户未同意」；若 Agent 那边先超时或回合被中断，这条评论**不丢**，转成会话里的「待发出草稿」，用户仍可确认发出或丢弃。不支持 HTTP MCP 的 Agent：开工对话框与会话顶部提示「这个 Agent 用不了 SuDuo 需求工具」，会话照常可用 |

### 4.5 讨论里共享任意 Agent

| 项 | 说明 |
|----|------|
| 做什么 | 「共享我的 Agent」可以选本机任意就绪的 Agent；讨论里显示「Duc 的 Gemini CLI · 设备名」 |
| 谁用 | Agent 所有者；讨论成员 @ 使用 |
| 怎么触发 | 讨论里的共享面板；@ 选择 |
| 前置条件 | 所选 Agent 就绪，且能做到只读（见 R6） |
| 预期结果 | 房间任务固定「只读」档、只挂只读工具、关掉所有者自己配置的 MCP（ADR-0009）；回答与执行过程挂在话题下，和现在一致。共享开关旁说明「个人订阅按个人日常使用设计，团队长期共用建议改用厂商的团队或企业订阅或 API Key」（ADR-0016） |

### 4.6 诊断与自检

| 项 | 说明 |
|----|------|
| 做什么 | 「诊断」页与 `pnpm run doctor` 按 Agent 分组显示检查结果 |
| 预期结果 | Codex 保留现有检查；其他 Agent 显示：可执行文件位置、版本、登录状态、ACP / SDK 握手是否成功、是否支持 HTTP MCP |

### 4.7 老会话与老客户端兼容

| 项 | 说明 |
|----|------|
| 做什么 | 已有 Codex 会话、房间任务历史、审批记录照常显示与续接；老客户端连新云端、新客户端连老云端都能用 |
| 预期结果 | 老会话自动视为 Codex 会话；云端在不认识新 Agent 种类时，新客户端只共享 Codex 并提示升级云端 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 不碰凭据 | SuDuo 不读取、不复制、不存储、不转发任何 AI 账号的令牌、会话或 Key；登录状态只通过各家 CLI 的官方命令或握手判断（ADR-0016） |
| R2 | 只驱动官方未修改的 CLI | 用用户本机安装的官方版本；不打补丁、不去掉其自带的登录方式；协议里的客户端名写 `suduo` |
| R3 | 登录走官方流程 | 「在终端中登录」只是替用户打开终端并执行官方登录命令，SuDuo 不显示账号密码或 OAuth 表单 |
| R4 | 不自动安装 | 除随 SuDuo 捆绑的 Codex 外，其他 Agent 只检测与给出官方安装命令 |
| R5 | 会话 Agent 固定 | 一个会话从建立到结束只用一家 Agent；换 Agent 即新会话 |
| R6 | 房间任务只读 | 房间任务固定只读档；SuDuo 拒绝该会话里所有写入类权限请求与文件写入；最严格模式仍可能不经询问写文件的 Agent 不能被共享进房间（ADR-0004「删除或覆盖用户文件」红线） |
| R7 | 写工具须确认且不丢 | 发评论等对外写入须用户在确认卡上确认（ADR-0004）；等待接近 Agent 的工具超时、或回合被中断时转为草稿，由用户决定发出或丢弃 |
| R8 | 能力缺失不报错 | Agent 不支持的能力不显示入口；只在用户明确选择时（如选了它做不到的权限档）才说明 |
| R9 | 以 SuDuo 账本为准 | 会话历史以 SuDuo 自己记录的事件为准，不依赖 Agent 回放；续接失败时告知并给「新开会话」选项 |
| R10 | 老数据不改写 | 已有 Codex 事件、审批、房间任务记录保持原样，靠读取兼容 |
| R11 | 条款核对先行 | 每加一家 Agent，先核对其条款要点并写进它的配置说明；不满足 R1–R3 的不进默认列表 |

## 六、边界 / 不做项

- SuDuo 之外启动的 Agent（开发自己终端或 IDE 里的）接入 SuDuo 需求工具——后续方向
- Agent 之间读会话、委派、交叉评审、并行试做——母需求 P2
- 替用户安装或升级 Codex 以外的 CLI；应用内账号登录
- 模型网关、额度代付
- 一个会话中途切换 Agent
- Codex 每会话独立进程；Tutti 那种目标模式（goal）的持久化流程；进程录制回放
- 子 Agent 的树形泳道展示（首期显示为时间线上的子 Agent 卡片）
- 会话分叉（fork）、旁路对话（side conversation）
- 扩展包式的第三方 Agent 安装（首期内置配置表；外部清单留待后续）

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |
|------|----------|
| Codex 0.159.2 能否在 `thread/start` 的配置覆盖里按线程新增一个 HTTP MCP 服务 | 移交技术设计 S0 实测；不行时退到「全局登记 + 按线程覆盖请求头」，再不行 Codex 保留 dynamicTools |
| 各 Agent 的 MCP 工具调用超时能否覆盖「等用户确认」 | 移交 S0 实测（Codex `tool_timeout_sec`、Claude `MCP_TOOL_TIMEOUT`、各 ACP Agent）；超时由 R7 的草稿兜底 |
| 各 ACP Agent 的启动参数、登录命令、只读模式、是否支持 HTTP MCP 与 `session/load` | 移交 S0 逐家实测，写进配置表；以 2026-10-08 查到的官方说明为起点：Copilot CLI `copilot --acp`、Gemini CLI `gemini --acp`、Cursor CLI `cursor-agent acp`、OpenCode `opencode acp`、Qwen Code `qwen --acp`、Kimi Code `kimi acp` |
| Claude Agent SDK 能否稳定驱动用户自装的 `claude`（`pathToClaudeCodeExecutable`）及最低版本 | 移交 S0 实测 |
| 用本机 Claude 订阅 | 已闭环：只提示、不限制（用户 2026-10-08）；剩余风险见 ADR-0016 第 10 条，配置表预留「仅 API Key」开关 |

## 八、拆分预览

与 P2 [多 Agent 协作机制](多Agent协作机制-需求.md) 合并排期（用户 2026-10-08：「p1 p2一起规划做」），统一分片见 [技术设计](../03_开发计划/多Agent接入与协作-技术设计.md) 第十一节。本需求对应的分片：

- **S0 实测**：Codex 按线程注入 MCP；各 Agent 的 MCP 超时；六家 ACP Agent 的握手、登录、只读、MCP、续接；Claude SDK 驱动自装 `claude`
- **S1 契约与地基**：条目模型与审批载荷中立化；权限档位四档；会话记录 Agent 与角色（为 P2 预留）；多运行时装配；调度器准入；Agent 配置表与状态检测；Agent 面板

## 九、数据（草案）

- **本机**
  - 会话：增加所用 Agent 的标识（老会话视为 `codex`）。
  - 审批：载荷增加中立的「对象」（命令 / 文件 / 权限 / 提问 / 工具确认）与 Agent 提供的可选决策列表；已有记录不改。
  - 工具草稿：被超时或中断的写工具调用，保存为会话内的待发出草稿（内容、目标需求、状态：待处理 / 已发出 / 已丢弃）。
  - 设置：默认 Agent、各 Agent 的启用状态与可执行文件路径覆盖。
- **云端**
  - `agents.kind`：从只允许 `codex` 放开为 Agent 标识；同一设备可登记多个 Agent（唯一键已含 kind）。
  - 共享 Agent 的显示名按 Agent 种类拼接。
- **Agent 配置表**（代码内，不进数据库）：标识、显示名、接入通道、启动命令、可执行文件名、最低版本、登录状态命令、登录命令、安装命令、模型来源、权限档位映射、能力集合、条款链接。

## 十二、交互 / 流程

```
开工
  选 Agent / 档位 / 模型 → 本机服务：检查 Agent 就绪
    → 签发会话令牌 → 按通道建会话（Codex 线程 / Claude SDK 查询 / ACP session/new）
      并注入：工具说明（按通道）+ SuDuo MCP 地址与令牌 + 需求卡
    → 时间线开始接收统一条目

写工具（发评论）
  Agent 调用 MCP 工具 → 本机服务挂起这次调用 → 审批坞弹确认卡
    ├ 用户确认 → 发出评论 → 回给 Agent「已发出」
    ├ 用户拒绝 → 回给 Agent「用户未同意」
    └ Agent 超时 / 回合中断 → 确认卡转为「待发出草稿」→ 用户之后可发出或丢弃

房间任务
  成员 @ 共享的 Agent → 所有者本机：按该 Agent 通道建只读会话（只读工具、关掉所有者 MCP）
    → 写入类权限请求一律拒绝 → 回答与过程上传到房间话题
```

## Claude 解读

本需求是母需求的地基阶段：让「成员自己的任何 Agent」都能进 SuDuo，并且对团队来说看起来一样、管起来一样。难点不在于多拉起几个进程，而在于把三处与 Codex 绑死的地方——事件形状、安全模型、工具注入——改成 SuDuo 自己的模型，同时不让现有 Codex 体验与历史数据受影响。

## 歧义点

- 「复用本机登录的 cli 为先」：已闭环（R1–R3、ADR-0016）。
- 「claude code 和 acp 同时一起做」：已闭环（S3、S4 同期）。
- 「工具层按长期最优」：已闭环（ADR-0015，S2）。
- 首批 ACP Agent 名单：按全球市场（东南亚 + 欧美）推荐 Copilot CLI、Gemini CLI、Cursor CLI、OpenCode，加 Qwen Code、Kimi Code 作为低价选择；如用户有偏好可增减。
- 移交技术项：第七节各项，在技术设计 S0 实测。

## 保真差异

相对原话的主动新增：

1. **四档权限中新增「只读」作为用户可选档**（原来只有房间内部使用）。不是拒绝式守卫。
2. **房间共享拒绝做不到只读的 Agent（R6）**。三问：仲裁者是 Agent 所有者；拿掉它的最坏结果是房间成员借 Agent 改写或删除所有者电脑上的文件；文件被覆盖可能无法恢复。属于 ADR-0004「删除或覆盖用户文件」红线。
3. **写工具超时转草稿（R7）**。是为了不丢数据，不拒绝任何操作。
4. **不自动安装（R4）**。范围收窄，不是守卫。

本需求不引入锁、版本校验、幂等表或 409 拒绝；新增的拒绝只有 R6 一条 ADR-0004 红线。
