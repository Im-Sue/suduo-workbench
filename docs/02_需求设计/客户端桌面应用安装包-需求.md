# SuDuo 客户端桌面应用（macOS / Windows 安装包）

> 一句话：把客户端（本机服务 + 前端 + 锁定版本的 Codex）打包成 Mac 和 Windows 上双击安装、双击打开的桌面应用。使用者不用再装 Node、pnpm，也不用克隆仓库和构建；源码运行留给开发者。｜最后更新：2026-10-06（决策全部确认，开始实施 D0）
>
> 技术设计：[客户端桌面应用-技术设计](../03_开发计划/客户端桌面应用-技术设计.md)｜决策：[ADR-0013](../06_决策记录/ADR-0013-客户端桌面外壳采用Electron-本机服务跑在捆绑的官方Node上.md)
>
> 前置需求：[客户端源码运行](客户端源码运行-需求.md)（当时用户把安装包、Electron、签名、自动更新都定为「后面再沟通」，本需求就是这次沟通）。相关：[云端私有化部署](云端私有化部署-需求.md)、[官网改版](官网改版-需求.md)（下载页）。

## 需求描述

现在使用者要从源码运行客户端：装 Node 24 和 pnpm，克隆仓库，`pnpm install`，再 `pnpm start`，首次构建要 1–2 分钟。Windows 上 SQLite 原生模块偶尔装不上；关掉终端服务就停了，房间里共享的 Agent 也跟着掉线。官网上线、仓库公开后，来试用的团队越来越多，这条路径门槛偏高。

本需求把客户端做成桌面应用：Mac 一个 `.dmg`，Windows 一个安装程序。安装后有独立窗口，关窗后留在菜单栏或通知区域继续运行，有系统通知，有新版本时会提示。本机服务和前端的形态不变：服务仍只监听 127.0.0.1，页面仍由它托管。桌面外壳只负责拉起服务、开窗口、常驻和更新。

## 二、背景与目标

**目标对齐**：使用者是团队里的工程师，以及从官网过来试用的团队。他们在官网下载对应平台的安装包，装好就能用：打开 SuDuo，填团队云端地址，登录，选本机工作目录，从需求开工。模型账号仍是各人自己的 Codex 配置：已经在用 Codex 的人装完即用，没用过的人在应用里配置。关掉窗口 SuDuo 仍在后台运行，房间里同事 @ 他共享的 Agent 照样能回复。有新版本时应用里会提示，由他决定什么时候更新。

**模拟示例（Mac，Apple 芯片）**：

```
1. 官网「下载」自动识别为 Apple 芯片 → SuDuo-0.9.0-mac-arm64.dmg（约 300 MB，实施时实测）
2. 打开 dmg，把 SuDuo 拖进「应用程序」
3. 首次打开
   · 已签名：直接打开
   · 未签名：提示「无法验证开发者」→ 系统设置 → 隐私与安全性 → 「仍要打开」（安装说明里有图文步骤）
4. 启动页「正在启动本机服务…」→ 几秒后进入工作台
5. 设置 → 需求服务：填团队云端地址 → 注册 / 登录
6. 设置 → 模型服务：检测到 ~/.codex 已登录 → 直接可用
   （没配置过：填 API Key，或点「用 ChatGPT 账号登录」，在系统浏览器里完成授权）
7. 关掉窗口 → 首次提示「SuDuo 仍在菜单栏运行」；进行中的会话不中断
8. 一周后：窗口顶部提示「SuDuo 0.9.1 可用 · 查看更新说明 · 更新」
9. 菜单栏图标 → 「退出 SuDuo」：有进行中的会话时先确认，确认后服务停止
```

**模拟示例（Windows 11）**：

```
1. 下载 SuDuo-Setup-0.9.0-x64.exe
   · 未签名：SmartScreen「Windows 已保护你的电脑」→ 更多信息 → 仍要运行
2. 安装到当前用户（不需要管理员），创建开始菜单与桌面快捷方式，完成后打开 SuDuo
3–9 同 Mac；常驻图标在任务栏通知区域
卸载：设置 → 应用 → SuDuo → 卸载，询问是否同时删除本机数据（默认保留）
```

- **背景**：
  - 源码运行已交付（delivering，等 Windows 11 实机验收），对外 README 目前只有这一条路径。
  - 仓库里有一套 Windows 全捆绑安装器（`client/scripts/dist-win/`，NSIS），从未对外发布。它的形态是「启动器拉起服务 + 浏览器应用窗口」，必须在 Linux / WSL 上构建，配套的验证手册还停留在访问令牌时代。
  - Mac 没有任何安装形态。
  - 要捆绑的东西：本机服务与前端产物；Node 运行时（≥ 24.10）；SQLite 原生模块（按平台和运行时版本预编译）；锁定版本的 Codex，即 `0.159.2` 的各平台二进制，单平台约 300 MB，Mac 版已带 OpenAI 的 Developer ID 签名。
  - 可以直接复用的现有能力：启动器的「探测 → 拉起 → 等就绪」逻辑、`--runtime-config`、`/healthz` 的产品标识、空闲自动退出、工作目录浏览接口（选目录不依赖原生对话框）、「用 VS Code / 终端 / 访达打开」。
- **目标**：
  1. macOS 13.5+（Apple 芯片、Intel）与 Windows 10/11 x64 上双击安装即用，不需要预装 Node、pnpm，也不需要克隆仓库。
  2. 用起来是个桌面应用：独立窗口、常驻托盘、系统通知、单实例。
  3. 有更新路径，发版时同时产出三个安装包。
  4. 源码运行继续可用，与安装版互不干扰。

## 三、讨论与决策

> 标「待拍板」的由用户决定，Claude 给推荐；标「推荐直接定」的如无异议按推荐执行。

### 讨论 1：桌面外壳选哪种（已定：Electron）

| | A. Electron 外壳（推荐） | B. 轻启动器 + 浏览器 | C. Tauri 外壳 |
|---|---|---|---|
| 形态 | 自己的窗口（内置 Chromium）；本机服务作为子进程 | 沿用现有 Windows 安装器的思路：启动器拉起服务，用浏览器「应用窗口」打开 | 系统自带的网页引擎（Mac 是 WebKit，Windows 是 WebView2）+ 打包 Node 作为附带程序 |
| 常驻 / 托盘 / 单实例 | 有 | 没有。关浏览器后服务靠「空闲 30 分钟自动退出」，共享 Agent 会掉线 | 有 |
| 与现有验收一致 | 一致：界面全部验收（gate-c、视觉基线）都在 Chromium 上跑 | Windows 用 Edge 一致；Mac 取决于使用者的默认浏览器 | Mac 上换成 WebKit，界面要重新验收 |
| 本机服务的 Node | 另捆一份官方 Node 24（技术设计决策 2：SQLite 模块没有最新 Electron 的预编译包，且这样与源码运行一致） | 另捆一份 Node | 另捆一份 Node |
| 下载 / 安装后体积（估） | 约 280–300 MB / 约 700 MB | 约 170 MB / 约 430 MB | 约 175 MB / 约 440 MB |
| 内存 | 多占一两百 MB（自带浏览器内核） | 取决于使用者的浏览器 | 较省 |
| 前端要改的 | 基本不用：通知、下载、外链在 Chromium 里现成可用 | 基本不用 | Mac 的 WebKit 不支持网页通知接口，要换成 Tauri 通知插件；附件下载、新窗口和外链也要外壳接管 |
| 内核安全更新 | 靠我们跟进 Electron 新版本（约每 8 周一个大版本，只维护最近三个） | 跟浏览器走 | 跟系统 / Edge 走 |
| 外壳代码语言 | TypeScript，与全仓一致 | TypeScript | Rust + TypeScript |
| 新增工具链 | electron-builder（同为 Node 生态） | 没有新增，但 Mac 要另写一个 .app 外壳 | Rust 工具链 |
| 更新 | 成熟方案（electron-updater）；Mac 一键更新要求应用已签名 | 自己写 | 自带更新器，用免费密钥签更新包，不依赖 Apple 签名；但首次打开同样受系统拦截 |

- **推荐 A。** 理由：界面已在 Chromium 上完成全部验收；常驻、单实例、通知、开机自启、更新都有成熟方案；外壳也用 TypeScript。代价是体积：Electron 外壳本身压缩后约 130 MB，比 B、C 大约多 120 MB 下载、约 270 MB 磁盘。
- **体积更正（2026-10-06）**：初稿写的是「约 200 MB、几种外壳差几十 MB」。按实际下载到的组件大小重估后改成上表：Codex 压缩后约 130 MB，Electron 44 的外壳约 130 MB。推荐不变，因为理由不在体积上；体积差距已如实告知用户。
- **最终决策（用户 2026-10-06「仍用Electron」，在得知体积更正之后）**：用 Electron，记为 ADR-0013（accepted）。
- 没推荐 B：它没有常驻。共享 Agent 要求「所有者本机在跑」，关掉浏览器后半小时服务就退出了。另外 Mac 上还要从零写外壳。
- 没推荐 C：Mac 上的网页引擎与验收环境不一致，还多一套 Rust 工具链；它省下约 120 MB 下载，不足以抵消这些。
- 澄清：之前那句「客户端不要去改 electron」说的是源码运行阶段。这里的 Electron 只是外壳，本机服务与前端的代码形态不变，用浏览器访问 `127.0.0.1` 照样可用。

### 讨论 2：签名与公证（已定：首版不签名，作为试用版）

| 平台 | 不签名的后果 | 签名的成本 |
|---|---|---|
| Mac | macOS 15 起，首次打开要到「系统设置 → 隐私与安全性」点「仍要打开」并输入密码；Apple 芯片的 Mac 要求至少有临时签名（构建时自动加）；应用内一键安装更新（替换应用本体）要求已签名 | Apple 开发者计划 99 美元 / 年，个人可以申请；签名加公证接入构建流程 |
| Windows | SmartScreen 提示「已保护你的电脑」，要点「更多信息 → 仍要运行」；部分杀软可能误报 | 商业代码签名证书每年数百美元，2023 年起私钥必须放在硬件令牌或云端 HSM；微软 Artifact Signing（原 Trusted Signing）个人开发者目前只对美国、加拿大开放 |

- **最终决策（用户 2026-10-06「首版不签名，作为试用版发布」）**：首版不签名（Mac 用临时签名），作为试用版发布，附 SHA256 和「首次打开」的图文说明。签名单独作为一片（D4），证书到位就能接入。Claude 的建议仍然是：对外推广前先办 Apple 开发者账号（Mac 上签与不签的体验差距最大，成本也最低）；Windows 证书看试用反馈再定。
- 试用期间 Mac 的影响：首次打开要手动放行；不能一键更新，只能跳转下载页；可能还要手动去掉隔离标记（技术设计待实测 1）。

### 讨论 3：关闭窗口后怎么办（已定：按推荐）

- **推荐**：关窗后留在菜单栏（Mac）或通知区域（Windows）继续运行。进行中的会话不中断，房间里共享的 Agent 继续响应。从托盘菜单或「退出」菜单（⌘Q）才真正停止；有进行中的会话时先确认一次。第一次关窗时提示一次「SuDuo 仍在后台运行」。开机自启在设置里提供开关，默认关闭。
- 备选：关窗即退出。实现最简单，但共享 Agent 会随之掉线，和房间的设计相悖。

### 讨论 4：更新方式（已定：按推荐）

- **推荐**：启动时检查一次新版本，之后每天检查一次。有新版时在应用内提示「x.y.z 可用」，附更新说明。Windows 一键下载安装，重启生效；Mac 在签名之前打开下载页手动替换，签名后改成一键更新。设置里可以关闭自动检查，团队要和云端版本保持一致时用。不强制更新（ADR-0004）。连不上外网（纯内网）时，检查失败不打扰使用者。
- 下载源：GitHub Releases 为主，官网下载页指向它。国内下载慢的话，在 suduo.dev 放镜像（见开放问题）。

### 讨论 5：数据与 Codex 配置放哪（推荐直接定）

- **本机数据与源码运行分开，互不接管。** 共用会有两个问题：同一份会话可能被两个服务同时驱动；两边版本不同时，数据库迁移会冲突。首版不做「从源码运行导入数据」：需求、房间都在云端，本机只有个人会话记录和目录映射。
- **Codex 配置用 `~/.codex`**，和源码运行、使用者自己装的 Codex 是同一个目录，已经登录过 Codex 的人装完即用。不再支持旧 Windows 安装器那种「构建时注入团队配置和密钥」（R7）。
- **Windows 的数据放本机目录（`%LOCALAPPDATA%` 下），不放漫游目录**：在域环境里，漫游目录会随登录同步 SQLite 文件。
- **默认端口与源码运行不同**，两者可以同时开着，谁也不把对方当成自己。具体路径和端口在技术设计里定。

### 讨论 6：旧 Windows 安装器（推荐直接定）

- **推荐**：用新方案替换旧安装器，删除 `client/scripts/dist-win/`，同时重写或删除 `docs/windows-verify.md`。旧安装器从未对外发布，没有存量用户；它只能在 Linux / WSL 上构建，文档也已过时。其中「探测 → 拉起 → 等就绪」的逻辑搬到新外壳里继续用。

### 讨论 7：Mac 出几个包（推荐直接定）

- **推荐**：Apple 芯片和 Intel 各出一个安装包，不做通用包，因为通用包要放两份 Codex 二进制，约 600 MB。官网下载页自动识别芯片，同时列出两个链接。

## 四、功能 / 范围

> 以下按讨论 1–4 的推荐写；用户拍板结果不同时相应调整。

### 4.1 安装与卸载

| 项 | 说明 |
|----|------|
| Mac | `.dmg`，拖进「应用程序」即装好。卸载就是删除应用；本机数据保留，文档写明数据位置和彻底清除的办法 |
| Windows | 安装程序 `.exe`，装到当前用户，不需要管理员权限；创建开始菜单和桌面快捷方式；可以在「设置 → 应用」里卸载，卸载时询问是否同时删除本机数据，默认保留 |
| 内含 | 本机服务、前端、锁定版本的 Codex、SQLite 模块，以及运行本机服务用的官方 Node。不依赖预装的 Node 和 pnpm。Git 不捆绑（见 4.6） |
| 语言 | 安装程序、菜单、托盘、提示框都有中英文，跟随应用的界面语言；首次启动时跟随系统语言 |

### 4.2 启动与窗口

| 项 | 说明 |
|----|------|
| 启动 | 双击图标后拉起本机服务（只监听 127.0.0.1），同时打开 SuDuo 窗口。服务就绪前显示启动页；启动失败时显示原因、日志位置和「运行自检」按钮，不会无声消失 |
| 单实例 | 再次双击只把已有窗口带到前面，不会启动第二个服务 |
| 窗口 | 记住上次的大小和位置。外部链接（文档、MCP 授权页、官网等）用系统默认浏览器打开 |
| 浏览器访问 | 在浏览器里打开窗口「关于」显示的本机地址照样能用，连的是同一个服务 |
| 与源码运行并存 | 端口和数据都分开，同时开着互不影响（讨论 5） |

### 4.3 常驻与退出

按讨论 3：关窗后常驻，托盘菜单里有「打开 SuDuo」「退出」；退出时如有进行中的会话先确认；开机自启开关默认关闭。

### 4.4 系统通知

现有的「设置 → 通知」（会话需要确认、会话完成等）改用系统原生通知，不再需要浏览器授权通知权限；点击通知打开对应页面。开关和规则沿用现状。

### 4.5 Codex 与模型账号

| 项 | 说明 |
|----|------|
| Codex | 只用应用内置的锁定版本，配置目录用 `~/.codex`（讨论 5） |
| ChatGPT 账号登录（推荐纳入首版） | 「设置 → 模型服务」在现有的 API Key 方式之外，增加「用 ChatGPT 账号登录」：走 Codex 自带的登录流程，在系统浏览器里完成授权；同时显示登录状态，可以退出登录。原因是安装版使用者没有现成的 `codex login` 命令可用 |
| 运行环境 | 从访达或开始菜单启动时，拿不到终端里的环境变量（主要是 PATH），Codex 在项目里执行 npm、pnpm、python 等命令会找不到。Mac 上启动时读取使用者登录 shell 的环境；Windows 用系统和用户的环境变量。公司代理沿用「设置 → 代理」 |

### 4.6 自检与诊断

- 启动失败页和「设置 → 诊断」沿用现有自检，去掉 Node、pnpm 这类源码运行才需要的检查项。
- 新增 Git 检查：检查点等功能需要 Git。没装时给出引导：Mac 安装 Xcode 命令行工具，Windows 安装 Git for Windows。缺 Git 不阻止启动。
- 「打开日志目录」「打开数据目录」两个入口。

### 4.7 更新

按讨论 4：启动时和每天检查一次，应用内提示并附更新说明，Windows 一键更新，Mac 在签名前跳转下载页；可以关闭自动检查；不强制。

### 4.8 构建与发布

| 项 | 说明 |
|----|------|
| 产物 | 每个发布标签产出 `mac-arm64.dmg`、`mac-x64.dmg`、`win-x64.exe` 三个安装包和各自的 SHA256，挂在 GitHub Release 上 |
| 构建 | 在 GitHub 托管的三种机器（Mac Apple 芯片、Mac Intel、Windows）上构建。每个包构建完都自动装起来跑一遍冒烟：启动 → 健康检查 → 页面能打开 → 用假 Codex 跑通一轮会话 |
| 发布流程 | 在现有发布流程（版本号、CHANGELOG、CI、gate-c）之后，加上「三平台安装包构建通过并附到 Release」。CHANGELOG 增加下载说明 |
| 官网 | 下载页属于官网仓库的改动，随[官网改版](官网改版-需求.md)里「本机一键体验另开需求」那条一起做；本需求只提供稳定的下载地址 |

### 4.9 文档（中英双语）

- README 快速开始改成「下载安装」为主，源码运行降为开发者路径，挪到 `client/README.md`。
- 安装说明：各平台的系统要求、首次打开（未签名时的图文步骤）、数据位置、卸载与彻底清除、常见问题（杀软误报、端口、代理、Git）。

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 支持 macOS 13.5+（Apple 芯片、Intel 各一个包）与 Windows 10/11 x64 | 与源码运行相同；不支持 Win7/8、32 位、Windows on ARM，不出 Linux 安装包 |
| R2 | 只用应用内置的锁定版本 Codex | 不用 PATH 上的 Codex，避免版本与协议不一致 |
| R3 | 本机服务只监听 127.0.0.1 | 沿用 |
| R4 | 模型凭据由 Codex 自己保存和使用 | SuDuo 只经 Codex 的配置和登录接口操作，不另存、不外传；安装包不预置任何凭据 |
| R5 | 有新版本、与云端版本不一致，都只提示不拦截 | ADR-0004；不强制更新 |
| R6 | 安装版与源码运行的数据、端口分开，互不接管 | 讨论 5 |
| R7 | 安装包不含任何密钥或团队配置 | 废弃旧安装器的「注入受管配置」 |
| R8 | 卸载默认保留本机数据 | 删除要使用者明确选择 |
| R9 | 退出时有进行中的会话，先确认再停 | 只确认不拦截：确认后照常退出 |

## 六、边界 / 不做项

- 不改本机服务与前端的形态：仍是 127.0.0.1 上的 Web 服务加页面，业务逻辑不放进外壳。
- 不出 Linux 安装包（AppImage、deb 等）。Linux / WSL 继续用 `install:m1`，供开发和 gate-c 使用。
- 不上架 Mac App Store、Microsoft Store。
- 不做 Mac 通用包。
- 不捆绑 Git，也不捆绑使用者项目需要的工具链。
- 不做模型中转，不预置团队模型配置。
- 首版不做「从源码运行导入本机数据」。
- 云端不出安装包，仍按[云端私有化部署](云端私有化部署-需求.md)的脚本安装。
- 证书到位前不做签名和公证（讨论 2）。

## Claude 解读

源码运行解决了「能跑」，安装包要解决的是「装上就用、关窗不掉线、能更新」。推荐 Electron 外壳包住现有的本机服务和前端：业务代码不动，外壳负责拉起服务、窗口、托盘、通知和更新。签名是成本问题，不影响架构，单独作为一片，证书到位再接入。

## 保真差异

- 原话只说「打包成 mac/win 支持的应用程序」。以下都是主动新增，各自对应讨论里的理由：托盘常驻、系统通知、单实例、更新提示、应用内 ChatGPT 登录、Git 自检、登录 shell 环境、退役旧 Windows 安装器。
- **单实例**（再次打开只把已有窗口带到前面）按 ADR-0004 过三问。仲裁者：使用者。拿掉它最坏的结果：两个服务抢同一端口和数据库，第二个起不来，或者界面连错服务。人能否恢复：能，关掉一个即可。而且它不拒绝任何操作，只是把已有窗口带到前面。
- **退出确认**（R9）只确认不拦截，确认后照常退出，不属于拒绝式守卫。
- 本需求没有引入锁、版本校验、幂等或 409 一类拒绝式守卫。
