# SuDuo V2 项目聊天房间与共享 Agent 需求设计

> 一句话：每个项目自带一个群聊房间，需求下也能另开房间；成员可以把自己的 AI 共享进房间，任何人 @ 它提问，它在所有者电脑上分析后把回答挂在那条消息下面，全员可见。｜最后更新：2026-09-30
>
> 依赖：[需求会话上下文重做](v2-需求会话上下文重做-需求.md) 的工具层（Agent 在需求房间里取需求信息用的就是那套工具），应先做。竞品参考：Tutti（tutti.sh），2026-09-30 实际进入其房间「技术小队」体验过。

---

## 需求描述

SuDuo 现在有两种协作方式：需求评论（正式、异步、不可撤回）和本机会话（一个人和自己的 Codex）。缺的是团队即时讨论的地方，更缺的是「把 AI 的分析摆到大家面前」：PM 电脑上没有代码，想知道某个功能现在怎么实现，只能去问开发，开发再去问自己的 Codex，再把结论转述回来。

本需求新增聊天房间。每个项目创建时自带一个房间，所有成员都在里面；需求下可以手动再开房间，机制相同。房间里有两类成员：真人和 Agent。成员主动把自己的 Codex 共享进某个房间后，房间里任何人都可以「消息 + @ 它」来提问；Agent 在所有者自己的电脑上、在该项目的代码目录里只读地分析，回答挂在被 @ 的那条消息下面，显示执行中、已完成等状态和一句摘要，点开后在右侧查看完整回答和执行过程。所有者随时可以关闭共享。

通信由我们自建：消息、图片、文件、视频全部存在自己的服务器上；上传、存储、实时推送都做成独立模块，存储以后可以切换到云存储。

## 原话（verbatim）

> 「2. 你帮我设计一套 聊天room机制和业务逻辑，我目前大概的想法，需求是：每个项目创建的时候自带一个群聊room，这个群聊room是自动拉上所有的参与人员在里面，可以进行即时聊天。房间里的用户可以把自己的 ai(当作一个agent用户)拉入房间，所有人都可以发送 消息内容+艾特它 来触发让它可以进行相关的分析和梳理（注意它的上下文机制和群聊的上下文，如何设计群聊的上下文保留多少条给它和相关的记忆机制？），所以一个群聊room有两个类型的用户（真人用户、ai agent用户）。ai 的回复直接挂在被艾特的消息下面（执行中、执行完毕等状态和简短的文字/内容/消息提示），点击可以右侧打开查看详细的回复。 这可能需要设计一个im即时通信？我们是否可以自建这个通信，全部基于服务端，只需要上传文件、视频、消息即可，存储在本地。注意做好相关各个功能的模块化，例如上传功能我现在是上传到服务器，后面可能迭代可以配置上传到云存储之类的。所以一定要业务模块化开发。另外需求 也需要可以手动额外创建一个 群聊room，只不过room的挂载属于 项目-需求 下。机制是一样的。 关于room和ai agent 有一个竞品可以参考（https://tutti.sh/zh）」

> 「关于这个问题，所以我们要有 用户共享机制，某人/用户 要主动去共享自己的ai到那个房间，其他人才能使用。他可以随时关闭自己的共享。可以理解为她需要沟通的时候就共享，沟通结束就可以取消共享」

> 「"它的 Agent 跑在隔离虚拟机里" 我们不能放在虚拟机吗？
> 还有就是 我们本身就是独立部署的，那么大概率在团队内属于内网或者可审批进入。所以不用担心agent被滥用，团队的ai也是团队本身提供给成员的，所以不需要什么约束。在业务层或者团队管理层做好管理、约束即可
> 暂时不需要悄悄话机制
> "共享 Agent 默认「只读问答」档（推荐），还是首期就允许改代码？" 暂时只问答、规划之类的
> 其他的决策按照你的方案处理即可。」

## 二、背景与目标

**目标对齐**：房间是团队的即时讨论空间，它和需求评论、本机会话的分工如下。

| | 需求评论 | 本机会话 | 房间（新增） |
|---|---|---|---|
| 性质 | 正式记录，不可撤回 | 私人工作台 | 团队即时讨论 |
| 谁能看 | 全员 | 只有自己 | 房间里的人 |
| AI 的角色 | 无 | 自己的助手 | 被 @ 的成员，回答全员可见 |

边界延续现有原则「共享的是需求，私有的是代码和对话」：房间里共享的是 AI 的**回答和执行过程**，代码和执行都留在所有者电脑上。

### 与项目定位的对齐（2026-10-01 复核）

用户 2026-10-01 要求「根据项目的定位、目标，对这两个需求进行目标对齐和相关的设计分析」后一路实施。复核结论：

| 项目定位 / 原则 | 本需求的对应 | 结论 |
|---|---|---|
| 需求协作工作台 | 在「评论（正式、异步）」与「本机会话（私人）」之间补上团队即时讨论；需求房间挂在需求下 | 对齐，补齐 L1 的同步协作 |
| AI 协作平台，人在回路里 | Agent 只在被 @ 时执行，所有者主动共享、随时关，触发人可停、可重试 | 对齐 |
| 共享的是需求，私有的是代码和对话 | **有变化**：共享期间 Agent 的回答与完整执行过程（含代码片段、命令输出）进服务器、全员可见；只读沙箱可读整盘 | 用户已拍板「完整展示、不做额外约束」，新边界写进 [ADR-0009](../06_决策记录/ADR-0009-房间共享Agent的数据边界.md)：共享的是需求和房间讨论（含被共享 Agent 的回答与执行过程），私有的是代码仓库和个人会话 |
| 不在服务端跑 Codex | Agent 在所有者本机执行，复用本机会话运行时 | 对齐 |
| 不做角色权限 / 组织租户 | 房间全员可见可加入，成员只决定未读与提醒 | 对齐 |
| 一致性边界（ADR-0004） | 消息按客户端 ID 合并、重复登记 / 重开共享 / 重复申请 / 重试都合并，不新增拒绝式守卫；「只有所有者能共享自己的 Agent」是授权，不是一致性守卫 | 对齐（三问见第三节「消息去重」） |

复核中做的细化（不改变已拍板的决策）：

1. **P0 拆成四片依次交付**：S1 房间与文本消息（实时、补拉、未读、@人、话题、合并重试）→ S2 存储与媒体 → S3 Agent 登记 / 共享 / 申请 / 在线 / 续期常驻 → S4 @Agent 执行与三层展示。每片可单独演示与验收。
2. **共享 Agent 不挂写工具**：房间里的 Agent 只有房间工具与需求只读工具，不写所有者的结论笔记、不发评论、不发布确认版（「只问答与规划」）。
3. **执行过程体积有上限**：单条命令输出截 4000 字、整段过程截 1.5MB，只为控制体积，不是脱敏。
4. **「今天」按浏览器本地时间算到期**。

### 模拟示例

项目「订单系统」创建时自动有了房间「订单系统」，全组 6 人都在里面。

1. 开发小王打开房间，点「共享 Agent」，把「小王的 Codex · MacBook Pro」共享到这个房间，时长选「今天」。房间成员列表里，小王名下出现这个 Agent，状态「可用」。
2. PM 小李在房间里发：「@小王的Codex 商家后台的订单详情现在能拿到收货信息吗？」
3. 消息下面立刻出现一行「小王的 Codex · 排队中」，随后变成「执行中 · 查看了 6 个文件」。
4. 小王电脑上的 SuDuo 在「订单系统」映射的代码目录里，以只读方式起了一个 Codex 线程。它拿到的上下文是：身份与房间说明、触发消息、前面 20 条房间消息。
5. 两分钟后，那行变成「✓ 已完成 · 后端已有 receiverSnapshot，前端抽屉没展示」。小李点开，右侧面板显示话题：原消息、任务状态卡、完整回答；再点「查看详情」，看到 Agent 查看了哪些文件、跑了哪些命令。
6. 测试小张在这个话题里追问：「@小王的Codex 历史订单也有吗？」——同一个 Codex 线程接着回答，不用重新交代背景。
7. 下午 PM 在需求「REQ-1 商家端-订单详情优化」下新建房间「REQ-1 讨论」，拉上小王和小张。在这个房间里 @ Agent 时，它还能用需求工具查需求正文、评论、附件。
8. 小王下班合上电脑。房间里他的 Agent 变成「离线」，这时 @ 它，消息下立即显示「离线，未执行」；第二天小王上线后，小李点「重试」即可。

## 三、讨论与决策

### 讨论：房间的定位，以及和 Tutti 的取舍

- Tutti 的主角是「房间里公开的 Agent 会话」：会话默认其他人可编辑，房间是一个云端文件系统，群聊只是右上角的浮层。
- **最终决策 + 理由**：我们以**群聊为主**，Agent 回复挂在消息下面（用户原话），本机会话保持私有。照搬 Tutti 群聊里的回复链路（消息下预览 → 话题面板 → 运行详情）、人与 Agent 在线状态分离、「申请共享」；不照搬会话公开和云端文件同步。

### 讨论：房间挂在哪、有哪几种

- **最终决策 + 理由**：两种，机制相同。**项目默认房间**：创建项目时自动建立，名称跟随项目，不能删除，可以归档。**需求房间**：在需求下手动建立，一条需求可以有多个。依据用户原话「每个项目创建的时候自带一个群聊room」「需求也需要可以手动额外创建一个群聊room……机制是一样的」。

### 讨论：「所有的参与人员」指谁

- 现状：系统没有项目成员概念，所有登录用户都能看所有项目和需求（「凡是新建的创建的"需求"都是全平台开放」）。
- **最终决策 + 理由**：房间对所有登录用户**可见、可加入**，不做权限。项目默认房间自动包含全部用户（后注册的也自动加入）；需求房间的初始成员默认是创建人、需求负责人和需求创建人，其他人可以自行加入。「成员」只决定未读、提醒和 @ 候选，不做访问控制。

### 讨论：Agent 在哪里执行，要不要放进虚拟机

- 备选：所有者本机直接执行 / 本机虚拟机或容器内执行 / 服务端集中执行。
- **最终决策 + 理由**：**在所有者本机、在该项目映射的代码目录里执行**，用 Codex 自带的只读沙箱。不做虚拟机：每台机器都要装虚拟机运行时和镜像，虚拟机里没有本机的开发环境和凭据（Tutti 就因此推不了 GitHub），Windows 安装包还要多捆一层；而它的主要收益「防止别人借你的 AI 动你的电脑」，在「内网部署、AI 由团队提供、首期只问答」的前提下很小。不做服务端执行：代码不在服务器上，也违反「不在服务端跑 Codex」的边界。**执行环境做成可替换的执行器**，以后要放开改代码时再评估虚拟机执行器，房间逻辑不用动。

### 讨论：谁能用某人的 Agent

- **最终决策 + 理由**：**所有者主动共享，随时可关**（用户原话）。补充三点：①共享按房间逐个开启；②可选时长「直到我关闭 / 2 小时 / 今天」；③房间成员可以对未共享的 Agent 点「申请共享」，所有者收到提醒后一键开启（借鉴 Tutti）。

### 讨论：共享出去的 Agent 能做什么、要不要额外约束

- **最终决策 + 理由**：首期**只做问答与规划**，不改代码文件（用户原话「暂时只问答、规划之类的」），用 Codex 自带的只读沙箱实现，不弹审批，可以联网查资料。**不做额外约束**：不限制只读项目目录、不屏蔽敏感文件、不设「发出前所有者过目」、不设额度上限。依据用户原话「团队的ai也是团队本身提供给成员的，所以不需要什么约束。在业务层或者团队管理层做好管理、约束即可」。

### 讨论：执行过程给房间看多少

- **最终决策 + 理由**：**完整展示**，与本机会话页的回合时间线一致（文字、查看了哪些文件、运行了哪些命令）。既然不做额外约束，就没有理由只给摘要；直接复用会话页的展示方式，实现也更简单。

### 讨论：Agent 的群聊上下文给多少，记忆怎么做

- **最终决策 + 理由**：分层给，默认值见 4.8。核心是**一个话题对应一个 Codex 线程**：在话题里追问就接着同一个线程，不需要重新交代背景；新开一次 @ 就是新话题、新线程，并带上近邻消息。不给全部历史：无关消息是噪音，也浪费额度。Tutti 的做法（最近 24 条过滤后最多 16 条，溢出时降到 4 条再到 0 条）与此量级一致，溢出逐级降级照搬。共享记忆（房间置顶与纪要）放到 P1。

### 讨论：所有者离线时被 @ 怎么办

- **最终决策 + 理由**：立即在消息下显示「离线，未执行」，**不排队等上线补跑**，避免所有者上线后在电脑上突然连续执行一批过期请求。所有者上线后，触发人可以一键重试。

### 讨论：通信自建还是用第三方

- **最终决策 + 理由**：**自建**。内网几十人的规模完全够用；消息、文件、视频都留在自己的服务器上。实时推送沿用现有方式（服务端推送下行 + HTTP 请求上行，全部经本机服务转发），不引入第三方 IM。数据模型参考 Tutti 的做法：每个房间一个递增序号、成员已读序号、断线按序号补拉。

### 讨论：消息要不要按客户端 ID 去重

- **最终决策 + 理由**：做。客户端发送时带一个 ID，网络重试时服务端返回已有的那条消息，**不拒绝、不报错**；这个 ID 同时用于发送时本地先显示、再和服务端返回对齐。依据用户原话「其他的决策按照你的方案处理即可」。按 ADR-0004 三问：仲裁者是系统按 ID 合并，不拒绝任何请求；拿掉它的最坏结果是网络重试产生重复消息，被 @ 的 Agent 把同一个问题跑两遍、话题里出现两份回答；人能自己恢复（忽略即可）。它够不上红线，但也不是拒绝式守卫，而是合并。

### 讨论：悄悄话

- **最终决策 + 理由**：**不做**（用户原话「暂时不需要悄悄话机制」）。

## 四、功能 / 范围

### 4.1 房间

| 项 | 说明 |
|----|------|
| 做什么 | 项目默认房间（建项目时自动建，名称跟随项目，不可删除，可归档）；需求房间（需求下手动建，可多个，可改名、可归档） |
| 谁用 | 所有登录用户 |
| 入口 | 侧栏项目区新增「讨论」：房间列表 + 房间页；需求详情页新增「讨论」区块：本需求的房间与「新建讨论」 |
| 预期结果 | 归档后房间只读，仍可查看历史。「只读」由界面保证（输入框换成归档说明）；服务端对归档前就已发出、晚到的消息照常收下，不拒绝（ADR-0004：拿掉拒绝最坏只是消息进了已归档房间，人可以取消归档，够不上红线） |

### 4.2 成员

| 项 | 说明 |
|----|------|
| 做什么 | 房间成员分真人和 Agent 两类；成员列表显示每人在线状态、名下 Agent 及其共享状态 |
| 加入 | 项目默认房间自动包含全部用户；需求房间初始成员为创建人、需求负责人、需求创建人，其他人可自行加入或被拉入 |
| 在线状态 | 真人：是否打开着 SuDuo。Agent：所有者本机的 SuDuo 是否在线且已登录、该房间的共享是否开着。两者分开显示（所有者本人「离线」时，他的 Agent 仍可能「可用」） |

### 4.3 消息

| 项 | 说明 |
|----|------|
| 类型 | 文本（Markdown）、图片、文件、视频；可在一条消息里组合 |
| @ | 可以 @ 人、@ 所有人、@ Agent。@ 所有人只提醒真人，**不唤起 Agent** |
| 话题 | 可以对任意消息回复，形成话题；消息下显示「N 条回复」及最近回复者 |
| 未读 | 每个房间的未读数、@ 我的提醒；侧栏「讨论」显示总未读 |
| 去重 | 网络重试不产生重复消息（见三、讨论） |
| 不做 | 编辑消息；撤回放 P1 |

### 4.4 文件与视频

| 项 | 说明 |
|----|------|
| 做什么 | 上传图片、文件、视频；图片内联预览，视频可在浏览器里直接播放（可拖动进度），其他文件可下载 |
| 限制 | 单个文件大小沿用现有附件上限 300MiB |
| 存储 | 存在自己的服务器上；存储做成可替换模块，以后可以按配置切换到云存储（见 4.10） |

### 4.5 Agent 与共享

| 项 | 说明 |
|----|------|
| Agent 是什么 | 某人本机的 Codex，显示为「<所有者> 的 Codex · <设备名>」。首期只支持 Codex |
| 共享 | 房间页「共享 Agent」：选择自己的 Agent、选择时长（直到我关闭 / 2 小时 / 今天）、开启。共享按房间逐个开启 |
| 前置条件 | 所有者在本机已为该项目关联代码目录；没有关联时引导先关联 |
| 关闭 | 随时可关；时长到期自动关闭；关闭或本机下线后立即不可被 @，**正在执行的任务停止** |
| 申请共享 | 房间成员可以对未共享的 Agent 点「申请共享」；所有者收到提醒，一键开启或忽略 |
| 所有者视角 | 所有者在本机 SuDuo 能看到自己的 Agent 正在为哪个房间、哪条消息工作，可随时停止 |

### 4.6 @Agent 的执行

| 项 | 说明 |
|----|------|
| 触发 | 消息里 @ 了某个已共享且可用的 Agent。只有 @ 才触发；同一条消息 @ 多个 Agent 时各自执行 |
| 执行位置 | 所有者本机、该项目映射的代码目录、Codex 只读沙箱、不弹审批、可联网 |
| 能做什么 | 问答、分析、规划；不修改代码文件 |
| 状态 | 排队中 → 执行中 → 已完成 / 失败 / 已停止；所有者不在线时为「离线，未执行」 |
| 排队 | 同一个 Agent 的任务按顺序执行，消息下显示「前面还有 N 个」 |
| 停止 | 触发人和所有者可以停止 |
| 重试 | 失败、已停止、离线未执行的任务，触发人可以重试 |

### 4.7 Agent 回复的展示

三层，借鉴 Tutti：

| 层 | 内容 |
|---|---|
| 消息下 | 「<所有者> 的 Codex · 状态」+ 执行中的进度（「查看了 6 个文件」）或完成后的一句摘要 |
| 右侧话题面板 | 原消息 → 任务状态卡（状态、用时、「查看详情」）→ Agent 的完整回答 → 后续话题回复；面板底部可以继续在话题里回复 |
| 运行详情 | 完整执行过程：文字、查看的文件、运行的命令及输出，与本机会话页的回合时间线一致 |

### 4.8 Agent 的上下文

| 层 | 内容 | 默认量 |
|---|---|---|
| 固定层 | 身份（「你是小王的 Codex，在房间 X 里被同事 @」）、房间与项目信息、需求房间附需求卡、能力说明（只问答与规划） | 约 1000 字 |
| 话题层 | 当前话题的全部消息 | 最多 50 条 |
| 近邻层 | 触发消息之前的房间消息（新话题时） | 最近 20 条，且在 24 小时内；单条截到 500 字；附件只给文件名 |
| 按需层 | 工具：翻更早的房间消息、按关键词找房间消息、看房间里的图片和文件；需求房间另有需求工具（查需求、评论、附件、确认版） | 模型自行决定 |
| 线程延续 | 一个话题一个 Codex 线程，保存在所有者本机；再次被 @ 时只追加上次之后的新消息 | — |
| 溢出降级 | 超出模型上下文时，近邻层逐级减到 5 条、0 条 | — |

### 4.9 实时与可靠性

| 项 | 说明 |
|----|------|
| 实时 | 新消息、任务状态、成员与共享变化实时推送到所有打开的页面 |
| 断线 | 重连后按房间序号补拉，不丢消息也不重复 |
| 多标签页 | 同一台电脑的多个标签页共用一条到服务端的连接 |

### 4.10 模块化

用户原话要求「一定要业务模块化开发」。按业务拆成独立模块，模块之间只通过接口协作：

| 模块 | 职责 | 可替换点 |
|---|---|---|
| 房间 | 房间、成员、归档 | — |
| 消息 | 消息、话题、@、未读、去重 | — |
| Agent | Agent 登记、在线状态、共享、申请共享、任务 | 执行器（本机直接执行先行，以后可加虚拟机执行器） |
| 实时 | 推送、按序号补拉 | 推送通道（首期服务端内存实现，以后可换数据库通知或独立推送服务） |
| 存储 | 文件存取、引用登记（被引用的文件不会被清理） | 存储驱动（首期服务器本地磁盘，以后按配置切换 S3 / OSS / MinIO 等） |
| 媒体 | 上传、下载、图片预览、视频分段播放 | — |
| 提醒 | 未读、@ 提醒、申请共享提醒 | — |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 房间全员可见可加入 | 不做房间级权限或角色 |
| R2 | 项目默认房间随项目自动创建 | 不可删除，可归档；自动包含全部用户 |
| R3 | Agent 只在共享期间可被 @ | 共享由所有者主动开启（用户原话） |
| R4 | 关闭共享即刻生效 | 关闭、到期或所有者下线后立即不可被 @，正在执行的任务停止 |
| R5 | 只有 @ 才唤起 Agent | 话题里不 @ 的回复不触发，但会成为下次的上下文 |
| R6 | @ 所有人不唤起 Agent | 只提醒真人 |
| R7 | 共享 Agent 只问答与规划 | 只读沙箱，不修改代码文件（用户原话「暂时只问答、规划之类的」） |
| R8 | 不做额外约束 | 读取范围、敏感文件、发出前审核、额度均不做系统限制，由团队管理层负责（用户原话） |
| R9 | 回复挂在触发消息的话题下 | 状态与摘要显示在触发消息下方 |
| R10 | 一个话题一个 Codex 线程 | 话题内被 @ 时延续同一线程 |
| R11 | 离线不补跑 | 所有者离线时立即标记「离线，未执行」，可由触发人重试 |
| R12 | 同一 Agent 串行执行 | 显示排队位置 |
| R13 | 消息按客户端 ID 合并 | 重试返回已有消息，不拒绝（理由与 ADR-0004 三问见三、讨论） |
| R14 | 执行过程对房间完整可见 | 与本机会话页的回合时间线一致 |
| R15 | 文件存储可替换 | 业务代码不依赖具体存储；被消息引用的文件不会被存储清理删除 |

## 六、边界 / 不做项

- 不做悄悄话（用户原话）。
- 不做共享 Agent 修改代码文件（首期只问答与规划）。
- 不做虚拟机或容器执行；不在服务端执行 Codex。
- 不做系统级的读取范围限制、敏感文件屏蔽、额度上限（由团队管理层负责）。
- 不做消息编辑；不做音视频通话；不做端到端加密。
- 不接入第三方 IM。
- 不做房间级权限与角色。
- 首期只支持 Codex 作为 Agent。

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |
|------|----------|
| 要不要把 Agent 放进虚拟机 | **已闭环**：首期不做，执行器可替换，放开改代码时再评估（用户 2026-09-30 追问后，同意按方案处理） |
| 房间成员范围 | **已闭环**：全员可见可加入（同上） |
| 共享 Agent 能力 | **已闭环**：只问答与规划（用户原话） |
| 登录 8 小时过期且不能续期，本机服务空闲会自动退出，会导致共享 Agent 莫名离线 | **移交技术方案**：共享期间保持本机服务常驻，并支持登录续期 |
| 现有推送只带「哪条变了」、不能补发、广播给所有连接 | **移交技术方案**：房间事件带内容、按房间序号补拉；这会改变「推送不带正文」的旧规则，只对房间事件生效 |
| 现有附件存储启动时会清理不被需求附件或确认版引用的文件 | **移交技术方案**：存储模块统一登记引用方，房间文件纳入保护 |
| 审计表的约束不允许「只属于项目、不属于需求」的记录 | **移交技术方案**：房间创建、改名、归档、共享开关写审计；消息本身不写审计（消息就是记录） |
| 视频经本机服务转发的播放性能 | **移交技术方案**：支持分段读取；必要时限制转码以外的处理 |
| 所有者本机如何展示「我的 Agent 正在为房间工作」 | **移交技术方案**：倾向在会话列表增加「房间任务」分类 |

## 八、拆分预览

- **P0**：房间（默认 + 需求）与成员 ｜ 消息（文本、图片、文件、视频，@，话题，未读，去重）｜ 存储模块（本地驱动）与媒体 ｜ 实时推送与断线补拉 ｜ Agent 登记、共享（含时长）、申请共享、在线状态 ｜ @Agent 在所有者本机执行（只读问答）｜ 消息下状态 + 话题面板 + 运行详情 ｜ Agent 上下文与房间工具

- **P2**：云存储驱动 ｜ 服务端多实例推送 ｜ 定时自动化 ｜ 放开改代码（届时评估虚拟机执行器）

## 十二、交互 / 流程

```
小李发消息「@小王的Codex …」
  → 服务端保存消息（序号 +1），为被 @ 的 Agent 建任务（排队中），推送给房间
```

## 十三、风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 所有者本机服务空闲退出或登录过期，Agent 莫名离线 | 高 | 共享不可用 | 共享期间保持常驻；登录续期；离线原因在界面上说清楚 |
| 所有者电脑同时承担多个房间任务，变慢 | 中 | 所有者体验 | 同一 Agent 串行；所有者可随时停止或关闭共享 |
| 房间消息驱动所有者的 Codex 读取其电脑上的内容 | 中 | 信息外流到房间 | 按用户决定不做系统限制；所有者通过「主动共享、随时关闭」控制，团队管理层负责约束 |

| 依赖需求会话上下文重做的工具层 | 中 | 排期耦合 | 先做工具层；房间工具与需求工具共用同一机制 |

## Claude 解读

用户要的是「团队讨论的地方 + 让每个人的 AI 能被大家使用」。关键在第二点：PM 没有代码，开发的 Codex 有；把开发的 Codex 共享进房间，PM 就能直接问到代码层面的事，回答全员可见，不再口口相传。

执行必须留在所有者电脑上，因为代码在那里，这也延续了 V2「不在服务端跑 Codex」的边界。共享是所有者主动开、随时关；首期只问答与规划，用 Codex 自带的只读沙箱；用户明确不需要额外约束，由团队管理层负责。

群聊上下文的核心设计是「一个话题一个 Codex 线程」：话题里追问天然连续，新问题带最近 20 条消息作背景，更早的内容由 Agent 用工具自己翻。

## 歧义点

- **「自动拉上所有的参与人员」指谁**：系统没有项目成员概念，按「全员可见可加入、项目默认房间包含全部用户」处理（用户 2026-09-30「其他的决策按照你的方案处理即可」）。
- **「把自己的 ai 拉入房间」是否等于任何人都能随时使用**：否。所有者主动共享、随时可关（用户原话）。
- **「存储在本地」**：理解为存在自己的服务器上，而不是第三方 IM 或云服务；存储驱动可替换。
- **群聊上下文保留多少条**：话题全文（≤50）+ 最近 20 条（24 小时内）+ 工具按需翻更早的消息（同上）。
- **虚拟机、约束、悄悄话、能力范围**：均已由用户拍板，见第三节。
- **推送、续期、存储引用、审计约束、视频播放**：移交技术方案。

## 保真差异

- 用户原话没有提到「申请共享」「共享时长」「离线不补跑」「同一 Agent 串行」「消息按客户端 ID 合并」，这些来自分析阶段的推荐和 Tutti 体验，已获用户「其他的决策按照你的方案处理即可」。其中只有消息合并涉及 ADR-0004，三问已在第三节作答。
- 用户原话「执行中、执行完毕等状态和简短的文字/内容/消息提示，点击可以右侧打开查看详细的回复」被细化为三层展示（消息下 → 话题面板 → 运行详情），第三层「运行详情」是新增，依据是用户决定不做约束后，完整过程可以直接给房间看。
- 撤回、群内文件面板、房间纪要等放进 P1，P0 范围比 Tutti 小。
- 原话中的「记忆机制」在 P0 体现为「一个话题一个 Codex 线程」，共享记忆（置顶与纪要）放在 P1。
- 2026-10-01 独立审查后的两处口径修正（不改范围）：①归档房间发消息原实现回 409，未过 ADR-0004 判据，改为界面只读、服务端收下晚到的消息；②第十一节「离线置灰」与模拟示例第 8 步矛盾，统一为「离线置灰但仍可 @、未共享不可 @」。
