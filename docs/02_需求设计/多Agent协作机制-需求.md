# 多 Agent 协作机制

> 一句话：让成员电脑上的多个 Agent 能互相读会话、接着做、委派、交叉评审、并行试做，讨论里能同时问多个 Agent，跨成员用交接包接力，一份项目 AI 规范对所有 Agent 生效；并为此设计统一的会话关系、上下文、调度、隔离与共享机制。与 P1 一起规划、一起实施。｜最后更新：2026-10-08（用户确认，开始实施）
>
> 母需求：[v3 规划](v3-多AI工具与多Agent协作规划-需求.md) 的 P2。前置：[P1 多 Agent 接入与本机工具服务](多Agent接入与本机工具服务-需求.md)。技术设计（P1 + P2 合并）：[多Agent接入与协作-技术设计](../03_开发计划/多Agent接入与协作-技术设计.md)。
>
> 术语：界面上的「讨论」在代码与 ADR-0009 里叫「房间」，「房间任务」指在讨论里 @ 共享 Agent 产生的只读任务；「子任务」指被委派出去的那件事，执行它的会话叫「子会话」；SuDuo 给 Agent 的工具统称「SuDuo 工具」，分「需求工具」（P1）与「协作工具」（本需求）。
>
> 决策：[ADR-0017 多 Agent 协作的核心模型](../06_决策记录/ADR-0017-多Agent协作核心模型-会话图上下文句柄调度隔离共享.md)（proposed），以及 ADR-0014 / 0015 / 0016。

## 需求描述

P1 让 SuDuo 能驱动多家 Agent，但每个会话仍是孤岛：Claude 做完的事，Codex 不知道；想让另一家帮忙评审或分担子任务，得靠人复制粘贴。人成了 Agent 之间的传话员。

本需求让 Agent 之间能协作，并把协作所需的底层机制一次设计好：

- **功能**：会话引用、接着做、委派、交叉评审、并行试做、讨论里问多个 Agent、交接包、项目 AI 规范。
- **机制**：
  - **会话**：会话的角色与相互关系（谁委派了谁、谁评审了谁、谁接着谁）；
  - **上下文**：每个 Agent 看到什么、怎么拿到别的会话的内容、拿到的东西从哪来；
  - **调度**：同一台电脑上多个 Agent 同时干活时，谁先谁后、上限多少、怎么等待、怎么停；
  - **隔离**：工作目录、权限、工具、凭据、对话历史彼此怎么隔开；
  - **共享**：哪些留在本机，哪些在什么条件下给团队看。

## 二、背景与目标

**目标对齐**：

- 在一个会话里能 @ 本机另一个会话（任意 Agent），当前 Agent 按需读取它的内容；能一键「交给另一个 Agent 接着做」。
- Agent 能把子任务委派给本机另一个 Agent，等它做完拿回结果；用户也能在输入框里直接 @ 一个 Agent 派活。
- 能请另一家 Agent 只读评审改动，得到结构化意见，一键交回原 Agent 修改；意见可以发到需求上。
- 同一任务能让两三家 Agent 在各自独立的工作目录里并行做一版，并排比较后选一版。
- 讨论里一条消息能同时 @ 多个共享 Agent。
- 跨成员接力用交接包：本人确认后发到需求上，接手的人开工时 Agent 自动读到。
- 项目 AI 规范写一份，所有 Agent 通过各自的指令通道生效。
- 以上都建立在一套清楚的机制上：会话有角色与关系、上下文按句柄按需取、本机有调度与排队、彼此隔离、共享分级且须本人确认。

**模拟示例**（工作室 Lotus Labs）：

```
Minh 的电脑上有 Claude Code、Gemini CLI、Codex 三个 Agent，并发上限按默认：每个 Agent 2 个、全部 4 个。

1. 引用：Minh 用 Claude Code 在 REQ-88 上做完了导出接口（会话 A）。他用 Gemini CLI 开会话 B，
   输入「@会话A 接着做前端页面」。
   → B 的时间线出现「引用了 Claude Code · 会话 A」。Gemini 先读 A 的最终回答与最近几轮问答，
     需要接口细节时再读 A 第 3 回合的工具调用；每次读取都显示一枚小标签。
2. 委派：做到一半，Gemini 调用「委派」工具：「让 Claude Code 给导出接口补集成测试，在同一目录」。
   → B 的时间线出现委派卡片「Claude Code · 补集成测试 · 运行中」，展开能看子会话 C 的过程；
     C 想运行 pnpm test，审批坞里出现「来自委派：Claude Code · 补集成测试」，Minh 允许；
     Gemini 调用「等待」工具，每次最多等 4 分钟拿一次进度；C 完成后结果（最终回答 + 改动文件列表）
     交回 B，Gemini 继续。
3. 排队：同时 Minh 又让 Codex 并行试做 REQ-91（两版：Codex、Claude Code）。Claude Code 已有 2 个在跑，
   → 「Claude Code 版」显示「排队中 · 第 1 位」，C 一结束它就开始。Minh 也可以手动「先跑这个」或取消。
4. 隔离：并行试做的两版各在独立工作目录与分支（suduo/REQ-91-codex、suduo/REQ-91-claude-code），
   互不干扰；委派 C 在 B 的同一目录（顺序协作）。B 与 C 同时改了 export.ts 时，两边都提示
   「另一个会话也在改这个文件」。
5. 评审：Minh 在 B 上点「请另一个 Agent 评审」，选 Codex。
   → 只读会话 D 读 B 的改动 diff、REQ-88 与验收说明，用「提交评审意见」工具交回 6 条结构化意见；
     Minh 勾选其中 4 条点「交给原 Agent 修改」，这 4 条作为新消息发给 Gemini；
     他又点「发布到需求」，确认后评审报告挂到 REQ-88，团队可见。
6. 试做比较：REQ-91 两版都完成，SuDuo 并排显示两版的说明、改动文件、测试命令结果、耗时；
   Minh 选 Codex 版「采用」，选择「保留分支，稍后提 PR」；Claude 版的工作目录与分支在他确认后删除。
7. 交接：Minh 下周休假，在会话 B 点「生成交接包」→ Gemini 用「提交交接包」工具起草
   （做到哪、关键决定、没做完的、分支名、相关文件），Minh 改两句后发布到 REQ-88。
   Tuan 在 REQ-88 上用 Codex 开工 → 会话卡里列出「交接包（Minh，10/08）」，Codex 先读它再干活。
8. 讨论：项目经理 Linh 在 REQ-91 讨论里同时 @ Duc 共享的 Codex 和 Minh 共享的 Claude Code
   → 两条任务分别在两人电脑上只读执行，回答并排挂在话题下。
9. 规范：Duc 在项目设置里改了「项目 AI 规范」第 3 版 → 之后新开的会话都带第 3 版，
   会话信息里显示「项目规范 v3」；已在进行的会话不受影响，显示「有新版本规范」并可一键应用。
```

- **背景**：见母需求 2.1、2.3；Tutti 研究（ADR-0014 背景）。
- **目标**：
  1. Agent 之间的上下文、子任务、评审由 SuDuo 传递，人不再复制粘贴。
  2. 多 Agent 同时干活时，人看得到谁在做什么、能排序、能停止；审批照常由人决定。
  3. 多 Agent 不互相踩：工作目录、权限、工具、凭据、对话各自隔离；冲突被告知而不是被锁住。
  4. 跨成员的协作只传本人主动分享的内容。

## 三、讨论与决策

| 决策点 | 结论 | 理由 / 否决 |
|---|---|---|
| 协作工具走什么通道 | P1 的本机 MCP 服务，按会话角色给不同工具 | 否决 Tutti 的「CLI + Skill」：Codex 要开免审批规则与沙箱网络；工具调用在时间线上只是命令文本（ADR-0015） |
| 跨会话传什么 | 传句柄，Agent 用工具分层读取；不注入摘要、不注入整段记录 | 摘要会走样，整段会撑爆上下文；按需读还能留下「读了什么」的记录 |
| 结构化产出怎么拿 | 评审意见、交接包让 Agent 调用「提交」工具交回结构化数据，不解析自由文本 | 各家 Agent 输出格式不一，工具参数有 schema |
| 委派深度 | 首期 1 层：子会话不能再委派 | 防止无限转派；以后可放开 |
| 超出并发上限 | 排队，不拒绝 | ADR-0004：不做拒绝式守卫；排队可见、可插队、可取消 |
| 同目录并发写 | 告知，不加锁 | ADR-0004；需要真正并行就用独立目录 |
| 委派默认在哪个目录 | 同目录（顺序协作）；可选独立目录；并行试做强制独立目录 | 委派多是「帮我补一块」，同目录最自然 |
| 子会话的对话历史 | 不继承父会话的对话，只拿任务说明 + 句柄 | 各家 Agent 的历史格式不通；按需读更省、更可控 |
| 跨成员共享 | 只传本人确认发布的内容：交接包、评审报告、会话快照（可选） | 「私有的是代码仓库和个人会话」不变 |
| 「协作记录」是否默认上需求 | **已定**：默认开启，只含元数据，可对单个会话关闭（P2-D1，按推荐） | 涉及数据边界，见 ADR-0017 |

## 四、功能 / 范围

### 4.1 会话引用

| 项 | 说明 |
|----|------|
| 做什么 | 一个会话引用本机另一个会话（任意 Agent，同一个 SuDuo 账号下的本机会话），当前 Agent 按需分层读取 |
| 谁用 | 开发 |
| 怎么触发 | 输入框 @ 选择会话（按项目、需求、最近排序）；Agent 自己调用「列出会话 / 读会话」工具 |
| 前置条件 | 当前 Agent 支持 SuDuo MCP 工具 |
| 预期结果 | 消息里显示会话标签；Agent 读取时时间线显示「读取了 Claude Code · 会话 A · 最近 3 轮」之类的小标签；被引用会话之后又有新进展时，读取结果会说明「引用后又有 2 个新回合」 |

### 4.2 接着做

| 项 | 说明 |
|----|------|
| 做什么 | 用另一个 Agent 继续一个会话的工作 |
| 怎么触发 | 会话菜单「交给另一个 Agent 接着做」→ 选 Agent、权限、目录（默认同目录） |
| 预期结果 | 新会话自动引用原会话，首条消息预填「接着 @原会话 继续：……」，用户确认后发出；两个会话互相显示「接续自 / 已由 X 接着做」 |

### 4.3 委派

| 项 | 说明 |
|----|------|
| 做什么 | 一个会话把子任务交给本机另一个 Agent（子会话），等它完成拿回结果 |
| 谁用 | Agent（调用委派工具）、用户（在输入框 @ 一个 Agent） |
| 怎么触发 | Agent 调用「委派」；用户在输入框 @Agent 写任务 |
| 前置条件 | 目标 Agent 就绪；发起者是主会话（只有主会话有委派工具与委派入口） |
| 预期结果 | 发起会话出现委派卡片（Agent、任务、目录、状态：排队中 / 运行中 / 等审批 / 已完成 / 失败 / 已取消），可展开看子会话、可停止、可打开子会话直接对话；子会话审批进审批坞并标明来源；完成后结果交回：若发起 Agent 正在等待则直接拿到，若发起回合已结束则卡片上出现「让原 Agent 继续」，发起时勾了「完成后自动交回」则自动开始新回合 |

### 4.4 交叉评审

| 项 | 说明 |
|----|------|
| 做什么 | 请另一家 Agent 只读评审一个会话的改动，得到结构化意见 |
| 怎么触发 | 会话「请另一个 Agent 评审」（可选重点：正确性 / 安全 / 测试 / 是否满足需求）；Agent 调用「请求评审」工具 |
| 预期结果 | 只读评审会话读取改动 diff、需求与验收说明，调用「提交评审意见」交回意见列表（严重程度、文件与行、问题、建议）；原会话出现评审面板，可勾选意见「交给原 Agent 修改」、可「发布到需求」（确认后团队可见） |

### 4.5 并行试做

| 项 | 说明 |
|----|------|
| 做什么 | 同一任务交给两到三家 Agent，各在独立工作目录与分支做一版 |
| 怎么触发 | 开工对话框「并行试做」并选 Agent；或会话菜单「用其他 Agent 也试一版」 |
| 前置条件 | 工作目录是 git 仓库 |
| 预期结果 | 每版一个工作目录（git worktree）与分支 `suduo/<需求号>-<agent>`；有未提交改动时提示「试做版本基于最近一次提交，不含未提交改动」并提供「先存检查点」；可配置「工作目录准备命令」（如 `pnpm install`）；全部完成后并排比较：说明、改动文件与 diff、测试命令及结果、耗时与用量；选一版「采用」（合并到原分支 / 保留分支稍后提 PR），其余在用户确认后删除工作目录与分支 |

### 4.6 讨论里问多个 Agent

| 项 | 说明 |
|----|------|
| 做什么 | 讨论里一条消息同时 @ 多个共享 Agent |
| 预期结果 | 每个 Agent 一条房间任务，分别在主人电脑上只读执行（ADR-0009），回答并排挂在同一话题下；各自独立失败、独立重试 |

### 4.7 交接包

| 项 | 说明 |
|----|------|
| 做什么 | 跨成员接力时传递的结构化摘要 |
| 怎么触发 | 会话菜单「生成交接包」→ 当前 Agent 调用「提交交接包」起草 |
| 预期结果 | 草稿字段：做到哪、关键决定、没做完的、风险、分支、相关文件；本人编辑确认后发布到需求；同一需求上新开会话时，会话卡列出交接包，Agent 可读；交接包可撤回（已被读过的无法收回，撤回时说明） |

### 4.8 项目 AI 规范

| 项 | 说明 |
|----|------|
| 做什么 | 一份项目级的 AI 规范，所有 Agent 生效 |
| 怎么触发 | 项目设置「AI 规范」编辑（项目成员都可编辑，记活动） |
| 预期结果 | 存在团队服务器、带版本；开工时通过该 Agent 的指令通道注入，会话记录所用版本；进行中的会话遇到新版本时提示并可一键应用；仓库里原有的 `AGENTS.md`、`CLAUDE.md` 等照常生效，SuDuo 不改它们 |

### 4.9 机制：会话与会话关系

| 概念 | 说明 |
|---|---|
| 会话角色 | **主会话**（用户开的）、**子会话**（委派出来的）、**评审会话**（只读评审）、**试做会话**（并行试做的一版）、**房间任务**（ADR-0009） |
| 会话关系 | 委派（父 → 子，记录父回合与工具调用）、接着做（新 → 旧）、评审（评审会话 → 被评审会话）、试做组（同组几版）。**引用**只记录读取事件，不建父子关系 |
| 会话树 | 会话列表按根会话分组，子会话、评审、试做显示在根下；每个会话仍可单独打开、单独对话 |
| Agent 固定 | 一个会话只用一家 Agent（P1 R5）；关系连接不同 Agent 的会话 |
| 删除与归档 | 删除根会话时询问是否连带子会话；子会话删除后，父会话的委派卡显示「子会话已删除」，结果摘要保留 |

### 4.10 机制：上下文

每个 Agent 拿到的上下文分四层：

| 层 | 内容 | 方式 |
|---|---|---|
| Agent 自己的对话 | 本会话的历史 | Agent 原生 |
| SuDuo 说明 | 角色说明（主会话 / 子任务执行者 / 只读评审者）、SuDuo 工具用法、项目 AI 规范 | 开工时通过该 Agent 的指令通道注入（P1） |
| 会话卡 | 需求标题与状态、任务说明（子会话）、可用句柄列表（被引用的会话、交接包、评审意见、父会话） | 开工时推送，简短 |
| 引用内容 | 需求全文与附件、别的会话、交接包、评审意见、改动 diff | Agent 按需调用工具拉取 |

读会话的分层：**概要**（最终回答、改动文件列表）→ **对话**（最近 N 轮的问答文本）→ **回合列表** → **回合细节**（某回合的命令、工具调用、文件 diff）→ **改动**（会话累计的 diff）。每层有大小上限与分页，大内容存到项目 `.suduo/` 下返回路径（ADR-0003）。

委派时子会话拿到：任务说明（发起者写）+ 父会话句柄 + 需求句柄 + 发起者列出的相关文件。完成时交回：子会话最终回答 + 改动文件与统计 + 子会话句柄（需要细节再读）。

### 4.11 机制：调度

| 规则 | 说明 |
|---|---|
| 并发上限 | 本机每个 Agent 默认同时 2 个运行中的回合，全部 Agent 合计默认 4 个；设置里可改 |
| 排队不拒绝 | 超出上限的回合进入本机队列，显示「排队中 · 第 N 位」；可「先跑这个」、可取消 |
| 委派等待 | 发起 Agent 的「等待」每次最多等几分钟（按 Agent 的工具超时设定），没完成就返回进度，Agent 可以再等或先做别的 |
| 完成交回 | 发起回合仍在等 → 直接交回；已结束 → 卡片「让原 Agent 继续」；发起时勾选「自动交回」→ 自动开新回合 |
| 停止级联 | 停止发起回合时询问是否一并停止其子任务（默认一并停）；停止子任务 → 发起者收到「已取消」 |
| 卡住提醒 | 子任务等审批或无进展超过设定时间，在发起会话与「我的工作 · 需要你处理」里提醒，不自动终止 |
| 失败处理 | 目标 Agent 未就绪 → 立即失败并给修复入口；额度或限流错误 → 给「换一个 Agent 重试」 |
| 房间任务 | 计入本机全部上限；每个共享 Agent 同时最多 1 个房间任务，其余排队 |
| 重启恢复 | 本机服务重启后，排队中的任务恢复排队；运行中的子任务若 Agent 进程已退出，标为中断并告知发起者 |
| 运行面板 | 一处看本机所有运行中与排队中的回合（按 Agent 分组），可调整顺序、停止 |

### 4.12 机制：隔离

| 维度 | 规则 |
|---|---|
| 工作目录 | 委派默认同目录、可选独立目录；并行试做强制独立目录（git worktree，放在 SuDuo 数据目录下，不放进仓库里）；评审只读，不需要独立目录 |
| 同目录并发 | 两个会话同时改同一工作目录时，检测到同一文件被两边改动即提示双方；不加锁 |
| 权限 | 子会话权限档位不高于发起会话（被降档时在委派卡与子会话顶部显示「已按发起会话降为 X」）；评审会话固定只读；房间任务固定只读 |
| 工具 | 按会话角色给工具：子会话没有委派工具（深度 1）；评审会话只有只读工具与「提交评审意见」；房间任务只有房间与需求只读工具，**不能读所有者的其他会话** |
| 对话 | 子会话不继承父会话对话；跨会话只通过工具读取，读取有记录 |
| 凭据 | 每家 Agent 用自己的登录；SuDuo 不在 Agent 之间传递任何凭据（ADR-0016） |
| 配置 | 各通道按会话注入 SuDuo 的 MCP 与说明（Codex 线程级配置覆盖、Claude 查询选项、ACP 进程级），不改用户的全局配置文件 |
| 故障 | 一个 Agent 崩溃不影响其他 Agent 的会话；Codex 共享进程重连时只影响 Codex 会话（现状） |

### 4.13 机制：共享

| 级别 | 存在哪 | 谁能看 | 包含 | 怎么产生 |
|---|---|---|---|---|
| **本机私有**（默认） | 成员电脑 | 本人 | 会话全文、改动、委派过程、评审全文、试做各版、结论笔记 | 默认 |
| **需求共享** | 团队服务器，挂在需求上 | 项目所有成员 | 交接包、评审报告、会话快照（本人选定的若干回合，只读） | 本人点「发布」并确认内容后 |
| **讨论共享** | 团队服务器，房间话题 | 房间成员 | 共享 Agent 的回答与执行过程 | 所有者共享 Agent、成员 @（ADR-0009） |
| **项目共享** | 团队服务器，项目设置 | 项目成员 | 项目 AI 规范（带版本） | 成员编辑 |
| **协作记录**（P2-D1，默认开启） | 团队服务器，需求活动 | 项目成员 | 元数据：谁用哪个 Agent 在这条需求上开工、委派、评审、试做，状态与分支名；不含对话与代码 | 自动，可关闭 |

共享规则：发布前预览；内容里疑似密钥（API Key、令牌、私钥格式）时提示并标出位置，由人决定是否继续；可撤回（已被读过的无法收回，撤回时说明）；每个共享对象标明来源（成员、Agent、会话、时间）。

### 4.14 可见与控制

- 会话页：委派卡、引用标签、评审面板、试做比较入口、交接包入口。
- 会话列表：按根会话分组的树；按 Agent 筛选。
- 运行面板（4.11）：本机运行与排队一览。
- 「我的工作」：等我审批的子任务、卡住的子任务、待处理的评审意见。
- 需求详情：「AI 协作」区块——交接包、评审报告、会话快照、协作记录（P2-D1）。
- 设置：并发上限、工作目录准备命令（按项目）、试做工作目录位置、自动交回默认值、新规范版本是否自动应用。

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 委派与试做只用本机自己的 Agent | 用本人自己的订阅；跨成员只通过讨论共享 Agent（只读）与需求共享对象 |
| R2 | 深度 1 | 只有主会话有委派工具与委派入口；子会话、评审会话、试做会话都不提供 |
| R3 | 子权限不高于父 | 子会话权限档位 ≤ 发起会话；评审与房间任务固定只读 |
| R4 | 排队不拒绝 | 超出并发上限一律排队；排队可见、可插队、可取消 |
| R5 | 同目录并发只告知 | 不加锁；需要并行请用独立目录 |
| R6 | 审批不越过人 | 子会话、评审会话的审批照常进审批坞并标明来源；档位策略自动作答的，照常记录 |
| R7 | 停得下 | 任何委派、评审、试做都能从卡片或运行面板停止；停止发起回合时询问是否连带子任务 |
| R8 | 读取留痕 | 每次跨会话读取在读取方时间线留下标签（读了哪个会话、哪一层） |
| R9 | 跨成员只传发布的内容 | 交接包、评审报告、会话快照须本人确认后发布；整段会话不自动上传 |
| R10 | 房间任务不读私人会话 | 房间任务只拿房间与需求只读工具（ADR-0009 边界） |
| R11 | 删除须确认 | 删除试做工作目录与未合并的分支须用户确认——会丢失未提交改动与未合并提交（ADR-0004 不可逆字节损失红线）；删除根会话时询问是否连带子会话只是方便操作（会话是软删除，不属红线） |
| R12 | 规范不覆盖仓库文件 | 项目 AI 规范通过指令通道注入，不写入、不修改仓库里的 `AGENTS.md`、`CLAUDE.md` 等 |
| R13 | 结构化产出走工具 | 评审意见、交接包由 Agent 调用「提交」工具交回；Agent 不支持工具时退化为让用户粘贴或手写 |

## 六、边界 / 不做项

- 跨成员委派（让 Agent 在同事电脑上执行任务）——讨论里的共享 Agent 只读问答已覆盖「问」，不覆盖「改」
- 多层委派、Agent 之间无人发起的自主多轮对话
- 自动合并试做结果、自动选「最好的一版」
- 把整段会话自动同步到服务器
- 团队值守机（母需求后续方向）
- SuDuo 之外启动的 Agent 使用协作工具（后续方向）

## 十二、交互 / 流程

```
委派
  Agent 调 delegate_start(目标 Agent, 任务, 目录方式)
    → 检查：目标就绪？
    → 建子会话（角色=子会话，权限 ≤ 父，工具=子会话集合）→ 进本机队列
    → 轮到 → 开回合（任务说明 + 句柄）→ 审批进审批坞（标来源）
    → 发起 Agent 调 delegate_wait（最多几分钟）→ 进度 / 结果
    → 完成 → 结果交回（等待中 / 卡片按钮 / 自动交回）

评审
  用户或 Agent 发起 → 建评审会话（只读、评审工具）→ 读 diff、需求、验收说明
    → review_submit(意见[]) → 原会话评审面板 → 勾选 → 交回原 Agent / 发布到需求（确认）

并行试做
  选 Agent ×N → 检查 git 状态（未提交改动 → 提示，可先存检查点）
    → 为每版建 worktree + 分支 → 运行准备命令 → 各自开会话（进队列）
    → 全部完成 → 比较视图 → 采用一版（合并 / 保留分支）→ 其余确认后清理

交接
  会话菜单 → 当前 Agent 调 handoff_submit(字段) → 草稿 → 本人编辑确认 → 发布到需求
    → 同需求新会话的会话卡列出交接包 → Agent 用 handoff_read 读取
```

## Claude 解读

用户要的「多 agent 机制」不只是让多家 Agent 能用，而是让它们在一个团队、一台电脑上协作而不乱：知道彼此做了什么、能分工、能互查、能比较，人始终在回路里。为此本需求在八个功能之下，定义了五套机制：会话的角色与关系、上下文的分层与按需读取、本机调度与排队、多维度的隔离、分级且须本人确认的共享。这些机制与 P1 的统一条目模型、本机 MCP 服务、多运行时是同一套地基，所以两期一起规划、一起实施。

## 歧义点

- 「session、上下文、调度、隔离、共享」：理解为 4.9–4.13 五套机制，每套给出概念、规则与界面落点。
- 「p1 p2 一起规划做」：已闭环——技术设计合并为一份，地基先做、功能叠上，统一分片。
- P2-D1（协作记录默认上需求）、P2-D2（会话快照本期做）：已按推荐定（用户 2026-10-08「按照你的规划开始推进」）。无遗留待用户拍板项。

## 保真差异

相对原话的主动新增：

1. **委派深度 1（R2）**：不是拒绝——子会话、评审会话、试做会话本来就不提供委派工具与入口。可在后续放开。
2. **并发上限 + 排队（R4）**：排队而非拒绝，符合 ADR-0004。
3. **删除试做工作目录与未合并分支须确认（R11）**：确认而非拒绝，对应 ADR-0004 不可逆字节损失红线。
6. **子会话降档**：子会话档位取发起会话与请求档位中较低者，降档时可见提示，不是静默限制。
7. **评审会话固定只读、试做会话不提供委派**：由会话角色决定提供哪些工具，不是运行时拒绝。
4. **房间任务不读私人会话（R10）**：ADR-0009 数据边界的延续，不是新守卫。
5. 协作记录默认上需求（P2-D1）、会话快照（P2-D2）：用户确认按推荐执行。

本需求不引入锁、版本校验、幂等表或 409 拒绝，也不新增拒绝；R11 是删除前的确认（ADR-0004 红线）。
