## 二、背景与目标

**目标对齐**：现在你把消息发出去之后，界面只在右上角亮一个「运行中」和一个「中断」按钮——输入框、发送按钮和空闲时长得一模一样。你要的是让对话栏自己会说话：**现在在跑吗、跑到哪一步了、我这会儿再发一条会怎样**。同时把输入框上方那两张常驻卡片（需求附件 / 需求评论）从"一直挂在那儿的黑话通知"改成"需要时才出现的动作 + 平时收在右栏的材料"。这三件事都属于对话界面的交互，不改任何业务能力。

**模拟示例**（端到端走一遍）：

你发「把测试跑一遍」。发送按钮立刻变成停止方块，输入框上方出现一行：`Codex 正在工作 · 正在执行 pnpm test · 12s`。你想起还要看覆盖率，直接再打一句发出去——这条消息的气泡上带着标记「已并入当前工作」，因为它确实被塞进了 Codex 正在做的这一轮。你又想到第三件事，但不想打断它，于是按 Tab 排进队列，队列项列在输入框上方，你还能点开改字。Codex 跑完这一轮，队列里那条自动发出去。中途你要是点了停止，队列会停在那儿等你，不会自作主张继续发。

- **背景**：
  - 运行态只落在页面右上角，离你的手（输入框）最远。参照 Codex CLI、Claude Code、Codex 桌面版，运行态都是紧挨输入框表达的。
  - 「中断」点下去到真正停下之间没有任何中间态，按钮还能重复点。
  - 运行中连发这件事**今天已经在发生**，而且行为和你想的不一样：它不是新开一轮，是被塞进当前这一轮。但界面上它只是又一个普通气泡，零表达。
  - 两张卡片解决的问题是真的（附件要经你确认才拉、评论发出去删不掉），但常驻在输入框上方、用弱化通知的样式装按钮、满屏内部黑话、显示一串裸 UUID——这些是实施期顺手的选择，不是设计。
- **目标**：
  1. 运行态在对话栏就能看全：跑没跑、跑到哪、跑了多久、怎么停。
  2. 运行中发消息有明确且**如实**的语义表达，不夸大也不隐瞒。
  3. 连发可以选择"插进当前这轮"还是"排队等下一轮"，排队项能改能删。
  4. 两张卡片按"一次性动作 vs 常驻材料"重新分家，文案说人话。
  5. 所有跟着运行态变的地方一次对齐，不留一处自说自话。

## 三、讨论与决策

### 讨论：运行中发出去的消息，界面能不能说准"它进了哪一轮"

这是本需求最硬的一个技术事实，我第一版方案在这里整个错了。

我原本打算用「发送接口返回的回合编号是否等于当前正在跑的回合编号」来判断。Codex 协商（`job_8b572e5fcb1f`）指出这不成立，我随后在 `rust-v0.143.0` 源码逐行复核，确认比它说的还硬：

| 事实 | 证据 |
|---|---|
| 运行中再发一条，确实被注入当前回合，不新开 | `core/src/session/handlers.rs:220` 调 `steer_input(..., expected_turn_id: None)`；只有 `NoActiveTurn` 才新建 |
| 但发送接口返回的是**新生成的编号**，不是真正接收它的那一轮 | `app-server/src/request_processors/turn_processor.rs:521` 注释原文：「Start the turn by submitting the user input. **Return its submission id as turn_id.**」；`core/src/session/mod.rs:761` `new_submission_id()` |
| 只有专门的插话接口才回传真实回合编号 | `mod.rs:3909` `Ok(active_turn_id.clone())` → `turn_processor.rs:955` |
| 回合正在收尾时注入的内容，会被记进历史但**不保证触发推理** | `core/src/tasks/mod.rs:603-623` `record_pending_input(...)`；中断还会清掉未消费的内容 |

**最终决策 + 理由**：撤回编号相等判定，也撤回"下一步一定会送到"这个承诺——最后一条是协议行为，任何实现都给不了这个保证。界面只说能证实的：能确定归属就说"已并入当前工作"，确定不了就说"已提交"。**宁可模糊，不可撒谎。**

### 讨论：为此要不要改后端

用户原话「UI方面的工作你来全权负责」被我读成"UI 决策授权"，2026-09-05 澄清后确认是两层意思：**UI 方面的实施工作由 Claude Code 直接完成**（不派给 Codex），且**没有禁止改后端**。

**最终决策 + 理由**：范围不由授权边界决定，由技术必要性决定。后端可改。具体走哪条路径（后端调专门的插话接口 / 后端在事件流里做关联回填 / 前端自行反查）交给技术设计，需求层只钉两条：**必须如实表达归属**，且**不得为此引入任何会拒绝用户发送的守卫**（见 R7）。

### 讨论：插话接口要求先传"当前是哪一轮"，这算不算 ADR-0004 说的拒绝式守卫

专门的插话接口有个必填参数 `expectedTurnId`，对不上就报错。形态上这就是一次前置条件校验。

按 [ADR-0004](../06_决策记录/ADR-0004-人机协作系统的一致性边界.md) 的判据过一遍：

- **仲裁者是谁**：人。用户想说的话，系统没有资格替他判定"你现在不能说"。
- **拿掉它最坏结果**：这条补充消息落到了相邻的另一轮，用户看得见，自己重发即可。
- **人能否恢复**：能，且成本是几秒。

**最终决策 + 理由**：`expectedTurnId` 是协议自带的必填参数（`turn_processor.rs:886`），不是我们发明的守卫——用它不违反 ADR-0004。但**它失败时的响应形态必须是告知加选项，不是拒绝**：对不上就如实说"当前跑的是另一轮工作"并给用户选择，绝不能让用户白发一次。同时明令不得新增"运行中禁止发送"这类守卫（R7）。

### 讨论：排队做到什么程度

**用户 2026-09-05 拍板：做，前端队列。** 限度写明：只在当前标签页有效，关页或换标签不保证继续；用户中断或回合失败后队列暂停、不自动发。

否决了"关页也继续替你发"的方案——那是一个新的能力承诺（"你关了页面我也会继续替你说话"），不属于对话界面交互，且必须落到后端常驻。

### 讨论：两张卡片是删掉还是搬家

它们承载的是上一需求已定的约束：评论必须由用户确认后再由界面执行、发出去不可撤回、附件必须经确认才拉。能力不能删。

**最终决策 + 理由**：搬家不删除。一次性动作（模型给出了具体附件或评论全文）作为动作卡出现在对应消息下方，处理完就消失；常驻的材料清单与手动入口移到右栏。文案全部改成人话，内部黑话只保留在确认弹窗的说明里。

Codex 指出我原方案有一处越界：我写了"模型主动提议时弹卡"，而上一需求 BR-6 明令**模型不得主动建议发评论**。已改为只有用户在对话里提出评论诉求后，模型给出的全文才触发动作卡。

## 四、功能 / 范围

### 4.1 运行态在对话栏的表达

| 项 | 说明 |
|----|------|
| 做什么 | 发送按钮在回合运行中变为停止控件；输入框上方增加一行运行状态（当前步骤 + 已耗时）；等待审批时状态行改为审批提示并给出跳转 |
| 谁用 | 会话页所有用户 |
| 怎么触发 | 回合开始 / 结束 / 被中断 / 失败；审批请求出现与消解 |
| 前置条件 | 会话已绑定 |
| 预期结果 | 不看页面右上角也能知道在跑没跑、跑到哪、跑了多久、怎么停 |

**运行中必须同时保留一个可点击的发送控件**——补充消息不能只能靠键盘发出。停止与发送并存的具体排布由实施决定。

### 4.2 运行中发消息的语义与表达

| 项 | 说明 |
|----|------|
| 做什么 | 运行中发送默认插入当前回合；消息气泡标注归属状态 |
| 归属三态 | 已并入当前工作 / 已作为新一轮 / 已提交（归属未能证实） |
| 不做什么 | 不承诺"下一步一定送达"；不显示任何无法证实的送达保证 |
| 预期结果 | 用户知道自己这条话去了哪儿，或者知道系统也不确定 |

### 4.3 排队

| 项 | 说明 |
|----|------|
| 做什么 | 次级动作把消息排入队列，回合正常结束后按顺序自动发出 |
| 队列表现 | 列在输入框上方，可编辑、可删除、可取回输入框 |
| 限度 | 仅当前标签页有效；关页、换标签、跨设备均不保证继续 |
| 暂停规则 | 用户中断、回合失败、发送结果不确定时队列暂停并显示"已暂停"，给恢复动作 |
| 暂停时点 | 从用户点击停止的那一刻起算，避免完成事件先到而自动发出下一条 |
| 消费节奏 | 一个真实回合结束只取一项；不得以 HTTP 受理为节拍连续发送，否则后续项会变成插话 |
| 不算结束 | 等待审批不算回合结束，不触发出队 |

### 4.4 需求附件 / 需求评论卡片重构

| 项 | 说明 |
|----|------|
| 一次性动作卡 | 用户提出诉求后模型给出具体附件或评论全文时，卡片出现在对应消息下方，处理完消失 |
| 常驻材料 | 需求标题、基线版本、附件清单与拉取状态、发表评论入口移到右栏 |
| 入口可达性 | 右栏折叠或被其他面板占用时，入口仍须可达 |
| 文案 | 改为人话；observed、基线、不可信输入这类内部说法只保留在确认弹窗说明里 |
| 标识 | 显示需求标题，不显示裸 UUID |
| 保留不变 | 独立确认动作、提交前逐字预览、提交后立即回显全文与评论标识、结果未确认时的"不要直接重发"提示、整回合完成后才解析、历史回放不出卡 |

### 4.5 跟着运行态变化的面一次对齐

发送按钮、状态行、顶栏徽章与中断入口、侧栏会话状态灯、模型切换器、改动面板与其中的检查点操作、审批区。此外须处理断线与恢复、历史补齐、切换会话时的状态清理。

现有的 `busy` 是一个被发送、上传、预览、diff、审批提交共用的开关，需按动作拆分，避免一处忙碌导致整个对话栏变灰。

### 4.6 中断的中间态

点击停止后立即给出本地反馈并禁用重复点击，直到收到任一终态。**自然完成也必须收口停止控件**，不能只等中断事件。中断请求事件是在远程调用返回后才写入的，因此终态优先于迟到的请求事件。

### 4.7 修复：运行中发送导致动作卡静默失效

现状缺陷：运行中发送时，界面把发送接口返回的那个新编号当作待观察回合，而该编号永远不会出现在事件流里，导致这条消息对应的附件 / 评论动作卡**静默地永远不出现**。归属判定做对之后此缺陷一并消失。

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 输入框在回合运行中**永不禁用** | 三个参照物的共识；也符合 ADR-0004——系统不替人判定"你现在不能说话" |
| R2 | 运行中必须保留一个可点击的发送控件 | 补充消息不能只能靠键盘发出，且端到端测试依赖可点击入口 |
| R3 | 归属只表达能证实的三态之一 | 证实不了就说"已提交"，不得编造 |
| R4 | 禁止显示"下一步一定会送到"或等价表述 | 协议在回合收尾存在竞态窗口，任何实现都给不了该保证 |
| R5 | 队列只承诺当前标签页 | 关页 / 换标签 / 跨设备不保证；限度必须在界面上说清 |
| R6 | 中断或失败后队列暂停，不自动发送 | 用户按停止通常是在收回继续执行的意图 |
| R7 | 不得引入任何拒绝用户发送的守卫 | 依据 ADR-0004。插话接口的 `expectedTurnId` 是协议必填参数不是自造守卫，但其失败响应必须是告知加选项，不得让用户白发一次 |
| R8 | 模型不得主动建议发评论 | 沿用上一需求 BR-6，只有用户提出诉求后模型给出的全文才触发动作卡 |
| R9 | 评论提交后立即回显全文与评论标识 | 沿用 BR-6 / BR-7；评论不可撤回，只显示"提交成功"不够 |
| R10 | 反馈时序沿用已有契约 | 按钮忙碌 0ms、后台刷新轻指示 150ms、1s"仍在处理"、2s 阻塞层且仅限排他操作 |
| R11 | 不引入新依赖 | 沿用已交付反馈契约的 N8 |

## 六、边界 / 不做项

- 不做关页继续执行、跨标签页共享队列、跨设备同步队列。
- 不改 Codex 协议锁定版本，不改远程需求服务的任何接口。
- 不做评论编辑与删除（远程无此接口）。
- 不重做视觉主题，不做国际化。
- 不改需求详情页与我的工作台——右栏只承载本会话的材料状态与入口，不复制需求详情。
- 不动会话创建、映射、快照等既有链路。

## 七、开放问题 / 假设

**无遗留待用户拍板项。** 命中的必问项已于 2026-09-05 在终端问齐并获答复：

| 拍板项 | 用户答复 |
|------|----------|
| 「UI方面的工作你来全权负责」的范围 | UI 方面的**实施工作由 Claude Code 完成**；**没有禁止改后端**。故范围由技术必要性决定 |

**移交技术设计的技术项**（非用户拍板，需实测或选型）：

| 项 | 说明 |
|------|----------|
| 归属判定走哪条路径 | 后端调专门插话接口 / 后端在事件流做关联回填 / 前端自行反查。三者均满足 R3、R7，取舍在实现复杂度与可测性 |
| 插话失败的具体产品行为 | 对不上当前回合时告知什么、给哪些选项；不得无条件重发到陌生回合 |
| 端到端测试改造面 | 测试标识基线按"文件 + 标识"比对，控件移位必须更新基线；现有步骤中有直接点击发送、以及不等回合结束就继续的时序依赖，须逐个核对 |
| 模型切换器的提示文案 | 现有"回合进行中，切换会中断当前工作"**无代码依据**，服务侧走的是配置刷新。须实测后改为准确表述，不得凭空改成另一句同样未经验证的话 |
| 回合耗时的计时基准 | 事件时间戳与本地时钟的选择，跨断线重连后的表现 |

**假设（已核实）**：Codex 协议锁定在 0.143.0，该版本具备插话能力、不具备服务端排队能力；现有反馈契约组件足以支撑全部表达形态，无需新依赖。

## 八、拆分预览

1. 运行态表达与中断中间态（发送/停止形态、状态行、同步面对齐、`busy` 拆分）
2. 归属判定与如实表达（含 4.7 缺陷修复；若走后端路径则含后端改动）
3. 前端队列（排队、编辑、暂停规则）

## 十二、交互 / 流程

运行中发送一条消息的完整链路：

```
用户在回合运行中按发送
  └─ 消息立即上屏，标记「已提交」
       └─ 系统尝试确认归属
            ├─ 确认并入当前回合 → 气泡改标「已并入当前工作」
            ├─ 确认当前回合已结束、已新开 → 气泡改标「已作为新一轮」
            └─ 无法确认 → 保持「已提交」，不编造
```

选择排队而非立即发送：

```
用户按排队键
  └─ 进入队列，列在输入框上方（可编辑 / 可删除 / 可取回）
       └─ 当前回合正常结束
            ├─ 取队首一条发出 → 等这一条对应的真实回合结束，再取下一条
            └─ 用户中断 / 回合失败 / 结果不确定
                 └─ 队列暂停并显示「已暂停」+ 恢复动作（不自动发送）
```

点击停止：

```
用户点停止
  └─ 立即本地反馈，控件禁用（不等远程返回）
       └─ 收到任一终态（已中断 / 已完成 / 失败）
            └─ 收口停止控件，恢复发送形态；队列停在暂停态
```

## 十三、风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 归属判定在真实竞态下不准，界面说了假话 | 中 | 用户据错误归属做判断 | R3 三态设计本身允许"说不知道"；技术设计须给出竞态下的实测证据 |
| 队列重复执行，同一条消息发两次 | 中 | 重复的模型调用与重复动作 | 一个真实回合结束只取一项；结果不确定时暂停而非重试 |
| 端到端测试大面积变红 | 高 | 交付被测试拖住 | 测试改造单独成片并排在页面改造之后；标识基线改动同步登记 |
| 评论回显退化 | 低 | 违反上一需求 BR-6 / BR-7 | R9 明确保留立即回显全文与标识 |
| 卡片搬到右栏后入口被折叠藏死 | 中 | 手动兜底能力事实消失 | 4.4 明确折叠或被占用时入口仍须可达 |
| 顺手改了模型切换器文案却依然不准 | 低 | 又一句没有依据的提示 | 第七章移交项要求实测后再改，不得凭空替换 |

## Claude 解读

你问的四件事里，前三件其实是同一件：**对话栏不会说话**。工作台已经有运行态数据（顶栏徽章就是用它渲染的），缺的是把它放到你手边、并把"运行中发消息会怎样"这件事说清楚。

分析中最重要的发现是：**运行中连发这件事今天已经在发生，而且和直觉相反**——它不是新开一轮，是被塞进 Codex 正在做的这一轮。我第一版方案打算用发送接口返回的编号来判断归属，Codex 协商推翻了它，我逐行复核 `rust-v0.143.0` 源码后确认：该接口无论是否插入当前回合，**都返回一个全新编号**（`turn_processor.rs:521` 注释原文写着 "Return its submission id as turn_id"）。这条判定不成立。更进一步，回合收尾存在竞态窗口，注入的内容会被记进历史但不保证触发推理，所以"下一步一定送到"这个承诺**任何实现都给不了**。

由此定了本需求的表达底线：只说能证实的，证实不了就说"已提交"。宁可模糊，不可撒谎。

顺带查出一个现存缺陷：运行中发送时，界面等待的是那个永远不会出现的编号，导致这条消息对应的附件 / 评论动作卡静默地永不出现。归属判定做对之后它一并消失。

第四件事（两张卡片）不是删不删的问题。它们承载的约束是上一需求已定的——附件要经你确认才拉、评论发出去删不掉——能力必须留。问题在于常驻在输入框上方、用弱化通知的样式装按钮、满屏内部黑话、显示裸 UUID。所以是搬家和改口，不是删除：一次性动作留在对应消息下方，材料清单收进右栏。
## 歧义点

**无遗留待用户拍板项。** 命中 1 项必问，已于 2026-09-05 在终端问到答案并闭环：

| 命中项 | 类别 | 用户答复与理由 |
|---|---|---|
| 「UI方面的工作你来全权负责」的边界 | 第 7 类 需求歧义澄清 | 用户澄清原话是两层意思：**UI 方面的实施工作由 Claude Code 完成**（不派给 Codex），且**没有禁止改后端**。故范围不由授权边界决定，由技术必要性决定 |

同批一并问的范围决定：**排队做，前端队列**，只在当前标签页有效、中断或失败后暂停不自动发（用户 2026-09-05 拍板；否决了"关页也继续替你发"，那是新的能力承诺而非对话界面交互）。

原话中的模糊表述与处理：

| 模糊词 | 处理 |
|---|---|
| 「对话栏的交互不应该是这样的」 | 无判据。转成可验收口径：运行态四要素（跑没跑 / 跑到哪 / 跑了多久 / 怎么停）+ 归属三态（4.1、4.2） |
| 「哪些按钮哪些状态需要同步」 | 未列举。已核实全部消费者并列成清单（4.5），含我原先漏掉的 `busy` 共享问题与断线恢复 |
| 「这玩意儿的提示和样式有什么意义吗」 | 是设问不是判断。已回答：能力有意义（上一需求 BR-6/BR-7 的落地），位置与文案没有（4.4） |
| 「应该放在这里吗」 | 结论：不应该。一次性动作下移到对应消息、常驻材料收进右栏 |
| 「连续发消息应该怎么设计」 | 拆成两条独立语义：插入当前回合（默认）与排队等下一轮（次级动作），分别在 4.2、4.3 定义 |
| 「codex 和 claude 是怎么设计的」 | 已联网核实官方文档：Codex CLI 是 Enter 插入当前回合、Tab 排队；Claude Code 是 Enter 排队、上箭头取回编辑、Esc 中断。共识写入 R1、R2 |

**技术歧义移交下一节点**（非用户权利事项）：归属判定的三条候选路径取舍、插话失败时的具体产品行为、端到端测试与标识基线的改造面、模型切换器那句无代码依据的提示文案如何实测后修正、回合耗时的计时基准。均已列入第七章。
## 保真差异

**与原话一致的部分**：四条原话全部覆盖——运行态表达（第 1 条）、两张卡片的意义与位置（第 2 条）、连发交互（第 3 条）、实施分工（第 4 条，已按 2026-09-05 澄清纠正为"UI 实施由 Claude Code 完成"）。原话两次点名的"codex 和 claude 怎么设计"已按官方文档核实并落入业务规则，不是凭印象写的。

**主动新增项**（每项按 ADR-0004 三问答复）：

1. **中断的中间态与自然完成收口（4.6）** —— 原话未提。依据：原话第 1 条问「哪些按钮哪些状态需要同步」，中断按钮点下去没有任何反馈正是这个问题的一部分。三问：仲裁者是人，系统只是补上缺失的反馈；拿掉它最坏结果是用户重复点击停止，可自行恢复；不引入任何拒绝。
2. **修复动作卡静默失效（4.7）** —— 原话未提，是分析中查出的现存缺陷，且与第 3 条原话同源（运行中发消息才会触发）。三问：仲裁者是人；拿掉它最坏结果是这条消息的动作卡不出现，用户可用右栏手动入口兜底；不引入拒绝。
3. **`busy` 按动作拆分（4.5）** —— 原话未提。依据：它是"状态同步"清单里的实际障碍，一处忙碌会让整个对话栏变灰。三问同上，纯呈现层，无拒绝。
4. **模型切换器提示文案列为移交项（第七章）** —— 原话未提。依据：核实发现该文案无代码依据，做运行态对齐时不处理等于固化一句错话。已明确要求实测后再改，不允许换成另一句未经验证的话。

**主动收窄项**：

1. **不做关页 / 跨标签页队列** —— 用户拍板结果，且它是新的能力承诺而非对话界面交互。
2. **不承诺"下一步一定送达"** —— 不是产品取舍，是协议事实：`core/src/tasks/mod.rs:603-623` 显示回合收尾时注入的内容被记进历史而不保证触发推理。承诺它就是撒谎。

**被推翻并撤回的初版内容**（留痕）：以"发送接口返回编号 == 当前运行回合编号"判断归属的方案，经 Codex 协商与源码复核证伪，整体撤回；以及原方案中"模型主动提议时弹出动作卡"的写法，违反上一需求 BR-6「模型不得主动建议发评论」，已改为仅在用户提出诉求后触发。

**引入拒绝式守卫的自查（ADR-0004 必答）**：本需求**未引入任何新的拒绝式守卫**，并以 R7 明令禁止。唯一涉及前置条件校验的是 Codex 插话接口自带的必填参数 `expectedTurnId`（`turn_processor.rs:886`）——它是协议要求而非本项目发明，且 R7 要求其失败响应必须是告知加选项，不得让用户白发一次。
