# SuDuo V2 一致性守卫退役需求设计

> 一句话：需求协作里谁想操作就操作，系统不因为「你手里的版本过期了」拒绝任何人；不可逆动作的确认保持不变。｜最后更新：2026-09-05

---

## 需求描述

需求是共享对象，多个人和多个 AI 在上面同时干活。系统当前的做法是：只要你手里的版本号和服务端对不上，就拒绝你的操作，让你刷新重来。

这套拦截防的是「两个人同时写、丢了一个」，但在这套系统里它防的场景几乎不存在——需求正文、附件集合、产物版本各自独立，改的根本不是同一块内容。实际效果是制造纯粹的假冲突：PM 改描述时有人传了个附件，保存就失败；看板拖卡片改状态，别人传个附件，卡片弹回原列。

本需求把这类拒绝式守卫全部退役。**不换成提示，也不换成告知**——人刷新页面自己看得见别人干了什么，自己决定接下来怎么办。AI 那一侧「基于审计识别有变动、告诉人、人决定要不要查/拉/处理」已由会话需求上下文闭环交付，本需求不重做。

不动的是不可逆动作的确认：删附件仍要确认、产物版本仍不可改、评论仍 append-only、AI 代提交仍需人点头。那些不是一致性守卫，是防不可恢复损失。

## 原话（verbatim）

> 我们的系统定位是：AI协作平台，也就是说很多操作和设计、交互都是基于人和AI协作的，例如遇到了一些加载、下载、上传、评论、更新相关的操作，不是强一致性，而是知道错了、对不齐 反馈给用户，用户自己决策问题和接下来处理。不然的话很多所谓的 强一致性、版本一致性、更新一致性导致整个系统非常冗余、过度设计？

> 协作中谁想干啥干啥，干完之后，自己的页面刷新加载到别人的东西，结果发现和自己干的事是重复的、冲突的或者不理解为什么会这么干，他自己决策要不要继续操作和如何操作？

> 人对手动操作的部分只需要主观观察就行，没必要系统强制行的一致性或者提示相关冲突吧？对于AI对话那边只需要对于审计日志的做个相关的识别知道有变动，告诉人就行，人再主观的决定自己或者发对话去 查一下动了什么、是不是要更新、是不是要拉取、是不是要处理？

> 现在决策，不需要告知和拦截了。谁想操作就操作

> （2026-08，PM 需求前置闭环期）注意一点，我们不需要特别严格的状态域……我们只需要做好相关的版本登记或者增量登记即可。

## 二、背景与目标

**目标对齐**：你要「谁想操作就操作」。今天系统会因为你手里的版本号过期而拒绝你保存、拒绝你传附件、拒绝你发布——这些拒绝全部拿掉。**不换成提示，也不换成告知**：人刷新页面自己看得见别人干了什么，自己决定接下来怎么办。删附件这类删了就没了的动作，确认照旧。

**术语**：本文「拒绝式守卫」指系统因为「你看到的版本 ≠ 服务端当前版本」而拒绝一次操作（表现为 409）；它和「不可逆动作的确认」是两回事，后者不在退役范围。

### 现状（读码核实，代码以 worktree `../SU-CCB-req-suduo-v2-session-context-closure-001` 为准）

| # | 事实 | 证据 |
|---|---|---|
| 1 | 需求编辑的 `expectedVersion` 是**必填** | `collaboration-repository.ts:486-497`，不匹配即 409 |
| 2 | 而这个 `version` 被附件增删和产物发布一起自增 | `attachment-repository.ts:211/300`、`artifact-version-service.ts:104` |
| 3 | 于是产生纯假冲突 | 改描述期间有人传附件 → 保存 409；拖卡片改状态 → 弹回原列 |
| 4 | 附件增删的 `expectedVersion` 头**可缺省**，缺省即不校验 | `attachment-repository.ts:172-181, 282-293`，可绕过的保证不是保证 |
| 5 | 它还逼出一个补丁 | 多文件上传必须用上次响应的版本串接，否则第 2 个文件必撞 409（`SKILL.md:28` 明写此串接） |
| 6 | 产物发布另有 `expectedVersion` 校验 | `artifact-version-service.ts:60` |
| 7 | 正文 PATCH 即使值没变也无条件 `version + 1` | 同 #1 的 SQL 无「值是否真变」判断 |
| 8 | `VERSION_CONFLICT` 被借去表达非版本语义 | `requirements-v2-service.ts:238` 表达「会话非活动」，`:658/:662` 表达「映射不一致」 |
| 9 | `material-service.ensureSnapshot`（v2，含附件版本 409）**生产无调用方** | 只有测试调用；生产走 `ensureRequirementSnapshot`（v3） |

### 为什么这些拦截本就不该有

需求正文、附件集合、产物版本是**三块互不相交的内容**，共用一个 `requirements.version` 计数器（现状 #2）。任何一块变动都会让另外两块的操作失败——防的是丢失更新，实际制造的是假冲突。

而 T1 就已经定了这套系统靠什么解释变化：

| 出处 | 原文 |
|---|---|
| `需求协作工作台-需求.md:50` | 状态任意可切换，**以审计记录而非强制流转解释变化** |
| `系统架构.md §七` | **不以状态流转规则替代审计**；状态可任意切换，但必须留下操作者、时间和前后值 |

审计有 `before_json` / `after_json` 全文、操作人、精确时间；`version` 只是一个数字。用后者拦人，等于用有损投影替代账本。

### 目标

1. 需求协作中的操作不再因版本对不齐被拒绝。
2. `version` 语义单一化为需求正文版本，不再是四种用途共用的计数器。
3. 不可逆动作的保护一处不减。

### 不是目标

- **不做告知，不做冲突提示**。人刷新页面主观观察即可（用户 2026-09-05 明确拍板）。
- **不做 AI 侧的变更识别**。会话需求上下文闭环已交付：`observation-service:505-525` 输出「开工后 N 条变更」+ 审计时间线，三级递进 L1/L2/L3，附件按需拉取（PR7）与评论提交（PR8）均走「模型表意图 → 人确认 → BFF 执行」。本需求不重做、不改动。

## 三、讨论与决策

### 讨论：退役之后要不要补告知

Claude 前后提过三版方案：把 409 改成「张三 14:20 改了描述 + 保留/覆盖/再编辑」；把告知钉在保存和发布时刻；由系统识别重复（同 sha256、同状态目标）与冲突并指出来。

**用户 2026-09-05 拍板：都不要。「不需要告知和拦截了。谁想操作就操作」。**

采纳。人手动操作的部分靠主观观察——刷新页面就能看见别人干了什么。系统替人识别"这跟你干的重复了"属于过度设计，同样落在 ADR-0004 判据的"拿掉它人能自己发现"一侧。

### 讨论：AI 那一侧要不要补

用户表述为「对审计日志做个识别知道有变动，告诉人就行，人再主观决定自己或者发对话去查一下动了什么、是不是要更新、是不是要拉取、是不是要处理」。

核实发现**这一整条链路已经交付**（会话需求上下文闭环八片全部 `done` + `review_status: passed`，已合入 `main`）。故本需求不含 AI 侧任何内容。

### 讨论：`version` 只停附件还是一并收窄

只停附件的话，发布仍自增、无实变 PATCH 仍自增（现状 #6/#7），语义仍混浊。

**用户拍板：一并收窄为纯正文版本。**

### 讨论：`expectedVersion` 删除入参还是保留但忽略

**结论：删除**（采纳 Codex 协商 `job_855c6d7a5be7` 建议）。该头本就可缺省，保留等于继续承诺它有效；新服务天然容忍旧客户端携带的未知头。

### 讨论：哪些拒绝必须留下

ADR-0004 的红线：不可逆字节损失、删改用户受管文件、共享服务 append-only 写入、不可逆对外副作用。据此逐条核对后，本需求保留全部不可逆保护（见六、边界），退役的只有版本对不齐类拒绝。

## 四、功能 / 范围

### 4.1 需求编辑不再拒绝

| 项 | 说明 |
|----|------|
| 做什么 | `updateRequirement` 删除 `expectedVersion` 必填入参与 409 分支；后写生效 |
| 为什么 | 正文、附件、产物三块内容不相交却共用一个计数器，拒绝的几乎全是假冲突（现状 #2/#3） |
| 预期结果 | 改描述、改状态、拖看板卡片不再因他人操作失败；审计仍完整记录谁在何时把什么改成了什么 |

### 4.2 附件增删不再拒绝

| 项 | 说明 |
|----|------|
| 做什么 | 附件上传/删除删除 `expectedVersion` 请求头与相应校验分支 |
| 为什么 | 附件是集合，加与删可交换，本无读-改-写竞争；且该头可缺省即形同虚设（现状 #4） |
| 连带清理 | 多文件上传的版本串接补丁一并去掉，含官方发布 skill 的 `SKILL.md:28` 与脚本（现状 #5） |
| 明确不做 | 不保留「接受但忽略」的兼容语义 |

### 4.3 产物发布不再拒绝

| 项 | 说明 |
|----|------|
| 做什么 | 发布删除 `expectedVersion` 校验；按提交的附件 ID 列表执行 |
| 为什么 | 发布语义本就是「发我勾选的那些」（需求 4.2 只接受已上传附件 ID 列表）；那个 409 是版本计数器的副作用，不是设计产物 |
| 明确不做 | **不做差异告知**。PM 发完在页面上看得见发了什么，需要补就再发一版 |
| 不动 | 产物版本不可变、历史全留、blob 引用保护 |

### 4.4 `version` 收窄为需求正文版本

| 项 | 说明 |
|----|------|
| 做什么 | 仅 `title` / `summary` / `status` **实际变化**时自增；附件增删与产物发布不再自增；值未变的 PATCH 不自增 |
| `updated_at` | **保持现状不动**。附件增删与产物发布仍刷新 `updated_at` / `updated_by`——这一行确实被写了，且它驱动列表排序与游标分页（用户 2026-09-05 拍板） |
| 剩余用途 | 材料快照目录名（`v3-<version>`）、前端读一致性重试、会话基线绑定。收窄后同 version = 同需求正文，快照复用更准 |
| 明确不做 | 不新增字段、不新增表 |

### 4.5 `VERSION_CONFLICT` 错误码收口

| 项 | 说明 |
|----|------|
| 做什么 | `requirements-v2-service.ts:238` 表达「会话非活动」，改用 `SESSION_NOT_ACTIVE`；`:658/:662` 的映射不一致同理改用贴切错误码 |
| 为什么 | 版本校验退役后仍留着一个叫「版本冲突」的码去表达状态前置，会持续误导 |
| 不动 | `:238` 这道**检查本身保留**——它拦的是 AI 往共享需求提交评论（append-only 对外写入，ADR-0004 红线），只改错误码不改行为 |

| 编号 | 规则 | 说明 |

| N8 | 不新增表、列、依赖，无 DB migration | 只删除校验分支与停止部分字段写入 |

## 六、边界 / 不做项

**保留的不可逆保护（ADR-0004 红线，逐条核对后确认不动）**

- 附件删除仍是显式操作、仍有确认、仍留审计；被产物版本引用的 blob 仍受保护不被物理清理。
- 产物版本发布后不可修改，历史版本全留。
- 评论 append-only，只有 GET/POST。
- AI 代提交评论、代拉附件仍走「模型表意图 → 人确认 → BFF 执行」（会话上下文闭环 PR7/PR8 已交付）。
- 附件写入/删除/列表与产物发布各自持有的需求行锁**保留**——它们保证附件数量上限与产物冻结的原子性，与版本校验不是一类东西（Codex 明确提示勿顺手删）。

**不做**

- **不做任何告知**：无冲突提示、无差异提示、无变更通知。
- **不做重复/冲突识别**。
- **不改 AI 侧任何内容**：会话上下文闭环已交付，本需求零改动。
- **不改 `updated_at` 行为**，故不影响列表排序、游标分页、卡片「最近更新」与停滞榜。
- **不清理 `material-service.ensureSnapshot`**（v2 死路径，现状 #9），另行清理。
- **不动本机目录映射的 `WORKSPACE_MAPPING_CONFLICT`**：属本机设置，不属需求协作，另议。
- **不动前端 `RequirementsWorkbench.tsx:383/523` 的读一致性重试**：它是同一次渲染内跨两个请求的自我一致，不是拦别人；退役后自然收窄。

## 七、开放问题 / 假设

**假设**（已读码核实）

1. 会话需求上下文闭环八片全部 `done` 且已合入 `main`，AI 侧变更识别链路完整可用。
2. 审计写入已收口为单一 `insertAuditLog`，发布路径 `comment.created` 与 `artifact_version.published` 均写入——审计作为「变化账本」是完整的。
3. `ensureSnapshot`（v2）生产无调用方，`version` 收窄不影响既有快照。

**移交技术设计的技术项**

1. 「正文实际变化」的比对口径：字段级逐个比对还是整体比对；`status` 与 `title`/`summary` 是否同权。
2. `incrementRequirementVersion` 的拆分方式：拆成 `touchRequirement`（只写 `updated_at`/`updated_by`）与版本自增两个函数，还是加参数。
3. 附件与发布响应中 `requirementVersion` 字段是保留（语义变为「当前正文版本」）还是移除。

**独立观察（不在本期范围，供后续判断）**

我的工作台的材料过期警示当前只比对 `title`/`summary`/`status` 三个字段（`my-workbench-service.ts` 的 `hasContentDrift`），附件与产物变化不告知人。其当初的设计依据是「重开会话也拿不到附件」，而该依据已被 PR7 附件按需拉取推翻。这属 AI 侧告知循环，与本需求的退役工作无因果关系，建议另立判断。

```

    ├─ 今天：version 已被 T1 撞成 8 → 409「请刷新」，改的字白打

    └─ 看见附件区多了 debug.log，审计里写着小王 T1 传的
       他自己决定：不管 / 再发一版 / 找小王问一句     ← 主观观察
```

## Claude 解读

这个需求最终形态比它起初的样子小得多，而缩小过程本身是它最重要的记录。

用户的定位是 AI 协作平台：写这一侧完全放开，谁想操作就操作；读这一侧靠人主观观察——刷新页面就看得见别人干了什么，自己决定要不要继续、怎么继续。系统既不替人拦，也不替人提示。

所以本需求只做一件事：**把因「你手里的版本过期了」而拒绝操作的守卫全部退役**。不换成告知，不换成冲突识别。`version` 顺带收窄为需求正文版本，因为它被三块互不相交的内容共用，正是假冲突的根。

一个关键核实结果决定了范围：用户描述的 AI 侧「对审计做识别知道有变动、告诉人、人决定要不要查/拉/处理」——**这条链路已经交付**（会话需求上下文闭环八片全 done 并合入 main），本需求零改动。原本准备补的东西，早就有了。

真正需要小心的是边界的另一侧。退役的是「版本对不齐就拒绝」，不是「不可逆动作的确认」。删附件仍要确认、blob 仍受产物引用保护、产物版本仍不可变、评论仍 append-only、AI 代提交仍需人点头、附件与发布的行锁仍保留（它们保证附件上限与产物冻结的原子性，与版本校验不是一类东西）。这条线画不清，退役就会变成事故。

`updated_at` 明确不动。它是 `requirements` 行的写入时间，驱动列表排序与游标分页，附件活动算作一次写入本来就对——问题从来不在它身上。
## 歧义点

本轮所有命中用户拍板项均已在终端问到答案并闭环，无遗留待用户拍板项。

**已闭环拍板记录**

1. 退役之后要不要补告知 —— **都不要**。Claude 前后提过三版（409 改成「谁何时改了什么 + 选项」、把告知钉在保存与发布时刻、由系统识别重复与冲突），用户 2026-09-05 明确「不需要告知和拦截了。谁想操作就操作」。人手动操作靠主观观察，系统替人识别"这跟你干的重复了"属过度设计。
2. AI 侧要不要补 —— **不做，已交付**。用户描述的链路经核实即会话需求上下文闭环的交付内容（八片 `done` + `review_status: passed`，已合入 `main`）：`observation-service:505-525` 输出「开工后 N 条变更」+ 审计时间线、L1/L2/L3 三级递进、PR7 附件按需拉取、PR8 评论提交。

## 保真差异

**与原话一致的部分**：「谁想操作就操作」「不需要告知和拦截」「人对手动操作只需主观观察」「AI 侧只需对审计做识别、告诉人、人自己决定要不要查/拉/处理」——四条均为用户 2026-09-05 原话，逐字对应需求的四个功能点与「不是目标」段。`version` 收窄、`updated_at` 不动同为当场拍板。

**Claude 归纳的部分**：
- 用户「谁想操作就操作」被具体化为 4.1/4.2/4.3 三处 `expectedVersion` 退役与 N1 的范围声明。
- 用户 2026-08 原话「只需要做好版本登记或增量登记」被用作 N2 依据——把「登记」还给审计，`version` 收窄为单一语义。

**Claude 主动新增、原话未提及的部分**（按 ADR-0004 三问逐项过判据）：
- 4.5 `VERSION_CONFLICT` 错误码收口。①仲裁者：无，纯命名清理 ②拿掉最坏结果：留一个叫「版本冲突」的码去表达「会话非活动」，持续误导 ③人能否恢复：能，但误导会持续累积。判为可做，且不改任何行为。
- 六、边界的「行锁保留」。①仲裁者：系统，但防的是附件上限与产物冻结原子性 ②拿掉最坏结果：附件可能超限、产物版本可能冻结到半截集合 ③人能否恢复：产物版本不可变，冻结错了无法原地修正 → **属红线，保留**。来源为 Codex 明确提示。
- N7「不可逆保护一处不减」与六、边界的逐条列举。属对退役范围的界定，防止退役扩散到红线，非新增功能。

**Claude 撤回的自身提议**（记录以免留下未标注漂移）：
