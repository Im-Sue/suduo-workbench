# SuDuo V2 反馈交互语言统一需求设计

> 一句话：让"我点了这个按钮之后会发生什么、现在到哪一步了、出错了要怎么办"在整个工作台里只有一套答案，而不是每个页面各自发明一套。｜最后更新：2026-08-23

---

## 需求描述

工作台的反馈层是**分叉的**：两套 toast 并存、破坏性确认三种做法混用、等待状态没有分工规则、真错误被降级成警告。这不是"缺样式"，是**同一件事在不同页面有不同答案**，用户学不会规律。

本需求要交付的不是一份风格指南，而是一套**可执行、可验收、可测试**的反馈契约：什么情况用哪种反馈、异步动作有哪些状态、等待时长到什么阈值换什么表现、哪些操作必须二次确认、以及自动化测试怎么断言这些反馈。契约先定，三个模块（需求 / 会话 / 设置）按契约收口。

**术语先说清楚**（后文反复用）：

| 词 | 在本文里指什么 |
|---|---|
| **反馈路由表** | 一张对照表：某类事件发生时，该用 toast / 行内提示 / 持久局部错误 / 模态 / 页面级失败中的哪一种 |
| **持久局部错误** | 不自动消失、留在出错位置旁边的错误块（区别于 5 秒就飘走的 toast） |
| **确认对话框 vs 表单对话框** | 前者只问"确定吗"（删附件），后者要用户填内容（新建需求、发布产物）。两者用同一个 Dialog 组件，但交互规则不同 |
| **打扰度分级** | 能自愈的异常静默（只更新角落状态），需要用户动手的才主动打扰 |

## 二、背景与目标

### 现状（全部读码核实，非推断）

| # | 事实 | 证据 |
|---|---|---|
| 1 | **两套 toast 并存** | `ui/message.tsx` 是 react-hot-toast 薄封装（顶部居中、5s 自动消失、可堆叠、支持同 id 去重）；`SessionRuntime.tsx:648` 另有自研 `<div className="toast" role="alert">`（手动关闭、不自动消失） |
| 2 | **读屏 politeness 不一致** | 前者 polite（不打断），后者显式 `role="alert"`（assertive，会打断读屏当前朗读） |
| 3 | **没有 error 档** | `MessageType = "info" \| "success" \| "warning"`。409 版本冲突、上传失败这类真错误只能降级成 warning |
| 4 | **warning 被当万能档** | 全仓 `"warning"` 字面量 33 处，success 13、info 3 |
| 5 | **破坏性确认三套并存** | `window.confirm` **9 处真实调用**，其中 **8 处集中在设置页**、1 处在会话页；需求页已迁到 `Dialog`（0 处）；`RequirementsDetailPage.tsx:88` 注释自陈"旧版用 `window.confirm`，样式不受控"——**迁移开了头没做完** |
| 6 | **Dialog 一身二用** | 既做确认（删附件 `:770`），也做表单（发布产物 `:798`、新建需求 `:1012`、新建远程项目 `:1050`）。两类交互规则不同却共用一套约定 |
| 7 | **loading 无分工规则** | `<Skeleton` 7 处、`disabled=` 60 处、`animate-spin` 1 处。绝大多数动作的等待反馈就是"按钮变灰"，用户分不清"在跑"还是"没点上" |
| 8 | **去重能力建好了零调用** | `MessageOptions.id` 注释写明给"断连风暴等重复告警场景"，全仓 0 处使用 |
| 9 | **Gate-C 断言按中文文案定位** | `requirements-board.ts:202/:259` 用 `hasText: "已发布产物版本"` 筛 `global-message`。testid 基线（68 条）**已登记** `global-message`，脆弱点不在基线漏登记，而在断言用文案定位 |
| 10 | **局部状态机各自为政** | `TablePreview.tsx` 自带 `"loading" \| "ready" \| "error"`，与全局无关联 |
| 11 | **空态是散落的裸文案** | `暂无需求` / `还没有安装任何 skill` / `暂无已发布的产物版本` 等 8 处以上，无共享组件、无插图、无引导动作 |
| 12 | **崩溃兜底已存在** | `AppErrorBoundary.tsx`（69 行，2026-07-23 白屏事故的产物），提供"清缓存重载"。是可复用基础，不是从零开始 |

### 目标

1. **一套决策规则**：任何调用点遇到"该给什么反馈"都能从反馈路由表查到唯一答案，不需要现场发明。
2. **异步动作有状态机**：`idle → pending → success / failed`，并明确最新请求胜出、卸载后不回写、重复点击去重、是否可重试。
3. **等待有分工**：首次区域加载、动作按钮忙碌、后台刷新保留旧内容、超阈值才上阻塞层——各有各的表现，不混用。
4. **破坏性操作有策略**：不可逆 / 高代价必须确认，普通可逆切换不确认。**不是把 9 处 `window.confirm` 机械替换成 Dialog**。
5. **反馈可被测试**：反馈组件提供稳定的语义 test id 与 role，Gate-C 断言"反馈类型 + 结果"，不再以中文文案作为唯一定位。

### 不是目标

统一**不等于**所有失败都显示成同一种 toast。会话终态错误留在上下文里才合理，把它并进 5 秒自动消失的全局 toast 会丢关键信息——这是本需求刻意避免的失败模式。

## 三、讨论与决策

### 讨论：范围是先做一个页面还是三个模块全覆盖

协商建议先定契约、只把需求页高频链路改到位，会话页与设置页列第二期，理由是范围可验收。

**用户 2026-08-23 拍板：契约 + 三模块全覆盖。**

采纳。代价是范围明显变大（尤其设置页有 8 处 `window.confirm` 要按策略逐个判定该不该确认、该用哪种确认），但用户的诉求本就是"当前 UI&UX"整体，分期会留下长期不一致。**交付节奏交由任务拆分节点决定，不反向压缩需求范围。**

### 讨论：连接和故障异常要不要打扰用户

现状 SSE 重连只在角落显示"实时重连中"，不弹任何提示。

关键认识：**"断网"其实是四种不同故障**——鉴权失效、浏览器→本机 BFF 不通、BFF→远端不通、SSE 断连。把它们统称"网络异常"会误报，也让用户不知道该做什么。

**用户拍板：分级——可恢复的静默，需要干预的才打扰。**

### 讨论：允不允许改既有提示文案

改文案会打断 Gate-C 两处按 `hasText` 定位的断言。

**用户拍板：允许改，同步把断言改成按语义定位。**

这条顺带消除了一个隐患：断言与中文文案耦合本身就脆弱，以后任何文案调整都会打断测试。

### 讨论：空态、页面级错误、崩溃兜底要不要进第一期

协商建议空态进、`AppErrorBoundary` 这类整页崩溃列第二期。

**用户拍板：全部进第一期。**

采纳。`AppErrorBoundary` 已存在且可用，第一期是把它纳入统一语言（文案、可操作项、与其他错误层级的关系），不是重写。

### 讨论：要不要引入新依赖

**结论：不需要，也不允许。** Radix Dialog、react-hot-toast、CSS `prefers-reduced-motion` 已足够覆盖全部场景。仅当后续确需跨页持久队列或复杂动画时才重新评估——那时属于新的必问项。

## 四、功能 / 范围

### 4.1 反馈路由表（契约核心）

一张对照表，穷举"什么情况用哪种反馈"。至少覆盖：

| 反馈形态 | 典型触发 | 关键属性 |
|---|---|---|
| 成功 toast | 创建、保存、发布成功 | 自动消失、polite |
| 信息 toast | 无需动作的状态告知 | 自动消失、polite |
| 警告 toast | 可继续但需注意（如达到上限） | 自动消失、polite |
| **错误 toast**（新增档位） | 操作失败但可重试 | 停留更久、assertive、**可带重试动作** |
| 行内提示 | 表单校验、字段级错误 | 贴在字段旁、不消失 |
| 持久局部错误 | 会话终态错误、区域加载失败 | 留在出错位置、不自动消失、带重试 |
| 确认对话框 | 不可逆 / 高代价操作 | 阻塞、焦点陷阱、危险动作用危险色 |
| 页面级失败 | 整页数据不可用、鉴权失效 | 占位整个内容区、带明确下一步 |
| 崩溃兜底 | 未捕获渲染异常 | 复用 `AppErrorBoundary` |

**同时明确**：连接重连用持久状态标识，**不用重复 toast**（把现有零调用的 `MessageOptions.id` 去重能力变成强制规则，防回归）。

### 4.2 异步动作状态机

每个异步动作统一为 `idle → pending → success / failed`，并规定：

- **最新请求胜出**：同一资源的并发/乱序完成，只有最后发起的那次结果生效。
- **卸载后不回写**：组件已卸载或用户已离开该资源时，结果不得回写状态。
- **重复点击去重**：pending 期间重复触发不产生第二个请求。
- **可重试性**：明确哪些失败可原地重试、哪些必须刷新、哪些需要用户先处理别的事。

### 4.3 loading 分工规则

| 场景 | 表现 |
|---|---|
| 首次区域加载 | 骨架屏（复用现有 `Skeleton`） |
| 动作按钮触发 | 按钮忙碌态：禁用 + 文案变化或小 spinner（**不能只是变灰**） |
| 后台刷新已有内容 | 保留旧内容，用轻量指示，不闪空 |
| 超过阈值的长操作 | 才显示进度或阻塞层 |

阈值需要给出具体毫秒数并写进契约，不留"较长时间"这类模糊表述。

### 4.4 破坏性操作确认策略

给出判定规则（不可逆性 × 影响范围 × 恢复成本），然后**逐个判定现有 9 处 `window.confirm`**：该保留确认的迁到统一确认对话框，本不该确认的直接去掉。

明确区分**确认对话框**与**表单对话框**的交互规则：确认类要有危险动作视觉、默认焦点在取消；表单类要处理未保存内容的关闭拦截。

### 4.5 导航与切换的交互契约

覆盖真实存在的路由与切换：`/`（看板）、`/requirements/:id`（详情）、`/sessions`、`/settings`，以及 `pushState` / `back()` 语义。

- 有未保存编辑时离开当前上下文，必须拦截并给取消 / 放弃 / 继续编辑三选一。
- 模式切换（需求 / 会话 / 设置）与详情进出时，**在途请求的处理规则**（取消还是允许完成但不回写）。
- 现有"退出详情用 `back()` 避免历史死循环"的设计（`RequirementsV2App.tsx:160`）必须保留，不得被新契约推翻。

### 4.6 故障分级与文案

四类故障各自的判定方式、打扰级别和文案：

| 故障 | 判定 | 打扰级别 |
|---|---|---|
| 鉴权失效 | 401 / 登录态失效 | **需干预**——持久提示 + 去登录 |
| 浏览器 → 本机 BFF 不通 | 本机请求失败 | **需干预**——SuDuo 可能没启动 |
| BFF → 远端不通 | 502 / 依赖不可用 | **需干预**——远端服务问题，给重试 |
| SSE 断连 | EventSource 错误 + 重连中 | **可自愈，静默**——只更新角落状态标识 |

### 4.7 空态

统一空态组件：说明为什么空 + 引导动作。收编现有 8 处以上散落裸文案（`暂无需求`、`还没有安装任何 skill`、`暂无已发布的产物版本` 等）。

### 4.8 可访问性契约

- toast politeness 分级：普通用 polite，错误用 assertive；**消除现有两套 toast 的 politeness 冲突**。
- 加载区域 `aria-busy`。
- 对话框焦点管理：打开时焦点入内、关闭后归还触发元素、Esc 关闭策略（表单对话框有未保存内容时不直接 Esc 关）。
- 尊重 `prefers-reduced-motion`。

### 4.9 可测试契约

- 反馈组件提供稳定语义 test id 与 role。
- Gate-C 断言改为按**反馈类型 + 结果**定位，不再以中文文案作为唯一定位（改造现有 `requirements-board.ts:202/:259` 两处）。
- 新增 test id 登记进 `data-testid-baseline.json`。

## 五、业务规则

- **N1**：统一的是**决策规则与适配入口**，不是强制所有失败显示成同一种 toast。
- **N2**：能自愈的异常（SSE 重连、后台刷新失败）不主动打扰，只更新持久状态标识。
- **N3**：需要用户动手才能恢复的故障，必须持久可见并给出可操作项。
- **N4**：会话终态错误保留在上下文中，**不并入自动消失的全局 toast**。
- **N5**：同一告警在短时间内重复触发时必须合并（用 `MessageOptions.id`），不叠加。
- **N6**：不可逆或高代价操作必须确认；普通可逆切换不确认。确认与否由策略判定，不由历史实现决定。
- **N7**：自动化断言不得以中文显示文案作为唯一定位手段。
- **N8**：不引入新依赖。

## 六、边界 / 不做项

- 不做视觉主题重做（颜色、字体、间距体系不在本需求内）。
- 不做国际化 / 多语言。（2026-10-02 起由[产品中英双语](产品中英双语-需求.md)需求覆盖）
- 不引入新依赖（N8）。
- 不重写 `AppErrorBoundary` 的恢复机制，只把它纳入统一语言。
- 不改任何服务端与 BFF 行为——本需求是纯呈现层。故障分级只改**前端如何呈现**已有的错误响应，不改错误码与响应结构。
- 不做离线可用 / 请求队列重放。
- 不做动效体系（除 `prefers-reduced-motion` 的尊重规则外，不设计新动画语言）。

## 七、开放问题 / 假设

**无开放问题。** 四项命中的用户拍板项已在 2026-08-23 于终端一次性问齐并获答复，均写入第三章：

| 拍板项 | 用户答复 |
|---|---|
| 第一期范围 | 契约 + 三模块全覆盖 |
| 故障打扰度 | 分级：可恢复静默、需干预才打扰 |
| 是否允许改既有文案 | 允许，同步把断言改成按语义定位 |
| 空态 / 错误页 / 崩溃兜底 | 全部进第一期 |

**假设（已核实）**：现有 Radix Dialog、react-hot-toast 与现有路由 / SSE 状态足以支撑全部范围，无需先重构路由、也无需新依赖。

## 八、拆分预览

规模偏大，建议拆分节点重点关注**契约先行**与**改造面互斥**：

1. 反馈契约与基础组件（路由表、错误档位、统一确认对话框、空态组件、异步状态 hook）
2. 可测试契约与 Gate-C 断言改造（含 testid 基线登记）
3. 需求页收口
4. 会话页收口（含 `SessionRuntime` 局部持久错误的定位与保留）
5. 设置页收口（8 处 `window.confirm` 逐个判定）
6. 故障分级与页面级失败 / 崩溃兜底纳管
7. 可访问性契约落实与验收

第 1、2 片是其余各片的前置。第 3～5 片改造面天然互斥（各自页面），可并行。

## 九、数据（草案）

不涉及。纯呈现层需求，无新增持久化数据、无 schema 变更。

## 十、接口（草案）

不涉及后端接口。前端内部 API 面：统一的 `showMessage` 扩展（新增 error 档）、确认对话框调用入口、异步动作状态 hook、空态组件 props。具体签名由技术设计给出。

---

## 十一、界面 / 页面布局

不改布局。本需求只改**反馈层的呈现与时序**，不动任何页面的信息架构与栅格。

唯一的布局影响：持久局部错误块与空态组件会占据其所在区域的空间，需在技术设计中明确它们与既有内容的让位规则。

---

## 十二、交互 / 流程

一次典型动作的完整反馈时序（以"发布产物版本"为例）：

```
用户点「发布」
  └─ 打开表单对话框（焦点入内）
       └─ 选择附件、填写说明 → 点确认
            ├─ 按钮进入忙碌态（禁用 + 文案变化），重复点击不产生第二个请求
            ├─ 成功 → 关闭对话框 → 成功 toast（polite、自动消失）→ 产物区刷新
            └─ 失败
                 ├─ 409 版本冲突 → 错误 toast（assertive）+ 自动刷新 + 保留对话框内容
                 ├─ 400 校验失败 → 行内提示贴在对应字段
                 └─ 502 远端不通 → 持久局部错误 + 重试按钮
```

对照现状：这条链路目前的失败分支**全部走同一个 warning toast**，用户无法区分"重试就好"和"得先解决别的事"。

## 十三、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 做成一份没人遵守的风格指南 | 调用点继续各自演化，需求白做 | 契约必须连同**状态机与可测试契约**一起交付；Gate-C 断言反馈类型 |
| 把所有错误迁入自动消失 toast | 丢失关键上下文（尤其会话终态错误） | N4 明确保留持久局部错误 |
| 把"离线"做成单一状态 | 误报真实依赖故障，用户被误导 | 4.6 四类故障分别判定 |

## Claude 解读

用户说的"设计一套合适的弹窗、提示、loading 交互效果"，字面看像个视觉活儿，实际是**语义活儿**。工作台已经有 toast、有 Dialog、有 Skeleton——缺的从来不是组件，是"什么时候用哪个"的规则，以及"异步动作有哪些状态、竞态怎么办"的定义。

所以本需求的重心从"设计效果"移到了"定契约"：先冻结决策规则、状态机、阈值、确认策略、测试契约五件事，再让三个模块按契约收口。只交付效果不交付契约，半年后又会分叉成今天这样。

"跳转"一词我最初以为是用词不精确（这是本机单页工作台），核实后发现确有 `/requirements/:id`、`/settings` 等路由与 `pushState`/`back()` 语义，且已有刻意的历史栈设计。已纳入 4.5。

### 二、走查记录以代码走查为主，运行时实证是少数

各片走查表的实证比例：pr3 28 行中 4 条、pr4 14 行中 4 条、pr5 17 点中 3 条、pr6 19 点中 4 条、pr7 调用点 2 条。其余多数诚实标注为「可构造但未做」（夹具能造、本轮没写），少数为「未验证（客观障碍）」。

**结论**：「三个模块按契约收口」在代码层面完成、关键路径有实证；**不得表述为「所有调用点均已验证」**。
