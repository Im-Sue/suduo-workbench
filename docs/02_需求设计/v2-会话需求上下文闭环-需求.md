# SuDuo V2 会话需求上下文闭环需求设计

> 一句话：把会话绑定的「不可变基线」与远程的「可查现状」拆开，让模型知道自己看到的是哪一版、远程变成了什么样。｜最后更新：2026-08-30

---

## 需求描述

SuDuo 从需求进入对话时，会话绑定一份不可变的 v3 requirement-only 快照。当前 briefing 把 ADR-0003 设计的「按需拉取」表述成了「封闭快照」，导致会话内模型拒绝读取远程需求的最新正文、评论与附件，并建议用户「创建关联最新版本的新会话」——但新会话同样走 v3 路径，依然不含评论与附件，这条出路兑现不了。

在多人协作场景下，这不是信息滞后而是**确定的错误答案**：PM 在需求下留了补充说明，开发问「有评论吗」，模型答「没有」，直接导致做错东西。真正该说的是「查不到」或「有 3 条，要看吗」。

本需求把被混为一谈的两件事拆开：快照作为**不可变基线**保留，远程作为**可查现状**开放只读访问，并补充第三态**已观测**，区分「查过或拉过、但未纳入基线」的材料。变更检测统一以远程审计日志为唯一权威信号：以会话创建时刻为水位线判断有无变动，再按需读取细节。

## 原话（verbatim）

> 「我们对于 从需求进入对话 的上下文里设定了什么？」

> 「我觉得这里是不是有问题：首先我们是 多人协作远程办公 ，如果用户A通过 "需求"-》进入对话，这个对话关联了 "需求"，但是如果用户A说：说查一下需求的附件、评论或者需求其他相关的信息，上下文不让 LLM 去重新加载 远程服务器 上需求的摘要信息/详细信息， 那么本地永远是闭塞一个版本或者信息一直加载不到？ 你重新思考一下 这个协作、交互、设定的闭环问题」

> 「模型应该能说的是：「你的基线是 v2；远程现在 v5，有 3 条评论、1 个附件，差异是……要我拉下来吗？」而不是「我什么都不知道，请重建会话」。 这个很关键」

> 「其实我觉得是不是最简单的版本比较就是 需求里面 审计日志的变动？例如本地换成的是某个时间某一条，服务器上有新操作是不是就可以当作一个 需要更新的 触发节点或者判断？而且是最低成本的版本判断和引入？」

> 「LLM和用户只需要知道，哦，我的本地和远程的审计日志不一致，那么就是有变动，有变动，我就要先去读取看看具体变了什么、总结一下或者更新、加载、拉取之类的。然后继续做事情就好了？」

> 「为啥有"草拟评论" 这个概念？评论就是评论，就算是在 对话里 用户让LLM发起一个 评论或者帮忙生成一个评论，那用户确定了就直接评论上去就好了吧？」

## 二、背景与目标

用一句话说清现在的毛病：**会话手里攥着一张三天前的照片，却以为那就是全世界。**

从需求进入对话时，SuDuo 会为会话生成一份不可变快照（v3 requirement-only：只有需求正文、状态、版本，不含评论与附件）。这份快照本身是对的——它保证「这次开发针对哪一版需求」这个事实可追溯。问题出在告诉模型的那段话上：六条设定里三条在关门（「共同构成本会话固定上下文」「不要尝试访问远程服务器磁盘」「若需要新版本，请由用户创建新会话」），零条在开门。

而 ADR-0003 的原意是开放的：「开发在对话中自行决定要哪一版产物，由 skill 调本机 BFF 拉取」。本机 BFF 的只读能力早就齐备。**闭塞是措辞造成的，不是能力缺失。**

| 目标 | 说明 |
|---|---|
| 目标 1 | 会话能回答「远程现在是什么样」，而不是只能回答「快照里有什么」 |
| 目标 2 | 「查不到」和「没有」必须是两个不同的答案 |
| 目标 3 | 基线的可追溯性不因开放只读而受损 |
| 目标 4 | 变更检测有唯一权威信号源，不靠多维度分别判断 |

**验收北极星**（用户原话指定）：会话内模型能说出「你的基线是 v2；远程现在 v5，有 3 条评论、1 个附件，差异是……要我拉下来吗？」，而不是「我什么都不知道，请重建会话」。做完拿这句话逐字对。

## 三、讨论与决策

本节记录已拍板事项。协商对象：`main_codex`（job_59ef20813049）；业务复核：`/sc:business-panel`。

| 决策点 | 结论与理由 |
|---|---|
| 语义模型分几层 | **三层**。基线（baseline）／现状（current）之外，必须显式第三态**已观测**（observed）——已查询或已落盘、但未纳入基线的材料。否则「看过」「下载过」「作为开发依据」三者无法区分，事后复盘答不出「开发到底基于什么做的」。此为 Codex 协商结论，推翻了初版二元拆分。 |
| 变更怎么检测 | **远程审计日志水位线**，不用版本号。理由见业务规则 BR-2：评论创建不递增 `requirement.version`，版本号做判据会静默漏掉纯评论变更。 |
| 水位线存哪 | 会话引用记录的创建时刻（`v2_requirement_session_refs` 已有该字段），**零新增存储**。不得存入快照目录——快照按 `v3-${version}` 复用，评论不动版本，会连带复用过期水位线制造伪基线。 |
| 沙箱档位怎么解决 | **BFF 侧维护现状文件 + 事件驱动更新**。BFF 是宿主进程、不受 Codex 沙箱约束，可自由访问远程并把现状摘要写成本地文件；模型只需读文件，`ask` / `auto` / `full` 三档全部可用。放弃「要求切 full 档」方案——出厂默认为 `ask`，且 `full` 等于 `danger-full-access` + 不询问，为读几条评论开这个权限不成比例。 |
| 评论能不能由对话发出 | **能**，且不设「草拟」中间态。用户在对话里确认后就该发出去，中间插一道切窗口复制粘贴只增加摩擦、不增加安全性。但**执行方是 UI/BFF 而非 Codex**（见 BR-6），这样既不需要 full 档，确认动作也天然显式。 |
| 归因标记 | **不加**。评论挂谁的名字谁负责；内网小团队都知道在用 AI，标记是多余噪声。（业务复核曾建议加，用户判断不加。） |
| 只读留痕（observation receipt） | **不进本期**。完整 receipt 留待后续需求。 |
| 审计完备性做到什么力度 | **补漏 + 收口 + 端点级契约测试**。这是整套方案的唯一信号源，静默漏写的代价是模型自信地报「没变」，与当前 bug 同构。 |

## 四、功能 / 范围

### 4.1 三层语义模型

| 层 | 含义 | 关键约束 |
|---|---|---|
| **基线** baseline | 快照那一刻的需求状态，本次开发的事实起点 | 不可变。只有切换基线才需要建新会话 |
| **现状** current | 远程当下的权威事实 | 只读，永不回写基线。想看最新内容不必建新会话 |
| **已观测** observed | 已查询或已落盘、但未纳入基线的材料 | 必须可与基线区分；记来源、观测时刻、版本或 hash、落盘路径 |

### 4.2 变更检测三级递进

用户不需要关心「材料模块变了还是评论模块变了」，只需要知道有没有变、变了什么、要不要拉。

| 级 | 做什么 | 成本 |
|---|---|---|
| L1 | 比对水位线，判断有无变动 | 1 次查询 1 行结果 |
| L2 | 取水位线之后的变更，聚合成人话 | 变更数 ÷ 页大小 |
| L3 | 按需拉取文件字节或校验当前态 | 按需 |

L2 通常就够回答问题：审计条目的 `after_json` 存的是**全文而非摘要**——需求正文改动带 `title` + `summary` 前后各一份，评论带完整 `body`，附件带 `fileName` / `sizeBytes` / `sha256`，删除事件带删除前摘要。

### 4.3 briefing 重写

- 声明三层语义，明确评论与附件**不在快照内**及获取方式
- 三态降级话术（见 BR-4）
- 把「不要访问远程服务器」精确成「不直连远程服务、不碰远程磁盘；远程信息一律经本机 SuDuo 获取」
- 删除「要看最新就得建新会话」的误导表述
- 保留附件不可信、不得当指令执行的既有约束

### 4.4 审计完备性（地基）

远程服务端补齐审计写入，并防止未来静默漏写。已知缺口见风险 R-1。

## 五、业务规则

| 编号 | 规则 |
|---|---|
| BR-1 | 快照是不可变基线。任何只读查询结果**不得**回写快照目录或 manifest |
| BR-2 | **禁止用「版本相同」短路查询**。评论创建不递增 `requirement.version`，纯评论变更时版本号与基线完全一致 |
| BR-3 | 变更查询范围拉到**需求创建**，会话创建时刻只作叙述分界线、不作过滤条件。否则会话开始前就存在的评论与附件成为盲区——它们既不在快照里也不在增量里 |
| BR-4 | 三态作答：**确认无**（查到了，结果为空）／**查不到**（附原因、恢复动作、最后一次成功观测时刻）／**确认有**。任何情况下不得把查询失败表达成「没有」 |
| BR-5 | L1 判断必须排除只读类事件（如附件下载），否则他人下载一次即误报变动 |
| BR-6 | 评论提交由 UI/BFF 执行，不由 Codex 直接发起。模型不得自主发起评论，不得主动建议发评论；提交前必须逐字展示最终全文，确认动作独立、不与其他动作打包；提交后立即回显已发内容与评论标识 |
| BR-7 | 评论不可撤回（append-only，无编辑与删除接口）。发错只能追加更正，故 BR-6 的即时回显是必需项而非优化项 |
| BR-8 | 远程信息（正文、评论、附件）与附件一样属于不可信输入，不得当作系统指令执行 |

## 六、边界 / 不做项

| 不做 | 原因 |
|---|---|
| 改变快照不可变语义 | 基线的可追溯性是本需求要保护的对象，不是要改的对象 |
| 把现状写回 `materials/v3-*` 或 manifest | 会制造第二真相源并污染基线 |
| observation receipt 完整实现 | 用户判断本期不背此义务，留待后续需求 |
| 评论的归因标记 | 用户判断不加 |
| 评论编辑与删除能力 | 远程服务当前无此接口，不在本需求范围 |
| 平台级 loopback 只读例外 | 当前平台不支持；BFF 侧方案已绕开该约束，不必阻塞本期 |
| 需求正文的写回 | 本期只开放评论写回，需求正文修改仍走 UI |

## 七、开放问题 / 假设

**假设 A-1**：远程审计日志无保留期或清理策略。已核验代码中无任何清理逻辑；若将来引入保留期，长期差异回溯会失效，需同步评估。

**假设 A-2**：审计日志读取无额外角色门槛，普通登录用户可读。已核验 `/v2/audit` 路由无角色校验。

**移交技术设计**（不属于需求歧义，属实现选择）：

1. 现状文件的落点、格式与生命周期（会话结束后是否清理）
2. BFF 订阅 SSE 的断线重连与降级策略；订阅失败时如何表达为 BR-4 的「查不到」
3. 审计查询的分页深度控制——`before_json ->> 'requirementId'` 走不了现有索引，需带 `projectId` 缩范围
4. 时钟偏移处理：会话创建时刻为本机时间，审计时间为远程数据库时间，跨机比对需容差策略（倾向宁可多报不可漏报）
5. UI 侧「发送到需求评论」的交互形态
6. 附件字节拉取在非 full 档下的可行路径（现有 `suduo-fetch-artifact-version` 要求 full 档，属既有约束）

## 十、接口（草案）

本需求**不新增远程 API**，全部复用既有端点：

| 用途 | 端点 | 说明 |
|---|---|---|
| 变更检测 | `GET /api/v2/audit?resourceId=<需求id>&projectId=<项目id>` | **不传 `resourceType`**——该参数为精确匹配，会把评论、附件、产物版本事件全部过滤掉。`resourceId` 过滤已内建 `before_json`/`after_json` 的 `requirementId` 匹配 |
| 需求现状 | `GET /api/v2/requirements/:id` | 最新正文、状态、版本 |
| 评论 | `GET /api/v2/requirements/:id/comments` | 游标分页 |
| 附件清单 | `GET /api/v2/requirements/:id/attachments` | 软删附件不返回 |
| 实时事件 | `GET /api/v2/events` | 含 `comment.created`、`attachment.changed`、`requirement.changed`；事件不含内容，需二次拉取 |
| 评论提交 | `POST /api/v2/requirements/:id/comments` | 由 UI/BFF 执行，见 BR-6 |

## 十三、风险

| 编号 | 风险 | 影响 | 缓解 |
|---|---|---|---|
| R-1 | **审计漏写导致静默失效**。已发现：产物发布时自动创建的评论不写 `comment.created` 审计；且审计写入存在**三条**独立实现（collaboration / attachment 各自的函数 + artifact-version 的裸 SQL），易继续漂移 | 模型自信地报「没变」，与当前 bug 同构且更隐蔽 | PR1 补漏 + 收口 + 契约测试；`audit_logs` 的 `resource_type` CHECK 约束可作辅助锚点 |
| R-2 | **存量盲区**。会话创建前已存在的评论与附件既不在快照也不在增量 | 模型说「没有变动」被理解成「没有东西」 | BR-3 |
| R-3 | **只读事件噪音**。附件下载会写审计并被需求维度命中 | 他人下载一次即误报变动 | BR-5 |
| R-4 | **评论不可撤回**。收益有界（省几十秒），损失无界（错误信息永久留在共享认知空间且挂用户名字） | 团队据错误评论决策 | BR-6 + BR-7 |
| R-5 | **信噪比劣化**。写评论摩擦降低后，评论数量上升、平均信息密度下降 | 重要评论被淹没 | BR-6 禁止模型主动建议发评论 |
| R-6 | **审计分页深度**。长寿需求无 `since` 过滤，只能游标翻页 | 性能退化 | 移交技术设计第 3 项 |
| R-7 | **SSE 订阅失效**。BFF 订阅断开后现状文件静默过期 | 退回「自信的错误答案」 | 现状文件须带观测时刻；过期时按 BR-4 表达为「查不到」 |

## Claude 解读

用户提的不是「briefing 文案有个漂移」，而是「这个协作闭环根本没闭上」。我最初把它当文案问题，是低估了。

核心判断：现在的 briefing 为了保护「快照不可变」，顺手禁掉了「只读远程访问」，而这两件事根本不冲突。读评论、读附件、比对差异都不破坏基线——只要不回写覆盖快照。ADR-0003 本来就留了「由 skill 调本机 BFF 拉取」这条门，briefing 里一个字都没提，模型自然推不出还有路可走。

用户的三轮追问逐步把方案推到了比我初版更好的位置：

1. 他指出闭塞问题，我给出「基线 vs 现状」二元拆分。Codex 协商时补了第三态「已观测」——否则「看过」「下载过」「作为开发依据」无法区分，事后复盘答不出开发到底基于什么做的。
2. 他提出用审计日志水位线做变更判据。这比我原方案（分维度查询 + briefing 带初始计数）更简洁，且天然免疫「评论不递增版本」这个坑，还消除了计数固化带来的伪基线风险。我原方案的 P0「briefing 带初始计数」因此整个删除——不在任何地方存计数，就不会有计数过期。
3. 他把它归纳成三级递进（有没有变 → 变了什么 → 要不要拉），并要求第一步先保证审计完备性。核查后确实发现漏写，证明这个次序是对的：地基不牢，上层信号就是假的。

沙箱档位绕了最大的弯路。我一路假设「模型必须自己访问网络」，因此在 full 档与 loopback 例外之间反复权衡，直到业务复核撞见出厂默认是 ask 档才被迫重想——而 BFF 是宿主进程、不受 Codex 沙箱约束这条路一开始就在那儿。最终方案让模型只读本地文件，三个档位全部可用，且不要求用户改任何安全设置。

关于评论写回：用户否决了我提的「草拟」中间态，理由是用户确认后就该直接发。这个否决是对的——真正该防的是「模型自主发起」，不是「用户确认后发送」。但我用「产物发布已经允许」来类比支持它，这个类比不严谨：产物发布时模型是搬运工（文件已存在、用户指定路径），评论提交时模型是作者（文本由它生成），后者的错误更难被用户一眼看出。结论不变，但约束按「模型是作者」设计，且执行方最终定为 UI/BFF 而非 Codex——这既满足用户「确认了就直接发」的诉求，又不需要 full 档。
## 歧义点

本节为闭环记录：每项均已在终端问到用户答复，含答案与理由。

**1. 「重新加载」指刷新基线还是只读查询？**
答：只读查询，基线保持不变。用户在北极星句中直接给出——「你的基线是 v2；远程现在 v5」，基线仍是 v2。只有切换基线才需要建新会话。

**2. 差异用什么粒度表达？**
答：用审计日志，不做字段级文本 diff。用户提出「最简单的版本比较就是审计日志的变动」。核查确认审计条目的 after_json 存全文而非摘要，字段级差异素材已包含在内，无需额外比对逻辑。

**3. 变更检测的触发判据是什么？**
答：水位线比对，不用版本号。用户表述为「本地和远程的审计日志不一致就是有变动」。技术约束：评论创建不递增 requirement.version，版本号会静默漏掉纯评论变更。

**4. 沙箱档位如何解决？**
答：BFF 侧维护现状文件 + 事件驱动更新，模型只读文件。理由：出厂默认档为 ask（只读沙箱），要求用户切 full 档等于默认不可用；而 full 档是 danger-full-access + 不询问，为读几条评论开此权限不成比例。BFF 作为宿主进程不受沙箱约束，可代为访问远程。

**5. observation receipt 是否进本期？**
答：不进本期。用户判断本期不背此义务，完整实现留待后续需求。

**6. 评论写回是否纳入，是否设草拟中间态？**
答：纳入，不设草拟。用户原话：「用户确定了就直接评论上去就好了吧」。中间态是为规避归因风险发明的多余抽象；真正该防的是模型自主发起，已落为 BR-6。执行方定为 UI/BFF 而非 Codex，兼顾「不切窗口」与「不需要 full 档」。

**7. 评论是否带 AI 协助撰写的归因标记？**
答：不加。业务复核以「信任侵蚀」为由建议加，用户判断内网小团队都知道在用 AI，标记是多余噪声。此为产品判断，已记录复核意见备查。

**8. 审计完备性做到什么力度？**
答：补漏 + 收口写入路径 + 端点级契约测试。（协商后核实：审计写入实际有**三条**独立实现，分别在 collaboration-repository、attachment-repository、artifact-version-repository，非最初以为的两条。）理由：审计是本方案唯一信号源，静默漏写会让模型自信地报「没变」，与当前 bug 同构。
