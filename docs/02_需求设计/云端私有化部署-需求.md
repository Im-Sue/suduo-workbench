# SuDuo 云端私有化部署（最简版）

> 一句话：使用方在自己的 Ubuntu / Linux 服务器上克隆仓库、执行一条命令，就能从源码构建并跑起 SuDuo 云端；升级、备份、恢复也各是一条命令。｜最后更新：2026-10-02
>
> 同批需求：[开源与商用授权](开源与商用授权-需求.md)、[客户端源码运行](客户端源码运行-需求.md)、[产品中英双语](产品中英双语-需求.md)、[官网](官网-需求.md)。部署资产：[cloud/DEPLOYMENT.md](../../cloud/DEPLOYMENT.md)（[中文](../../cloud/DEPLOYMENT.zh-CN.md)）、`cloud/scripts/suduo-cloud.sh`、`cloud/server/Dockerfile`、`cloud/server/compose.yaml`。

## 需求描述

云端（`cloud/server`，Fastify + PostgreSQL + 附件卷 + 房间文件卷）已经有 Dockerfile、compose 和备份恢复说明，但部署全靠手工：复制 `.env`、手填随机密钥、拼 `docker compose` 参数，从没在全新机器上走通过。

本需求把它变成「克隆 → 一条命令」的最简部署：

1. **安装**：检查 Docker → 生成配置和随机密钥 → 从源码构建镜像 → 启动 → 等健康检查通过 → 打印访问地址和下一步提示。
2. **日常运维**：升级（自动先备份）、备份、恢复、状态、日志、启停、卸载。
3. **国内网络**：构建时能切换到国内镜像源，避免拉不到基础镜像和依赖。
4. **中英双语的部署文档**和一次全新机器验收。

## 二、背景与目标

**目标对齐**：目标用户是团队里负责运维的人，有一台能上网的 Linux 服务器和 sudo 权限，会用 SSH，不一定熟悉 Docker 和 PostgreSQL。他照着文档十分钟内把云端跑起来，团队成员的客户端填上地址就能注册使用。以后升级是一条命令，出事能用备份恢复。不做预构建镜像、离线包、HTTPS 自动化和管理员功能。

**模拟示例**：

```
$ git clone https://github.com/Im-Sue/suduo-workbench.git && cd suduo-workbench
$ git checkout v0.7.0                    # 用发布标签，不用 main
$ cd cloud && sudo ./scripts/suduo-cloud.sh install --mirror cn
  ✓ Docker 27.3 / Compose v2.29
  ✓ 已生成 server/.env（数据库密码与签名密钥为随机值，请妥善保管此文件）
  … 构建镜像（首次约 3–8 分钟）
  ✓ PostgreSQL 就绪 ✓ SuDuo 云端就绪（schema 011，版本 0.7.0）

  访问地址：http://10.0.0.12:4100
  下一步：在 SuDuo 客户端的设置里填上这个地址，第一个注册的人即可开始使用。
  ⚠ 当前任何能访问这个地址的人都能注册账号。请只在内网或 VPN 内开放，
    或者放到带访问控制的反向代理后面（文档有 Nginx / Caddy 示例）。

（三个月后）
$ git fetch --tags && git checkout v0.8.0
$ sudo ./scripts/suduo-cloud.sh upgrade
  ✓ 已备份到 /var/backups/suduo/2026-12-01T10-00-00（数据库 + 附件 + 房间文件）
  … 重新构建并启动
  ✓ 升级完成：0.7.0 → 0.8.0（schema 011 → 013）
```

- **背景**：现状资产能用，但缺安装脚本、随机密钥生成、升级流程、国内镜像源支持；全新机器部署从未验证（原 T5-3 已取消）；健康检查只报数据库 schema 版本，不报程序版本。
- **目标**：
  1. 全新 Ubuntu 22.04 / 24.04 上，一条命令从源码装好。
  2. 升级、备份、恢复各一条命令，升级前自动备份。
  3. 国内服务器能顺利构建。
  4. 部署文档中英双语，全新机器验收走通。

## 三、讨论与决策

### 讨论：从源码构建还是提供预构建镜像

- **决策（用户 2026-10-02）**：先从源码构建。仓库公开，使用方克隆即可；预构建镜像需要先搭发布流水线和镜像仓库，放到后续版本。

### 讨论：要不要自动安装 Docker

- **决策**：不自动装。脚本只检查 Docker Engine 与 Compose 插件的版本，缺了就打印官方安装方法（含国内镜像站的安装方式），由用户自己装。往服务器上装系统级软件属于改动宿主机，交给运维人员自己决定。

### 讨论：HTTPS

- **决策**：不内置。文档给 Nginx 与 Caddy 的反向代理示例（含 HTTPS 证书配置与 SSE 需要的超时 / 缓冲设置）。

### 讨论：怎么挑版本

- **决策**：以 git 标签发布，两端共用一个版本号（`vX.Y.Z`，与 `client/package.json`、`cloud/package.json` 一致）。文档引导检出最新标签，不直接用 `main`。客户端和云端用同一个标签最稳妥；版本不一致时客户端会提示（见 R7）。

## 四、功能 / 范围

所有命令都在 `cloud/` 目录下通过一个脚本执行：`./scripts/suduo-cloud.sh <子命令>`。

### 4.1 install 安装

| 项 | 说明 |
|----|------|
| 做什么 | ① 检查系统（非 Linux 给提示）、Docker 与 Compose 插件是否可用、端口是否被其他程序占用（只提示，不拦截）；② 若 `server/.env` 不存在，从 `.env.example` 生成，数据库密码与签名密钥用随机值；已存在时沿用，其中的签名密钥若仍是示例占位值则换成随机值（代价只是所有人重新登录），数据库密码为占位值时给出警告；③ 构建镜像并启动；④ 轮询 `/v2/health` 直到就绪（绕过代理；端口只绑在其他地址时改为在容器内检查），超时给出排查提示；⑤ 打印访问地址、下一步、开放注册与商用登记提示。已安装且运行版本与检出版本不同时，提示改用 upgrade（只提示） |
| 参数 | `--port <端口>`（默认 4100）、`--mirror cn`（见 4.4）。端口默认在所有地址（IPv4 与 IPv6）开放；反向代理在同一台服务器时，用不进 git 的 `server/compose.override.yaml` 把端口改为只对本机开放，脚本存在该文件时自动带上（Docker 发布的端口不受 ufw 约束，文档已说明） |
| 前置条件 | 有 sudo 或在 docker 组里；能访问外网（或国内镜像源） |
| 预期结果 | 服务以 `restart: unless-stopped` 运行，服务器重启后自动起来 |

### 4.2 upgrade 升级

| 项 | 说明 |
|----|------|
| 做什么 | 用户先 `git checkout` 到新标签，再执行 upgrade：① 记录当前版本；② 自动执行一次 backup；③ 重新构建并启动（服务启动时自动执行数据库迁移）；④ 健康检查；⑤ 打印「旧版本 → 新版本、schema 变化、备份位置」 |
| 失败时 | 打印回滚步骤：检出旧标签 → restore 刚才的备份 → 启动。迁移只能向前，**回滚必须恢复升级前的备份** |

### 4.3 backup / restore 备份与恢复

| 项 | 说明 |
|----|------|
| backup | 按 DEPLOYMENT.md 现有的一致性流程：先停写入服务 → 导出数据库 → 打包附件卷与房间文件卷 → 恢复服务。产物放在一个带时间戳的目录（默认 `/var/backups/suduo/`，可用 `--to` 指定），附一份清单（版本、schema、文件校验值） |
| restore | `restore <备份目录>`：核对清单校验值，确认数据库导出与文件归档可读（损坏则在动数据前停下）→ 要求输入 `restore` 确认（见 R4a）→ 自动备份当前数据（`--no-pre-backup` 跳过），恢复本身可撤回 → 停服务 → 删库重建并在单个事务里导入 → 清空并恢复两个文件卷 → **按当前检出的版本重建并启动**（回滚时先检出旧版本）→ 健康检查。某一步失败时说明进行到哪一步、服务保持停止、可用同一份备份重试 |
| 预期结果 | 备份目录拷到另一台机器上也能恢复 |

### 4.4 国内镜像源

| 项 | 说明 |
|----|------|
| 做什么 | `--mirror cn` 或环境变量切换三处来源：Node / PostgreSQL 基础镜像的仓库前缀、npm 依赖源、pnpm 本体的下载源。选择写入 `server/.env`，后续 upgrade 沿用 |
| 文档 | 中文文档列出常用国内源及其设置方法；说明这些第三方源的可用性会变，失败时如何换一个 |

### 4.5 status / logs / start / stop / uninstall

| 子命令 | 说明 |
|----|------|
| status | 容器状态、程序版本、schema 版本、监听地址、磁盘占用、最近一次备份时间 |
| logs | 跟随服务日志（`--db` 看数据库日志） |
| start / stop | 启停，不动数据 |
| uninstall | 停止并删除容器与镜像，**默认保留数据卷和 `.env`**；`--purge` 才删数据，执行前要求输入确认词（见 R3） |

### 4.6 健康检查报告程序版本

| 项 | 说明 |
|----|------|
| 做什么 | `/v2/health` 在现有 schema 版本之外增加程序版本（取自 `cloud/package.json`） |
| 用途 | install / upgrade / status 打印；客户端设置页显示云端版本，并与本机版本比对（客户端侧在[客户端源码运行](客户端源码运行-需求.md)里做） |

### 4.7 部署文档（中英双语）

| 项 | 说明 |
|----|------|
| 做什么 | 重写 `DEPLOYMENT.md` 为面向使用方的部署指南，中英两份：系统要求、安装 Docker、一条命令安装、反向代理与 HTTPS 示例、升级与回滚、备份与恢复、常见问题、安全提示（开放注册、端口暴露）、许可与商用登记提示 |
| 原有内容 | 现有的一致性备份要求（禁止把在线 `pg_dump` 与在线卷拷贝当成一份备份）原样保留进新文档 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 正式支持 Ubuntu 22.04 / 24.04（x86_64）；其他装了 Docker Engine + Compose v2 的 Linux（含 aarch64）尽力支持 | 文档写明两档 |
| R2 | install 遇到已存在的 `server/.env` 时不覆盖，沿用其中的密钥，提示「检测到已有配置」 | ADR-0004 红线「不可逆字节损失」：数据库初始化后若重新生成密码，旧密码一旦覆盖就无法找回，已有数据库连不上。这里不是拒绝用户，而是不替用户覆盖；要重置由用户自己删文件 |
| R3 | `uninstall --purge` 删除数据前要求输入确认词 | ADR-0004 红线「不可逆字节损失」：数据库、附件和房间文件删掉无法恢复。默认 uninstall 不删数据 |
| R4 | restore 期间服务必须是停止状态，脚本自行停服 | 沿用原部署说明：在线恢复会造成元数据与文件错位（不可逆的数据不一致）。脚本自动停服，不是拒绝 |
| R4a | restore 执行前要求输入确认词 `restore`；无终端时需显式设置 `SUDUO_ASSUME_YES=1` | ADR-0004 红线「不可逆字节损失」：恢复会用备份替换当前全部数据，当前数据无法找回 |
| R5 | upgrade 前自动备份；备份失败就不继续升级，并说明原因 | ADR-0004 红线「不可逆字节损失」：迁移只能向前，没有升级前的备份就没有回滚路径。用户可以修好后重试、换备份目录，或加 `--no-backup` 自担风险 |
| R4b | 备份清单校验值不符时拒绝恢复 | ADR-0004 红线「不可逆字节损失」：用损坏的备份覆盖现有数据，现有数据与备份都救不回来 |
| R9 | 备份、恢复中途失败或被中断时，服务回到原来的状态（备份）或保持停止并说明进行到哪一步（恢复）；备份目录只给 root 读写，失败的备份不留下残缺目录 | 来自独立复核（2026-10-02） |
| R6 | 脚本不修改宿主机的系统配置（不装软件、不改 Docker 守护进程配置、不动防火墙） | 只打印建议命令 |
| R7 | 客户端与云端版本不一致时只提示，不拦截 | ADR-0004：检测并告知，由人决定是否升级 |
| R8 | 安装完成必须打印开放注册的安全提示 | 本期不做管理员与注册开关（用户 2026-10-02：「云端暂时不需要最小管理」） |

**保真差异三问（R2 / R3 / R4a / R4b / R5 为主动新增的阻止性行为）**：

| 规则 | 仲裁者是谁 | 拿掉最坏结果 | 人能否自己恢复 |
|------|------|------|------|
| R2 不覆盖 `.env` | 运维人员（要重置就自己删文件） | 已有数据库密码被覆盖，数据库连不上 | 能，但麻烦：要进数据库容器用本地连接重设密码。这里本质是不替用户覆盖，不是拒绝 |
| R3 purge 确认词 | 运维人员 | 误删全部数据库、附件、房间文件 | 不能，除非另有备份 |
| R5 备份失败不升级 | 运维人员（修好后重试，或按文档手动升级） | 迁移后出问题却没有回滚路径 | 不能：迁移不可逆 |
| R4a restore 确认词 | 运维人员（输入确认词即执行；自动化用 `SUDUO_ASSUME_YES=1`） | 误操作把当前数据整体替换成旧备份 | 默认能：恢复前会自动备份；用了 `--no-pre-backup` 则不能 |
| R4b 校验不符拒绝恢复 | 运维人员（换一份完好的备份） | 用损坏的备份覆盖现有数据 | 不能 |

## 六、边界 / 不做项

- 不做预构建镜像和镜像仓库（后续版本）。
- 不做离线安装包。
- 不做 HTTPS 自动签发，不内置反向代理。
- 不做管理员、注册开关、邀请（用户明确暂不需要）。
- 不做多实例、高可用、Kubernetes / Helm。
- 不自动安装 Docker，不改宿主机配置。
- 不做定时自动备份（文档给 cron 示例）。

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |
|------|----------|
| 默认数据存放 | 已定：只用 Docker 具名卷；`--data-dir` 不做（保持最简，备份走脚本） |
| x86_64 验收环境 | 已定：`.github/workflows/cloud-install.yml` 在 GitHub 的 Ubuntu 22.04 / 24.04（x86_64）上跑完整生命周期；本机 Lima 虚拟机（Ubuntu 24.04 aarch64，全新、无预装）跑同样流程并验证国内镜像源 |
| 国内镜像源的默认值 | 已定：基础镜像走 `docker.m.daocloud.io`，npm 与 pnpm 本体走 `registry.npmmirror.com`；文档注明是第三方源、可替换 |
| 脚本语言 | 已定：bash，目标系统不需要预装 Node；业务冒烟脚本 `scripts/smoke.mjs` 在服务容器里用自带的 Node 跑，只给验收与 CI 用 |
| Dockerfile 的 `# syntax=` 指令 | 已去掉：它会让构建器额外从 Docker Hub 拉前端镜像，镜像源设置管不到，国内服务器会因此构建失败；用到的语法内置构建器都支持 |

## 十二、交互 / 流程

```
git clone → git checkout vX.Y.Z → suduo-cloud.sh install
      │
      ├─ 检查 Docker / Compose / 端口 ──缺失──→ 打印安装方法，退出
      ├─ server/.env 不存在？→ 生成（随机密钥）；存在 → 沿用
      ├─ 构建镜像（--mirror cn 时走国内源）→ 启动

升级：git checkout 新标签 → suduo-cloud.sh upgrade
      └─ backup（失败则停）→ 重建启动 → 迁移 → 健康检查 → 打印版本变化与备份位置
```

## 十三、风险

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 国内服务器拉不到 Docker Hub 镜像 / npm 依赖 | 高 | 安装失败 | `--mirror cn`；文档列备选源 |
| 第三方镜像源失效 | 中 | 安装失败 | 源地址可配置，文档说明替换方法；后续提供预构建镜像根治 |
| 服务直接暴露公网，被陌生人注册 | 中 | 数据泄露 | 安装完成打印醒目警告；文档给反向代理访问控制示例；管理功能留待后续 |
| 小内存服务器构建失败 | 中 | 安装失败 | 文档写明最低配置（建议 2 核 4G）；构建失败时提示可能是内存不足 |
| 升级跨多个版本时迁移失败 | 低 | 服务起不来 | 升级前自动备份；失败打印回滚步骤 |

## Claude 解读

最简但完整的自托管：一个脚本覆盖安装、升级、备份、恢复，从源码构建，支持国内镜像源，附中英文档和一次全新机器验收。只在不可逆的地方加了保护（不覆盖已有密钥、清除与恢复要确认、损坏的备份不能用来恢复、升级前默认必须备份成功），恢复前自动备份当前数据，回滚即「检出旧版本 + 恢复」。

## 保真差异

- 原话只说「支持 ubuntu、linux」，本需求把 Ubuntu 22.04 / 24.04 x86_64 定为正式支持档、其他 Linux 为尽力支持档。
- 主动新增：升级 / 备份 / 恢复命令、国内镜像源、健康检查报版本、中英部署文档、开放注册警告。R2 / R3 / R4a / R4b / R5 几处阻止性行为已过 ADR-0004 判据（见 §五三问表）。端口占用由拦截改为提示。
- 用户选择的「最简」体现在：不做离线包、预构建镜像、HTTPS 自动化、管理员功能、自动装 Docker。
