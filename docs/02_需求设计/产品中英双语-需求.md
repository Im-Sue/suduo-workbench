# SuDuo 产品中英双语

> 一句话：每个使用者可以选中文或英文；界面、提示、错误、系统生成的协作记录、SuDuo 代表使用者对 Codex 说的话、命令行输出和对外文档，都按他选的语言出现；用户自己写的内容原样显示，不翻译。｜最后更新：2026-10-02
>
> 技术方案：[产品中英双语 技术设计](../03_开发计划/产品中英双语-技术设计.md)。同批需求：[开源与商用授权](开源与商用授权-需求.md)、[云端私有化部署](云端私有化部署-需求.md)、[客户端源码运行](客户端源码运行-需求.md)、[官网](官网-需求.md)。

## 需求描述

SuDuo 面向国内和海外，但不做中心化服务，由各团队自己部署，所以「国际化」落在产品本身：一个海外团队部署后，成员看到的应该是英文产品；一个中外混合的团队，每个人各看自己的语言。

目前产品只有中文：前端文案、服务端错误、房间里的系统消息、给 Codex 的需求工具说明、命令行提示、README 和部署文档全是中文（现状盘点见 §二）。

本需求做中文（zh-CN）和英文（en）两套，并保证以后新增功能不会再写死单一语言。

## 原话（verbatim）

> 「3. 目标市场 中国 + 海外（英文），但是我们又不是中心化部署的，是他们使用者公司/团队/个人 自己部署，所以我们只需要做好相关的语言之类的。」

## 二、背景与目标

**目标对齐**：语言跟着「人」走，不跟着「团队」走。同一个团队云端上，张三用中文、Alice 用英文，两人看同一条需求：需求正文是谁写的就是什么语言，但状态名、按钮、活动记录（「张三 把状态改为 开发中」/ “Zhang San changed status to In progress”）、房间系统消息、错误提示各自按自己的语言显示。Alice 从需求开工时，SuDuo 交给 Codex 的工具说明和需求卡也是英文。切换语言立即生效，历史记录也跟着变。

**模拟示例**：

1. Alice 第一次打开客户端，浏览器语言是 en-US，界面直接是英文。
2. 她在团队云端的需求 REQ-128 下看到张三的中文评论（原样显示），活动流显示 “Zhang San changed status to In progress · 2 hours ago”。
3. 她点「Start session」，本机 Codex 收到的需求工具说明是英文；她用英文提问，Codex 用英文回答。
4. 她上传一个超大附件被拒，提示是英文：“File is larger than the 300 MB limit.”
5. 张三在设置里把语言从「跟随系统」改成「English」，界面立刻变英文，刚才的活动记录也变成英文。
6. 运维人员在一台 `LANG=en_US.UTF-8` 的服务器上运行 `suduo-cloud.sh install`，输出是英文。

- **背景（现状盘点）**：见本节末「现状」。
- **目标**：
  1. 产品内所有 SuDuo 自己产生的文字都有中英两版，按使用者的选择显示。
  2. 用户写的内容不翻译、不改动。
  3. 以后新增文案缺任何一种语言，构建或检查会失败，不会悄悄漏掉。
  4. 对外文档（README、部署、商用登记、贡献、商标）中英齐全。

**现状**（2026-10-02 只读盘点，按 TypeScript 语法树统计字符串与 JSX 文本，不含注释）：

| 方面 | 现状 |
|------|------|
| 机制 | 没有任何多语言机制；`client/web/index.html` 写死 `lang="zh-CN"`；日期格式化有 4 套各自写死中文的实现 |
| 前端文案 | 约 2,200 处，分布在 138 个文件：设置约 590、需求约 360、房间约 290、会话约 190、外壳约 130……；其中约 550 处在属性里（无障碍标签 180、提示 120），约 300 个带插值的句子，124 个带量词（英文要处理单复数） |
| 服务端错误 | 两端统一返回 `{ error: { code, message, requestId, details? } }`，`message` 是中文；前端**直接显示** `message`，错误码只用来分类。本机后端约 270 处报错，其中 147 处同为 `VALIDATION_ERROR` 却各是不同的句子；云端的 `message` 实际到不了用户（本机后端只取错误码再换成自己的中文） |
| 服务端拼好的展示文字 | 会话列表的活动描述、自检各项、MCP / 模型服务 / 代理连通性提示、远程健康提示 |
| 已经是「类型 + 参数」的 | 云端审计与需求活动流（前端渲染）、各种状态枚举——换语言没问题 |
| 以中文成句落库的 | ① 发布产物的自动评论（还被拿来做相等比较判断「是否写了发布说明」）；② 房间 @ 提及里的「所有人」与 Agent 标签；③ 共享 Agent 任务的原因、进度、事件（由所有者本机生成，房间里所有人看同一份）；④ 本机事件账本里部分运行时警告与审批撤回原因；⑤ git 检查点的提交说明（写进用户自己的仓库历史，改不了） |
| 靠比对中文字符串运行的逻辑 | 会话运行态按步骤标题（「执行命令」「更新文件」「思考」）判断；发布评论的相等比较；自动存档提交按中文前缀识别；前端用正则改写服务端中文提示（代理、模型服务、自检摘要）。**换语言会悄悄出错** |
| 给 Codex 的文字 | 工具说明约 40 处、注入会话的说明与规则约 70 处、工具返回文本约 150 处、房间 Agent 每轮输入；只在建线程时下发，已有会话不会跟着变 |
| 测试 | 单元测试约 670 处中文断言；gate-c 约 100 处按中文定位；视觉基线按像素哈希比对，文案一变全变；测试环境默认语言是英文（jsdom 与 Playwright 都没固定） |
| 其它 | 自检页与命令行、启动报错、联调脚本、Windows 安装器与启动器（暂缓发布）、README 与部署文档 |
| 与旧需求的冲突 | [UI/UX 产品化重设计](v2-UIUX产品化重设计-需求.md) 与 [反馈交互语言统一](v2-反馈交互语言统一-需求.md) 曾写明「不做多语言」；自本需求起由本需求覆盖 |

## 三、讨论与决策

### 讨论：语言跟人还是跟团队

- **决策**：跟人。每个使用者在自己的客户端选择，记在本机。云端不设「团队语言」。理由：团队可能是混合的；云端没有管理员功能（本期不做）。

### 讨论：默认语言

- **决策**：默认「跟随系统」：浏览器语言以 `zh` 开头用中文，其他一律英文。设置页可改为固定中文或英文。

### 讨论：系统生成的协作记录怎么存

- **决策**：活动记录、房间系统消息这类由系统生成的文字，**按「事件类型 + 参数」保存，显示时按看的人的语言拼出来**，不把某种语言的成句文本存进数据库。这样切换语言后历史记录也一致。已经以中文成句存下来的历史数据怎么处理，在技术方案里给出（倾向能解析的转成类型 + 参数，解析不了的原样显示）。

### 讨论：SuDuo 对 Codex 说的话用什么语言

- 涉及需求工具的名称说明、需求卡、注入会话的说明、房间共享 Agent 的执行说明。
- **决策**：跟随发起这次会话的使用者的语言（会话创建时确定，之后不变）。理由：这些文字会影响 Codex 回答所用的语言和措辞；中文用户拿到中文说明、英文用户拿到英文说明最自然。工具的**名称**（`suduo_*`）不翻译，只翻译说明文字。
- 共享 Agent 在所有者本机执行，用**所有者**的语言；提问内容原样转交。它产生的任务原因、进度在房间里对所有成员可见，这部分按「类型 + 参数」存，各人按自己的语言看（见 4.4）。

### 讨论：错误提示

- **决策**：使用者看到的错误与提示一律按他的语言显示。本机后端是每个人自己的、知道请求者的语言，由它按请求者的语言生成文字；云端的错误文字本来就不直接给用户看（本机后端只取错误码再换成自己的文字），云端只保证错误码齐全，文字统一用英文。服务端日志不翻译（面向开发与运维，统一用英文便于搜索）。无法识别的错误显示通用提示和原始信息，不吞掉。具体机制见技术方案。

### 讨论：命令行与脚本

- **决策**：`pnpm start`、`pnpm run doctor`、`suduo-cloud.sh` 的输出跟随系统语言（`LANG` / `LC_ALL`；Windows 跟随系统界面语言），中文环境用中文，其他用英文。

### 讨论：文档

- **决策**：对外文档中英两份。GitHub 习惯以 `README.md` 为门面，面向国内外，**`README.md` 写英文、顶部链到 `README.zh-CN.md`**；其余对外文档同样「英文主文件 + `.zh-CN.md`」。`docs/` 下的需求、架构、ADR 等内部设计文档继续只写中文。

## 四、功能 / 范围

### 4.1 语言设置

| 项 | 说明 |
|----|------|
| 做什么 | 设置页（外观或通用分组）加「语言」：跟随系统 / 中文 / English。切换立即生效，不需要刷新或重启 |
| 存储 | 存在本机（客户端设置），每台电脑各自记 |
| 首屏 | 页面加载前就确定语言，不出现「先中文一闪再变英文」 |
| 附带 | 页面 `<html lang>`、浏览器标签页标题随语言变化 |

### 4.2 前端界面

| 项 | 说明 |
|----|------|
| 范围 | 全部页面与组件：导航、按钮、表单、校验、空状态、加载与失败提示、通知、对话框、快捷键一览、工具提示、无障碍标签（屏幕阅读器读的文字）、状态名与枚举名 |
| 格式 | 日期、时间、相对时间（「2 小时前」/ “2 hours ago”）、数字、文件大小按语言格式化；英文正确处理单复数 |
| 术语 | 建立中英术语表（需求 / Requirement、讨论 / Room、会话 / Session、共享 Agent / Shared agent、我的工作 / My work、概览 / Overview、审批 / Approval、本机工作目录 / Local folder 等），全产品统一 |
| 版式 | 英文普遍更长，所有页面在英文下检查截断、换行、按钮宽度 |

### 4.3 服务端提示

| 项 | 说明 |
|----|------|
| 范围 | 客户端后端返回给界面的错误与提示（约 270 处报错，以及会话活动描述、MCP / 模型服务 / 代理连通性提示）按请求者语言生成；前端不再用正则改写服务端文字，改为读结构化字段 |
| 本机诊断页 | 客户端后端直接输出的纯文本诊断页（`/doctor`）按使用者语言输出 |
| 云端 | 云端没有界面，只需保证错误码齐全、参数完整；错误响应里的人读信息改为英文（供开发者调试与日志） |

### 4.4 系统生成的协作记录

| 项 | 说明 |
|----|------|
| 范围 | 发布产物的自动评论、房间 @ 提及（「所有人」与 Agent 标签）、共享 Agent 任务的原因与进度（房间里所有成员都看得到）、本机会话里的运行时警告与审批撤回原因、通知。需求活动流与审计记录已经是类型 + 参数，只需把渲染文字放进字典 |
| 做法 | 按 §三 决策：存类型 + 参数，显示时按看的人的语言渲染 |
| 历史数据 | 能识别的旧中文记录（如固定句式的自动评论）在迁移时转成类型 + 参数；识别不了的原样显示 |
| git 检查点 | 提交说明写进用户自己的仓库，历史改不了：新提交的说明按使用者语言写，同时带一个与语言无关的标记供 SuDuo 识别；旧的中文前缀继续认 |
| 默认名称 | 「新会话」、「REQ-12 讨论」、「房间任务」这类默认名称按创建者的语言生成，创建后就是用户数据，不再随语言变化 |

### 4.5 SuDuo 对 Codex 说的话

| 项 | 说明 |
|----|------|
| 范围 | `suduo_*` 需求工具的说明与参数说明、需求卡、注入会话的说明文字、房间共享 Agent 的执行说明、工具返回结果里由 SuDuo 生成的固定文字 |
| 做法 | 按会话创建者（共享 Agent 为所有者）的语言选用对应版本；会话创建后语言固定 |
| 不做 | 不控制 Codex 自己的回答语言，不翻译用户提问 |

### 4.6 命令行与脚本输出

| 项 | 说明 |
|----|------|
| 范围 | `pnpm start` 启动器、`pnpm run doctor`、`suduo-cloud.sh`（云端安装运维）、Linux 安装脚本 `install:m1` 的提示 |
| 做法 | 跟随系统语言，中文环境中文、其他英文 |

### 4.7 对外文档

| 项 | 说明 |
|----|------|
| 范围 | README、云端部署指南、客户端快速开始、`COMMERCIAL`、`CONTRIBUTING`、`TRADEMARKS`、许可证中文参考译文 |
| 做法 | 英文主文件 + `.zh-CN.md`；两份内容一一对应 |
| 协调 | 部署文档、快速开始、商用登记等的内容由各自需求负责撰写，本需求负责中英两版齐全与一致 |

### 4.8 防止回归

| 项 | 说明 |
|----|------|
| 做什么 | ① 新增文案必须同时有中英两版，缺任何一版类型检查或构建失败；② 界面代码里出现写死的中文（或英文）成句文本时检查报错；③ 关键流程的自动化测试在两种语言下各跑一遍；④ 英文界面的关键页面纳入视觉检查 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 用户写的内容（需求、评论、消息、文件名、项目名等）一律原样显示，不翻译 | |
| R2 | 每条 SuDuo 自己产生的文案都有中英两版，缺一不能合入 | 由检查保证（4.8） |
| R3 | 语言是每个使用者在本机的个人设置，不同步到云端、不影响别人 | |
| R4 | 系统生成的协作记录按看的人的语言显示，不以某种语言的成句文本落库 | 新数据一律遵守；历史数据见技术方案 |
| R5 | 错误提示按使用者语言显示；无法识别的错误显示通用提示加原始信息 | 不吞错误 |
| R6 | 发给 Codex 的说明文字在会话创建时按会话创建者的语言确定，之后不随设置变化 | 避免同一会话前后说明语言不一致 |
| R7 | `suduo_*` 工具名、API 路径、错误码、配置项名、环境变量名不翻译 | 它们是接口，不是文案 |
| R8 | 全产品使用同一份中英术语表 | |

## 六、边界 / 不做项

- 不做第三种语言（但做法要允许以后加）。
- 不翻译用户内容，不接机器翻译。
- 不翻译 `docs/` 下的内部设计文档、代码注释、服务端日志。
- 不控制 Codex 回答所用的语言。
- 不做从右到左书写的语言支持。
- 不做按团队统一设置语言（云端没有管理员功能）。
- 不改 Windows 安装器与启动器的语言（安装包整体暂缓，随打包需求一起做）。
- 不改已存在用户仓库里的 git 提交说明（只能兼容识别）。

## Claude 解读

语言是个人设置；SuDuo 自己说的每一句话（界面、错误、系统记录、对 Codex 的说明、命令行、对外文档）都有中英两版，用户内容不碰。关键做法是「存类型和参数、显示时翻译」与「缺译文就失败」，保证历史一致、以后不回退。

## 歧义点

## 保真差异

- 原话「做好相关的语言之类的」：落实为产品全链路中英双语，范围经用户确认（界面、服务端提示、文档、官网；官网的双语在[官网需求](官网-需求.md)里做）。
- 主动新增：给 Codex 的说明文字双语、命令行输出双语、防回归检查、术语表。均不引入拦截行为（「缺译文构建失败」是开发期检查，不影响使用者）。
- 主动新增（S9，切换语言时保护用户输入）：三处都是「告知 + 给选项」，不拒绝任何人的操作。
  - 切换前的确认框（有打开的对话框、未保存的编辑或正在发送的内容时）：仲裁者是切换语言的人；拿掉它最坏是丢掉还没保存的输入（不可逆字节损失，ADR-0004 红线一）；人可以取消、处理完再切。
  - 另一个标签页改了语言时这里先不跟、顶部提示并给「现在切换」：仲裁者是这个标签页的使用者；拿掉它最坏同上；人随时可以自己切。
  - 切换那一刻恰好有排队消息要发出时暂停队列（原因「切换语言时正要发下一条，需要你确认继续」）、发送结果未确认的那一条标成待核对：仲裁者是会话的使用者；拿掉它最坏是把同一条消息发给 Codex 两次（不可逆对外副作用，红线二）；人点「继续」即恢复。
