# SuDuo V2 PM 需求前置闭环需求设计

> 一句话：把产品经理从「接到一个模糊想法」到「交出可开发的需求」这一段留在 SuDuo 里，靠状态、产物版本和 skill 三件事完成，而不是靠新增一套工作流。｜最后更新：2026-08-18

---

## 需求描述

SuDuo V2 当前只承接「需求已经想清楚之后」的协作：PM 必须先在系统外把想法澄清、把 PRD 写完，才能进入 SuDuo 创建需求并上传材料。从模糊想法到成型需求这一整段——澄清、对标、调研、起草、反复修订——在系统里没有任何落点，PM 真正花时间的部分全部发生在 SuDuo 之外。

本需求补上这一段，使 SuDuo 承接需求登记、流转与项目管理的全流程。做三件事：需求状态在草稿与待开发之间补一档「梳理中」，让「我在认真搞这个」成为对团队可见的信号；把需求材料从平铺附件升级为可发布、可追溯的产物版本，使「发布」成为 PM 向开发交接的明确动作；以及把会话起始时的材料预拉行为改为按需拉取，由 skill 与对话决定拉什么、放哪里。

全程不改变 V2「共享的是需求，私有的是代码和对话」的边界：PM 与 AI 的对话仍留在本机，只有 PM 主动发布的产物与评论进入共享侧。

## 二、背景与目标

**目标对齐**：你要的是「PM 接到一个模糊想法之后，不用离开 SuDuo 就能把它变成可以交给开发的需求」。今天做不到，因为系统里只有「需求已经想清楚」之后的那半段。这份需求补三件事：① 状态多一档「梳理中」，让"我在认真搞这个"变成团队能看见的信号；② 需求材料从一堆平铺附件升级成**可发布的产物版本**，让「发上去」变成一个对开发有约束力的交接动作；③ 起会话时不再自动把材料全拖到本机，改成谁要谁拉、由 skill 决定拉哪版、放哪里。不新增角色、不新增权限、不做状态守卫。

**模拟示例**（端到端走一遍）：

产品小李接到一句「老板说要做个类似某某的导出功能」。他在 SuDuo 需求页新建一条需求，只填标题「订单导出优化」和一句话来源说明，状态是**草稿**，30 秒完事。接着他在这条需求上起一个会话——他的电脑上映射的是项目根目录 `订单系统/`，里面 `requirements/` 放产品资料、`services/` 放各微服务代码。AI 按 skill 的指引只读 `requirements/`，翻出 2024 年那份被砍掉批量导出的旧 PRD，帮他拆出五个还没答案的问题，再起草 `requirements/订单导出优化/PRD.md`。改了三轮之后小李说「发上去」，skill 读取 PRD.md、原型.html、字段清单.xlsx 三个文件，调本机 BFF 发布为**产物 v1**，同时自动落一条评论写明这版包含什么。全组通过 SSE 看到。第二天小李补了边界条件，再发一次得到 **v2**，评论写明与 v1 的差异。他把需求拖到**梳理中**——开发看到这条"在认真搞了，可以提前扫一眼"。定稿后拖到**待开发**。开发小王在自己电脑上映射同一个项目根目录，从这条需求起会话，会话只带需求信息（标题、描述、状态），**不预拉任何材料**；小王说「把已发布的 v2 产物拉下来」，skill 调接口拉取 v2 那一版的全部文件并放到它约定的位置。小李之后又传了两个未发布的草稿截图——不影响小王，因为小王拿的是 v2。

- **背景**：
  - 需求实体只有 `title` / `summary(4000)` / `status` / `version`，材料是平铺附件，**没有版本概念**。PRD 迭代必然长出 `PRD_v2.docx`、`PRD_final.docx`，开发进来不知道该看哪个、哪个 Excel 配哪版 PRD。
  - 六个状态里 `draft` 同时装着"昨天刚记下的一句话"和"就差定稿的东西"，二者对开发的意义完全不同，但看板上长得一样。
  - `createRequirementSession`（`client/server/src/application/requirements-v2-service.ts:307-310`）预拉**当前全部活跃附件**，不绑任何固化版本。即使做了产物版本，开发也会拿到"已发布版 + 之后随手传的未发布材料"，「发布」对交接方毫无约束力。
  - 附件删除立即物理删除 blob（`cloud/server/src/application/attachment-service.ts:114-122`），服务重启的 `reconcile` 还会清掉所有不在活跃集合里的对象（`cloud/server/src/infrastructure/attachment-storage.ts:56-74`）。**在当前存储行为下，"历史版本全留"无法成立。**
- **目标**：
  1. PM 登记一个模糊想法的成本压到 30 秒，且不需要先想清楚。
  2. 「发布」成为 PM 向开发交接的明确边界，而不是一次普通上传。
  3. 产物历史可追溯、可对照、不会因为删文件而烂掉。
  4. 会话材料由 skill 与对话决定，SuDuo 不替用户预设工作流。
  5. 不动 V2「共享的是需求，私有的是代码和对话」的边界。

## 三、讨论与决策

### 讨论：「想法」要不要独立于需求存在

- 备选：新增 idea 实体做想法池 / 用现有 `draft` 状态承载。
- **最终决策 + 理由**：用 `draft` 承载，**不新增实体**。用户确认 `draft` 从一开始就是设计来装模糊想法的；独立实体会带来"想法转需求"的同步与归属问题，收益只有"看板更干净"，而后者用视图默认（列折叠、排序）就能解决，是纯前端的事。

### 讨论：状态要加几档，叫什么

- 判断标准：**状态是给别人看的，不是给自己看的**。PM 自己知道每条到哪一步，状态存在的唯一理由是让开发和测试知道"这条跟我有没有关系"。
- 按这个标准只有一个真实的分辨需求：`draft` 里"刚记下的"和"就差定稿的"对开发意义不同。PM 的内部工序（调研/对标/初稿/评审/定稿）不该做成状态——那是一个人的工序，别人不消费，而且会来回跳。
- **最终决策 + 理由**：只加一档 `in_refinement`「梳理中」，插在 `draft` 与 `ready_for_development` 之间。命名取 `in_*` 构词与既有 `in_development` / `in_testing` 对齐，三者语义统一为"某个角色正在里面干活"。不用 `in_planning`，因为 planning 在项目管理语境里常指排期规划，会与 `ready_for_development` 之后的排期动作混淆。

### 讨论：需求要不要新增可演进的「正文」字段

- 初判：`summary` 上限 4000 字撑不下 PRD，所以需要一个 Markdown 正文字段承载迭代中的 PRD。
- 用户纠正：标题和描述是需求实体的说明，**可以和 PRD/产物没有任何关系**，可以只是一段背景介绍或需求来源，且不该变来变去；PRD 及配套材料是另一码事，属于产物。
- **最终决策 + 理由**：**撤回正文字段**。初判的理由不成立——PRD 从来就不该进 `summary`。这说明既有业务规则 R5「简要需求说明与完整材料分离」**一开始就是对的**，本需求不推翻它。现有 `summary varchar(4000)` 装"背景 + 需求来源 + 简短描述"绰绰有余。

### 讨论：产物区做成独立存储，还是附件之上的版本层

- 用户原话给了两个方向："打包发到附件或者我们设计一个单独的需求产物区域"。
- **最终决策 + 理由**：做**附件之上的版本层**。附件表已有 `sha256` / `storage_key` / 软删除（`cloud/server/migrations/002_attachments.sql`），上传、下载、校验和、受控落盘（R11）全部可复用，只需新增版本表与版本-文件关联。独立存储区要把这些能力再造一遍，没有收益。"被某个版本引用的即产物，未被引用的即随手材料"，不另立区域。

### 讨论：变更说明落在哪里

- 备选：版本记录带 `change_note` 字段 / 发布时自动生成一条评论。
- **最终决策 + 理由**：**用评论**，不加 `change_note`。评论是 append-only 的——`cloud/server/src/http/server.ts` 只注册了 GET(:312) 与 POST(:340)，repository 只有 INSERT 与 SELECT，没有 UPDATE/DELETE。所以变更说明落进评论后不可篡改，天然是一条可信的发布日志，比一个可改的字段更稳。更正采用追加更正评论或发新版本，不编辑历史说明。

### 讨论：AI 怎么操作需求——内建 MCP server 还是 skill

- 初判：SuDuo 内建 MCP server，暴露 读需求 / 发布产物 / 发评论 / 改标题描述 四个工具。
- 协商发现（Codex，已核实）：`client/server/src/application/mcp-service.ts:430` 的 `addCommand` 走 `codex mcp add`，注册进共享 `CODEX_HOME` 全局配置，**所有 SuDuo 会话都能看到这些工具**，包括开发的会话；而现有三档审批只覆盖命令、文件与权限请求，**不含 MCP 写操作**，所谓"发布走写入预览审批"在当前机制上落不了地，必须自建一层托管审批。
- 用户明确：产物由 skill 或对话口头控制，与工具无关。
- **最终决策 + 理由**：**不做内建 MCP server**。SuDuo 只提供发布/拉取的 BFF 接口，由 skill 调用。这样三个问题一起消失：不用处理 MCP 全局可见性、不用自建托管审批（skill 调本机 BFF 走 shell 命令，本就在现有审批链路内）、不用往用户的 Codex 配置里注册自己。

### 讨论：起会话时拉什么材料

- 现状：`createRequirementSession` 预拉当前全部活跃附件。
- 备选：绑定最新已发布产物版本（协商建议）/ 维持现状 / **默认不拉、按需拉**（用户）。
- **最终决策 + 理由**：**默认只带需求信息，不预拉任何材料**；开发在对话里自己决定要什么，由 skill 拉取并决定放到哪里。这一条同时解掉三个问题：不会拉到未发布材料、开发能指定要哪一版（而不是只能拿最新）、SuDuo 不必规定本机材料目录结构。与用户既定原则一致——**SuDuo 提供能力和数据，skill 决定怎么用**。

### 讨论：需求要不要权限、归属或隐藏

- **最终决策 + 理由**：**不做**。用户明确"凡是新建创建的需求都是全平台开放"。这让分层反而更干净：真正的私人草稿留在 PM 本机目录（真私有），一旦登记成需求就是给团队看的。"要不要让别人看到"由**放在哪里**决定，而不是权限开关。看板上草稿列可能很长是**信息噪音**问题，用视图默认解决，不涉及数据与权限。

## 四、功能 / 范围

### 4.1 需求状态新增「梳理中」

| 项 | 说明 |
|----|------|
| 做什么 | `REQUIREMENT_STATUSES` 在 `draft` 与 `ready_for_development` 之间插入 `in_refinement`，中文标签「梳理中」 |
| 谁用 | 全体成员；由 PM 拖动 |
| 怎么触发 | 需求页看板拖拽或详情页状态切换 |
| 预期结果 | 看板多一列；语义为"PM 在认真梳理，开发可提前查看但先别动手" |
| 影响面 | `cloud/contracts/src/status.ts` 数组与 `REQUIREMENT_STATUS_LABELS`；`schemas.ts:62/77/102` 引用常量自动跟随；`001_initial.sql:38-47` 的 CHECK 约束需新增迁移放开；看板加一列 |
| 存量数据 | **零迁移**，没有任何需求会自动变档 |

### 4.2 需求产物版本化与发布

| 项 | 说明 |
|----|------|
| 做什么 | 一次「发布」= 把一组指定文件固化为该需求的一个产物版本，语义等同一次提交 |
| 谁用 | PM（也允许其他成员，不做角色限制） |
| 怎么触发 | 需求页手动发布，或会话中由 skill 调 BFF 接口发布 |
| 前置条件 | 需求存在；**待发布文件已上传**。发布只接受已上传附件的 ID 列表，不支持随本次发布上传（用户 2026-08-21 拍板收窄，理由见技术设计 §3.9） |
| 版本内容 | 版本号、发布人、发布时间、文件清单（不可变的文件名/大小/sha256/存储键） |
| 未变文件 | 靠 `sha256` 命中已有记录直接复用，不重复上传也不重复存储 |
| 预期结果 | 版本一经发布不可修改；历史版本全部保留，本期不做清理策略 |
| 明确不做 | 主文档标记；产物版本不快照标题与描述（二者与产物解耦） |

### 4.3 发布评论与变更说明

| 项 | 说明 |
|----|------|
| 做什么 | 每次发布在同一事务内自动落一条评论，承载该版变更说明 |
| 关联方式 | 评论表新增**可空且唯一**的 `artifact_version_id`；发布事务保证必写一条，从而形成一对一 |
| PM 未填说明 | 仍落一条系统生成的评论（如"发布了产物 v3，含 4 个文件、2 个变更"），保证时间线不断 |
| 呈现 | 带 `artifact_version_id` 的评论在评论流渲染为发布卡片，可点回该版；普通评论正常渲染 |
| 更正方式 | 追加更正评论或发布新版本，**不编辑历史说明**（评论 append-only） |

### 4.4 产物文件生命周期保护

| 项 | 说明 |
|----|------|
| 做什么 | 被任何产物版本引用的文件，其存储对象不可被物理清理 |
| 为什么必须做 | `attachment-service.ts:114-122` 删除时立即 `storage.remove()`；`attachment-storage.ts:56-74` 的 `reconcile` 在服务启动时删除所有不在活跃集合内的对象。不改则 PM 删掉一个已发布文件即导致历史版本损坏，重启还会补刀 |
| 预期结果 | 删除操作对活跃列表生效，但被版本引用的 blob 保留；`reconcile` 的"活跃集合"须包含全部被版本引用的存储键 |

### 4.5 会话材料改为按需拉取

| 项 | 说明 |
|----|------|
| 做什么 | `createRequirementSession` 不再预拉附件，只带需求信息（标题、描述、状态、版本等元数据） |
| 谁用 | 所有从需求创建会话的成员 |
| 预期结果 | 会话起始更快；不会拿到未发布材料；开发在对话中自行决定拉取哪一版产物 |
| 影响面 | `client/server/src/application/requirements-v2-service.ts:307-310` 与 `material-service` 的快照语义 |

### 4.6 产物发布 / 拉取接口与配套 skill

| 项 | 说明 |
|----|------|
| 做什么 | 远程服务提供产物版本的创建、列表、详情与文件下载；本机 BFF 代理并提供"把某一版拉到本机"的能力 |
| 调用方 | 会话中的 skill，或需求页 UI |
| 认证 | 沿用现有 BFF 登录态代理，不新增认证机制 |
| 官方 skill | SuDuo 内置发布与拉取两个开箱 skill；团队可自行编写替代或补充 |
| 明确不做 | 内建 MCP server；不往用户 Codex 配置注册任何 server |

### 4.7 容量上限调整

| 项 | 说明 |
|----|------|
| 单需求活跃附件 | 20 → **100** |
| 单个产物版本文件数 | ≤ **50** |
| 单附件大小 | 维持 300 MiB |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| N1 | 状态可任意切换，不做守卫 | 沿用既有 R3。新增的 `in_refinement` 同样不设进入/退出条件，也不限制任何角色在任何状态下的操作 |
| N2 | 产物版本一经发布不可修改 | 版本的文件清单与元数据不可变；纠错靠发新版本 |
| N3 | 被任何产物版本引用的文件不可物理清理 | 附件删除只影响活跃列表；`reconcile` 的活跃集合必须并入全部被版本引用的存储键 |
| N4 | 每个产物版本恰好关联一条发布评论 | 评论的 `artifact_version_id` 可空但唯一；发布与评论在同一事务内完成 |
| N5 | 发布说明不可编辑 | 评论 append-only；更正靠追加评论或发新版本 |
| N6 | 产物版本不承载标题与描述 | 标题、描述属需求实体，与产物解耦，PM 想改随时改，与任何版本无关 |
| N7 | 会话不预拉材料 | 创建需求会话只带需求信息；材料由 skill 按对话需要拉取 |
| N8 | 需求全平台开放 | 不做权限、归属或隐藏；看板视图默认属呈现层，不得实现为访问控制 |
| N9 | 发布与并发写必须显式版本校验 | 发布、附件增删与状态更新都会影响需求版本，须以 `expectedVersion`、行锁与幂等键处理，避免版本文件集与说明错配 |
| N10 | 不新增本机向远程的执行证据通道 | 沿用既有 R5 边界，"共享的是需求，私有的是代码和对话"不松动 |

## 六、边界 / 不做项

- **不做需求正文字段**：`summary` 即描述，既有 R5「简要说明与完整材料分离」保持不变。
- **不做内建 MCP server**，不往用户 Codex 配置注册任何 server；产物由 skill 与对话控制。
- **不做状态机守卫**：不限制任何状态下任何人的操作，只保证操作有审计。
- **不做需求权限、归属或隐藏**。
- **不做主文档标记**与 `change_note` 字段。
- **不做产物历史清理策略**：本期全留，容量策略后续再议。
- **不做本机目录整体递归发布**：首期按明确文件集发布；目录遍历、符号链接、重名相对路径、批量预览与失败原子性属独立范围。
- **不做「随本次发布上传」**：发布是一次纯数据库事务，只引用已上传附件，不在同一请求内接收文件字节。skill 内部先调既有上传接口（自带幂等）再调发布，PM 侧仍是一句「发上去」。原 4.2 前置条件写的「或随本次发布上传」与本条边界自相矛盾，已按用户拍板收窄。
- **不做项目到本机目录的一对多映射**：一个项目根目录下可同时容纳 `requirements/` 与各服务代码目录，现有单映射已够用。
- **不动会话运行时协议与事件投影语义**。
- **不并入沙箱 `networkAccess` 与文件权限正交化**：`client/contracts/src/config.ts:19-33` 中 `full` 档同时给 `danger-full-access` 与 `approvalPolicy: never`，是唯一给网档位，与工作台界面重构需求 R6「`full` 档需可锁定」冲突。该问题独立成需求，不在本期。

## Claude 解读

这个需求的本质不是"给 PM 加功能"，而是**把 SuDuo 里一段本来就该存在、却被跳过的时间补回来**。今天系统只承接"需求已经想清楚之后"，PM 真正花时间的澄清与起草全在系统外，SuDuo 对他而言是登记处而非工作台。

三块改动各自解决一个具体断裂：状态加「梳理中」解决"看板分不出刚记下的和快定稿的"；产物版本化解决"PRD 迭代必然长出 PRD_final2.docx、开发不知道看哪个"；会话不预拉材料解决"发布对交接方没有约束力"。

其中最容易被低估的是第三块与配套的 blob 保护。协商核实发现：createRequirementSession 预拉当前全部活跃附件，若不改，PM 郑重发布的版本会被之后随手上传的文件污染，"发布"退化成装饰动作；而附件删除即物理删 blob、服务重启还会清理非活跃对象，意味着"历史全留"在当前存储行为下根本不成立。这两条都不是范围取舍，是设计不自洽，必须在本期解决。

贯穿全需求的原则由用户给定并在多轮中反复应用：**SuDuo 提供能力和数据，skill 决定怎么用**。正是这条原则让内建 MCP server 整块被撤掉（改由 skill 调 BFF，天然落在现有审批链路内）、让会话材料改为按需拉取、也让"知识目录与代码目录冲突"这个伪问题消失——映射的是项目根，根下分子目录，skill 各读各的。

边界一步没退：PM 与 AI 的对话仍私有，只有主动发布的产物与评论过河。
## 歧义点

本轮所有命中用户拍板项均已在终端问到答案并闭环，无遗留待用户拍板项。

**已闭环拍板记录**

1. 状态是否新增、加几档、如何命名 —— 只加 in_refinement「梳理中」一档。判断标准是"状态是给别人看的"，draft 里"刚记下的"与"就差定稿的"对开发意义不同，这是唯一真实的分辨需求；PM 内部工序不做成状态。命名由用户授权 Claude 按系统规则设计，取 in_* 构词与既有 in_development/in_testing 对齐。
2. 是否新增需求正文字段 —— 撤回。用户明确"标题描述可以和 PRD/需求产物没有任何关系"，PRD 属产物而非描述，故既有 R5 保持不变。
3. 产物区形态 —— 采用附件之上的版本层，复用既有上传/下载/校验和/受控落盘能力，不另立存储区。
4. 变更说明落点 —— 用评论承载，不加 change_note 字段。评论 append-only（仅 GET/POST，repository 无 UPDATE/DELETE），作为发布日志不可篡改。
5. AI 操作产物的路径 —— 用户明确"产物和工具没关系，产物是 skills 或者对话口头控制的"，故不做内建 MCP server。连带解决了 MCP 全局可见性与托管审批两个问题。
6. 起会话拉取哪些材料 —— 用户明确"默认拉取需求信息不默认拉任何材料下来"，由 skill 决定拉什么放哪里。
7. 容量上限 —— 用户回复"按照你的推荐走"，确认活跃附件 100、单个产物版本文件 50、单附件维持 300 MiB。
8. 需求权限与可见性 —— 用户明确"全平台开放，没必要做什么特殊的权限、隐藏、所属"。
9. PM 目录与开发目录是否冲突 —— 用户指出不冲突，映射的是项目根，根下 requirements/ 归产品、各服务目录归开发，skill 控制各自读什么。Claude 原先"同机需二选一"的判断已撤回。

**显式移交技术设计的技术项**

- auto 档为 workspace-write + networkAccess:false，若 codex 沙箱将 loopback 计入网络访问，该档下 skill 可能调不通本机 BFF，须实测确认。
- 现有 SSE 仅按 requirementVersion 去重，新增产物事件需要独立版本或刷新语义。
- 迁移必须以新增文件放开 CHECK 约束，不得修改 001_initial.sql（T4-4 已将迁移链重写为仅注册 [1,2,10]）。
## 保真差异

**与原话一致的部分**：三块主体范围、状态语义、产物由 skill/对话控制、会话默认不拉材料、历史全留不清理、全平台开放不做权限——均直接来自用户原话，未作引申。

**Claude 归纳的部分**：
- 用户口语"梳理中的这些命名什么的你按照系统规则和业务发展设计即可"被具体化为枚举值 in_refinement 与中文标签「梳理中」，并给出与既有 in_* 构词对齐的理由。
- 用户"最粗暴的就是……只需要完整的发一版上去"被规范化为"产物版本 = 一组文件在该时刻的不可变快照"，并补充 sha256 复用与同事务写入等实现约束。
- 用户"发布产物产生一个评论就行了吧"被具体化为"可空且唯一的 artifact_version_id + 发布事务保证必写一条"，以同时满足一对一与评论表 append-only 的纯粹性。

**Claude 主动新增、原话未提及的部分**（均来自代码核实或协商，已在文档中标注依据）：
- 产物文件 blob 生命周期保护（4.4 / N3）。用户说"历史全留"，但代码核实发现附件删除即物理删、reconcile 重启清理非活跃对象，不做保护则该诉求无法成立。这是对用户意图的必要补全，非范围扩张。
- 并发与版本校验规则（N9）、SSE 去重语义（移交技术设计）。
- 容量上限三处硬编码收敛（4.7），原判"属实施配置项"经核实为跨端协同改动。

**Claude 撤回的自身提议**（避免文档留下未标注的漂移）：需求正文字段、主文档标记、change_note 字段、内建 MCP server、status 与内容拆并发域、"PM 兼开发者同机需二选一"的边界判断。

**明确移出本需求的关联项**：沙箱 networkAccess 与文件权限正交化，独立成需求。

### 剩余风险

1. **官方 skill 的最低可用档位是 `full`（= `danger-full-access`）**。pr1 用 `codex sandbox` 实测：`workspace-write` 下 loopback 在 0 ms 内被沙箱拒绝（`curl (7)`），连审批环节都到不了；`network_access` 是二元开关，`allowed_domains` / `allow_loopback` / `network_allowlist` 三种键名均无效，无法只放行 127.0.0.1。PM 要用发布/拉取 skill 就得整体放开沙箱。skill 已做档位预检并给中文提示、提示可改用需求页 UI，但这是产品级约束而非实现缺陷。
2. **两条跨服务接缝未作真实 E2E**（承上）——中等风险，带已披露风险交付。
3. **迁移未在生产执行**。004 建表、003 加状态值，发布路径依赖 004；上线顺序错会让发布接口直接 500。
4. **`codex-home.ts` seed 语义是「已存在的文件永不覆盖」**。好处是用户改过的 skill 不被升级冲掉；代价是官方 skill 后续修 bug 也不会自动生效，需手动删旧文件或另做升级机制。
5. **`in_refinement` 无状态守卫是用户明确要求**（「不需要特别严格的状态域」）。因此「未发布任何产物就被拖到待开发」这类流程空转系统不阻止，靠团队约定。
6. **仓库 Node 版本策略自相矛盾**（`engines >=24.10.0` vs doctor 精确 `24.10.0`），非本需求引入，但会让任何非 24.10.0 机器的全量测试常红。
