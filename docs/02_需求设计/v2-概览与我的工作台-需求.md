# SuDuo V2 概览与我的工作台需求设计

> 一句话：主导航补两个数据入口——「概览」看项目态势，「我的工作台」看我手上的活，后者是全站唯一同时呈现共享需求与本机会话的地方。｜最后更新：2026-08-18

---

## 需求描述

当前主导航只有需求、会话、设置三个模式。需求页是看板（单条需求粒度），会话页是运行时（单个会话粒度），两者都停在「逐条看」的层次，没有任何位置回答两个更高层的问题：**这个项目整体什么情况**，以及**我现在该干什么**。

本需求在主导航新增「概览」和「我的工作台」两个入口。概览承载项目态势（状态分布、停滞、动态流水），跟随顶栏当前项目；我的工作台承载个人待办（待审批、失败回合、我在做的需求、我的会话），跨项目汇总。

设计上有一条硬约束贯穿全文：**现有数据模型没有负责人、优先级、截止日期、工时字段**。因此本期不做任何依赖这些字段的指标（逾期率、进度百分比、燃尽图），只做三类有真实数据支撑的口径：**状态分布（存量）、审计流水（流量）、时间停滞（时间差）**。

## 二、背景与目标

**目标对齐**：给工作台补上「态势层」和「个人层」两个视角。概览让任何人打开就知道项目堵在哪、最近谁在推进什么；我的工作台让我打开就知道有没有 Codex 卡着等我审批、我在做的需求有没有被别人改过、我的会话跑到哪了。两个页面都不新增业务实体，只对现有数据做聚合与交叉，做完之后「我的工作台」应当取代需求看板成为登录后的默认落地页。

**模拟示例**：开发张三早上打开 SuDuo，默认落在「我的工作台」。顶部「待我处理」显示 2 条待审批（昨晚跑的会话里 Codex 要执行一条命令停在那儿）、1 条映射失效（他昨天挪了工作目录）。中部「我在做的需求」列出 3 条，其中「导出对账单」标着**需求正文或状态已变更**——他基于旧快照写的代码，产品昨天改过验收口径。他点进去看当前内容，再点右侧「我的会话」回到昨晚那个会话继续。整个过程没进需求看板，也没逐个项目翻会话列表。

- **背景**：
  - 需求页与会话页各自只能看见一半数据——需求页只有远程共享数据，会话页只有本机私有数据。**没有任何页面能同时看到两边**，而 V2 立项的理由（L3 需求→会话桥接）恰恰在这个交叉点上。
  - 待审批数（`pendingApprovals`）目前只以徽标形式藏在会话页左栏，不进会话页就看不见。Codex 停在那儿等人点头，等待时间是纯粹的浪费。
  - 会话材料是**创建会话时冻结的本机快照**，远程需求后来改了不会同步（系统简报里明写「若需要新版本，请由用户创建新会话」）。但**当前没有任何界面告诉用户「你手上的材料已经过期」**。
  - 目录映射失效目前是「点了创建会话才知道坏了」，属于事后暴露。
- **目标**：
  1. 概览用三类真实口径呈现项目态势，不造假指标。
  2. 我的工作台把「阻塞我的事」前置到打开即见，覆盖待审批、失败回合、映射失效。
  3. 首次把「会话材料已过期」这个信号暴露给用户。
  4. 两个页面都不新增业务实体、不改需求看板与会话运行时的既有行为。

## 三、讨论与决策

> 本章前四节是需求分析阶段的决策；后四节是技术设计阶段勘察代码后**推翻或补充**的决策，均已经用户拍板。

### 讨论：指标口径受限于数据模型

- 现状：`RequirementDto` 只有 `id / projectId / title / summary / status / createdBy / updatedBy / createdAt / updatedAt / version`。没有 assignee、优先级、截止日期、工作量。
- **最终决策 + 理由**：本期只做**状态分布、审计流水、时间停滞**三类口径。不做逾期率、进度百分比、燃尽图、速率预测——这些全部依赖缺失字段，硬做只能靠估算填充，产出的是**看起来精确实际编造**的数字，比不做更有害。

### 讨论：「我的需求」如何定义（无 assignee 字段）

- 候选 A：本机 `v2_requirement_session_refs` 推导，即「我从这条需求拉起过会话」= 我在做。
- 候选 B：远程需求表新增 `assignee` 字段，涉及 PostgreSQL 迁移、契约、看板 UI、指派交互，还要一并想清「谁能指派谁」。
- 候选 C：两者并存。
- **最终决策 + 理由**：**选 A**。零数据模型改动，且语义比「我创建的」更准——创建人往往是产品，动手的才是开发。B 的建模成本不在字段本身而在权限语义，当前没有角色权限体系（项目总览明确「不做角色权限」），贸然引入指派会牵出一串没答案的问题。C 是 A+B 的工作量之和，在 B 尚未被验证需要时不成立。

### 讨论：概览的统计范围

- **最终决策 + 理由**：**跟随顶栏当前项目**。与需求看板口径一致，切项目即换数据，实现简单。跨项目全局视图需要脱离顶栏上下文单独设计，且要先解决审计无 `projectId` 过滤的问题，收益不足以在本期承担。

### 讨论：聚合在哪里算

- **最终决策 + 理由**：**服务端加聚合端点**。前端拉全量分页自己算虽然零后端改动，但需求上千条后首屏会明显变慢，属于确定要还的技术债；而状态分布、停滞榜、按天流转量三者都是 SQL 天然擅长的聚合，下沉后数据量增长也不塌。
- 由此推导端点归属：概览数据全在远程 PostgreSQL → 聚合端点放**远程 requirements-service**；我的工作台是**跨库 join**（ref 在本机 SQLite，需求本体在远程 PostgreSQL），**只有本机 BFF 同时够得着两边** → 工作台聚合必须落在 `client/server`。由此派生一个必补的缺口：**远程目前没有按 id 批量取需求的接口**。
- 架构约束不变：**浏览器不直连远程服务**，Web 只调 `/api/v2/*`，远程数据一律经 BFF 代理。

### 讨论：是否做「我的足迹」（我最近改过/评论过的需求）

- **最终决策 + 理由**：**砍掉**。它依赖审计新增 `actor` 过滤（又一处服务端改动），而要展示的信息与「我在做的需求」高度重叠。

### 讨论（技术设计阶段推翻）：「我在做的需求」是否要并入「我创建的需求」

- 需求分析阶段曾提出：把 `createdBy === 当前用户` 作为第二来源并入同一列表，理由是「零成本缓解他人指派的盲区」。
- 勘察发现它**不是零成本**：远程 `listRequirements` 只支持按项目分页查，没有「跨项目查我创建的需求」这个能力，该来源实际需要新增一个端点 + 一个索引。
- 用户澄清原意：> 「我说的所谓的『我创建的需求』其实是指 在做的这个需求 如果有对应的远程需求信息应该拉取下来」
- **最终决策 + 理由**：**砍掉 `createdBy` 第二来源**。列表只由本机会话推导，但每条都从远程批量拉取完整信息（标题、所属项目、当前状态）。远程因此不需要新增「查我创建的需求」端点与 `created_by` 索引，范围缩小。他人指派、我尚未开工的需求仍然看不见——该缺口显式记账，等它真的疼了再引入 assignee。

### 讨论（技术设计阶段推翻）：「材料过期」怎么判定

- 需求分析阶段的口径是：会话快照 `requirementVersion` < 需求当前 `version` 即判定漂移，显示「需求已更新 N 版」。
- 勘察推翻了这个口径的前提：`requirements.version` 不只在需求正文/状态被改时增加，**附件增删**（`attachment-repository.ts:211/296`）和**产物版本发布**（`artifact-version-service.ts:103`）也会 +1；而交给 Codex 的会话材料是 **v3 requirement-only 快照，根本不下载附件**（`material-service.ts:230` 注释明写）。所以产品删一个附件，用户就会被提示「需求已更新 1 版」，点进去发现手上的材料一个字没变——**这是不可行动的假警报**，而它恰恰是本期自称的最高价值单点。
- **最终决策 + 理由**：改判**材料内容漂移**——比对本机快照 `requirement.json` 里的 `title`/`summary`/`status` 与远程当前值，这三项真变了才警示，文案「需求正文或状态已变更」。快照里已存着完整需求 JSON，比对是纯本地文件读，不增加任何远程调用；附件与产物发布不再触发警示，因为重开会话也拿不到附件。快照缺失或损坏时显示「快照不可读取」，不误报。

### 讨论（技术设计阶段补充）：审计按项目过滤要不要动表结构

- 勘察发现 `audit_logs` **没有 `project_id` 列**，只有 `(resource_type, resource_id)`。概览的时间线与流转量要按项目过滤，必须绕回需求表；`comment`/`attachment`/`artifact_version` 还要多跳一层才落到项目。
- 零迁移方案（查询时 join 解析项目归属）的问题：planner 可能退化成 hash join；而给它加「扫描上限」防护会与游标分页互斥，造成少页、空页甚至漏读。
- 本需求第九章原写「不做数据迁移」，但该约束是在**不知道审计表缺字段**的情况下定的。
- **最终决策 + 理由（用户拍板）**：**授权迁移**——给 `audit_logs` 加 `project_id` 列、回填历史、建 `(project_id, created_at DESC, id DESC)` 索引。时间线和流转图是概览的核心读模型，值得一次性迁移换确定性性能。

### 讨论（技术设计阶段补充）：会话归档后该需求还算不算「我在做」

- **最终决策 + 理由（用户拍板）**：**只算活跃会话**。关联会话全部归档后，该需求自动移出「我在做的需求」。否则这个列表会随时间退化成「我碰过的所有需求」，失去待办属性。

## 四、功能 / 范围

### 4.1 概览页

#### 4.1.1 状态漏斗条

| 项 | 说明 |
|----|------|
| 做什么 | 用**一条横向分段条**展示当前项目七个需求状态的数量与占比。六个流水线状态（草稿→梳理中→待开发→开发中→测试中→已完成）按顺序排列，`on_hold`（暂缓）拆到右侧单列 |
| 谁用 | 全角色 |
| 怎么触发 | 进入概览页自动加载；SSE `requirement.changed` 到达时刷新 |
| 前置条件 | 已登录且顶栏已选中项目 |
| 预期结果 | 一眼看出哪一段最宽（即堵点）。点击任一段跳需求看板并预置该状态筛选 |
| 为什么不用数字卡 | 一排数字卡占满一屏宽却只传达几个数字，且看不出「堵在哪」；分段条的宽度本身就是信息。`on_hold` 不在流水线上，混进漏斗会让读数失真，故单列 |

#### 4.1.2 停滞需求榜

| 项 | 说明 |
|----|------|
| 做什么 | 按「多久没动」排序列出停滞需求，阈值**按状态分级**（见 R2） |
| 谁用 | 全角色，尤其项目负责人 |
| 怎么触发 | 进入概览页自动加载 |
| 前置条件 | 同上 |
| 预期结果 | 每行显示：需求标题 + 状态徽章 + 停滞天数 + 最后操作人；点击进需求详情 |
| 设计理由 | 没有截止日期，`now - updatedAt` 是**唯一可信的风险信号**。这是概览里唯一能真正驱动行动的模块 |

#### 4.1.3 最近动态时间线

| 项 | 说明 |
|----|------|
| 做什么 | 展示本项目审计流水（12 种 action，含 `artifact_version.published`），SSE 实时追加 |
| 谁用 | 全角色 |
| 怎么触发 | 进入概览页加载首屏 + SSE 增量追加 |
| 前置条件 | 同上 |
| 预期结果 | 按「人 + 时间窗」合并显示（如 `张三 14:20 更新了 3 条需求`），可展开看细节；状态变更事件**视觉突出**，用 `before/after` 渲染成 `待开发 → 开发中` |
| 设计理由 | 每条审计单独一行会被评论和附件事件刷屏，把状态变更这类真正代表流程推进的事件淹没 |

#### 4.1.4 流转量迷你图

| 项 | 说明 |
|----|------|
| 做什么 | 按天统计 `requirement.status_changed` 数量，支持 7 天 / 30 天窗口 |
| 谁用 | 全角色 |
| 怎么触发 | 进入概览页自动加载，窗口可切换 |
| 预期结果 | 回答「团队最近在推进还是空转」，次要模块，位置靠下 |

### 4.2 我的工作台

#### 4.2.1 待我处理

| 项 | 说明 |
|----|------|
| 做什么 | 汇总三类阻塞项，按优先级排列（见 R5）：① **待审批**（跨所有会话的 `pendingApprovals`）② **失败回合**（`lastTurnOutcome === "failed"`）③ **失效的目录映射**（预检 `available === false`） |
| 谁用 | 当前登录用户本人 |
| 怎么触发 | 进入页面自动加载；页面可见时按固定间隔轮询刷新（见 R11） |
| 前置条件 | 已登录 |
| 预期结果 | 每条可一键直达处理现场——待审批和失败回合跳对应会话，映射失效打开映射设置对话框 |
| 设计理由 | 待审批意味着 Codex 正停在那儿等我点头，是**活的阻塞**，每多等一秒都是纯浪费；而这个信号目前只藏在会话页左栏徽标里 |

#### 4.2.2 我在做的需求

| 项 | 说明 |
|----|------|
| 做什么 | 列出我关联的需求。**唯一判定口径：我从这条需求拉起过会话**（`v2_requirement_session_refs`），且该会话仍活跃（见 R6） |
| 谁用 | 当前登录用户本人 |
| 怎么触发 | 进入页面自动加载 |
| 前置条件 | 已登录；跨项目，不受顶栏项目选择影响 |
| 预期结果 | 每行显示：需求标题 + 所属项目 + 当前状态 + 我的会话数与运行态 + **材料过期警示**。标题、所属项目、当前状态均从远程批量拉取，保证是最新值 |
| 关键子功能 | **材料过期警示**：比对本机快照 `requirement.json` 的 `title`/`summary`/`status` 与远程当前值，任一不同即显示「需求正文或状态已变更」，点击进需求详情看当前内容；快照缺失或损坏显示「快照不可读取」。详见 R4 |

#### 4.2.3 我的会话

| 项 | 说明 |
|----|------|
| 做什么 | 按 `lastActivityAt` 倒序列出我的会话，**跨项目** |
| 谁用 | 当前登录用户本人 |
| 怎么触发 | 进入页面自动加载 |
| 预期结果 | 每行显示：标题 + `purpose` 徽章 + 运行态（运行中/待审批/失败）+ 所属项目 + 关联需求；点击直达会话 |
| 设计理由 | 现在必须先在顶栏选中项目才能看到该项目的会话，跨项目找「我昨天那个会话」需要逐个项目翻 |

### 4.3 导航与路由调整

| 项 | 说明 |
|----|------|
| 做什么 | `AppNav` 顶部新增「概览」「我的工作台」两项，排在「需求」「会话」之前；新增 `/overview` 与 `/my` 两条路由；默认落地页由需求看板改为我的工作台 |
| 前置条件 | 仅在 `shellReady`（已配置且已登录）时显示，与现有导航项一致 |
| 预期结果 | 折叠态需带 tooltip 与 `aria-label`，与现有 `NavItem` 约定一致 |
| 兼容性 | `/` 的兜底语义由「需求看板」改为「我的工作台」，需求看板迁至 `/requirements`（当前它挂在 `/` 上，不存在 `/requirements` 路径）；`/requirements/:id` 详情路由**语义不变** |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 不引入任何依赖缺失字段的指标 | 禁止逾期率、进度百分比、燃尽图、速率预测。仅允许状态分布、审计流水、时间停滞三类口径 |
| R2 | 停滞阈值按状态分级 | `in_development`/`in_testing`：3 天提示、7 天警示；`in_refinement`/`ready_for_development`：7 天 / 14 天；`draft`：14 天 / 30 天；`on_hold`：30 天提示；`completed` 不计入停滞。`in_refinement`（梳理中）与 `ready_for_development` 同档，因为它表示 PM 正在处理，不能与被动放置的草稿同档 |
| R3 | 停滞时长基于 `updatedAt` | 计算 `now - updatedAt`。已查证写入逻辑：**评论不刷新** `updatedAt`；**附件增删与产物发布刷新**。判定为合理口径——附件上传与产物发布本身就是「有人在动这条需求」，而纯讨论不等于推进。UI 文案用「最后更新」，不写「最后状态变更」 |
| R4 | 材料过期判定基于内容比对，不基于版本号 | 比对本机快照 `requirement.json` 的 `title`/`summary`/`status` 与远程当前值，任一不同即判定过期。**不得用 `version` 差值判定**：该字段同时被附件增删与产物发布 bump，而会话材料不含附件，会产生不可行动的假警报。同一需求有多个活跃会话时取**最旧**快照比对，因为最旧的那个偏离最远 |
| R5 | 待我处理的优先级顺序 | 待审批 > 失败回合 > 映射失效。待审批是活的阻塞（Codex 正在等），失败是已发生待查看，映射失效是潜在的、尚未触发的 |
| R6 | 「我在做的需求」只计活跃会话 | 排除 `archived`/`deleted` 会话关联的 ref。关联会话全部归档后该需求自动移出列表，否则列表会退化成「我碰过的所有需求」，失去待办属性。同一需求被多个会话关联时只出现一次 |
| R7 | 概览跟随顶栏项目，工作台跨项目 | 概览必须响应顶栏项目切换；工作台不受其影响，切项目不改变工作台内容 |
| R8 | 浏览器不直连远程服务 | Web 只调 `/api/v2/*`，所有远程聚合数据经本机 BFF 代理，不得在前端直接请求远程服务 |
| R9 | 空态必须有意义 | 无停滞需求显示「没有停滞需求」而非空白；无待我处理项显示明确的「当前没有需要你处理的事」；新项目零需求时漏斗条显示引导而非零值图表；本机无会话记录时说明原因并引导从需求看板拉起会话 |
| R10 | 聚合失败不拖垮整页 | 工作台三个区块的数据来源不同（本机 SQLite / 本机文件 / 远程服务），任一来源失败时其余区块正常展示，失败区块单独显示错误与重试 |
| R11 | 工作台刷新用可见性感知轮询 | 本机侧没有全局事件流可订阅（现有机制只支持按单个 `sessionId` 订阅），本期以「页面可见时定时轮询 + 手动刷新」实现，待审批感知最长延迟一个轮询周期。概览页仍走既有远程 SSE |

## 六、边界 / 不做项

- **不新增 `assignee` 字段**，不做需求指派功能，不做角色权限。
- **不做「我的足迹」**（我最近改过/评论过的需求），因此本期**不需要**审计的 `actor` 过滤能力。
- **不做「我创建的需求」第二来源**，因此远程不新增「跨项目查我创建的需求」端点与 `created_by` 索引。
- 不做逾期率、进度百分比、燃尽图、工时统计、速率预测——依赖字段不存在。
- 不做跨项目的概览视图（本期概览仅项目内）。
- 不做自定义仪表盘、指标配置、数据导出、图表下钻分析。
- 不改需求看板与会话运行时的既有交互，两页只做只读聚合展示 + 跳转。
- **不改造会话材料的刷新机制**——「会话材料不能刷新、只能重开会话」是既有设计，本期只负责把过期信号暴露出来，不负责修它。
- **不扩展本机事件广播机制**（`EventBroker` 现只支持按 `sessionId` 订阅），全局本机事件流留作独立后续需求。
- **不引入图表库**——分段条用纯 CSS，迷你图用内联 SVG；沿用既有 Tailwind v4 + shadcn/Radix。
- 不做部署发行相关内容（属主线需求 T5-3）。

## 九、数据（草案）

**不新增业务实体，不新增数据表。** 唯一的结构变更是审计表增加项目归属列（已获用户授权，见第三章）。

- **结构变更（远程）**：`audit_logs` 新增 `project_id uuid`，回填历史后置 `NOT NULL`，建索引 `(project_id, created_at DESC, id DESC)`。回填推导：`project` 类型取 `resource_id` 本身；`requirement` 取 `requirements.project_id`；`comment`/`attachment`/`artifact_version` 经各自的 `requirement_id` 再取。三处写审计的代码需同步补该字段。
- **复用的远程数据**：需求（`status`/`updatedAt`/`version`/`title`/`summary`）、审计流水（`actor`/`action`/`before`/`after`/`createdAt`）、项目。
- **复用的本机数据**：`v2_requirement_session_refs`（`remoteRequirementId`/`requirementVersion`/`materialPath`/`sessionId`）、会话材料快照文件 `requirement.json`、会话与运行态（`pendingApprovals`/`lastTurnOutcome`/`lastActivityAt`/`state`）、目录映射及其预检结果。
- **需要新增的查询能力**（非新增数据）：
  - `RequirementSessionRefRepository` 现只有 `getBySessionId` 与 `listByRemoteProjectId`，**缺跨项目全量查询**，工作台跨项目汇总必须补。
  - 待审批现只能逐会话计数，**缺全局分组聚合**，跨项目待审批汇总必须补。
  - 运行态现由逐会话服务推导，其内部会扫该会话全部回合事件，**全局使用会退化**，必须改为按会话 id 集合一次取事件再归约。
  - 会话列表现只能按本机项目查，**缺跨项目按活跃度排序**。

## Claude 解读

主导航新增「概览」与「我的工作台」两个只读聚合页。**概览**跟随顶栏当前项目，用状态漏斗条、停滞需求榜、动态时间线、流转量迷你图四块呈现项目态势；**我的工作台**跨项目汇总个人待办，用待我处理、我在做的需求、我的会话三块回答「我现在该干什么」，并首次把「会话材料已过期」这个信号暴露给用户。

关键决策已全部拍板。需求分析阶段定下三条：「我的需求」用本机会话推导而非新增 `assignee` 字段；概览统计跟随当前项目；聚合下沉到服务端。由此推导出聚合端点分两处——概览聚合在远程服务，工作台聚合因跨库 join 必须落在本机 BFF，并派生出「远程需要按 id 批量取需求」这一必补缺口。

技术设计阶段勘察代码后，**推翻了两条原本写定的口径，并突破了一条原本写定的约束**：其一，「我在做的需求」的 `createdBy` 第二来源经用户澄清后砍掉，列表只由活跃会话推导；其二，材料过期不再用 `version` 差值判定，改为比对快照与远程的标题/正文/状态——因为 `version` 会被附件增删与产物发布 bump，而会话材料根本不含附件，原口径会产生不可行动的假警报；其三，审计表缺 `project_id` 导致按项目过滤绕不开，用户授权突破本文档原「不做数据迁移」的约束，给该表加列、回填、建索引。

除上述审计表结构变更外，本期不新增任何业务实体或数据表，其余改动全部是对现有数据的聚合、交叉与新增查询能力。设计上主动拒绝了一切依赖缺失字段（负责人、优先级、截止日期、工时）的指标。
## 歧义点

**需求分析阶段闭环的四项**：①「我的需求」定义（本机会话推导，接受他人指派盲区）②概览范围（跟随当前项目）③聚合位置（服务端，且工作台聚合落 BFF）④「我的足迹」砍掉。

**技术设计阶段闭环的七项**（前三项为用户拍板，后四项为 AI 自决的实现取舍）：

- **审计按项目过滤是否动表结构**——用户授权迁移：`audit_logs` 加 `project_id` + 回填 + 索引。理由是零迁移的 join 方案在 planner 下可能退化，而给它加扫描上限会与游标分页互斥、造成漏读；时间线与流转图是概览核心读模型，值得一次性迁移换确定性。
- **「我在做的需求」是否含已归档会话**——用户拍板只计活跃会话，否则列表会退化成「我碰过的所有需求」。
- **`createdBy` 第二来源是否保留**——用户澄清原意后砍掉。原文档称其为「零成本缓解」，勘察证明它实际需要一个新端点加一个新索引；用户澄清真实意图是「在做的需求应从远程拉取完整信息」，与该来源无关。
- **评论/附件是否刷新 `updatedAt`**——查证结论：评论不刷新，附件增删与产物发布刷新。判定为合理口径，停滞继续用 `updatedAt`。
- **材料过期判定口径**——改为内容比对而非版本号差值。该项经两轮澄清：用户初次质疑前提（认为 agent 读了就是最新的），经出示三条代码证据（系统简报明写快照不会随远程更新、快照仅在创建会话时生成一次且无更新路径、v3 快照不下载附件）后，用户认可「旧会话没有感知」并表示「先不管，我可以命令 codex 重新拉取或者重新加载」，未在选项中明确择一，故按推荐项落定并显式记为可否决假设。
- **批量取需求的接口形式与上限**——`GET ?ids=`，上限 100，BFF 分批，缺失 id 静默跳过。
- **工作台如何感知本机事件变化**——本机 `EventBroker` 只支持按 `sessionId` 订阅，没有全局事件流。本期降级为可见性感知轮询，不扩展广播机制（属会话运行时改造，超出本需求边界）。

**无遗留待用户拍板项。**
## 保真差异

原话只给出「加两个入口用来看数据，你来规划展示什么、怎么展示」这一层意图，页面内容全部由 Claude 勘察代码与数据模型后规划，并经用户以「你的建议都没毛病」整体确认。三个关键决策由用户在选项中明确选定，原文已逐条记入「原话」章节。

相对原话的主要归纳：①补充了「数据模型缺少负责人/优先级/截止日期/工时」这一原话未提及、但决定了全部指标口径的约束；②把「看数据」拆解为项目态势与个人待办两个视角，并据此界定两页范围不重叠；③主动裁剪了「我的足迹」模块并记录理由。无删减原话诉求。

**本次修订（技术设计阶段回写）相对首版需求文档的差异**——首版有四处与代码实际不符，均以代码为准更正，并在第三章记录推翻过程：

| 首版写的 | 代码实际 | 本次改法 |
|---|---|---|
| 六个需求状态、五个流水线状态 | 七个状态（migration 003 加了 `in_refinement`） | 漏斗条改为六个流水线状态 + 暂缓单列；R2 补 `in_refinement` 档位（7/14 天） |
