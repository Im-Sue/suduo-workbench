# SuDuo 遗留 token 文档漂移与 runtime 事件噪音 需求设计

> 一句话：清掉 access-token 移除后残留在文档与样例里的失效说明，并让全局 runtime 事件不再以"背景错误"形式污染启动日志。｜最后更新：2026-08-15

---

## 需求描述

在一台全新机器上按 README 完整安装并启动 SuDuo 的过程中，暴露出两处与代码现状不一致的问题。

第一处是 **access-token 机制移除后的文档漂移**。服务端已确立"不提供登录机制、以 loopback Host 校验 + 写请求同源 Origin 校验作为防护"的设计（`client/server/src/infrastructure/http/loopback-guard.ts`），Windows 安装器也已内置 `removeLegacyAccessToken()` 主动清理遗留令牌文件。但 README、`.env.example` 与 Windows 验收手册仍在描述这套已不存在的令牌流程，其中 `docs/windows-verify.md` 的两条验收项已永远无法通过，会直接卡住 Windows 真机验收。

第二处是 **全局 runtime 事件被当作错误抛出**。`RuntimeEventIngestor.ingest` 对无法关联到 suduo session 的事件一律抛异常，这是刻意设计——注释说明其目的是让被 consumer 丢弃的事件内容至少留在日志里，用于排查 codex 进程死因。但 codex 启动时必然产生 `configWarning`、`remoteControl/status/changed` 这类本就不属于任何 session 的全局事件，导致每次正常启动都固定产生背景错误，把该机制原本要保护的真实故障信号淹没在噪音里。

两处都不影响服务可用性，但都会影响新机器上手与故障排查效率。

## 二、背景与目标

**目标对齐**：SuDuo 早期版本用一个"访问令牌"文件来控制谁能打开工作台，后来这套机制被整体移除，改成靠"只接受本机地址的请求"来划边界。代码已经改完了，但讲这件事的文档一处没改——README、Windows 验收手册、项目总览、环境变量样例里仍在描述那个不存在的令牌。这次要做的是让文档回到和代码一致，并给这条安全边界补上自动化回归测试，让它下次重构时不会再悄悄漂走。顺带把每次启动都固定报两条假错误的日志问题一并修掉。

> 名词白话：**loopback（环回地址）**＝只有本机能访问的地址，如 `127.0.0.1`、`localhost`；**同源写请求校验**＝只有从本机页面发出的修改类请求才放行，防止你在别的网站上被诱导去操作本机服务。

**为什么这不只是"改错别字"**：`client/server/src/main.ts:36` 硬性要求 `SUDUO_HOST` 必须严格等于 `127.0.0.1`，启动即校验；`loopback-guard` 是第二道防线。也就是说"本机无登录"是一条**安全边界契约**，而不是省事没做登录。安全审查、试点运维和发版验收都以文档为输入——文档描述了一套不存在的令牌机制，等于让审查者对着错误的模型做判断。

**模拟示例（一次真实发版验收走一遍）**：

```
运维小张拿到 SuDuo-Setup.exe，按 docs/windows-verify.md 逐条验收
        │
        ├─ 第 45 行要求：确认 data\access-token 由服务首启自动生成
        │     ▼
        │  打开 data\ 目录 —— 没有这个文件
        │     ▼
        │  小张的两种反应都是坏结果：
        │     (a) 判定"安装失败"，把一个正常的包退回      → 误报，阻塞发版
        │     (b) 判定"手册过期"，顺手跳过第 62 行 ACL 检查 → 验收清单失去约束力
        │
        └─ 第 35 行要求：确认浏览器"自动登录（无需粘贴令牌）"
              ▼
           页面直接就开了 —— 到底是"自动登录成功"还是"根本没有登录"？
           手册无法区分，验收结论不可信
```

- **背景**：令牌机制随架构调整移除，Windows 安装器甚至专门写了 `removeLegacyAccessToken()` 清理遗留文件，说明移除是有意为之；但文档侧一处未同步，共残留 14 处失效表述。同期发现 codex 每次启动固定产生 2 条无法归属会话的全局事件，被当作错误抛出。
- **目标**：
  1. 文档、样例、验收手册与项目总览统一到当前安全模型，14 处失效表述清零。
  2. 这条边界获得自动化回归保护，不再依赖人工记忆。
  3. 明确写出 WSL 部署形态下的真实暴露面，供安全审查判断。
  4. 启动日志不再出现固定的假错误，使真实故障信号可被察觉。

## 三、讨论与决策

### 讨论：A 的严重性定性

- Claude 初判：文档漂移，不影响可用性，主要伤害是新用户上手困惑。
- Codex 反驳：判轻了。`main.ts` 强制 `127.0.0.1` + guard 二道防线构成安全边界契约，错误文档会误导安全审查、运维与验收。
- **最终决策 + 理由**：采纳 Codex 定性。本需求按"安全契约文档一致性"处理，而非文案清理。因此 README、`.env.example`、Windows 手册、项目总览必须作为**同一个错误模型**整体交付，不拆开单修——只修 Windows 手册会让同一错误留在 README 里继续误导。

### 讨论：runtime 全局事件降噪方案

- 方案 a：按 `event.type` 建白名单。
- 方案 b：`ingest` 返回 null，由 consumer 定级。
- 方案 c：保留抛错，consumer 对已知全局类型不调 `onError`。
- Codex 反驳：方案 a 不成立——`codex-event-normalizer.ts:95` 把所有未映射原生方法一律归为 `runtime.unknown`，`event.type` 没有区分力；纯结构性判定（无 `threadRef` 且无 `sessionHint`）又会把真正无关联的 `error` 一起降级，违背 2026-07-24 的排查教训。
- **最终决策 + 理由**：采用"精确白名单 + 结构条件"的组合：仅当 `payload.extensions.codex.nativeType` 命中已证实的全局通知**且**无 `threadRef`／`sessionHint` 时，视为已知全局事件而不报错；未知通知、带 thread 却找不到 binding、approval 异常一律继续抛错进 `onError`。否决纯结构性判定，因为它会吞掉未来 codex 的无关联故障。

### 讨论：Windows 两条失效验收项如何处理

- 直接删除 vs 替换为等价验证。
- **最终决策 + 理由**：替换，不删。删除会让 Windows 验收的防护覆盖度净下降。原"令牌文件存在 + ACL 正确"替换为"`data\access-token` 不存在"与"loopback 边界成立"两项。

### 讨论：旧版本清理逻辑保留多久

- Codex 建议：保留到所有带 token 的受支持旧版本退役，现在不应删。
- 用户拍板：**现在就删**，判断已无带 token 的旧版本在用。
- **最终决策 + 理由**：按用户决定执行，一并移除 `client/scripts/install.mjs:37` 与 `client/scripts/dist-win/templates/install-runtime.mjs` 的 `removeLegacyAccessToken()`。此决策与 Codex 建议相反，残留风险记入第十三节；采纳理由是用户掌握实际分发范围，Codex 的保留建议基于"存在未知旧用户"的保守假设。

### 讨论：doctor 未知参数是否纳入

- Codex 建议纳入：`README:75` 的过期 `--access-token-file` 之所以能制造"假验收"，正是因为 `doctor.ts` 的 `parseOptions` 静默忽略未知参数。
- 用户拍板：**排除**出本需求。
- **最终决策 + 理由**：按用户决定排除，记入不做项。本需求只删除 README 里那个失效参数，不改 CLI 行为。

| 风险 | 概率 | 影响 | 缓解 |

## Claude 解读

本需求的实质是让描述「本机访问边界」的文档回到与代码一致，而不是文案清理。SuDuo 曾用访问令牌控制工作台访问，该机制已被有意移除（Windows 安装器专门写了 removeLegacyAccessToken 清理遗留文件），改由 main.ts:36 强制 SUDUO_HOST 严格等于 127.0.0.1、loopback-guard 校验 loopback Host 与写请求同源 Origin 共同构成边界。代码已完成切换，文档一处未改，全仓残留 14 处失效表述。

把它按「安全契约文档」而非「可用性文档」处理，是本次分析中被 Codex 纠正的关键判断：安全审查、试点运维与发版验收都以文档为输入，描述一套不存在的令牌机制等于让审查者对着错误模型做判断。最实质的即时伤害在 docs/windows-verify.md——其中两条验收项已永远无法通过，验收人无论判「安装失败」还是「手册过期跳过」都是坏结果。

第二个问题独立且较轻：codex 启动时必然产生 configWarning 与 remoteControl/status/changed 两类本就不属于任何会话的全局事件，被 RuntimeEventIngestor 当作错误抛出。抛错本身是刻意设计（注释记录了 2026-07-24 因事件被丢弃而查不到 codex 死因的教训），问题在于每次正常启动固定产生 2 条假错误，把该机制要保护的真实信号稀释了。修法必须精确到 payload.extensions.codex.nativeType，因为 normalizer 会把所有未映射方法统一归为 runtime.unknown，event.type 没有区分力。

范围按用户拍板取 Codex 建议的整体打包：14 处文档与 loopback 自动化回归测试作为同一错误模型整体交付，runtime 降噪次之。doctor 未知参数处理经用户决定排除；旧令牌清理逻辑经用户决定立即移除。
