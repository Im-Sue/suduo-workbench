# SuDuo v3 规划：多 AI 工具与多 Agent 协作

> 一句话：本期核心是两件事——让 SuDuo 能驱动成员本机的多种 AI 编码工具（多 AI 工具接入），并让这些 Agent 在团队协作里互相接力、委派、评审（多 Agent 协作机制）。SuDuo 继续以独立部署交付，不涉及托管与收费。｜最后更新：2026-10-08（用户确认，开始实施 P1 + P2）

## 需求描述

SuDuo 现在只能驱动 Codex，一个会话里也只有一个 Agent 在干活。团队里的成员各用各的 AI 工具（Claude Code、Codex、Copilot、Gemini、Cursor……），它们之间的上下文要靠人复制粘贴：Claude 做完接口，Codex 接着做前端时要人重新交代一遍；想让另一家 Agent 帮忙评审，也要人把改动和需求再搬一遍。人成了 Agent 之间的「传话员」。

本期做两件事：

1. **多 AI 工具接入（P1）**：成员用自己电脑上已登录的任意主流编码 Agent 开工；时间线、审批、权限档位、需求工具、讨论里的共享对所有 Agent 一致。
2. **多 Agent 协作机制（P2）**：在 SuDuo 里，一个 Agent 能读到另一个 Agent 的会话、能把一部分活委派给另一个 Agent、能请另一个 Agent 评审；同一个任务可以让几家 Agent 并行各做一版再由人挑；讨论里可以同时问几个 Agent；一份项目规范对所有 Agent 生效。

团队权限、通知、交付与验收等协作闭环的其他部分列为后续方向，本期不做。

## 二、背景与目标

### 2.1 要解决的问题

AI 编码 Agent 让个人写代码快了几倍，但团队里的多个 Agent 之间是割裂的：

| 断点 | 今天的样子 | 后果 |
|---|---|---|
| **只能用一家** | SuDuo 只驱动 Codex | 用 Claude Code、Copilot、Gemini 的成员只能离开 SuDuo 干活，需求上下文与进展都断了 |
| **Agent 之间靠人传话** | Claude 做完接口，换 Codex 做前端，要人把接口文档、来龙去脉重新贴一遍 | 人成了信使；上下文在转述中走样 |
| **评审靠同一家** | 写代码的 Agent 自己检查自己 | 同一家模型的盲点重复出现；想换一家评审要手工搬运改动与需求 |
| **选不出最好的那版** | 一个任务只交给一个 Agent | 不同 Agent 各有所长，没有便宜的办法比较 |
| **规范各管各** | Codex 读 `AGENTS.md`，Claude 读 `CLAUDE.md`，Gemini 读 `GEMINI.md`…… | 同一个项目的规范要写好几份，或者只有一部分 Agent 遵守 |

行业数据：GitLab 2026-06 调查（1528 人）中 91% 的组织同时在用两个以上 AI 编码工具，85% 认为瓶颈已从写代码转到评审与验证（[来源](https://about.gitlab.com/press/releases/2026-06-23-gitlab-research-reveals-organizations-are-generating-ai-code-faster-than-they-can-control-it/)）。

### 2.2 谁在用、他们怎么工作

**目标用户**：全球的小团队与工作室，重点是东南亚工作室（越南、印尼、菲律宾、泰国、马来西亚、新加坡，常给欧美、澳洲、日本客户做项目）与欧美小团队，3–30 人。SuDuo 以独立部署交付：团队在自己的服务器上跑云端服务，成员在自己电脑上装客户端。

| 角色 | 已有习惯 | 卡在哪 | 在多 Agent 上想要什么 |
|---|---|---|---|
| **开发** | 已经在用某一两家 Agent，自己选模型、自己的订阅；在 IDE 与终端里干活 | 只能在 SuDuo 里用 Codex；换 Agent 要重新交代上下文；评审压力大 | 用自己的 Agent；让 B 接着 A 的活干；让另一家帮忙评审 |
| **技术负责人** | 评审 PR、定规范 | 规范要写好几份；AI 代码质量参差 | 一份规范所有 Agent 生效；交叉评审 |
| **项目经理 / 产品** | 在讨论里问技术问题 | 共享 Agent 只能是 Codex | 在讨论里同时问几个 Agent、比较回答 |
| **预算紧的成员**（东南亚常见） | 混用免费或便宜的 Agent（Gemini 免费额度、低价模型） | SuDuo 不支持 | 便宜的 Agent 做简单的活，贵的做难的，彼此能接力 |

两个习惯决定了产品形态：

- **开发不会换掉自己的 Agent，也不会离开 IDE。** SuDuo 不做编辑器，而是让每家 Agent 都能接上需求上下文、彼此接上对方的上下文。
- **人不应该当 Agent 之间的信使。** 上下文通过 SuDuo 在 Agent 之间流动：传的是「句柄」，Agent 按需用 SuDuo 工具取，而不是人复制粘贴摘要。

### 2.3 参照：别人怎么做

| 产品 | 多 Agent 做法 | SuDuo 借鉴 / 不同 |
|---|---|---|
| **Tutti**（开源） | 多家 Agent 统一成一套会话模型；在一个 Agent 里 @ 另一个 Agent 的历史会话、文件、产出，Agent 用 `tutti` 命令行按需取回；@ 另一个 Agent 派活（启动、等待、追加、回应审批）；房间里 @ 同事的 Agent | 借鉴「传句柄、按需取」与「委派 = 启动 + 等待 + 追加」；SuDuo 用本机 MCP 工具实现，而不是命令行（ADR-0015），并把这些挂在需求上 |
| **GitHub** | 同一个 issue 可以同时指派给 Copilot、Claude、Codex，比较各自的 PR | 借鉴「并行各做一版、人来挑」，SuDuo 在本机用独立工作目录实现 |
| **Conductor、Vibe Kanban** | 每个任务一个 git worktree，多个 Agent 并行，统一看 diff | 借鉴 worktree 隔离 |
| **Cursor Bugbot、Devin Review** | 用 AI 评审 PR | 借鉴交叉评审，但让「写的」和「评的」是不同家的 Agent |

### 2.4 定位

**SuDuo（速舵）：团队里的多个 AI Agent 一起干活的协作台。** 每个人用自己的 Agent，代码留在自己电脑上；Agent 之间能接力、委派、评审；需求、讨论、进展在团队服务器上共享；决定由人来做。

口号不变：**速度交给 AI，方向由团队掌舵。**

SuDuo 不是：IDE 或编辑器；在服务器或云端替你跑代码的 Agent；模型网关或额度转售。部署形态：独立部署（团队自己的服务器 + 成员本机客户端）。

### 2.5 设计原则

| # | 原则 | 含义 |
|---|---|---|
| 一 | **带上自己的 Agent** | 不绑定任何一家；用成员自己已有的订阅；SuDuo 不碰 AI 凭据（ADR-0016） |
| 二 | **体验一致，能力如实** | 所有 Agent 的时间线、审批、权限、工具看起来一样；某家没有的能力不显示，做不到的档位如实说明 |
| 三 | **人不当信使** | Agent 之间传句柄，按需取上下文；委派与评审的结果自动回到发起的地方 |
| 四 | **人在回路里** | 委派、评审、并行试做可以由人发起，也可以由 Agent 发起；每一步都在时间线上可见、可停，子任务的审批照常交给人（ADR-0004） |
| 五 | **代码与对话默认留在本机** | 本机 Agent 之间的协作不出本机；跨成员只传本人主动分享的内容 |
| 六 | **需求是协作的单位** | 会话、委派、评审都关联到需求；团队通过需求看到本人发布的交接包、评审报告（以及经同意的协作记录） |

**目标对齐**：

- P1：成员能用 Claude Code、Codex、Copilot CLI、Gemini CLI、Cursor CLI、OpenCode、Qwen Code、Kimi Code 等开工，体验一致。
- P2：在 SuDuo 里，Agent 能读另一个 Agent 的会话、能委派给另一个 Agent、能请另一个 Agent 评审；能让几家并行各做一版；讨论里能同时问几个 Agent；一份项目规范对所有 Agent 生效。
- 部署与收费不变：独立部署，不做托管，不涉及收费。

**模拟示例**（工作室 Lotus Labs，P1 + P2 完成后）：

```
Minh 装了 Claude Code，Tuan 只装了 Gemini CLI（免费额度），技术负责人 Duc 用 Codex。

1. Minh 在 REQ-88「导出报表按月汇总」上用 Claude Code 开工，做完了后端接口。
2. Minh 想让前端也由 AI 先搭起来，但 Claude 额度快用完了。他在同一台电脑上用 Gemini CLI
   新开一个会话，输入「接着 @REQ-88 的 Claude 会话做前端页面」。
   → Gemini 通过 SuDuo 工具读到 Claude 会话里的接口设计与最终回答，不用 Minh 再贴一遍。
3. 前端做到一半，Gemini 需要补一组接口测试，它调用 SuDuo 的「委派」工具，把这件事交给 Claude Code
   （Minh 本机的另一个 Agent）。
   → 时间线上出现「委派给 Claude Code：补充导出接口测试」卡片；Claude 那边要运行命令时，
     审批照常出现在 Minh 的审批坞里；完成后结果回到 Gemini 的会话，Gemini 继续。
4. Minh 点「请另一个 Agent 评审」，选 Codex。
   → Codex 以只读方式读这次的改动、需求与验收说明，给出 5 条意见，挂在会话与 REQ-88 上；
     Minh 点「交给原 Agent 修改」，意见回到 Gemini 会话里。
5. 另一个棘手的需求 REQ-91，Minh 选「并行试做」：Claude Code 与 Codex 各在一个独立工作目录
   （各自一个分支）里做同一件事。
   → 做完后 SuDuo 并排显示两版的改动与说明，Minh 选了 Codex 那版，另一版的工作目录在他确认后删除。
6. 项目经理 Linh 在 REQ-91 的讨论里同时 @ Duc 共享的 Codex 和 Minh 共享的 Claude Code：
   「这个导入功能有哪些风险？」→ 两个 Agent 各自在主人电脑上只读分析，两份回答并排挂在话题下。
7. Duc 在项目设置里维护了一份「项目 AI 规范」（代码风格、测试要求、禁止事项）。
   → 不管谁用哪家 Agent 开工，这份规范都通过该 Agent 自己的指令通道生效。
```

- **目标**：
  1. 主流编码 Agent 都能在 SuDuo 里用，体验一致（P1）。
  2. Agent 之间的上下文、子任务、评审由 SuDuo 传递，人不再复制粘贴（P2）。
  3. 多 Agent 协作的每一步人都看得到、管得住、停得下（P2）。
- **验收时看的指标**：非 Codex 会话的占比；每周发生的跨 Agent 引用、委派、评审次数；评审意见被采纳的比例；并行试做被采用的比例。

## 三、讨论与决策

### 讨论：多 AI 工具怎么接（已定）

- 用户：「claude code和acp同时一起做」；工具层「按照项目的长期发展、最优优化方案进行处理」。
- **决策**：Codex 与 Claude Code 走各自官方接口，其余 Agent 走 ACP；会话条目、审批、权限档位、能力集合统一；工具层改为本机 MCP 服务。见 ADR-0014、ADR-0015 与 P1 需求。

### 讨论：复用本机登录的 CLI（已定）

- 用户：「我们应该也要复用本机登录的cli为先。这个需要做什么申请吗？」
- 结论（原文与依据见 ADR-0016）：
  - Codex、Copilot CLI、Gemini CLI 等：驱动官方 CLI、由用户自己登录，**不需要申请**。
  - Claude Code：Anthropic 允许产品运行未修改的 Claude Code、由用户用自己的订阅登录，但要求产品方同意其商业条款、不碰凭据、不代付、不用其名字作产品名；同一页又说用 Agent SDK 的开发者「should use API key」。**用户拍板（D1）：只提示、不限制**——SuDuo 是工具，用户怎么用自己的 Claude 账号适用的是用户与 Anthropic 之间的条款；SuDuo 不篡改、不获取用户与 Claude Code 的敏感信息。剩余风险（Anthropic 对 Agent SDK 开发者的「should use API key」）由用户接受，配置表预留「仅 API Key」开关应对（ADR-0016 第 9、10 条）。
- **决策**：只驱动官方未修改的 CLI；登录走官方流程；SuDuo 不读、不存、不转发任何 AI 凭据（ADR-0016）。

### 讨论：Agent 的主次（推荐，见 D2）

- 东南亚（缅甸除外）与欧美都在 Anthropic、OpenAI 的支持地区内。
- **推荐**：Claude Code、Codex 为主力；ACP 首批 Copilot CLI（很多团队已为 Copilot 付费）、Gemini CLI（免费额度大）、Cursor CLI、OpenCode（可接任意模型）、Qwen Code、Kimi Code（低价模型）。Agent 面板把本机已就绪的排在前面。

### 讨论：多 Agent 协作怎么实现（推荐）

- Tutti 用「`mention://` 句柄 + Skill 说明书 + `tutti` 命令行」：Agent 在 shell 里跑命令取上下文、派活。代价是 Codex 要给每个命令开免审批规则、沙箱开网络，工具调用在时间线上只是一条命令。
- **推荐**：SuDuo 用 P1 建好的本机 MCP 服务提供协作工具，对所有 Agent 一致：
  - **读会话**：传会话句柄，Agent 用工具分层读取（最近几轮的问答 → 回合列表 → 某回合的工具细节），不注入摘要、不注入整段记录。
  - **委派**：「启动子会话 → 等待 → 追加 → 取结果」四个工具；子会话是一个普通 SuDuo 会话，用本机另一个 Agent，权限档位不高于发起会话；它的审批照常交给人。等待采用「等一段、没完就返回进度、Agent 再等」的方式，避开 MCP 调用超时。
  - **评审**：评审就是一次只读的委派，输入是改动 diff、需求与验收说明，输出是一组结构化意见。
- 所有协作都能从界面发起（不依赖 Agent 自己想到要调工具）：会话里 @ 会话、「请另一个 Agent 评审」「交给另一个 Agent 接着做」「并行试做」按钮。

### 讨论：跨成员读取会话内容（已并入 P2 的共享机制）

- 本机的 Agent 之间读会话没有边界问题：都是同一个人的电脑、同一份本机账本。
- 跨成员（Tuan 想接 Minh 的会话）时，Minh 的会话只在 Minh 的电脑上。现有边界是「私有的是代码仓库和个人会话」。
- **结论**：跨成员只传本人确认发布的内容（交接包、评审报告、会话快照），整段会话不自动上传；分级规则见 [P2 需求](多Agent协作机制-需求.md) 4.13 与 ADR-0017。协作记录（元数据）是否默认上需求、会话快照是否本期做，在 P2 需求里待拍板。

### 讨论：部署与收费（已定）

- 用户：「我们暂时面向的是独立部署，不存在收费的概念」。
- **决策**：维持独立部署（`cloud/scripts/suduo-cloud.sh` + 桌面应用 / 源码运行）；本规划不涉及托管云、订阅与收费。

## 四、功能 / 范围

### 4.1 P1 多 AI 工具接入

详见 [P1 需求](多Agent接入与本机工具服务-需求.md)。要点：

| 功能 | 说明 |
|---|---|
| Agent 面板 | 检测本机 Agent 的版本与登录状态，给出安装命令与官方登录入口；设默认 Agent |
| 开工选 Agent | 需求开工、项目会话、新会话都可选 Agent、权限档位、模型 |
| 统一会话体验 | 时间线、审批坞、中断、图片、Skill 对所有 Agent 一致；缺的能力不显示 |
| 四档权限 | 只读 / 写前询问 / 自动 / 完全访问，按各家机制落实 |
| 本机 MCP 需求工具 | 现有需求工具对所有支持 MCP 的 Agent 可用；发评论须确认，超时转草稿 |
| 讨论里共享任意 Agent | 讨论里的共享 Agent 固定只读 |

### 4.2 P2 多 Agent 协作机制

| 功能 | 做什么 | 怎么触发 | 预期结果 |
|---|---|---|---|
| **会话引用** | 在一个会话里引用本机另一个会话（任意 Agent） | 输入框 @ 会话；或 Agent 自己调用读会话工具 | Agent 按需分层读取被引用会话的问答、回合与工具细节；时间线显示「读取了 Claude Code 会话：xxx」 |
| **接着做** | 用另一个 Agent 继续一个会话的工作 | 会话菜单「交给另一个 Agent 接着做」 | 新会话（所选 Agent）自动引用原会话，首条消息由用户确认后发出 |
| **委派** | 一个 Agent 把子任务交给本机另一个 Agent | Agent 调用委派工具；或用户在输入框里写「让 Claude Code 做……」 | 时间线出现委派卡片（子 Agent、任务、状态），可展开看子会话；子会话的审批照常进审批坞并标明来源；完成后结果回到发起会话；用户可随时停止 |
| **交叉评审** | 请另一家 Agent 评审一个会话的改动 | 会话「请另一个 Agent 评审」；或 Agent 调用评审工具 | 只读子会话读取改动 diff、需求与验收说明，产出结构化意见（位置、问题、建议、严重程度），挂在会话与需求上；可一键把意见交给原 Agent 修改 |
| **并行试做** | 同一任务交给两到三家 Agent，各在独立工作目录做一版 | 开工对话框「并行试做」并选择 Agent | 每家一个 git worktree 与分支；做完后并排比较改动与说明；用户选定一版，其余工作目录在用户确认后删除 |
| **讨论里问多个 Agent** | 一条消息同时 @ 多个共享 Agent | 讨论输入框 @ 多个 Agent | 各 Agent 在各自主人电脑上只读回答，回答并排挂在话题下 |
| **交接包** | 跨成员接力 | 会话菜单「生成交接包」 | AI 起草、本人确认后发到需求；接手的人在该需求上开工时，Agent 自动读到 |
| **项目 AI 规范** | 一份规范所有 Agent 生效 | 项目设置里编辑；或仓库内 `.suduo/instructions.md` | 开工时通过每家 Agent 自己的指令通道注入；显示「本会话已应用项目规范」 |

### 4.3 后续方向（本期不做，届时另开需求）

协作闭环的其他部分，在多 Agent 机制落地后再按需排期：团队成员、角色与访客；「需要我」收件箱与外部通知（Slack、Discord、邮件）；交付记录与 GitHub PR 关联、团队验收与客户验收；需求结构（截止日期、子任务、导入）；团队值守机（共享 Agent 不随个人下线）。

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 不碰 AI 凭据 | 只驱动官方未修改的 CLI，登录走官方流程，不读不存不转发令牌与 Key（ADR-0016） |
| R2 | 委派只用本机自己的 Agent | 委派、接着做、评审、并行试做都只启动本人电脑上的 Agent，用的是本人自己的订阅；跨成员只通过讨论里的共享 Agent（只读，ADR-0009）与交接包 |
| R3 | 子会话权限不高于发起者 | 委派与评审的子会话权限档位不高于发起会话；评审固定只读 |
| R4 | 人看得到、停得下 | 每次委派、评审、并行试做都在时间线上有卡片，可展开、可停止；子会话的审批照常交给人 |
| R5 | 委派深度 1 | 只有主会话有委派工具；子会话、评审会话、试做会话都不提供，防止 Agent 之间无限转派 |
| R6 | 跨成员只传主动分享的内容 | 交接包须本人确认后发出；整段会话不上传（D3） |
| R7 | 删除工作目录须确认 | 并行试做未选中的工作目录与分支，在用户确认后才删除（ADR-0004「删除或覆盖用户文件」红线） |
| R8 | 同目录并发只告知 | 两个会话同时改同一个工作目录时提示「另一个会话也在改这里」，建议用并行试做的独立目录；不加锁、不拒绝（ADR-0004） |
| R9 | AI 起草的对外内容须人确认 | 交接包、评审意见发到需求上之前由人确认（评审意见留在本机会话里不需要） |
| R10 | 延续现有约束 | 独立部署、中英双语、无障碍检查、源码公开许可（ADR-0011） |

## Claude 解读

用户要的是「多 AI 工具 + 多 Agent 机制」：先让 SuDuo 能驱动多家 Agent，再让这些 Agent 在团队里能接力、委派、评审，人不再当 Agent 之间的传话员。部署维持独立部署，不涉及托管与收费。协作闭环的其他部分（成员权限、通知、交付验收）留作后续方向。

## 歧义点

- 「商业级的需求、业务、功能闭环」：理解为产品完整、可靠、能交给团队正式使用，**不是**商业化收费；上一版误加的托管云与收费已删除（用户 2026-10-08 纠正）。
- 「多 agent 机制」：理解为「多家 Agent 接入」加上「Agent 之间协作」（读会话、委派、评审、并行、讨论里问多个）。如只指前者，P2 可整体后移。
- D1、D2、D4 已由用户拍板；D3 并入 P2。无遗留待用户拍板项。

## 保真差异

相对原话的主动新增：

1. **P2 多 Agent 协作机制的具体形态**（会话引用、接着做、委派、交叉评审、并行试做、讨论里问多个 Agent、交接包、项目 AI 规范）——由「多 agent 机制」与 Tutti 研究推出，范围已由用户确认（D4）。
2. **委派深度 1（R5）**：不是拒绝——子会话、评审会话、试做会话不提供委派工具。可在后续放开。
3. **未选中的工作目录删除须确认（R7）**：ADR-0004「删除或覆盖用户文件」红线。

本需求不引入锁、版本校验、幂等表或 409 拒绝。
