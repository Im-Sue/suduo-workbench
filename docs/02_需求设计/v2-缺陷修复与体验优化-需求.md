## 二、背景与目标

V2 主链路（远程需求服务、本机 BFF、统一工作台、附件与实时协作、旧线清理）已跑通并经本地实机验收。继续推进部署发行（T5-3：全新机器、Docker/compose、备份恢复演练、发行放行）需要外部环境与授权，短期不具备条件；而使用中暴露的缺陷与体验问题不应被它阻塞。

- **目标 1**：把缺陷与优化从主线需求中解耦，各自独立推进。
- **目标 2**：已发现的问题有明确定位与证据，可直接进入拆分，不必重新排查。
- **目标 3**：不重复承担 `suduo-v2-requirements-workbench-001` 的 T5 部署发行范围。

## 四、功能 / 范围

### 4.1 已确认问题（Claude 于 2026-08-15 本地实机部署验收中实测发现）

#### P1 · 全局 runtime 事件走会话关联路径，持续刷 ERROR 日志

> ⚠️ **本项已移交，不在本需求范围内实施。**
> 同一问题已由 [`suduo-token-docs-runtime-noise-001`](文档漂移与runtime事件噪音-需求.md) 的 **4.4「runtime 全局事件精确降噪」** 承载，且该需求已完成需求分析（`planning`），修法更精确：按 `payload.extensions.codex.nativeType` 白名单 + 无 `threadRef`/`sessionHint` 识别，并以 R3「未知无关联 runtime 事件必须继续报错」保住 2026-07-24 的排查教训。
> 本条**仅作为现场证据保留**（实测事件类型与计数），避免两个需求重复实施同一修改。归属如需变更，须先在两份需求文档同步。

| 项 | 说明 |
|---|---|
| 现象 | 本机服务每次启动，日志出现约 6 条 `SuDuo background error: Error: runtime event cannot be associated with a suduo session: runtime.unknown ...` |
| 定位 | `client/server/src/application/runtime-event-ingestor.ts:23-32`。`sessionId` 为空即 `throw`。 |
| 实测事件类型 | 全部为 codex **全局通知**，天然不属于任何会话：`configWarning`（bubblewrap 未在 PATH）、`remoteControl/status/changed`、`rateLimits`（2 次）、`extensions`（2 次）。 |
| 问题实质 | 该 `throw` 的原意见代码注释：关联失败的事件会被 consumer 丢弃，抛错是为把事件内容留进日志，避免丢失 codex 进程退出码等线索（2026-07-24 双横幅排查的教训）。但全局事件必然关联失败、必然抛错，反而用噪音淹没了真正需要排查的信号，与设计初衷相悖。 |
| 建议方向 | 区分「全局 runtime 事件」与「会话 runtime 事件」：前者按 info/warn 记录并保留完整 payload，不再走会话关联与 error 路径；后者维持现有行为。 |
| 影响 | 不影响功能，影响可观测性与排障效率。 |

#### P2 · 增量构建残留已删除源文件的产物

| 项 | 说明 |
|---|---|
| 现象 | 源码中 `003`~`009` 迁移文件已由 T4-4 删除，但 `client/server/dist/infrastructure/db/migrations/` 仍保留全部 10 个 `.sql`，其中 7 个含 TAPD 内容。 |
| 实测 | 产物 TAPD 扫描首次命中 45 处，全部来自这些陈旧文件；执行 `pnpm clean && pnpm build` 后归零。 |
| 影响 | 迁移链已改为仅注册 `[1,2,10]`，陈旧 SQL **不会被执行**，无运行时风险；但若以增量产物发行，将违反「V2 产物与源码无 TAPD 痕迹」不变量，且易在审计中引起困惑。 |
| 建议方向 | 二选一或并行：构建脚本在编译前清理目标目录；或在发行流程中强制 `clean build` 并加校验。 |

#### P3 · 审计查询按 `resourceType` 过滤的语义待确认

| 项 | 说明 |
|---|---|
| 现象 | `GET /v2/audit?resourceType=requirement&resourceId=<id>` 仅返回 1 条 `requirement.created`；不带过滤时可见同一需求下的 `comment.created` 等记录。 |
| 待确认 | 属预期行为（严格按 `resourceType` 匹配，评论审计的 `resourceType` 为 `comment`）还是查询语义缺口——用户视角常期望「某需求相关的全部审计」。若为前者，需在接口文档中写清；若为后者，需补充按需求聚合的查询能力。 |
| 影响 | 取决于确认结果，可能为文档问题而非缺陷。 |

## Claude 解读

这个需求的价值在于**解耦**：主线需求只剩 T5-3 卡在外部环境上，若把日常缺陷修复也压在它后面，会让整条线长期停摆。独立成需求后，缺陷与优化可以立刻推进，部署验收等条件成熟再单独接上。

当前三条已确认项都不是功能性故障——P1 影响排障效率、P2 影响发行产物洁净度、P3 可能只是文档问题。其中 P1 与 `suduo-token-docs-runtime-noise-001` 4.4 是同一问题，已判归后者实施，本档只留证据；这类跨需求撞车是并行开需求时最容易长出来的漂移，归属必须写死在文档里，不能靠记忆。真正的重点仍是用户手上尚未录入的那份清单。
