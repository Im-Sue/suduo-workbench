# SuDuo V2 工作台界面重构与能力补全需求设计

> 一句话：把 T4 清理旧壳时断掉的成熟组件接回 V2 壳，用已装好的 shadcn 基座统一三页呈现层，并补上看板、需求-会话分组、MCP 三个真缺口。｜最后更新：2026-08-16

---

## 需求描述

V2 工作台的需求、会话、设置三个页面，当前都停在「功能可用、界面粗糙」的状态。用户提出三条诉求：需求页参考现代 issue tracker 的看板展示与交互；会话页做成 Codex/Claude Code 桌面应用那样的会话工具，左侧有新建会话、需求-会话列表、会话列表三段；设置页补齐一个 AI 会话工具该有的基础配置（MCP、Skills、CLI 与模型等）。

对着代码勘察后发现，这三条诉求的根因是同一件事：**T4 整体清理 `/legacy` 旧壳时，把挂在旧壳上的三个成熟组件（`LeftRail`、`SettingsPanel`、`TopBar`）连同入口一起断了线，V2 壳只重新实现了最小可用版本**。66 行的设置页和 118 行的会话页就是这么来的——代码还在仓库里，后端路由也都健在，只是没人调用。同时，项目在 ADR-0003 就装好了 Tailwind v4 + Radix + `components.json`，但三个 V2 页面几乎没用上，全是裸 `<button>/<input>/<p>` 加自定义 `v2-*` class。

因此本需求的主体是**接线与呈现层统一**，真正从零新建的只有三处：需求页看板形态、会话页需求-会话分组列表、设置页 MCP 管理。

## 二、背景与目标

**目标对齐**：SuDuo 的产品定位被重新表述为「**加了项目/需求管理协作的 AI 会话工具**」——参照系从"需求协作平台附带会话"翻转为"AI 会话工具附加需求协作层"。但经确认，这次**只影响各页面内部的形态与完整度，不改信息架构**：顶栏仍然并列切换需求／会话／设置三模式。本需求要做的是让每个页面都达到同类工具的常规水准：需求页像现代 issue tracker，会话页像 Codex 桌面端，设置页像一个正经 CLI 工具的配置面。

**模拟示例**：团队成员打开 SuDuo，在需求页看到一块按状态分列的看板，把「附件预览」卡片从"进行中"拖到"评审中"，状态即时同步给全组；切到会话页，左侧列出当前项目下所有会话，其中「附件预览」需求下挂着 3 个会话，点开最近一个，右侧是完整的消息流、审批行和改动面板；发现某个 MCP 工具没生效，切到设置页的「能力扩展」，看到 MCP 服务器列表，加一个 stdio 服务器，测试连通性通过，回到会话继续干活。全程不需要手动编辑任何配置文件。

- **背景**：
  - T4 清理旧线时按「整体删除」处理 `/legacy` 壳，附带断掉了 `LeftRail`（400 行，含会话列表、重命名、归档、状态灯）与 `SettingsPanel`（四 Tab，含模型服务、Skills 安装启停、主题缩放、诊断）的全部入口；V2 壳只补了最小版本，能力出现事实性倒退。
  - ADR-0003 已确立 Tailwind v4 + shadcn/Radix 基座并落了 `components.json`，但 `requirements-v2/` 下三个页面几乎未采用，呈现层与项目既定基调脱节。
  - 会话运行时侧其实相当完整（`Stream` 636 行的 per-turn 聚合投影、`Composer` 539 行含附件/拖拽/`/`Skills/`@`文件引用、审批流与三档策略、Drawer 的 diff 与 Monaco 预览），但被困在「打开单个会话」这一条路径里，没有会话工具应有的列表与导航。
  - MCP 是全仓唯一零实现的能力（仅在 `dev/UIKitPage.tsx` 出现过字样）。
- **目标**：
  1. 三页呈现层统一到 shadcn/Radix 基座，消除裸 HTML 与 `v2-*` 私有 class 的双轨。
  2. 需求页从纵向状态分组列表升级为横向看板，支持卡片拖拽改状态。
  3. 会话页变成「左列表 + 右会话区」的 Codex 桌面端形态，左侧含新建会话、需求-会话分组、会话列表三段。
  4. 设置页按「谁拥有这个设置」分六组重建，接回 `SettingsPanel` 已有能力并新增 MCP 管理。
  5. 全程不改动共享/私有数据边界，后端除 MCP 薄封装外零改动。

## 三、讨论与决策

### 讨论：`openai/symphony` 作为参考对象的前提

- 用户诉求：需求页 UI/UX 参考 `https://github.com/openai/symphony` 的需求展示与交互。
- 勘察事实：该仓库根目录只有 `.codex/`、`.github/`、`docs/`、`elixir/` 四个目录，加 `README.md`（1.7 KB）与 `SPEC.md`（92 KB）。`elixir/` 参考实现无 Phoenix、无 assets/templates、无 LiveView，是纯后端。Symphony 本身**不提供任何需求展示界面**——它是一份编排规范：监听外部看板（demo 中为 Linear）→ 为每个任务拉起隔离 agent run → 回交 proof of work（CI 状态、PR review、复杂度分析、演练视频）→ 人在 human review 栏验收。demo 视频里那块看板是 Linear 的。
- **最终决策 + 理由**：将参考对象明确为「Linear/Height 这类现代 issue tracker 的看板形态」，即用户实际看中的视觉与交互；**不引入 Symphony 的工作流语义**。理由见下一条。

### 讨论：需求页做「看板形态」还是「Symphony 执行记录」

两个方向的本质差异是**改「怎么显示」还是改「需求是什么」**：

| | 看板形态 | Symphony 执行记录 |
|---|---|---|
| 改动性质 | 纵向状态分组 → 横向列 + 卡片拖拽 | 需求详情长出「执行记录（run）」区块 |
| 数据层 | **零改动**，拖拽即调现有 `updateRequirement({status})` | 需新增 run 与 proof 实体、会话结束回写链路 |
| 边界影响 | 无 | **直接撞上 V2 立项约束** |
| 量级 | 前端一周内 | 跨端设计，需另开需求分析 |

- **最终决策 + 理由**：本期做**看板形态**。Symphony 方向的致命障碍不是工作量，而是 run 的证据（代码 diff、测试结果、Git 检查点）全部来自私有侧（本机工作目录与本机 SQLite），要展示在共享需求上就必须回答「哪些执行证据允许上传远程服务」——这会动摇 V2「共享的是需求，私有的是代码和对话」的立项约束。该问题不定，选项二无法开工。已记入边界，如需推进另立需求。

### 讨论：产品定位重述要不要落到信息架构

- 用户表述「本质上只是加了项目管理/需求管理协作的 AI 会话工具」，若严格落地应翻转为会话为主、需求降格为侧栏。
- **最终决策 + 理由**：**保持双模式并列**（用户确认）。顶栏仍切换需求／会话／设置，三条改进各自在自己页面内进行、互不牵动，风险最小；定位重述体现在「每页都做到同类工具的常规水准」，而非重排信息架构。

### 讨论：设置页的覆盖范围与实现路径

用户要求由 Claude 依项目定位与同类 CLI/AI 会话工具惯例给出综合意见。勘察本机 Codex CLI（0.147.0）后的判断：

- **按「谁拥有这个设置」分层，而非按 `config.toml` 结构平铺**。当前 66 行设置页的根本问题不是条目少，而是 SuDuo 自有配置、Codex CLI 配置、纯客户端偏好三个来源混在一起没有骨架。
- **Codex 侧一律走官方 CLI 子命令，不自行解析 TOML**：`codex mcp list/get/add/remove/login/logout` 已覆盖增删改查与 OAuth，`codex mcp add <NAME> (--url <URL> | -- <COMMAND>...)` 同时支持 stdio 与 streamable HTTP，另有 `--env KEY=VALUE`、`--bearer-token-env-var`。项目已用 `CODEX_HOME` 隔离自有配置目录，带该环境变量调用即可。自行读写 `config.toml` 会在 Codex 每次升版时碎裂。
- **明确不做**：`config.toml` 全量字段可视化（用户是团队成员而非 Codex 高级用户，字段随版本漂移，留「高级 → 直接编辑」入口即可）；`codex plugin` 与 marketplace（新机制，内网未必连得通，等 Skills 用顺再议）；多 profile 切换（会话级已有模型与审批 switcher，重复）。
- **安全档必须收口**：`APPROVAL_MODE_POLICIES` 的 `full` 档直接给 `sandbox: danger-full-access` + `networkAccess: true`，任何人在会话里点一下即生效。个人 CLI 如此无妨，**团队内网协作工具**应有可锁定的边界。

### 讨论：工作量重心（对初判的更正）

初次判断依 `RequirementsSessions.tsx` 仅 118 行，认为会话页最重、设置页最轻。补充勘察 `SessionRuntime.tsx`（787 行）、`Composer.tsx`（539 行）、`LeftRail.tsx`（400 行）与后端路由后**更正**：会话区的交互、弹窗、权限、附件能力早已具备，`LeftRail` 更是现成的会话侧栏，需求-会话与项目-会话两个列表接口也都在。

- **最终决策**：工作量重心为 **呈现层统一 > 接线 > 三个真缺口**。呈现层统一量大且机械、有明确样板可依，是典型的 Codex 实施活。

## 四、功能 / 范围

### 4.1 需求页 · 看板形态

| 项 | 说明 |
|----|------|
| 做什么 | 将 `RequirementsWorkbench` 的纵向状态分组列表改为横向看板：每个 `RequirementStatus` 一列，需求为卡片，卡片可拖拽跨列 |
| 谁用 | 团队全体成员 |
| 怎么触发 | 进入需求模式默认呈现；拖拽卡片改状态 |
| 前置条件 | 已登录且已选定远程项目 |
| 预期结果 | 卡片落列即调用现有 `updateRequirement({status, version})`，成功后经 SSE 广播给全组；失败（含 version 冲突）回弹原列并提示 |
| 卡片信息 | 标题、版本号、最后更新人、附件数、评论数 |
| 保留能力 | 现有的详情面板、状态切换按钮、附件上传/下载/删除、评论、审计、分页加载、SSE 实时，全部保留不减 |

### 4.2 需求页 · 详情区呈现层升级

| 项 | 说明 |
|----|------|
| 做什么 | 用 shadcn/Radix 重做详情区：评论从 `<p>作者：正文</p>` 升级为带头像/时间/Markdown 正文的结构化条目；审计从字符串数组升级为带类型图标与时间轴的记录；附件列表、上传进度、对话框统一组件化 |
| 预期结果 | 与项目 ADR-0003 既定基调一致，不再有裸 HTML 与 `v2-*` 私有 class 双轨 |

### 4.3 会话页 · 左侧三段导航

| 项 | 说明 |
|----|------|
| 做什么 | 会话模式改为「左列表 + 右会话区」的同屏形态。左侧自上而下三段：① 新建会话（项目会话 / 从需求发起）；② **需求-会话列表**（按需求分组，组内列该需求下的会话）；③ 会话列表（当前项目全部会话，含项目级会话） |
| 数据来源 | `GET /api/v2/projects/:projectId/sessions`（已有）、`GET /api/v2/requirements/:requirementId/sessions`（已有）；后端零改动 |
| 复用 | `LeftRail.tsx` 已实现会话行、状态灯、重命名、归档与能力中心分区，接回并扩展需求分组即可 |
| 预期结果 | 点击任一会话在右侧直接打开，不再需要跳转独立页面；当前会话高亮；运行中会话有状态指示 |
| 会话操作 | 重命名、归档、删除；按标题搜索/过滤 |

### 4.4 会话页 · 会话区能力保持与呈现层升级

| 项 | 说明 |
|----|------|
| 已具备（保持不减） | `Stream` 的 per-turn 聚合投影与截断头标记、审批行与 `ApprovalModeSwitcher`、`ModelSwitcher`、中断、会话重命名、`Drawer` 的 diff/文件/Monaco/表格预览、`ChangesPanel` 与 Git 检查点、`Composer` 的附件上传与拖拽、`/` 唤起 Skills、`@` 唤起文件引用（带索引缓存） |
| 做什么 | 不新增运行时能力，只将上述界面统一到 shadcn/Radix 基座，并补齐同类工具的常规细节（空态、加载态、错误态、键盘可达性） |
| 边界 | 本条**不含**任何会话协议或运行时行为变更 |

### 4.5 设置页 · 六组重建

按「谁拥有这个设置」分组：

| 分组 | 内容 | 来源 | 现状 |
|---|---|---|---|
| 账号与服务 | 远程需求服务地址、登录态、连通性测试 | SuDuo | 已有，接入即可 |
| 工作目录 | 项目 → 本机目录映射（可联动 codex `[projects].trust_level`） | SuDuo + Codex | 已有，可增强 |
| 模型 | provider / base_url / API Key（脱敏）/ model / 推理力度 / 上下文窗口 | `config.toml` | **代码已在 `SettingsPanel`，仅缺入口** |
| 能力扩展 | **MCP 服务器**（新增）、Skills 安装/启停/卸载/按 scope 分级 | `codex mcp` / `/api/v1/skills/*` | Skills 已有；MCP 全新 |
| 安全与执行 | 默认审批模式、沙箱策略、网络访问、env 透传范围 | `config.toml` + SuDuo settings | 部分有，需收口 |
| 外观与诊断 | 主题、界面缩放、doctor 自检、Codex 版本与协议漂移提示 | 客户端 + doctor | 已有，接入即可 |

### 4.6 设置页 · MCP 服务器管理（唯一后端新增）

| 项 | 说明 |
|----|------|
| 做什么 | MCP 服务器的列表、新增、编辑、删除、连通性测试与登录/登出 |
| 传输类型 | stdio（命令 + 参数 + 环境变量）与 streamable HTTP（URL + bearer token 环境变量名） |
| 实现路径 | BFF 侧薄封装 `codex mcp list/get/add/remove/login/logout`，携带 SuDuo 隔离的 `CODEX_HOME`；**不自行解析或写入 `config.toml`** |
| 谁用 | 需要给 Codex 挂外部工具的团队成员 |
| 预期结果 | 新增后可立即在会话中使用；连通失败给出可读诊断而非静默 |

### 4.7 横切 · 呈现层基座统一

| 项 | 说明 |
|----|------|
| 做什么 | 三页共用一套基于 `components/ui/` 的组件（对话框、下拉、表单、卡片、徽章、空态、骨架屏、Toast），替换当前的裸 HTML 元素与 `v2-*` 私有 class |
| 为什么放在需求里 | 这是三条诉求的公共底座；若拆到三份需求各自实施，基座会被建三遍并产生分歧 |

## 五、业务规则

| 编号 | 规则 | 说明 |
|------|------|------|
| R1 | 看板拖拽改状态必须走现有 `updateRequirement` 的 `version` 乐观并发 | 冲突时卡片回弹原列并提示刷新，不得静默覆盖他人修改 |
| R2 | 本需求不得改动远程需求服务的数据模型与接口契约 | 需求页的全部改动限于呈现与交互 |
| R3 | Codex 相关配置一律通过官方 CLI 子命令读写，禁止自行解析或写入 `config.toml` | 保证随 Codex 升版自动兼容；例外仅限只读诊断展示 |
| R4 | MCP 与模型配置的敏感值（API Key、bearer token）在前端一律脱敏显示 | 沿用现有 `apiKeyMasked` 约定；token 只存环境变量名不存值 |
| R5 | 「共享的是需求，私有的是代码和对话」边界不得松动 | 本需求不新增任何从本机向远程服务上传执行证据的通道 |
| R6 | `full`（完全访问）审批档需要具备可锁定的管理边界 | 团队内网工具不应允许任意成员一键进入 `danger-full-access` + 网络全开 |
| R7 | 会话运行时的协议与事件投影行为不得变更 | 4.4 仅做呈现层统一，不触碰 `event-projection/` 的语义 |
| R8 | 三页共用同一套 `components/ui/` 基座组件 | 不允许某一页另起炉灶 |

## 六、边界 / 不做项

- **不做 Symphony 式执行记录 / proof of work**：需求与会话执行证据的回写、run 实体、CI/测试结果展示均不在本期。该方向须先解决「哪些私有执行证据允许进入共享需求」，属独立需求。
- **不改信息架构**：顶栏仍并列切换需求／会话／设置，不翻转为会话主导。
- **不做 `config.toml` 全量字段可视化**：只保留「高级 → 直接编辑配置文件」入口。
- **不做 `codex plugin` 与 marketplace 相关能力**。
- **不做多 profile（`profiles.*`）切换**。
- **不引入前端路由库**：沿用现有按 `pathname` 分流的方式（`client/web` 架构既定边界）。
- **不恢复任何 TAPD / WorkItem / `/legacy` 旧壳能力**。
- **不新增会话运行时能力**：不动会话协议、事件投影语义与审批链路。
- **不承担部署发行范围**：属主线需求 `suduo-v2-requirements-workbench-001` 的 T5-3。

## 七、开放问题 / 假设

| 问题 / 假设 | 当前倾向 / 结论 |

## Claude 解读

这三条诉求表面是三个页面的 UI 改进，实际是**一次接线事故的修复**：T4 按「整体删除」清理 `/legacy` 旧壳时，把挂在旧壳上的 `LeftRail`（400 行完整会话侧栏）与 `SettingsPanel`（四 Tab 完整设置面）连同入口一起断了，V2 壳只补了最小可用版本。用户感受到的「会话页太简陋」「设置页什么都没有」，本质是**能力倒退而非能力缺失**——代码在仓库里，后端路由（含需求维度与项目维度两个会话列表接口）全部健在。

因此本需求真正从零新建的只有三处：需求看板、需求-会话分组列表、MCP 管理。其余是接线与呈现层统一。而呈现层统一恰恰是最大的一块——三个 V2 页面几乎没用上 ADR-0003 已装好的 Tailwind v4 + Radix 基座，全是裸 HTML 加私有 class。这块量大、机械、有明确样板，是典型的 Codex 实施活。

两个必须守住的判断：一是**参考对象的前提被纠正**——`openai/symphony` 没有任何 UI，用户看中的是 demo 里 Linear 的看板；顺着 Symphony 的真实语义走会触及「私有执行证据能否进共享需求」，那是动摇 V2 立项约束的问题，已明确列入不做项。二是**Codex 版本策略必须先于设置页开工拍板**——项目锁 0.143 而实测环境已是 0.147，设置页一旦暴露 config 字段，这个漂移就从后台哨兵告警变成用户直接可见的功能错乱。

顺带发现一个不属于本次诉求但值得提的问题：`APPROVAL_MODE_POLICIES` 的 `full` 档直接给 `danger-full-access` + 网络全开，任何成员在会话里点一下即生效。个人 CLI 这样合理，多人协作的内网工具应当有可锁边界，已作为 R6 与拆分块 F 纳入。

## 歧义点

四项已闭环拍板：参考对象改为 Linear 类看板（Symphony 无 UI，其工作流语义列入不做项）；不翻转信息架构，保持双模式并列；需求页本期做看板而非执行记录；设置页范围由用户授权 Claude 判断并已给出六组方案。

五项显式移交技术设计节点：Codex 版本策略、组件基座迁移策略、两个孤立组件接回还是重写、`RequirementsSessions` 独立页面去留、R6 安全锁定的机制形态。

无遗留待用户拍板项。

## 保真差异

原话三条诉求全部保留并各自落为功能条目：第 1 条落 4.1/4.2，第 2 条落 4.3/4.4，第 3 条落 4.5/4.6。

相对原话做了三处调整，均已在「三、讨论与决策」记录理由：① 原话指定的参考对象 `openai/symphony` 经勘察无 UI，参考对象改为其 demo 中实际出现的 Linear 类看板；② 原话「会话区域的交互、弹窗、权限、附件所有功能」经勘察绝大部分已实现，故 4.4 表述为「保持不减 + 呈现层统一」而非新建；③ 原话「本质上只是加了需求协作的 AI 会话工具」未落为信息架构翻转，依用户当场确认保持双模式并列。

新增了原话未提及的两项：4.7 组件基座统一（三条诉求的公共前置，不做会导致基座重复建设）与 R6 安全档收口（勘察中发现的既有风险，用户未提出）。
