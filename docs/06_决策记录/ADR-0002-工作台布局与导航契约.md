# ADR-0002: 工作台采用「左侧主导航 + 顶栏项目上下文」骨架，并确立四层落点契约

> 一个决策一篇,记下"为什么这么定",防止以后反复扯 / 误改
>
> **状态**(见 frontmatter `status`):accepted ｜ **拍板人**: 用户（苏业建）

---

## 一、背景

V2 主链路交付后，用户对工作台的评价是「整套 UI & 交互非常不成熟」，并提出疑问：**是不是没用成熟的 UI 框架？**

排查后发现前提不成立，真实情况分三层：

1. **框架早已就位**：`package.json` 里有 shadcn/ui(new-york) + Radix + Tailwind v4 + CVA + lucide-react + react-hot-toast，`components/ui/` 已有 15 个原语，设计令牌是「原始色阶 → 语义层 → `@theme inline`」三层结构并支持双主题。

2. **但基座从未真正生效**：`styles.css` 的控件 reset 是**无 layer 的裸规则**，而 Tailwind 工具类落在 `@layer utilities`。CSS 级联规定无 layer 声明胜过任何 layer 内声明、与选择器优先级无关，于是 `button { border:0; background:none; padding:0 }` 把 `.border` / `.bg-*` / `.px-*` 整体吃掉。实测 `<Button variant="default">` 的计算样式是 `border-width: 0px` + 背景透明——**自 pr2 引入基座起，每个 `<Button>` 都渲染成裸文字**。用全局 `.btn` 的地方正常，因为 `.btn` 同为无 layer 规则、优先级高于 utilities。

3. **导航层级缺失**：一级导航「需求 / 会话 / 设置」在顶栏是三个纯文字，其 `.active` 类**在 CSS 里根本没有任何定义**——选中态不是"弱"，是不存在。顶栏同时混装了品牌、项目上下文、一级导航、页面级操作、账号、全局刷新六类作用域不同的元素，导致「新建会话」（顶栏）与「新建需求」（页面头）两个 primary 按钮上下相邻互相打架，`↻` 与页面头「刷新」重复。

此外 `components/ui/MIGRATION.md` 早已记录 `RequirementsWorkbench.tsx` 有 18 个裸控件（全仓最多），并预约了触发时机：「下次动看板交互时一并换」。本次正是该时机。

---

## 二、决策

1. **不引入新 UI 框架**，补完既有 shadcn 基座迁移。
2. **控件 reset 必须放进 `@layer base`**；后续新增的任何全局元素选择器规则同此约束。
3. **骨架 = 顶栏（项目上下文）+ 左侧主导航 + 模块内容**：
   - 主导航为竖栏，**默认折叠成 48px 图标条**，可展开为 180px「图标 + 文案」；
   - 设置与账号菜单置于主导航底部；
   - 顶栏只保留品牌、项目切换器与项目操作菜单，设置页不显示项目上下文。
4. **不统一各模块的左右结构**，统一的是规则与几何。确立**四层落点判据**：
   > 跨页面有效 → 顶栏；模块入口 → AppNav；本页有效 → 页面头；对象间切换 → 左栏；当前对象附属 → 右栏。
5. **左右栏几何收敛为两档**：`--nav-w: 240px`（导航型左栏）、`--side-w: 300px`（细节型右栏），禁止各页面硬编码。
6. **会话页让位顺序**：<1400px 收工作区 → <1100px 收会话列表 → 主导航始终保持图标条。自动折叠**只在跨越断点时应用一次**，不在挂载时应用。
7. **需求详情改为独立路由** `/requirements/:id`；载体按「①需不需要独立 URL ②需不需要打断」两条判据选择。

规范全文见 `docs/01_架构设计/client-web-架构.md` 第七、八章。

## 三、否决的方案

| 方案 | 为什么没选 |
|------|------------|
| 引入 Ant Design / MUI / Mantine | 三者都自带完整设计语言，与既有「深色驾驶舱」令牌（10–12px 信息密集、双主题从同一语义角色派生）正面冲突。压制其默认样式的成本高于把现有页面接回既有基座；且 shadcn 是 copy-in 源码，已全在仓内，可控性最好 |
| 一级导航留在顶栏做 tab | 顶栏横向空间要与品牌、项目切换、全局状态竞争，导航每次都是被挤掉的那个（实证：它退化成了无样式纯文字）。竖栏给了导航专属位置，且新增模块只是往下排 |
| 左侧导航默认展开（约 240px） | **曾以此为由否决左侧导航方案，判断错误**。该反对建立在「左侧导航必然占用大量宽度」这一自设前提上。默认折叠 48px 后成本极低——看板六列各只少 8px，会话页四区在 1600px 下对话区仍有 1000px 以上 |
| 统一各模块的左右结构 | 四个模块的内容形态本质不同（看板要全宽、详情要主+侧、会话要三区、设置要分类+内容），强行统一必然伤害其中至少一个 |
| 详情做快速预览（Sheet / Popover） | 「快看」与「详情页」并存意味着两份布局、两套加载逻辑、两处状态同步。同一文件里拖拽路径已做乐观更新而 `changeStatus` 仍在全量重拉，成熟度已差一个量级，不宜再造第三条路径 |
| 本批引入 react-router | 属架构级依赖，需单独拍板。当前以扩展手搓路由实现详情路由，逻辑集中于 `RequirementsV2App.routeOf()`，后续切换成本低。**判据**：出现第二个带参数段的路由时即应引入——手搓路由的代价已实证发生过一次（`RequirementsV2App.tsx` 注释所载 pr8「回退时地址栏对了但右侧还停在上一个会话」） |
| 项目切换器换 Radix `Select` | gate-c 用 `getByLabel("当前远程项目").selectOption(...)`，而 `selectOption` 只对原生 `<select>` 有效，替换会直接打断该断言 |

## 四、影响

- **好处**：
  - 基座真正生效，`<Button>` 等原语恢复设计意图；裸控件由 18 降至 1。
  - 一级导航获得专属位置与明确选中态；顶栏消除两处重复入口与 primary 按钮互相打架。
  - 「某个按钮该放哪」有可引用的判据，不必每次重新讨论。
  - 看板六列同屏（原本只看得到 3.5 列，需横向滚动）；详情页可深链接、可后退。

- **代价 / 风险**：
  - 会话页在 <1100px 下压缩为「图标条 + 图标条 + 对话区」，属降级形态。
  - gate-c 的 `v2-user-path` 定位器已同步改走项目菜单，**视觉基线 `06/07-*.png` 需重出**。
  - 顶栏在设置页近乎空置（仅品牌），属可接受的一致性代价。

- **受影响**：`client/web` 外壳与三页主体、`styles.css` 令牌与 reset、`client/server/test/gate-c/steps/v2-user-path.ts`、`docs/01_架构设计/client-web-架构.md`、`components/ui/MIGRATION.md`。

## 六、决策依据(可选)

- 用户原话：「现在整套是不是没有用成熟的UI框架」「现在整套UI&交互 非常不成熟」「设置也放左侧导航栏被，可以放最下面…甚至用户信息都可以直接放左下角」。
- 实测证据（playwright + mock BFF）：
  - 修复前 `<Button variant="default">` 计算样式 `border-width: 0px`、`background: rgba(0,0,0,0)`；修复后为 `1px` + `rgb(31,92,80)`。
  - 看板 `scrollWidth == clientWidth`（六列同屏），页面无整页纵向滚动。
  - 主导航 48 ⇄ 180；会话列表在 1050px 自动折至 36、回宽恢复 240，且窄屏下用户手动 `⌘B` 仍可覆盖。
- 过程中发现并修复的缺陷：审计文案因 `ACTION_LABELS` 键与契约不符而 100% 回落（测试 fixture 用 `as` 断言喂了契约上不存在的值，全绿但零保护）；折叠态导航按钮缺 accessible name。
