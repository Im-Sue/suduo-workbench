# ADR-0004: 人机协作系统的一致性边界：系统检测与告知，人仲裁冲突

> 一个决策一篇，记下"为什么这么定"，防止以后反复扯 / 误改
>
> **状态**：accepted（用户 2026-09-05 拍板原则；Codex consult `job_2a9c64cd6158` 复核 8 个守卫点与红线清单后定稿）｜ **拍板人**：用户

---

## 一、背景

SuDuo 的定位是 **AI 协作平台**：人永远在回路里，且人掌握的上下文永远比系统多。但截至本 ADR，系统已按"无人值守多租户 SaaS"的思路积累了一批一致性机制。用户 2026-09-05 指出这个倾向并要求定义核心原则。

复盘出三条实证：

1. **一个计数器制造纯假冲突**。`requirements.version` 被附件上传/删除（`attachment-repository.ts:211/300`）与产物发布（`artifact-version-service.ts:104`）自增，同时又是 `updateRequirement` 的**必填**乐观锁（`collaboration-repository.ts:493`）。结果：PM 改描述期间有人传了个附件，PM 保存即 409。两个操作字段不相交，不存在丢失更新。
2. **机制的主要工作是修复自己**。PR3 给附件增删加 `expectedVersion` 后，多文件上传第 2 个文件必撞 409，于是又加"响应回传新版本 + 链式串行"来救。且该头为可选——缺失即不校验——任何调用方可跳过的保证不是保证。
3. **已经翻过一次车**。`AttachmentStorage.reconcile` 的"活跃即全部"不变量在启动时物理删除一切不在活跃集合内的对象；产物版本要留历史时它直接删用户数据，被 ADR-0003 推翻。一条"只报告、不删除"的 reconcile 根本不会有这个失败模式。

需求层的漂移路径：用户原话说"只需要做好版本**登记**或增量登记"，业务规则 N9 写成"显式版本**校验** + 行锁 + 幂等键"。保真差异检测到了这是 Claude 主动新增，但没有判据把它拦下。

更深一层：**AI 的失败模式是自信的错误，不是冲突。** 两个人同时改需求会察觉、会沟通；读了过期快照的模型会理直气壮写 500 行代码，两天没人发现。锁、版本校验、事务针对的是前者，对后者毫无作用，还会制造"我们有版本校验所以是一致的"的幻觉。

---

## 二、决策

1. **仲裁者是人，不是系统。** 系统的职责是让"对不齐"**可被发现、可被表达、可被恢复**；不替人判定"你不能这么做"。
2. **判据**（设计中出现任何一致性 / 并发机制时必答）：
   > 把它拿掉，最坏结果是什么？
   > - 用户看到过期 / 重复 / 乱序的东西，自己能修 → **不做**
   > - 字节没了 / 对外副作用发了两次 → **做**
3. **红线**（唯一允许系统强制拒绝或强制确认的场景），判断标准是"事后无法由人恢复"，不是"看起来危险"：
   - **不可逆的字节损失**：物理删 blob（`attachment-storage.remove` / `reconcile`）、覆盖写已有文件、清理存储对象
   - **删除或覆盖用户受管文件**：skill 目录的 `rm -rf` / `cp`（`skill-admin-service.ts:43/131/148`）、用户工作目录内文件
   - **共享服务上的 append-only 写入**：需求评论一经提交对全组可见且不可删（`:238` 的会话活动前置属此类，错误码应为 `SESSION_NOT_ACTIVE` 而非 `VERSION_CONFLICT`）——红线形态是"必须经用户显式确认"，即会话上下文闭环已定的「模型表达意图 → 用户确认 → BFF 执行」
   - **不可逆的对外副作用**：推远端仓库、发外部消息、对第三方系统写入
   - **不属红线**（可再生成或可仲裁）：观察副本、材料暂存、baseline 快照、共享 `version`、目录映射元数据、本机 session 状态
4. **检测全留，拒绝改告知。** 版本比对、sha256、审计水位线、时间戳都是本原则的执行器，保留并优先补全。变的是**响应**：不返回 409 让人"刷新重试"，而是说清**谁、何时、改了什么**并给出选项。
5. **不可变优先。** 能 append-only / 不可变的地方一律如此（产物版本、评论、基线快照）。这是"不做一致性"的前提，不是一致性机制。
6. **三态表达。** 任何查询结果只能是「确认有 / 确认无 / 查不到（附原因与恢复动作）」，禁止把失败表达为"没有"。沿用会话上下文闭环 BR-4，升格为全系统规则。
7. **前后端同一套语言。** 反馈交互语言统一需求定义了前端反馈路由表；本 ADR 定义后端的"拒绝语言"：拒绝只在红线场景出现，其余一律告知。

## 三、否决的方案

| 方案 | 为什么没选 |
|------|------------|
| 保持现状，逐案权衡 | 已证明逐案会漂：N9 有保真差异标注仍被放行。缺的是判据，不是注意力 |
| 以"弱一致性 / 最终一致性"为原则 | 轴不对。问题不在强弱，在仲裁者是谁；且会误伤不可变性、真相检测、引用保护三类必须保留的东西 |
| 拆多个 version（内容 / 附件 / 发布各一） | 存量清理的候选方案之一，属实现层，不在原则 ADR 里定 |
| 全部 last-write-wins、不检测 | 违反第 4 条。检测是人能仲裁的前提；拿掉检测等于让模型自信地错 |
| 写进 kernel 必问清单 | kernel 属 plugin 侧，CLAUDE.md 明令项目内不重定义；改为在需求 / 设计模板里加必答题 |

## 四、影响

- **好处**：设计预算从防御罕见、低成本、可见的冲突，转向防御常见、高成本、不可见的"模型基于过期事实自信地干活"；假冲突消失；多文件发布等被机制拖累的功能不再需要补丁救补丁。
- **代价 / 风险**：
  - 存量机制需分批退役，单开需求，本 ADR 不动代码。Codex 复核给出的分片与断裂面：
    - 片 1：附件增删 `expectedVersion` 头退役（独立，`attachment-repository.test` / `attachment-service.test` 的 stale-409 用例作废）
    - 片 2：附件操作不再刷需求的 `version / updated_at / updated_by`，连带附件响应回传、上传串行链与发布版本基线（`audit-project-id.test` 版本链、附件 HTTP 与 artifact-version 断言需改）
    - 片 3：需求编辑合同改告知——检测保留，提交后告知谁 / 何时 / 字段差异 + 保留 / 覆盖 / 再编辑（contracts schema、collaboration service/repository、BFF 代理、web client 与 Workbench）
    - 随手项：发布 `expectedVersion` 退役，改为逐附件 ID 存在性检查（更精确的告知：具体哪个文件没了）；幂等表保留为重放检测，同 key 异请求改报"已发生内容 + 重放 / 另发"；映射冲突与 `:658/:662` 改告知；`withMappingOperation` 串行锁与 session CAS 可随相关改动退役，不单独立片
  - 红线清单可能不完整；新增红线须以后继 ADR 补入，不得口头扩张。
  - "告知"比"拒绝"多一套 UI 与文案；由反馈路由表承接，不另起炉灶。
- **受影响**：`docs/00_项目总览.md`、`CLAUDE.md` / `AGENTS.md` 项目原则段、技术设计模板 §四（原"一定写清并发 / 幂等"改为指向本 ADR 的一处指针；需求 / 架构模板不承载判断规则）、`cloud/server` 与 `client/server` 的版本校验与幂等路径（后续需求）。

## 六、决策依据

- 用户 2026-09-05 原话："系统定位是 AI 协作平台……不是强一致性，而是知道错了、对不齐反馈给用户，用户自己决策……强一致性、版本一致性、更新一致性导致整个系统非常冗余、过度设计"
- 用户 2026-08 原话（PM 前置闭环）："我们不需要特别严格的状态域……只需要做好相关的版本登记或者增量登记即可"
- 代码证据：`collaboration-repository.ts:486-497`、`attachment-repository.ts:172-181/282-293`、`artifact-version-service.ts:60/104`
- Codex consult `job_2a9c64cd6158`（main_codex，2026-09-05）：8 个守卫点判定——1 改告知、2 退役、3 发布校验退役 + 幂等表转检测、4 退役、5 改告知、6 `:238` 保留改名 / `:658,:662` 改告知、7 退役、8 改告知；红线补"用户受管文件"与"评论 append-only 写入"两类实例；建议 `analysis_depth_hint: sc-design`，理由是告知载荷与版本域拆分跨三个应用
- Claude 复核差异：采纳全部 8 点；发布校验从我原拟的"409 改告知差异"进一步收为"逐 ID 存在性检查"（更精确）；`reconcile` 经核实与 ADR-0003 一致，Codex 所指为"仍是物理删除路径"而非缺陷
