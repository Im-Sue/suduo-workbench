# ADR-0017: 多 Agent 协作的核心模型

## 一、背景

[多 Agent 协作机制](../02_需求设计/多Agent协作机制-需求.md) 要让一台电脑上的多个 Agent 互相读会话、委派、评审、并行试做，并让跨成员接力只传本人发布的内容。这些功能都依赖同一组底层概念：会话之间是什么关系、Agent 看到什么、多个 Agent 同时跑时谁先谁后、彼此怎么隔开、什么能给团队看。如果每个功能各自处理，很快会出现「委派出去的子任务权限比父任务还大」「房间成员借共享 Agent 读到所有者的私人会话」「多个 Agent 同时跑把额度耗光」这类问题。

参照 Tutti：它有会话树（根会话、子会话、父工具调用）、按需读取的 `agent get`（对话 → 回合 → 细节）、按会话的生命周期锁与空闲回收；但它的派活走命令行、生命周期里有大量拒绝式守卫（会话忙就报错、清理不掉就拒绝启动），SuDuo 不照搬后者（ADR-0004）。

## 二、决策

1. **会话图**：会话有**角色**——主会话、子会话、评审会话、试做会话、房间任务；会话之间有**关系**——委派（父 → 子，记父回合与工具调用）、接着做（新 → 旧）、评审（评审 → 被评审）、试做组（同组）。**引用不建关系**，只记读取事件。会话列表按根会话成树。每个会话只用一家 Agent，关系把不同 Agent 的会话连起来。
2. **上下文按句柄分层、按需读取**：开工时只推「SuDuo 说明 + 会话卡」（角色、任务、需求、可用句柄）；其余由 Agent 通过本机 MCP 工具拉取。读会话分五层：概要、对话、回合列表、回合细节、改动；每层有上限与分页，大内容落 `.suduo/`（ADR-0003）。每次读取在读取方留痕。子会话**不继承**父会话对话，只拿任务说明与句柄。这一套依赖 ADR-0014 的统一条目模型：Codex 读 Claude 会话拿到的是同形条目。
3. **本机调度器**：本机服务内一个调度器管理所有 Agent 的回合——每个 Agent 并发上限、全部上限、房间任务每个共享 Agent 上限 1；超出**排队，不拒绝**；可插队、可取消；排队中的委派与试做落库，重启后恢复；停止发起回合时询问是否连带子任务；卡住只提醒、不自动终止。
4. **按角色隔离**：
   - 目录：委派默认同目录、可选独立目录；并行试做强制独立 git worktree（放在 SuDuo 数据目录下）；同目录并发写只告知、不加锁。
   - 权限：子 ≤ 父；评审与房间任务固定只读。
   - 工具：本机 MCP 按会话角色给工具集合（会话令牌即身份与角色，ADR-0015）；子会话、评审、试做没有委派工具（深度 1）；房间任务没有读会话工具。
   - 凭据与配置：各 Agent 用自己的登录，SuDuo 不在 Agent 间传递凭据（ADR-0016）；按会话注入，不改用户全局配置。
5. **共享分级、须本人发布**：本机私有（默认，会话全文、改动、委派过程、评审全文、试做各版）→ 需求共享（交接包、评审报告、会话快照，本人预览确认后发布、可撤回）→ 讨论共享（ADR-0009）→ 项目共享（项目 AI 规范，带版本）。发布前对疑似密钥提示、不拦截。**协作记录**（谁用哪个 Agent 在需求上做了什么类型的协作，只含元数据）是否默认上需求，待用户拍板；若采纳，即修订「私有的是个人会话」的边界：会话**内容**仍私有，会话**存在与状态**对项目成员可见。
6. **结构化产出走工具**：评审意见、交接包由 Agent 调用「提交」类 MCP 工具交回，参数有 schema；不解析自由文本。

## 三、否决的方案

| 方案 | 为什么没选 |
|------|------------|
| 跨会话传摘要（由 SuDuo 或 Agent 生成后注入） | 摘要会走样、丢细节；Agent 自己按需读更准，也留下读了什么的记录 |
| 子会话继承父会话的完整对话 | 各家 Agent 的历史格式不通；整段注入撑爆上下文；按需读足够 |
| 超出并发就拒绝新任务 | ADR-0004：拒绝式守卫；排队可见、可调整即可 |
| 同目录加锁，一个 Agent 写时别的等 | ADR-0004；真正需要并行时用独立 worktree |
| worktree 放在仓库目录里（如 `.suduo/worktrees`） | 构建工具、文件监听、搜索会扫到嵌套的工作目录 |
| 派活走命令行（Tutti 的 `tutti agent start/wait`） | Codex 要为每个命令开免审批规则与沙箱网络；MCP 工具在各 Agent 里是一等的结构化调用（ADR-0015） |
| 会话全文默认同步到服务器 | 违背「代码与对话默认留在本机」；跨成员只传发布的内容 |

## 四、影响

- **好处**：八个协作功能共用一套模型；权限、工具、目录、共享的边界在一个地方定义，后续加功能不会各自开口子；与 P1 的统一条目模型、本机 MCP 服务是同一地基，两期可以一起实施。
- **代价 / 风险**：本机服务多了调度器与会话图，状态更多；需要运行面板让人看清；worktree 的磁盘与依赖安装开销；协作记录若采纳，需修订总览的数据边界表述。
- **受影响**：`client/contracts`（会话角色与关系、MCP 工具契约）、`client/server`（会话服务、调度器、委派 / 评审 / 试做 / 引用 / 交接服务、MCP 工具集合）、`client/web`（会话页、会话树、运行面板、试做比较、需求「AI 协作」区）、`cloud`（需求共享对象、项目 AI 规范、协作记录）。
