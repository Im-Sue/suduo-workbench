# 需求协作附件与实时模块规格

> 维护期常青规格：说明 SuDuo V2 附件、材料快照和实时协作当前能力。最后更新：2026-08-14。

## 一、模块概述

| 项 | 说明 |
|----|------|
| 名称 | 需求协作附件与实时模块 |
| 所属部分 | requirements-service、本机 BFF、统一 Web 工作台 |
| 核心职责 | 受控附件存储/审计、localhost 流代理、会话材料同步、SSE 刷新 |
| 边界 | 不在线预览主动内容；不持久化 SSE；不替代 T4 部署切换 |
| 原则 | 浏览器只访问 localhost；附件内容不可信；事件只提示、拉取才是真相 |

```text
Web 工作台 → localhost BFF → requirements-service → PostgreSQL + 受控附件根
                         └→ 本机会话材料 staging → 原子发布不可变快照
```

## 二、对外能力

| 能力 | 调用方 | 约束 |
|------|--------|------|
| 附件列表/上传/下载/删除 | Web、本机 BFF | 详细契约见 T3 对接文档 |
| 需求附件材料快照 | 会话创建服务 | 版本、大小、SHA-256 全部复验后才建会话 |
| 鉴权 SSE | 本机 BFF、Web | 断线重连后补拉；不作事实日志 |
| 附件审计 | 需求工作台 | 上传、下载、删除均记录 actor 和时间 |

## 三、数据与文件

- PostgreSQL `attachments`：UUID、需求 ID、服务器生成 `storage_key`、展示文件名/MIME、大小、SHA-256、上传者和逻辑删除字段。
- 远端附件根：marker + `.staging/` + `objects/<前缀>/<UUID>`；根目录由单个数据库 advisory-lock owner 管理。
- 本机会话材料：正文、manifest、`attachments/<attachmentId>`；目录发布后不可变并按版本复用。

## 四、关键设计

1. 上传边读边计算 SHA-256，写入同卷 staging，fsync 后原子 rename；声明大小和实际大小都受 300 MiB 硬限制。
2. 文件名永不参与物理路径。HTML/HTM/SVG 允许保存，但下载强制 `attachment + nosniff + application/octet-stream`，UI 无预览。
3. 上传/删除事务在持 advisory lock 的同一 PostgreSQL 连接上串行执行；失锁后禁止写。关闭时先结束 SSE，再释放锁和连接池。
4. 删除先提交逻辑删除、需求版本和审计；物理清理失败可由启动 reconcile 处理。
5. SSE 不携带 Token 给浏览器；BFF 从本机设置注入远端认证，并流式转发。

## 五、业务规则

| 规则 | 说明 |
|------|------|
| 单附件大小 | 恰好 314572800 字节上限 |
| 每需求附件数 | 最多 20 个未删除附件 |
| 扩展名 | 固定 allowlist，含 html/htm/svg |
| 幂等 | UUID 操作键；相同键必须对应相同内容 |
| 一致性 | 附件列表的 `requirementVersion` 必须与详情版本一致 |
| 会话创建 | 任一附件下载、大小、摘要或版本复验失败，均不得创建会话 |
| 实时刷新 | 保留评论/编辑草稿；旧响应不得覆盖新响应；分页深度不回退 |

## 六、失败处理

| 失败 | 处理 |
|------|------|
| 上传中断/超限 | 删除 staging；返回 400/413 |
| 数据库提交结果不确定 | 先按 storage key / 幂等键读回；无法判定时保留文件供 reconcile |
| 物理删除失败 | 逻辑删除仍成功，记录 warning，后续 reconcile |
| 远端 401 | BFF 清远端会话，浏览器重新登录 |
| SSE 断线 | 1～10 秒退避重建，成功后补拉项目、列表和当前详情 |
| 服务启动/关闭失败 | 构建/监听失败释放附件 ownership；解锁失败销毁连接 |

## 七、并发与一致性

- 需求行锁和附件写事务保证数量上限、版本递增与审计一致。
- 单写 owner 使共享硬盘根的 reconcile 与正式写不会跨实例交错。
- Web 使用项目、列表、详情、评论和附件独立 sequence；组合刷新在同一错误代次并行启动。
- 本机材料先写 staging，摘要与版本复验通过后原子 rename，避免半成品会话。

## 八、维护检查清单

- [ ] 新扩展名仍按不可信下载处理。
- [ ] 新附件入口不接受客户端路径/storage key。
- [ ] 新事件消费者仍在重连后补拉事实状态。
- [ ] 变更材料 manifest 时同步验证不可变复用和失败不建会话。
- [ ] 涉及存储所有权时验证构建失败、监听失败、活动 SSE 和解锁失败路径。

## 九、FAQ

**Q：为什么 SSE 不补发丢失事件？** 事件只负责提示页面刷新，服务端当前状态才是真相；重连补拉避免维护事件日志和游标一致性。

**Q：为什么附件物理文件不用原文件名？** 原文件名是不可信展示数据，服务器生成路径可阻断目录穿越、覆盖和跨需求猜测。
