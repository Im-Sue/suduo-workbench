## 二、任务分解

### 呈现层收口与迁移清单

#### 任务概述

技术设计 D4 给组件基座迁移定了**明确出口**：不是「改到哪算哪」，而是有终点、有清单。这一片就是那个终点。

它存在的理由是前十二片各自只清自己那块 `v2-*`，没人负责回答「**全都清干净了吗**」——而 `styles.css` 里那段 39 行的 `v2-*` 定义（609–647）必须等所有使用者消失后才能删，交给任何一个页面片都会踩到别人。同理，跨片集成回归也需要一个统一的执行点。

**这一片不新增任何功能。**

#### 任务分解

1. **`v2-*` 清零核查**：全仓 TSX `grep -c 'v2-'` 必须为 0（迁移前基线：7 个文件共 77 处）。若仍有残留，定位到具体片并报告，不自行改别片的业务代码。
2. **删除 `styles.css` 的 `v2-*` 段**（609–647，39 行）。本片独占此操作。
3. **孤儿组件去留判定**：
   - `TopBar.tsx`(155)：已核实只被 `dev/UIKitPage.tsx` 引用，V2 用的是 `RequirementsTopBar`。判定为删除并同步改 demo，或明确保留为 UIKit 展示件——二选一并写明理由，不留悬空。
   - 复核 `OpenMenu.tsx` / `EnvPanel.tsx` **仍在役**（`Drawer.tsx` 4 处、`ChangesPanel.tsx`），确认前面各片没有误删。
   - 复核 `LeftRail.tsx`、`RequirementsSessions.tsx`、`SettingsPanel.tsx` 已按计划删除且无残留引用。
4. **产出剩余迁移清单**：哪些界面仍未迁到 `components/ui/` 基座、为什么本期不迁、建议何时迁。这是 D4「迁移有终点」的交付物，写进技术设计或独立清单文件。
5. **全量 gate-c 回归**：按 pr1 建的编排，把各片注册的步骤模块跑一遍全绿。
6. 基于 pr1 的 `data-testid` 基线快照复核十二片迁移中确实只增不删。
7. **核销 pr1 的断言迁移矩阵**：逐行核对每个 `replacement` 条目是否已由责任片落成；仍未核销的定位到责任片并报告，不在本片替其实现。

### 视觉回归判定（spec 要求「不接受看着没问题」）

新增 `visual-baseline.ts` 与 `visual-closeout` 步骤：三页同视口（1440×900）截图 +
sha256。逐像素比对**用 Chromium 自带的 PNG 解码**完成——不为一次收口引入 `sharp`/`pngjs` 依赖。

关键在于设了**对照组**：同一份代码跑两次，量化「运行间噪声」，否则无法判断差异是删除造成的还是本来就会变。

| 页面 | 删除前 vs 删除后 | 同代码对照（纯噪声） | 删除前 vs 对照 |
|---|---|---|---|
| 需求页 | 0.0004%（5 px） | 0.0004%（5 px） | **0.0000%** |
| 会话页 | 0.1898% | **0.2778%** | 0.2896% |
| 设置页 | 0.0198% | 0.0187% | 0.0203% |

**结论：删除带来的差异全部落在运行间噪声范围内**，会话页甚至比噪声更小；需求页存在一组
0 差异，直接证明删除本身不产生像素变化。

噪声来源也已定位而非当作黑箱：会话页 81 个差异行中，**y=0/1 两行各 1024 px 是顶部在途
请求进度条**（`getInflightCount` 驱动），其余 79 行每行仅 1–7 px，是会话文本内容差异
（两轮是独立 gate-c 运行，模型回复本就不同）。**不是布局重排。**

因此**无需具名人工验收项**——差异已全部自动比对并逐处解释。

### `styles.css` 删除的一处精细处

第 647 行的 `@media (max-width: 900px)` 里**混着 `.requirements-shell` 与
`.requirements-topbar` 两条非 `v2-` 规则**。整行删会连带删掉在役的响应式规则，
故按**规则粒度**剔除 5 条 `v2-` 规则、保留那两条。删除后该 media query 仍在：

```css
@media (max-width: 900px) { .requirements-shell { min-width: 0; }.requirements-topbar { … } }
```
