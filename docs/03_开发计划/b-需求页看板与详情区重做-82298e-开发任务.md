## 二、任务分解

### B · 需求页看板与详情区重做

#### 任务概述

需求页要从「纵向按状态分组的列表」变成「横向看板」：每个状态一列，需求是卡片，卡片能拖到别的列去改状态。参考对象是 Linear／Height 这类现代 issue tracker 的看板形态。

**这里藏着一个正确性缺陷，不只是观感问题**：现在是单一 cursor 拉一页再在前端 `filter(status)`。`limit=50` 的第一页可能全落在两列里，**其余四列显示为空但实际有数据**——用户会以为那些状态下没有需求。改看板正好把它修掉：六列各自请求、各自 cursor。

拖拽冲突的处理也要讲究。`RequirementsEventDto` 只有 `{id,type,projectId,requirementId,requirementVersion}`，**不带 from/to**，所以 SSE 到达时得靠本地 state 知道旧列、再取新状态，只搬这两列——不能再像现在这样每个事件都全量 `refresh()`。

#### 任务分解

1. 列表区改看板：六列各自 `listRequirements({status, limit:20})`（status 过滤 BFF 已白名单放行），并发上限 3、其余排队，每列独立 skeleton；切项目用 `AbortController` 掐掉在途请求。
2. 列头计数显示已加载 N；`nextCursor≠null` 时显示 `N+`——API 无 count，**不伪造总数**。
3. 拖拽用 HTML5 原生 DnD，**零新依赖**。只做跨列改 status，不做列内排序（无优先级字段，服务端 `ORDER BY updated_at DESC`，前端排序无处可存）。
4. 乐观落位；同一卡片同时只允许一个 pending mutation。
5. 提交 `updateRequirement({status, expectedVersion})`；失败（version 冲突／网络）时**不机械回弹原列**，而是 `getRequirement(id)` 取真实 status 后按真实列落位——并发下他人可能已经把它移到了第三列。
6. SSE 改两列局部搬移，按 `requirementVersion` 去重回声。
7. 卡片信息：标题、版本号、最后更新人、附件数、评论数。
8. 详情区呈现层升级：评论从 `<p>作者：正文</p>` 升级为带头像／时间／Markdown 正文的结构化条目；审计从字符串数组升级为带类型图标与时间轴的记录；附件列表、上传进度、对话框统一用 `components/ui/`。
9. 键盘可达：键盘用户走**详情区的状态按钮组**改状态，**不伪造键盘拖拽**。
10. 本文件内 `v2-*` class 清零。

#### 验收标准

- 六列各自加载，构造「首页数据集中在两列」的场景，其余列**不再假空**。
- 拖拽改状态成功后经 SSE 广播全组；只搬两列，不再全量 refresh。
- **冲突分支可复现并正确**：模拟他人已改到第三列（version 冲突 409），卡片落到真实列而非回弹原列，并给出可读提示。

- 列内虚拟滚动仅在实测出现性能问题时作为备选，本期不预先实现。

### 修掉的正确性缺陷

原实现是**单游标拉一页再前端 `filter(status)`**：`limit=50` 的第一页可能全落在两列里，**其余四列显示为空但实际有数据**——用户会以为那些状态下没有需求。改为六列各自请求、各自游标、并发上限 3。

### Codex 复核挑出的真 bug（已修并补测）

**跨列复活**：SSE 已把卡搬到新列后，一个更早发出的翻页请求才返回，里面还带着旧快照——原按列合并会把它复活回旧列，同一需求同时出现在两列。改为 `mergeColumnPageIntoBoard` 全局视角合并，只让更高版本覆盖。这种竞态在浏览器里极难复现，单测是唯一可靠抓法。

另三条同样采纳：`requirementVersion` 是**可选字段**（原代码当必填）；冲突回查可能 **404**（原无此分支，现摘除卡片并关闭详情）；**pending 不得纳入 SSE 丢弃条件**（会吞掉自己的权威回声与他人的并发更新）。

### 两处我拍板的决定

**1. 授权 `api/client.ts` 纯追加 optional `AbortSignal`。** 边界原文禁的是「pr4／pr9／pr10／pr12 **并发**追加」，而 pr4 已归档、后三片未开工、全程串行——**该禁令要防的并发危害此刻不存在**，其目的已由串行执行满足。改动为 3 处纯追加，不影响任何既有调用方。后续三片会看到该字段。

**2. 卡片「附件数、评论数」正式降级，记为验收豁免。** 查证：`RequirementDto` 无 count 字段；`RequirementsCursorPage` 只有 `{items, nextCursor}` 无 total；附件/评论均为单需求接口，6 列×20 卡 = 120 次请求。而本片边界禁改 contracts、R2 禁改远程服务——**两条取数路径都被封死**。slot2_codex 复核确认无遗漏数据源。**不做 N+1，也不用审计数据凑近似值。** 卡片改显示标题／版本号／最后更新人。补齐需另立任务，涉及远程服务契约。

### 安全取舍

评论 Markdown **刻意只做 `code`/`strong`/`em` 三种内联标记，且全部按纯文本输出**，不解析链接与图片、不产出任何 HTML。评论正文来自他人输入，跑完整 Markdown 渲染器等于把一大片攻击面接进来。已有测试断言 `[x](javascript:...)` 与 `<img onerror=...>` 均按纯文本处理。
