## 二、任务分解

### pr5 本机 BFF：产物代理、按需拉取落盘与会话材料 v3

#### 任务概述

这片做两件事，都在本机 BFF（`client/server`）里：

1. **把远端的产物能力接到本机**，并加一个远端没有的动作——「把某一版拉到我电脑上」。
2. **停掉会话起始时的材料预拉**。现在创建需求会话会先把该需求**当前全部活跃附件**下载成本机快照（`requirements-v2-service.ts:307-323`）。这意味着开发拿到的是"已发布版 + 之后随手传的未发布材料"的混合体，PM 郑重发布的那一版对交接方毫无约束力。改成只带需求信息，材料由 skill 按需拉。

这是 ADR-0003 的落地，**推翻了 T3 建立的「创建会话即预拉全量快照」模型**。

两件事放同一片，是因为它们都要改 `material-service.ts`（受控落盘的路径安全校验、文件数上限），拆开必然两片改同一个安全敏感文件；而且合起来做不会出现"已经不预拉了、但拉取能力还没上线"的能力真空。

#### 任务分解

1. **代理路由**（`http-server.ts`，`/api/v2` 下）：产物版本列表 / 发布 / 详情 / 版本文件下载四条，沿用服务端持有 token 的既有代理方式（`remote-client.ts:313-328`），**不新增认证机制**。发布代理要把 `operationKey` 与 `expectedVersion` 原样透传，幂等与版本校验都在远端生效。

2. **`remote-client.ts`** 补对应远端调用。

3. **拉取落盘**：`POST /api/v2/artifact-versions/:versionId/fetch`，把该版全部文件落到调用方指定的**映射目录下相对路径**，返回落盘清单。
   - 必须复用既有的受控落盘与路径安全校验，**不能自己写一套**——这是防目录穿越的地方。
   - 单次拉取的文件数上限用 contracts `limits.ts` 里那个「按需拉取单次文件数上限」常量。原 `material-service.ts:439` 那个写死的 20 就是干这个用的（超限抛 502），**不要删掉**——去预拉之后 skill 批量拉仍然需要它防止把本机打爆，只是把它从"快照下载全集上限"改名并挪到 fetch 路径上。

4. **manifest v3**
   - `material-service.ts:159-174` 现在**恒写** `schemaVersion: 2`。引入 `schemaVersion: 3`，语义是「requirement-only，材料未拉取」。
   - **不要复用 v1 的 `attachments: []`**：v1 的语义是"远端确实没有附件"，是一条历史断言，只在远端附件为空时才容许复用（`:252-258`）。方向是反的，复用会让"远端有附件但本次不拉"被误判成不一致。
   - **v3 分支的 `verifySnapshot` 必须停止比对远端附件集合**，否则远端一新增附件，已有 v3 快照就复用失败、每次起会话都重建。
   - `requirement.md` 不再写"无附件"字样。
   - `material_path` / `manifest_sha256` 照常写，所以 `v2_requirement_session_refs` 的 NOT NULL 约束不受影响，**client/server 的 SQLite 迁移链 `[1,2,10]` 不用动**（注意：`[1,2,10]` 是 client/server 的 SQLite 链，与远端 Postgres 的迁移链是两回事）。
   - 已有 v2 快照继续按 v2 路径校验，**不做存量迁移**。

5. **去预拉**：`requirements-v2-service.ts:307-323` 去掉 `listAttachments` 与随后的版本一致性前置校验，只带需求信息（标题、描述、状态、版本）建会话。

6. **gate-c**：会话创建路径的夹具与步骤按"不再产生附件下载请求"调整。

#### 验收标准

- [x] 创建需求会话时，**不产生任何附件下载请求**（用夹具的请求记录断言，不靠肉眼看日志）。
- [x] 新建会话写出的 manifest 是 `schemaVersion: 3`；`material_path` 与 `manifest_sha256` 均非空。
- [x] **远端新增附件后，已有 v3 快照仍可复用**，不会每次起会话都重建。
- [x] 已有 v2 快照不受影响，继续按 v2 路径校验通过。
- [x] 四条代理路由能取到远端数据；发布代理把 `operationKey` 与 `expectedVersion` 原样透传。
- [x] fetch 能把指定版本的文件落到指定相对路径，返回清单与实际落盘一致。
- [x] fetch 的路径参数尝试目录穿越（`../`、绝对路径、符号链接）一律被拒。
- [x] 一次 fetch 超过单次文件数上限时被拒绝，且错误信息说得清原因。
- [x] **已被软删的附件所属的版本文件仍能通过 fetch 拉下来**（依赖 pr4 的不过滤软删查询，这里做端到端确认）。
- [x] build / typecheck / lint 通过。

#### 边界

不改远端 requirements-service。**不放宽 `loopback-guard`**——它对写方法强制同源 `Origin` 是 CSRF 防护，skill 自己带头，不为 skill 便利开口子。不改会话运行时协议与事件投影语义。不改前端。**不规定 skill 该把文件放在哪里**——落点由调用方传参决定，SuDuo 只提供能力（这是本需求贯穿的原则：SuDuo 提供能力和数据，skill 决定怎么用）。不做项目到本机目录的一对多映射。

#### 依赖与顺序提示

依赖 **pr4**（远端端点与 DTO 必须先在）。本片会改 `http-server.ts`，**pr3 必须已经合入**，否则与附件路由的改动冲突。
