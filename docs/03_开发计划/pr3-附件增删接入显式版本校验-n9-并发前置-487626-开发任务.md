## 二、任务分解

### pr3 附件增删接入显式版本校验（N9 并发前置）

#### 任务概述

需求 N9 写着「发布与附件增删都用 `expectedVersion` + 行锁 + 幂等键处理并发」。但**代码里根本没有 `expectedVersion` 这个入参**——附件上传和删除只有行锁和版本自增（`attachment-repository.ts:175-207, 271-285`），没有任何地方拿客户端看到的版本去比对。技术设计 §3.4 已经纠正了需求文档这处对现状的错误描述，并把补齐这个缺口列为**实现前置**。

不补的话，pr4 的「发布」再严谨也是半截：PM 界面上看到 4 个附件、点了发布，中间别人删掉一个，**发布这侧**能靠 `expectedVersion` 挡住；但**反过来**——有人拿着过期界面删附件——没有任何拦截。N9 这条风险的缓解措施就是空的。

所以这片单独先做，把"改附件要带上你看到的版本号"这条链路从远端一路打通到界面。它排在 pr4 前面，既是因为「前置」这个语义，也是因为两片会改同一批文件（`attachment-repository.ts` / `attachment-service.ts` / `http-server.ts`），必须串行。

#### 任务分解

1. **远端路由收参**（`cloud/server/src/http/server.ts:363-392` 上传、`:424-441` 删除）
   - 上传路由的 body 是**原始 multipart 流**（`Body: Readable`），没有 JSON body 可以放字段，所以 `expectedVersion` 必须走**请求头**，与既有的 `Idempotency-Key`、`X-Attachment-Size` 保持同一种风格。
   - 删除是 `DELETE` 且无 body，同样走请求头。
   - **头缺失时的语义已拍板，不要再自行决定**：**缺失 = 不校验**（保持向后兼容，也符合 N1「不做严格守卫」的一贯取向）；**存在 = 严格比对，不匹配即 409**。两种情况都要有用例。

2. **仓储比对**：`attachment-repository.ts` 在既有 `SELECT … FOR UPDATE` 拿到当前 `version` 之后、任何写入之前比对；不匹配抛 409 `VERSION_CONFLICT`，事务回滚，附件集合与需求版本都不变。

3. **上传 / 删除响应返回新的 `requirementVersion`**（本片新增，理由见下）
   - 现在上传路由只返回附件 DTO（`http/server.ts:403` 的 `reply.code(201).send(result.attachment)`），**但 `result.requirementVersion` 就在手边**——同一个 handler 的 `:397-402` 已经拿它去 publish SSE 了，只是没回给调用方。
   - **为什么必须补**：每次附件增删都会 `incrementRequirementVersion`（`attachment-repository.ts:207` 上传、`:285` 删除）。pr7 的发布 skill 要连传 N 个文件，如果拿不到新版本，**第 2 个文件就会带着已经过期的 `expectedVersion` 撞 409**，多文件发布直接不可用。
   - 做法：上传与删除的响应体都带上操作后的 `requirementVersion`；BFF 原样透传；契约 DTO 同步。这是让 §3.4 真正可用的配套，不是额外功能。

4. **BFF 透传**：`client/server/src/infrastructure/http/http-server.ts:853-885, 919-924` 与 `requirements-v2/remote-client.ts:207-237, 274-278`，把头原样带到远端，**不在本机做二次判断**（本机没有权威版本，判断了只会引入第二个真相）。

5. **Web 调用方带上版本**：`client/web/src/api/client.ts:271-285, 654-718` 及其调用处，上传与删除都带上界面当前持有的 `requirement.version`；收到 409 时提示"需求已被他人改动，请刷新"并触发一次刷新。

6. **契约**：新增的错误码或请求头名称常量放进 contracts，不要在远端/BFF/前端三处各写各的字符串字面量。

#### 验收标准

- [x] **走 BFF → 远端的完整链路**验证（不是只测远端单元）：带**正确**版本的上传/删除成功，且需求版本递增。
- [x] 带**过期**版本的上传/删除返回 409，且**附件集合与需求版本都没有变化**——不能出现"半个操作"。
- [x] 不带版本头时行为与改造前一致（向后兼容）——这是已拍板语义，要有用例覆盖，不是靠读代码推断。
- [x] **上传与删除的响应体都返回操作后的 `requirementVersion`**，且 BFF 透传后前端拿得到。
- [x] **连续上传 3 个文件**：每次都用上一次响应里的新版本作为下一次的 `expectedVersion`，三次全部成功、不出现 409（这条直接决定 pr7 的多文件发布能不能用）。
- [x] 界面收到 409 后给出可理解的提示并自动刷新，不是静默失败。
- [x] 既有附件上传 / 下载 / 删除 / 幂等重试用例全部不回归。
- [x] build / typecheck / lint 通过。

#### 边界

**第 6 条的证据边界（如实记录）**：
- 已实证：服务端 409 `VERSION_CONFLICT` 经真实 BFF→远端链路可复现（第 2 条）。
- 已实证（代码级）：`uploadOne` / `deleteAttachment` 捕获 `ApiClientError` 且 `code === "VERSION_CONFLICT"` 时调用
  `reportErrorMessage("需求已被他人改动，请刷新")` 并 `refreshAttachmentSections`；
  `reportErrorMessage` → `showMessage(msg, "warning")`，与组件内其他用户可见提示同一通道，确非静默。
  多文件上传循环在失败时 `return` 中断，不会带着过期版本继续撞 409。
- 缺失：真浏览器端到端断言。gate-c 现有步骤无一覆盖需求附件 UI
  （`assistantAttachmentStep` 是聊天会话贴图，与需求附件无关）。新写该步骤需要构造
  「界面持旧版本 + 带外抬升版本」的时序，成本显著。
- **结转**：该浏览器断言交由 pr6 承担——pr6 是前端片，持有产物区与发布交互，
  本就要建立需求详情页的浏览器断言面，在那里补一条附件 409 断言是顺路的。

**额外健壮性（超出 spec 要求，评审确认）**：版本头解析用
`Number.isSafeInteger(v) && v >= 1`，畸形头抛 400 `VALIDATION_ERROR`，
不会静默变 `NaN` 而跳过校验。
