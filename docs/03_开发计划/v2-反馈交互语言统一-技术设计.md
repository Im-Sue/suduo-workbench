# SuDuo V2 反馈交互语言统一 技术设计

> 一句话：把「出了什么事」和「该怎么告诉用户」拆成两件事——前者做成一个不依赖 React 的纯函数分类器，后者做成一张可单测的路由表，三个模块按表收口 ｜ 最后更新：2026-08-24

---

## 一、设计概述

**目标对齐**：需求要的不是新组件，是「什么时候用哪个组件」的规则。所以这份设计的核心不是画 UI，而是**把一次失败拆成两个独立问题**：第一问「这到底是什么故障」（纯数据判断，和界面无关），第二问「这种故障在这个位置该怎么呈现」（查表得到，不现场发明）。两问都做成纯函数，因为现有测试全是纯函数单测，只有纯函数化才能在不加依赖的前提下被测到。组件层只是把查表结果渲染出来的薄壳。三个模块（需求 / 会话 / 设置）随后按同一张表收口，任何调用点都不再自己决定用 toast 还是弹窗。

| 项 | 说明 |
|----|------|
| 名称 | 反馈交互语言统一（前端反馈契约层） |
| 核心职责 | 失败分类 → 反馈路由 → 呈现出口；异步动作状态与并发策略；确认策略 |
| 设计原则 | 契约即代码（不是风格指南）· 纯函数内核 + 薄组件壳 · code 优先于 status · 不归因未知传输错误 · 零新依赖 |
| 需求来源 | [SuDuo V2 反馈交互语言统一需求设计](../02_需求设计/v2-反馈交互语言统一-需求.md) |
| 覆盖范围 | 反馈路由表、失败分类器、异步并发原语、loading 分工与阈值、确认策略、故障分级、空态、可访问性契约、可测试契约与 testid 基线重建 |
| 不覆盖 | 视觉主题、国际化、新依赖、服务端与 BFF 行为、离线队列重放、动效体系 |

**术语**：**反馈出口**（= 承载反馈的组件，如 toast / 行内提示 / 局部错误块）；**路由**（= 由「故障类型 + 所在位置」查表得到该用哪个出口，不含渲染）；**single-flight**（= 同一资源同时只放行一个写请求）；**latest-wins**（= 并发读取只有最后一次的结果生效）。

## 二、方案与架构

```
            ┌──────────────── 调用点（需求页 / 会话页 / 设置页）─────────────┐
            │  不再自己决定用什么反馈，只交出 (cause, context)              │
            └───────────────────────────┬───────────────────────────────────┘
                                        │
        ┌───────────────────────────────▼──────────────────────────────┐
        │ L0  classifyFailure(cause) -> Failure    【纯函数·可单测】     │
        │     只回答「这是什么故障」，不碰 React、不决定长相             │
        └───────────────────────────────┬──────────────────────────────┘
                                        │ Failure{kind,retryable,politeness,message}
        ┌───────────────────────────────▼──────────────────────────────┐
        │ L1  routeFeedback(failure, context) -> Route  【纯函数·可单测】│
        │     反馈路由表本体：kind × surface -> 出口 + 停留 + politeness  │
        └───────────────────────────────┬──────────────────────────────┘
                                        │ Route{outlet,...}
        ┌───────────────────────────────▼──────────────────────────────┐
        │ L2  反馈出口（组件薄壳）                                       │
        │  showMessage(error档)  InlineError  RegionError                │
        │  PageFailure  EmptyState  AppErrorBoundary(复用)               │
        └──────────────────────────────────────────────────────────────┘

        ┌──────────────────────────────────────────────────────────────┐
        │ L3  并发原语（两种，按读/写分工，不是一个万能 hook）            │
        │   读取: latest-wins + abort      写入: 按资源 single-flight    │
        │   reduceAsyncAction() 纯函数 ← 单测；useAsyncAction() 可选壳    │
        └──────────────────────────────────────────────────────────────┘

        ┌──────────────────────────────────────────────────────────────┐
        │ L4  确认策略  needsConfirm(动作声明) 【纯函数】 + ConfirmDialog │
        │     与 FormDialog（未保存拦截）分成两个 API，不再一身二用       │
        └──────────────────────────────────────────────────────────────┘
```

| 关键原则 | 为什么 |
|----------|--------|
| 分类与呈现分离 | 「是什么故障」全局唯一答案；「怎么呈现」随位置不同。混在一起就是今天 33 处 warning 的成因 |
| code 优先于 status | 409 一个状态码下有 **13 种**语义不同的 code（见三-D2），按 status 分类必然误判 |
| 未知不归因 | 裸 `TypeError` 无法区分本机未启动 / CORS / 超时，谎报"SuDuo 没启动"比不说更糟 |
| 契约即代码 | 路由表是常量表 + 纯函数，markdown 只是它的镜像。风格指南没有强制力 |
| 纯函数内核 | 现有测试全是纯函数单测且无组件测试工具；内核纯函数化才能零依赖被测到 |

**与现有系统的关系 / 边界**：

| 涉及模块 | 本设计如何动它 | 保留 / 不动什么 |
|----------|----------------|------------------|
| `ui/message.tsx` | 改：`MessageType` 加 `error` 档；逐条 `ariaProps` / `duration`；message 支持内嵌重试按钮 | `showMessage()` 签名向后兼容；`global-message` testid 保留 |
| `ui/format.ts` `messageOf()` | **不动**。它的职责是"取文案"，分类是新增的独立能力，不做升格 | 现有全部调用点行为不变 |
| `SessionRuntime.tsx:648` 自研 toast | 改：重新定性为 `RegionError`（持久局部错误），不并入全局 toast | 「不自动消失、留在上下文」的语义必须保留（需求 N4） |
| `AppErrorBoundary.tsx` | 只纳入统一语言（文案、可操作项、与其他错误层的关系） | 恢复机制与"清缓存重载"不重写 |
| `RequirementsWorkbench` 并发实现 | 收编为 L3 策略函数；已有 `pending Set` / `refreshSequence` 语义**原样保留** | `resolveConflictPlacement` / `shouldApplyEvent` 等已单测纯函数不动 |
| `client/server` 全部 | **不动**。分类判据全部来自前端已能拿到的 `(status, code)` | 错误码与响应结构零变更 |
| `data-testid-baseline.json` | 重建为真实快照 + 新增 drift checker（用户 2026-08-24 拍板） | — |

## 三、关键决策与取舍

- **D1 分类器独立新增，不升格 `messageOf`**：选新增 `classifyFailure`，因为 `messageOf` 的职责是把任意 cause 变成可读文案，与分类正交；升格会让一个函数兼两职，且 server 侧还有同类转换器，"全仓唯一收口点"的前提本就不成立。代价是多一个模块，收益是两者都能独立演化。

- **D2 判定顺序 = cancelled → code → status → unknown**：实测 BFF 有 **26 种字面量 `(status, code)` 组合 + 4 处运行时变量组合**，其中 409 下就有 13 种 code（`VERSION_CONFLICT` / `AUTH_INVALID` / `IDEMPOTENCY_CONFLICT` / `WORKSPACE_MAPPING_REQUIRED` / `PROJECT_HAS_ACTIVE_SESSIONS` …）。按 status 分类会把「远程地址变更需重新登录」误判成「版本冲突→自动刷新」，用户陷入刷新循环。**因为存在运行时变量组合，枚举必须可穿透**——匹配不到一律落 `unknown`，禁止穷举式 switch。

- **D3 裸 `TypeError` 只到 `transport_unknown`，不归因**：否决了「fetch reject = 本机 BFF 未启动」。CORS 失败、超时、DNS 都走同一条路径。仅当请求目标是相对 `/api/*` 时，文案可写"无法连接本机工作台"，但**不断言原因、不给"去启动 SuDuo"这种误导性动作**。

- **D4 `AbortError` / `signal.aborted` → `cancelled`，默认不产生任何反馈**：切项目、组件卸载、用户主动取消都会走到这里。把它当故障报出来是纯噪音。这是分类顺序里排第一位的原因。

- **D5 不做万能 `useAsyncAction`**：否决了原案的全仓 hook 收编。读取与写入的并发语义本就不同——读取要 latest-wins + abort，写入要按资源 single-flight，而现有看板**两种都在用**。强推单一 hook 会改坏已经正确的竞态语义。改为：抽 `reduceAsyncAction()` 纯函数与两个策略函数，`useAsyncAction()` 仅作可选 React 壳，新写的动作用它，已有手写模式只在收口该页面时顺带迁移。

- **D6 反馈路由表是代码不是文档**：需求十三章第一条风险点名"做成一份没人遵守的风格指南"。表以 `FEEDBACK_ROUTES` 常量 + `routeFeedback()` 为真相源，可单测；文档表只是镜像。

- **D7 会话终态错误不并入全局 toast**：需求 N4。它不是"第二套 toast 要被消灭"，而是**一个本就不该长成 toast 的持久错误块**。定性改了，实现才对。

- **D8 testid 用固定组件 id + 状态属性**：否决 `feedback-error` 这类随状态变化的 testid——它会让基线「只增不删」核对失真（状态一变就像是新增了一个 id）。改为固定 `global-message` / `region-error` / `page-failure` 等，状态走 `data-feedback-kind` 与 `data-feedback-result` 属性。

- **D9 零新依赖已实证，不是承诺**：react-hot-toast 2.6.0 类型定义确认原生支持 `toast.error`、逐条 `ariaProps:{role,aria-live}`、逐条 `duration`、`message` 可为任意 `ReactElement`（因此错误 toast 可内嵌重试按钮）、`toast.dismiss(id)`。**「新增 error 档」不是新增能力，是接出库里已有却没接出来的能力。** 同理否决 `toast.promise()`（会引入与 L3 重复的第三种范式）与 `@testing-library/react`（内核纯函数化后不需要）。

## 四、核心流程 / 逻辑

```
 用户动作
   │
   ├─ 破坏性？ ─是─▶ needsConfirm(不可逆×影响范围×恢复成本)
   │                    │是─▶ ConfirmDialog（危险色、默认焦点在取消）
   │                    └否─▶ 直接执行（本不该确认的就别拦）
   │
   ▼ 执行
 并发闸：写入 single-flight（pending 期间重复点击不产生第二个请求）
   │      读取 latest-wins（旧请求结果到达即丢弃）
   ▼
 pending ──▶ loading 分工（阈值见下表）
   │
   ├─ 成功 ─▶ 成功 toast(polite, 自动消失) ─▶ 局部刷新
   │
   └─ 失败 ─▶ classifyFailure(cause)          【L0 纯函数】
                  │
                  ├─ cancelled ─▶ 静默返回，不反馈
                  │
                  └─ 其余 ─▶ routeFeedback(failure, {surface, hasField, retry})  【L1 纯函数】
                                │
                                ├─ global  ─▶ 错误 toast（assertive、停留更久、可带重试）
                                ├─ field   ─▶ InlineError（贴字段、不消失）
                                ├─ region  ─▶ RegionError（留在出错位置、不消失、带重试）
                                └─ page    ─▶ PageFailure（占内容区、给明确下一步）
```

**模拟示例（端到端走查：发布产物版本，对应需求十二章）**：

| 步 | 发生什么 | 契约怎么起作用 |
|---|---|---|
| 1 | 点「发布」 | `FormDialog` 打开，焦点入内 |
| 2 | 选附件、填说明、点确认 | 写入闸 single-flight：按钮进入忙碌态（0ms，禁用+文案变化，**不是只变灰**），期间重复点击不产生第二个请求 |
| 3a | 成功 | 关闭对话框 → `showMessage(…, "success")`（polite、自动消失）→ 产物区刷新 |
| 3b | 409 `VERSION_CONFLICT` | 分类 `version_conflict` → 路由 `global` → 错误 toast（assertive）+ 自动刷新 + **保留对话框内容** |
| 3c | 400 `VALIDATION_ERROR` 且带字段 | 分类 `validation` → 路由 `field` → `InlineError` 贴在对应字段 |
| 3d | 502 `DEPENDENCY_UNAVAILABLE` | 分类 `upstream_unavailable` → 路由 `region` → `RegionError` + 重试按钮 |
| 3e | 409 `AUTH_INVALID`（远程地址变更） | **code 优先**命中 `auth_expired` → 路由 `page` → `PageFailure` + 去登录。若按 status 分类，这里会错误地走 3b 的自动刷新，用户永远刷不出来 |
| 3f | 用户中途切项目触发 abort | 分类 `cancelled` → 无任何反馈 |

**处理规则**：

| 规则 | 怎么保证 |
|------|----------|
| loading 分工与阈值 | 按钮忙碌 **0ms**（立即）；首屏区域骨架屏 **0ms**；已有内容的后台刷新轻指示 **150ms**（防闪，保留旧内容不闪空）；**1s** 显示"仍在处理"；**2s** 阻塞层——阻塞层**仅限已显式声明为排他的操作**，不是全局规则 |
| 最新请求胜出 | 读取路径带序号/`AbortSignal`，非最新序号的结果直接丢弃 |
| 卸载后不回写 | 组件卸载或资源已切换时，结果不得写回状态 |
| 重复点击去重 | 写入路径按资源 key single-flight，pending 期间不再发起 |
| 重复告警合并 | 同一告警短时间重复必须传 `MessageOptions.id`（把现有零调用的去重能力变成强制规则，防 SSE 重连风暴刷屏） |
| SSE 断连 | 判为可自愈：**不发 toast**，只更新角落持久状态标识（沿用现有 `RealtimeState`） |
| politeness | 普通 polite；`error` 档 assertive。消除现有两套 toast 的 politeness 冲突 |
| 加载区域 | `aria-busy` |
| 对话框焦点 | 打开时焦点入内、关闭归还触发元素；表单对话框有未保存内容时 Esc 不直接关 |
| 动效 | 尊重 `prefers-reduced-motion` |

## 五、测试策略

- [ ] **单元（vitest，纯函数，零新依赖）**：`classifyFailure` 覆盖 26 种字面量组合 + 运行时变量兜底 + `AbortError` + 裸 `TypeError`；`routeFeedback` 覆盖 kind × surface 全矩阵；`reduceAsyncAction` 覆盖乱序完成 / 卸载后回写 / 重复触发；`needsConfirm` 覆盖判定表
- [ ] **集成**：三个模块各自的收口链路——失败注入后断言落到正确出口
- [ ] **端到端（Gate-C）**：断言改为 `getByTestId("global-message")` + `data-feedback-kind` / `data-feedback-result` 属性，**不再以中文文案作为唯一定位**；改造现有 `steps/requirements-board.ts:202` 与 `:260` 两处
- [ ] **testid 基线重建（用户 2026-08-24 拍板）**：现基线登记 44 条但源码实有 120 条（覆盖率 37%），含 8 条指向已删除组件的死条目、3 个整体不存在的文件。第 2 片**第 0 步**先重建为真实快照（允许删死条目）+ 新增 drift checker，之后新增 testid 才登记。顺序不能反——登记在失真快照上的新条目没有校验价值

**Gate-C 实跑授权（用户 2026-08-24 拍板：授权实施方自行实跑）**：`pnpm gate:c` 会消耗真实模型调用（需 `CODEX_HOME` / `SUDUO_CODEX_HOME` 且有可用模型配置）、执行 `systemctl --user enable --now`（脚本使用自有 install-home，不触碰真实部署）、并拉起浏览器。实施方可自行运行，无需逐次确认。

## 六、数据设计

不涉及持久化。契约枚举如下（前端内部）：

| 枚举 | 值 | 说明 |
|------|----|------|
| `FailureKind` | `cancelled` / `auth_expired` / `not_configured` / `version_conflict` / `stale_state` / `validation` / `forbidden` / `not_found` / `upstream_unavailable` / `runtime_failed` / `transport_unknown` / `unknown` | 分类结果。`unknown` 是必备兜底，不可省 |
| `FeedbackOutlet` | `silent` / `global` / `field` / `region` / `page` / `boundary` | 路由结果 |
| `MessageType` | `info` / `success` / `warning` / **`error`（新增）** | `error` 档 assertive + 停留更久 + 可带重试 |
| `AsyncState` | `idle` / `pending` / `success` / `failed` | 异步动作状态机 |
| `ConcurrencyPolicy` | `latest-wins`（读） / `single-flight`（写） | 按读写分工，不混用 |

## 七、接口设计

不涉及后端接口。前端内部 API 面（签名细节由实施方定）：

| 入口 | 作用 |
|------|------|
| `classifyFailure(cause)` | 任意 cause → `Failure`。纯函数 |
| `routeFeedback(failure, context)` | `Failure` + 位置上下文 → `Route`。纯函数 |
| `reportFailure(cause, context)` | 上面两者的组合调用，页面级统一出口 |
| `showMessage(text, type, options)` | 扩展 `error` 档；签名向后兼容 |
| `needsConfirm(action)` | 破坏性判定，纯函数 |
| `reduceAsyncAction(state, event)` | 状态机转移，纯函数 |
| `useAsyncAction(fn, opts)` | 可选 React 壳，非强制 |
| `<InlineError>` `<RegionError>` `<PageFailure>` `<EmptyState>` `<ConfirmDialog>` `<FormDialog>` | 反馈出口组件 |

## 九、依赖与配置

**零新增依赖**（需求 N8），且已实证而非承诺——见 D9。

| 依赖 | 调用方式 | 说明 |
|------|----------|------|
| react-hot-toast 2.6.0 | 已有 | `toast.error` / `ariaProps` / `duration` / `ReactElement` message / `dismiss` 全部原生支持 |

## 十、迁移影响与风险

- **受影响**：`ui/message.tsx`、三个模块页面、9 处确认、8+ 处空态、Gate-C 断言与 testid 基线。**服务端零影响。**
- **打法**：契约与基础组件（第 1 片）先行；测试契约与基线重建（第 2 片）紧随且依赖第 1 片；三个页面收口（第 3～5 片）改造面天然互斥，可并行，任一片失败不阻塞其余。
- **回滚 / 恢复**：契约层为新增目录，回滚即删目录 + revert 各页面收口 commit。基线重建前先留一份旧快照副本，便于比对而非直接丢弃。

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 取消 / 传输歧义被误报为故障 | 中 | 用户看到不存在的"故障"，信任下降 | D3 + D4：`cancelled` 排在判定首位；裸 `TypeError` 只到 `transport_unknown` 且不归因 |
| 用万能 hook 改坏既有竞态语义 | 中 | 看板出现比现在更难查的乱序 bug | D5：不强推；已有手写模式原样保留，仅在收口该页面时迁移 |
| 不重建基线导致新契约继续失真 | 高 | Gate-C 断言建立在 37% 覆盖率的快照上，形同虚设 | 第 2 片第 0 步强制重建 + drift checker（已获用户拍板） |
| 设置页 28 处按"建了局部出口"就算收口 | 中 | 档位换了但路由没定，warning 变 error 而已 | 变更清单明确要求**每个动作逐项定路由**；审查时逐点核对 |
