# SuDuo V2 概览与我的工作台 技术设计

> 一句话：概览的聚合下沉到远程 SQL，工作台的聚合落在本机 BFF（因为只有它同时够得着两个库），前端两页都是只读投影 ｜ 最后更新：2026-08-24

---

## 一、设计概述

**目标对齐**：你要的是两个「看数据」的入口。**概览**回答「这个项目整体什么情况」，跟着顶栏项目走；**我的工作台**回答「我现在该干什么」，跨项目汇总，做完后取代需求看板成为默认落地页。

这份设计要解决的核心难题只有一个：**这两页的数据分别躺在两个够不着彼此的库里**。项目态势全在远程 PostgreSQL，个人待办却要把本机 SQLite 的会话、审批、目录映射和远程需求本体对起来。所以方案的骨架是——概览的聚合用 SQL 在远程一次算完；工作台的聚合放在本机 BFF，由它先查本机、再批量问远程、最后在内存里对齐。前端两页都不含业务逻辑，只做展示和跳转。

勘察中发现四处需求文档写的与代码实际不符，本设计一并更正（见三、D0）。

| 项 | 说明 |
|----|------|
| 名称 | 概览页（`/overview`）与我的工作台（`/my`） |
| 核心职责 | 对现有数据做只读聚合与跨库交叉，不产生新业务实体 |
| 设计原则 | 聚合下沉到数据所在层；跨库 join 只在 BFF；分块失败不整页塌；浏览器不直连远程 |
| 需求来源 | [SuDuo V2 概览与我的工作台需求设计](../02_需求设计/v2-概览与我的工作台-需求.md) |
| 覆盖范围 | 远程 stats 聚合与审计项目过滤、BFF 工作台聚合、两个前端页面、导航与路由调整 |
| 不覆盖 | 会话运行时改造、需求看板既有交互、角色权限、assignee、部署发行 |

## 二、方案与架构

```
浏览器 (client/web)
 ├─ /overview ──→ GET /api/v2/projects/:id/stats   ─┐
 │                GET /api/v2/audit?projectId=      ─┤ BFF 纯透传
 │                SSE /api/v2/events (既有)          ─┘
 └─ /my ───────→ GET /api/v2/my/workbench ──── BFF 自有聚合
                        │
   本机 BFF (client/server)│
   ┌────────────────────┴─────────────────────┐
   │ MyWorkbenchService                        │
   │  ①本机 SQLite: refs / sessions / approvals│
   │              / events / workspace mappings│
   │  ②远程批量: GET /v2/requirements?ids=     │
   │  ③内存对齐 → 分块 envelope                │
   └────────────────────┬─────────────────────┘
                        ↓
   远程 requirements-service (PostgreSQL)
    ├─ GET /v2/projects/:id/stats?window=&tz=   [新增]
    ├─ GET /v2/audit?projectId=                 [既有端点加参数]
    └─ GET /v2/requirements?ids=                [新增]
```

| 关键原则 | 说明 |
|----------|------|
| 聚合下沉到数据所在层 | 概览数据全在远程 → SQL 一次算完；工作台跨两库 → 只有 BFF 够得着，必须落 BFF |
| 浏览器不直连远程 | Web 只调 `/api/v2/*`，远程数据一律经 BFF（需求 R8） |
| 先截断再 join | 工作台按活跃度截断后再问远程，避免需求数增长后首屏塌 |
| 阻塞项不截断 | 待审批是「活的阻塞」，宁可多算也不能漏（见 D5） |
| 两页都是只读投影 | 不写任何业务数据，每个区块必须能点穿到处理现场 |

**与现有系统的关系 / 边界**：

| 涉及模块 | 本设计如何动它 | 保留 / 不动什么 |
|----------|----------------|------------------|
| `cloud/server` | 新增 stats / 批量取需求端点；audit 加 `projectId` 过滤；审计表加 `project_id` 列 | 现有端点语义、认证方式、游标分页契约不动 |
| `client/server` (BFF) | 新增 `/api/v2/my/workbench` 与两个透传；仓储补跨项目查询、批量 run-status | 会话运行时、审批链路、`EventBroker` 一行不动 |
| `client/web` | 新增两页 + 路由 + 导航项；`RequirementsV2App` 接线 | `RequirementsWorkbench`（1221 行）与 `SessionRuntime` 不动 |
| `client/contracts`、`cloud/contracts` | 新增 stats / workbench / 批量查询类型 | 现有 DTO 不改字段 |

## 三、关键决策与取舍

**D0 · 需求文档四处失真，本设计以代码为准更正**

| 需求文档写的 | 代码实际 | 更正 |
|---|---|---|
| 六个需求状态 | 七个（migration 003 加了 `in_refinement`） | 漏斗条按 7 档；`in_refinement` 停滞阈值定为 7 天提示 / 14 天警示——它表示 PM 正在处理，不能与被动草稿同档 |
| 审计 11 种 action | 12 种（含 `artifact_version.published`） | 时间线按 12 种渲染 |
| R3 待查证「评论/附件是否刷新 updatedAt」 | 评论**不**刷新；附件增删与产物发布**刷新**（且同时 bump version） | 停滞仍用 `updatedAt`，见 D1 |
| 第九章「不做数据迁移」 | 审计表没有 `project_id`，按项目过滤绕不开 | 用户已授权迁移，见 D3 |

- **D1 停滞口径**：选 `now - updatedAt`。附件上传与产物发布本身就是「有人在动这条需求」，算作活动合理；评论不刷新反而正确（纯讨论≠推进）。没选「改用审计里 `requirement.updated/status_changed` 的最近时间」——审计是可裁剪日志，早于审计的历史需求算不出，且要为每条需求做一次聚合。UI 文案用「最后更新」，不写「最后状态变更」。

- **D2 版本漂移判定**：选**材料内容漂移**——BFF 读本机快照的 `requirement.json`，把 `title/summary/status` 与远程当前值比对，不一致才警示，文案「需求正文或状态已变更」。没选需求 R4 原写法（`version` 差值）：勘察证实 `version` 同时被附件增删和产物发布 bump（`attachment-repository.ts:211/296`、`artifact-version-service.ts:103`），而会话材料是 v3 requirement-only 快照，压根不含附件（`material-service.ts:230`），删个附件就报「已更新 1 版」属不可行动的假警报。快照里已存着完整 `RequirementDetailDto`，比对是纯本地文件读，不增加任何远程调用。快照缺失或损坏时显示「快照不可读取」，不误报。

- **D3 审计按项目过滤**：选**加 `project_id` 列 + 回填 + 索引**（用户已授权）。没选零迁移的 join 解析：审计表只有 `(resource_type, resource_id)`，comment / attachment / artifact_version 还要多跳一层才落到项目，planner 可能退化成 hash join；而给 join 方案加「扫描上限」防护会与游标分页互斥，造成少页、空页甚至漏读。时间线和流转图是概览的核心读模型，值得一次性迁移换确定性。

- **D4 批量取需求**：选 `GET /v2/requirements?ids=a,b,c`，上限 100，BFF 分批。没选 `POST /batch`——只读查询用 POST 语义不对，且 uuid 37B×100≈3.7KB 远低于 URL 长度限制。缺失 id 静默跳过不 404（可能已删或无权），BFF 标记为「需求不可用」。

- **D5 截断策略**：待审批**全局全量**（`GROUP BY session_id` 走 `idx_approvals_pending` 部分索引，命中集本身极小）；「我的会话」取 `last_activity_at DESC` 前 20，「我在做的需求」前 50。run-status 只对「top-N 会话 ∪ 有待审批的会话」计算——后者只扩展计算集合、不扩展展示列表，所以列表长度不会跳变。没选复用逐会话的 `SessionRunStatusService`：它内部 `listRunningTurnRefs` 会扫该会话全部 turn 事件，全局用会退化成 N 次全扫，改为按 session ids 一次取事件再归约。

- **D6 「我在做」的范围**：只统计**活跃会话**关联的需求（排除 `archived`/`deleted`）。会话全部归档后该需求自动移出列表，否则「我在做的需求」会随时间退化成「我碰过的所有需求」，失去待办属性。

- **D7 第二来源**：**砍掉** `createdBy` 来源（用户澄清原意并非「我创建的需求」）。列表只由本机会话推导，但每条都从远程批量拉取完整信息（标题、所属项目、当前状态）。远程因此不需要新增「查我创建的需求」端点和 `created_by` 索引。需求文档第三章相应讨论段需同步更正。

- **D8 图表方案**：不引图表库。分段条 = flex + 百分比宽度（纯 CSS），迷你图 = 内联 SVG `<rect>`（约 30 行）。引 recharts/visx 会加 100KB+ 且要重做主题适配，收益不成比例。可访问性：分段条每段 `role="img"` + `aria-label`，迷你图配 sr-only 数据表。

- **D9 刷新载体**：概览页新建 `use-requirements-event-stream` hook 复用远程 SSE；工作台用**可见性感知轮询**（页面可见时 10s 一次 + 手动刷新）。没选「扩展 `EventBroker` 支持全局订阅 + 新增本机 SSE 端点」——`EventBroker` 只支持按 `sessionId` 订阅（`event-broker.ts:9-25`），改它等于动会话运行时核心，超出本需求边界。这是对需求 4.2.1「本机事件流变化时刷新」的降级实现，已记为后续项。

- **D10 分块降级**：单端点 + **判别联合** envelope：每块为 `{status:"ready",data}` 或 `{status:"unavailable",error:{code,message}}`，HTTP 恒 200。没选三个独立端点——待我处理与我的会话共享 run-status 计算（最贵的一块），拆开要算两遍。

## 四、核心流程 / 逻辑

```
GET /api/v2/my/workbench
  │
  ├─①本机 SQLite（一次事务内读完）
  │   refs.listAll() ──→ 过滤掉 archived/deleted 会话的 ref (D6)
  │   sessions 跨项目按 last_activity_at DESC 取 top20
  │   approvals GROUP BY session_id（全量，走部分索引）
  │   mappings.list() + 目录可用性预检
  │   批量 run-status（top20 ∪ 有待审批的会话）
  │
  ├─②本机文件：读选中 refs 的 materials/<proj>/<req>/v3-<ver>/requirement.json
  │
  ├─③远程批量：GET /v2/requirements?ids=（≤100 一批，分批并发）
  │
  └─④内存对齐 → 三块 envelope
      待我处理  = 待审批 > 失败回合 > 映射失效（R5 顺序）
      我在做    = ref∪ 去重，按最近会话活动排序，比对②③得漂移标记 (D2)
      我的会话  = top20 + 运行态 + 所属项目 + 关联需求
```

**模拟示例**：张三打开 `/my`。BFF 查到本机有 37 条 ref，其中 12 条的会话已归档→剔除，剩 25 条覆盖 9 条需求。审批表全局查出 2 条 pending，都属于会话 `s-a1`。会话按活跃度取前 20，`s-a1` 本就在内。批量 run-status 一次取回这 20 个会话的 turn 事件，归约出 `s-a1` 运行中、`s-b7` 上一回合 failed。目录映射预检发现「结算中心」根目录已不可读。远程批量取 9 条需求详情，其中「导出对账单」远程 `summary` 与快照里的不一致 → 打漂移标记；另一条只是 `version` 从 3 变 5（附件增删），三字段全同 → **不打标记**。返回：待我处理 3 条（2 待审批 + 1 失败 + 1 映射失效按 R5 排序）、我在做 9 条（1 条带漂移警示）、我的会话 20 条。远程若此刻不可达，①②仍成功，只有「我在做」块返回 `unavailable`，另两块正常展示。

| 处理规则 | 说明 |
|----------|------|
| 分块隔离 | 三块各自 try/catch，任一失败只让该块变 `unavailable`，不抛整个请求（R10） |
| 快照读失败 | `requirement.json` 缺失/损坏 → 该条标「快照不可读取」，不阻断其余条目 |
| 远程分批 | ids 超 100 分批并发，任一批失败则整块 `unavailable`（不做半块） |
| 映射预检 | 复用既有 `verifyWorkspaceMappingPath`，只读不写；**不**走 `requireValidatedLocalProject`（它遇失效映射直接抛 409，会拖垮整页） |
| 时区 | 流转量按天分桶必须由调用方传 IANA 时区名，服务端 `AT TIME ZONE`，否则 UTC 分桶让「今天」偏 8 小时 |
| 空态 | 三块各有独立空态文案，说明口径与原因（R9），本机 refs 为空时引导从需求看板拉起会话 |

## 五、测试策略

- [ ] 单元：停滞分级阈值（7 状态 × 提示/警示/不计入三档边界）

## 六、数据设计

**不新增业务实体、不新增数据表。** 唯一结构变更是审计表加项目归属列（用户已授权）。

| 实体 / 表 | 关键字段 | 说明 |
|------|----------|------|
| `audit_logs`（远程，改） | `project_id uuid NULL` | 新增列 + 回填历史 + 索引 `(project_id, created_at DESC, id DESC)` |

**回填推导**：`project` 类型取 `resource_id` 本身；`requirement` 取 `requirements.project_id`；`comment`/`attachment`/`artifact_version` 经各自的 `requirement_id` 再取。回填后置为 `NOT NULL`。三处写审计的代码（`collaboration-repository` / `attachment-repository` / `artifact-version-repository`）需同步补该字段。

**停滞分级阈值**（服务端计算，R2 + D0 更正）：

| 状态 | 提示 | 警示 |
|------|------|------|
| `in_development` / `in_testing` | 3 天 | 7 天 |
| `in_refinement` / `ready_for_development` | 7 天 | 14 天 |
| `draft` | 14 天 | 30 天 |
| `on_hold` | 30 天 | — |
| `completed` | 不计入 | 不计入 |

## 十、迁移影响与风险

- **受影响**：远程审计写入链路（三个仓储）、审计查询、需求看板路由路径、默认落地页
- **打法**：迁移与端点先行（远程可独立发布，旧客户端不受影响，新列对旧查询透明）；BFF 聚合次之；前端壳层与两页最后。前端两页组件可并行，但 `RequirementsV2App` 接线必须串行以免冲突
- **回滚 / 恢复**：迁移侧 `project_id` 为新增列，回滚只需 `DROP COLUMN`（不丢既有数据）；应用侧全部为新增端点与新增页面，`git revert` 即可，不影响既有链路

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 回填期间新写入的审计缺 `project_id` | 中 | NOT NULL 约束失败 | 先加可空列 → 补写入代码 → 回填 → 再置 NOT NULL，四步分开 |
| 工作台跨库 join 在需求数多时变慢 | 中 | 首屏变慢 | 先截断再 join；批量上限 100 分批；三块独立降级 |
| 批量 run-status 归约与逐会话服务结果不一致 | 中 | 徽标与会话页对不上 | 单测直接比对两种实现在同一数据下的输出 |
| 默认落地页改变，老 `/` 链接语义变了 | 高 | 老书签落到工作台 | 内部工具，需求已接受；`/requirements/:id` 详情语义不变 |
| 轮询替代事件流，待审批最长延迟 10s | 中 | 阻塞项感知变慢 | 页面可见才轮询 + 手动刷新；全局本机事件流记为后续需求 |
| 切换远程账号后本机 refs 仍显示为「我在做」 | 低 | 口径误解 | 本机私有数据的固有特性，在口径说明中写清 |
