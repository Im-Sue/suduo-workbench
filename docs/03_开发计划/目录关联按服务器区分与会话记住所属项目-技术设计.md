# 本机目录关联按服务器区分、会话记住所属项目 技术设计

> 一句话：新增「项目会话归属」表，项目会话在创建时写入所属项目，所有按目录反查归属的地方改为读它；关联表加服务器地址列，列表类查询只看当前服务器；解除关联不再访问远程。按 D1 乙，去掉「一个目录一个项目」的唯一约束和 409，改为在选目录时告知。｜最后更新：2026-10-06
>
> 需求：[目录关联按服务器区分与会话记住所属项目-需求](../02_需求设计/目录关联按服务器区分与会话记住所属项目-需求.md)

---

## 一、现状与改动点

关联表 `v2_project_workspace_mappings`（迁移 010）：`remote_project_id` 是主键，`local_project_id` 是 `UNIQUE`，没有服务器信息。目录本身的唯一真相是 `projects.root_path_key`。

**按目录反查项目归属的地方**（改为读归属表）：

| 位置 | 现在 | 改后 |
|------|------|------|
| `session-tools/session-context.ts` `toolContext()` / `describe()` | 先看房间任务、需求引用，最后 `mappings.getByLocalProjectId(session.projectId)` | 最后一步改为 `projectSessionRefs.getBySessionId()` |
| `session-list-repository.ts` `sessionListSql()` | `LEFT JOIN v2_project_workspace_mappings m ON m.local_project_id = s.project_id`，归属 `COALESCE(rt, r, m)` | 改为 `LEFT JOIN v2_project_session_refs ps ON ps.session_id = s.id`，归属 `COALESCE(rt, r, ps)` |
| `requirements-v2-service.ts` `listProjectSessions()` | 列出关联目录对应本机项目里的全部会话 | 列出归属为该远程项目的会话（项目会话引用 ∪ 需求会话引用），不限目录 |

**读取关联列表的地方**（加当前服务器过滤）：`settingsView().mappingCount`、`listMappings()`、`local-directory-service.ts` `mappedWorkspaceRoots()`（最近使用）、`my-workbench-service.ts` 的「目录失效」提醒。

**不用改**：`requireValidatedLocalProject()` 和 `room-agent/runner.ts`，它们按远程项目 ID 取关联。远程项目 ID 是 UUID，跨服务器不会撞。

**冲突与解除**：`saveMapping()` 里的 `getByLocalProjectId` 检查和唯一约束兜底（删掉）；`removeMapping()` 开头的 `remote.getProject()`（删掉）。

## 二、数据设计

迁移 `018_workspace_mapping_scope.sql`，由迁移运行器放在一个事务里执行。

```sql
-- 项目会话归属：建会话时写入，之后不变（与 v2_requirement_session_refs、room_task_sessions 同级）
CREATE TABLE v2_project_session_refs (
  session_id        TEXT PRIMARY KEY,
  remote_project_id TEXT NOT NULL,
  created_at        INTEGER NOT NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE RESTRICT,
  CHECK (length(remote_project_id) > 0)
) STRICT;
CREATE INDEX v2_project_session_refs_remote ON v2_project_session_refs (remote_project_id);

-- 存量补记：按当前关联，补给既不是需求会话、也不是房间任务会话的普通会话（与现在界面上的归属一致）
INSERT INTO v2_project_session_refs (session_id, remote_project_id, created_at)
SELECT s.id, m.remote_project_id, s.created_at
FROM sessions s
JOIN v2_project_workspace_mappings m ON m.local_project_id = s.project_id
WHERE s.kind = 'normal'
  AND NOT EXISTS (SELECT 1 FROM v2_requirement_session_refs r WHERE r.session_id = s.id)
  AND NOT EXISTS (SELECT 1 FROM room_task_sessions t WHERE t.session_id = s.id);

-- 关联表重建（SQLite 不能去掉列上的 UNIQUE）：加 server_origin，去掉 local_project_id 的唯一约束
CREATE TABLE v2_project_workspace_mappings_next (
  remote_project_id TEXT PRIMARY KEY,
  local_project_id  TEXT NOT NULL,
  server_origin     TEXT,             -- NULL = 升级前的存量，本机服务启动时记为当前服务器
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  last_validated_at INTEGER NOT NULL,
  FOREIGN KEY (local_project_id) REFERENCES projects(id) ON DELETE RESTRICT,
  CHECK (length(remote_project_id) > 0),
  CHECK (length(local_project_id) > 0),
  CHECK (server_origin IS NULL OR length(server_origin) > 0)
) STRICT;
INSERT INTO v2_project_workspace_mappings_next
  (remote_project_id, local_project_id, server_origin, created_at, updated_at, last_validated_at)
SELECT remote_project_id, local_project_id, NULL, created_at, updated_at, last_validated_at
FROM v2_project_workspace_mappings;
DROP TABLE v2_project_workspace_mappings;
ALTER TABLE v2_project_workspace_mappings_next RENAME TO v2_project_workspace_mappings;
CREATE INDEX v2_project_workspace_mappings_local
  ON v2_project_workspace_mappings (server_origin, local_project_id);
```

- 没有别的表引用关联表，直接重建是安全的。实施时核对迁移运行器对 `PRAGMA foreign_keys` 的处理，迁移测试里跑 `PRAGMA foreign_key_check`。
- **存量关联记服务器**：SQL 读不到服务器地址的配置文件，所以由本机服务启动时执行一次 `UPDATE … SET server_origin = @当前地址 WHERE server_origin IS NULL`（仅在已配置地址时执行）。没配置地址就不可能有关联，不用处理。
- 服务器地址取 `settings-store` 规范化后的 origin（`normalizeRequirementsServiceUrl`）。

## 三、本机服务改动

### 3.1 仓储

- `WorkspaceMappingRepository`
  - `save({ remoteProjectId, localProjectId, serverOrigin })`：upsert 时一起更新 `server_origin`。
  - `list(serverOrigin)`：只列这个服务器的关联。
  - `listByLocalProjectId(serverOrigin, localProjectId)`：给「选目录时告知」用。
  - `adoptUnscoped(serverOrigin)`：启动时补记存量。
  - 删除 `getByLocalProjectId()`，调用方都已改走归属表。
- 新增 `ProjectSessionRefRepository`（`infrastructure/db/repositories/project-session-ref-repository.ts`）：`create({ sessionId, remoteProjectId })`、`getBySessionId()`、`listSessionIdsByRemoteProjectId()`。

### 3.2 建项目会话时写归属

`SessionService.create()` 增加可选的 `remoteProjectId`。会话行建好以后、开始建 Codex 线程之前，同步写入 `v2_project_session_refs`。这样就算建线程失败，会话进入 error 状态时归属也是完整的。`RequirementsV2Service.createProjectSession()` 传入 `remoteProjectId`。需求会话、房间任务会话不走这条路，各自已有引用表。

### 3.3 `RequirementsV2Service`

- `saveMapping()`：`serverOrigin = requireConfiguredBaseUrl()` 写入关联。删掉 `byLocal` 冲突检查和 `isUniqueConstraint` 兜底（保留本机项目 `removed` 状态的既有判断）。
- `removeMapping()`：删掉开头的 `remote.getProject()`，只在 `withMappingOperation` 里删本机记录。
- `listMappings()`、`settingsView()`：按当前服务器过滤。
- `listProjectSessions()`：保留 `requireValidatedLocalProject()` 校验（错误语义不变），会话改为按归属取。

### 3.4 其他

- `SessionContextService`：依赖从 `mappings` 换成 `projectSessionRefs`。线程重建（`projectSetup`）读的是 `toolContext()` 里的项目，自动跟着改。
- `mappedWorkspaceRoots()`、`MyWorkbenchService`：传入当前服务器地址过滤。
- `server-application.ts`：装配新仓储；启动时调用 `adoptUnscoped()`。
- `LocalDirectoryService` 的目录检查结果加上 `linkedRemoteProjectIds`。按 realpath 找到本机项目（`projects.getByRootPathKey`），再取当前服务器下关联到它的远程项目 ID。
- 删除 i18n 文案 `workspace.mapping.linkedElsewhere`（中英两份）。

## 六、测试策略

| 层 | 覆盖 |
|----|------|
| 迁移 | 存量库升级：归属补记正确（普通会话补、需求会话和房间任务会话不补、没有关联的会话不补）；关联数据保留，`server_origin` 为 NULL；`foreign_key_check` 通过 |
| 仓储 | 按服务器列表；`adoptUnscoped` 只改 NULL 行；同一目录多条关联 |
| 服务 | 换服务器后旧关联不出现、不影响保存；换回去原样恢复；解除关联不访问远程（远程 mock 抛错时仍能解除）；建项目会话写入归属；改关联或换服务器后，旧会话的 `toolContext` / `describe` 仍是原项目；`listProjectSessions` 按归属列出 |
| 会话列表 | 按远程项目筛选走归属表；同一目录关联多个项目时不出现重复行 |
| 前端 | `DirectoryPicker` 的告知逻辑（自己不算、看不到的项目写「另一个项目」） |
| 端到端 | 用 stack-b 起两个需求服务（两个 PostgreSQL 库、不同端口），复现本次场景：服务器 A 的项目关联目录 D → 切到服务器 B → 给 B 的项目选 D 成功、A 的会话不出现在 B 的项目下 → 切回 A，关联和会话原样都在 |

质量门：`client/` 下 `pnpm typecheck` / `pnpm lint` / `pnpm test`。改了 `client/contracts`，只影响客户端一端。提交前用独立 subagent 复核一遍（涉及迁移，属于高影响改动）。

## 八、迁移影响与风险

- **迁移只能前进**：和此前的迁移一样，升级后不支持降回旧版本客户端；发行说明里注明。
- **换过服务器又没清理的存量**：旧关联会被记成当前服务器的，列表里能看到，可以解除；它不挡路。
- **同一远程项目在两个地址写法下**（`localhost` 和 `127.0.0.1`）：关联主键是远程项目 ID，后保存的会把这条关联的服务器改成新地址。属于需求第六节「不识别同一服务器的不同写法」，接受。

## 九、实施记录

2026-10-06，分支 `fix/workspace-mapping-scope`（工作树 `Dev/tmp/suduo/wt-mapping`，基于 `origin/main` fcc02cf），一片交付。

**与设计的差异**

- `pathKey` 原本在 `project-service.ts`、`requirements-v2-service.ts` 各有一份；目录检查要用，导出了 `project-service.ts` 那份。
- `SessionService` 新增的依赖放在构造参数末尾（与 `requirementSessionRefs` 同样可空）；建项目会话时会话行和归属在同一事务里写，早于建 Codex 线程。
- `listMappings` / 「最近使用」/ 我的工作 / 目录检查都经 `server-application.ts` 里的 `currentServerMappings` 取当前服务器的关联；服务器地址配置文件读不了时当作未配置（列表为空），不拖垮这些页面。
- 测试工具 `addWorkspaceMapping`（`http.test.ts`）的比较键改为真实路径：macOS 临时目录 `/var` 指向 `/private/var`，原先 3 条开会话的用例在本机一直失败，现在能跑通并覆盖新断言。

**独立复核后的修正**（独立 subagent 只读复核：迁移安全、没有引入新的拒绝式守卫）

- 【中】会话页「当前项目跟到打开的会话所属项目」原先按目录反查（`SessionsPage.tsx`），共用目录或换过服务器时会跟错项目：改为读会话上下文（`GET /api/v1/sessions/:id/context` 的 `remoteProjectId`）。
- 【低】我的工作「目录失效」提醒、修复对话框、会话列表的兜底行显示的是本机项目名（第一个关联该目录的项目名）：改为先按远程项目 ID 取远程项目名（`useRemoteProjectName`），取不到再用本机名。
- 【低】「也关联给了」里多个看不到名字的项目会重复「另一个项目」：合并成「另外 N 个项目」。
- 【低】启动时没配地址的话存量关联认领不到服务器：改服务器地址（`updateSettings`）时也认领一次。
- 【低】保存关联时先读服务器地址再查项目：中途换了地址，查项目会落到新服务器而查不到，不会把旧服务器的项目记到新服务器名下。
- 去掉 `requirements-v2-service.ts` 里重复的 `pathKey`。
- 补测试：会话行与归属同一事务（写归属失败时会话行回滚）、按所属项目列会话（不限目录、排除房间任务与已移除的本机项目、按视图过滤）、改地址时认领存量关联、提示文案中英。

**已知边界（复核提出，接受）**

- 通用接口 `POST /api/v1/projects/:id/sessions` 建的会话不写归属，属于「不属于任何项目」。前端和 gate 脚本都不用这个接口。
- 需求会话建线程失败时需求引用不写入（沿用现状），这类出错会话不属于任何项目；而升级前同类会话被迁移按当时的关联补记成了项目会话。只影响出错状态的会话。
- 会话页「跟到所属项目」只在真实浏览器里验证过（现有前端测试把会话页整个换成了桩）。

**验证**

- `client/`：`pnpm typecheck`、`pnpm lint` 通过。`pnpm test`：contracts 12、desktop 33、web 874 全过；server 664 条中 659 过，失败的 5 条（`git-service.test.ts` 4 条、`workspace-i18n-en.test.ts` 自动存档 1 条）在未改动的 `origin/main` 上同样失败，是本机 macOS 临时目录路径的老问题，与本次无关。
- 端到端：起两个临时需求服务（独立 PostgreSQL 库）和用新代码的本机服务，按接口走 19 项全部通过，包括：同一目录关联给两个项目；会话只属于开它的项目；换到服务器 B 后看不到 A 的关联与最近使用，B 的新项目能关联同一目录（本次报错的场景）；A 的旧会话仍属 A 的项目；在 B 上解除 A 的关联不访问服务器；换回 A 原样恢复。
- 界面：无头浏览器打开设置 → 工作区 → 更改目录，提示「这个目录也关联给了「前端」，两个项目的会话都会在这里运行」显示在目录状态下方，不影响保存。
- 真实旧库升级：用 2026-10-06 清理前备份的本机库副本（v16，24 个会话、2 条关联）跑迁移，依次执行 17、18；7 个普通会话按当时的关联补记归属（与按规则算出的应补数一致），关联保留且服务器待认领，`foreign_key_check` 与 `integrity_check` 通过。
