# SuDuo V2 工作台界面重构与能力补全 技术设计

> 一句话：三页仍并列，但每页都补到同类工具水准；Codex 配置改走有 schema 的官方接口。｜最后更新：2026-08-16
>
> **无独立 status** —— 跟随 `requirement_id` 指向的需求。

---

## 一、设计概述

**目标对齐**：你要的是让 SuDuo 三个页面都"像个正经工具"。需求页从纵向列表变成能拖卡片的看板；会话页变成左边有会话列表、右边是对话区的样子（现在左边只显示"当前会话"一行）；设置页把已经写好但断了线的模型、Skills 面板接回来，再补上 MCP。顶栏仍然是需求／会话／设置三个平行页，**不翻转成会话为主**——但三页各自做深。这份设计讲四件事：这些界面怎么搭、Codex 的配置从哪条路写、看板的数据怎么取才不会显示假空列、以及怎么在不碰会话运行时协议的前提下做完。

一句话概括本期性质：**这不是新建功能，是把 T4 清理旧壳时断掉的线接回来，顺带补三个真缺口（看板、需求-会话分组、MCP）。**

| 项 | 说明 |
|----|------|
| 名称 | V2 工作台界面重构与能力补全 |
| 核心职责 | 三页呈现层补齐 + 孤儿组件接回 + MCP 管理 + 审批档可收口 |
| 设计原则 | 后端零改动（MCP 除外）；运行时协议不动；配置只走官方 schema 化接口；迁移有终点有清单 |
| 需求来源 | [需求设计](../02_需求设计/v2-工作台界面重构与能力补全-需求.md) |
| 覆盖范围 | `client/web` 三页 + `client/server` MCP 薄封装 + 审批档服务端 clamp |
| 不覆盖 | 会话协议与事件投影语义、远程需求服务、部署发行、Codex 版本升级 |

**Codex 能力一律接官方口子**（用户 2026-08-16 定的架构原则）。选 Codex CLI 而不是自建 LLM API harness，就是为了用它自带的机制——官方机制最完整最强。CLI 子命令和 app-server RPC 都是 `codex` 这一个二进制给的官方口子，**不预设谁优先，按每件事官方给了哪个就用哪个**：

```
                        ┌─ MCP 增删 ─────→ codex mcp add/remove        CLI
                        ├─ MCP 状态/连通 ─→ ListMcpServerStatus         RPC
client/server             ├─ MCP OAuth ────→ McpServerOauthLogin         RPC
  mcp-service.ts   ─────┼─ MCP 刷新 ─────→ McpServerRefresh            RPC
                        └─ 敏感 env ─────→ ConfigBatchWrite            RPC
                                            写 env_vars（只存变量名）

  model-provider   ─────┬─ 读当前配置 ────→ config/read                RPC
  -service.ts           │                    includeLayers:true（要来源）
  （本期迁到官方口子）    ├─ 整表单一次写 ──→ config/batchWrite          RPC
                        │                    + reloadUserConfig:true
                        │                    + expectedVersion
                        ├─ 写 API Key ───→ codex login --with-api-key   CLI(stdin)
                        ├─ 登录态 ───────→ codex login status          CLI
                        └─ 可用模型清单 ──→ model/list                  RPC
                                            （只能读已保存配置，见 D3-b）

  doctor-service.ts ────── Codex 侧体检 ──→ codex doctor --json         CLI
                                            checks 是**对象**不是数组

  codex-global-state.ts ─┬─ configWarning ─┐
  [NEW]                  ├─ skills/changed  │ threadId 为 null 的全局通知
  Codex 全局状态投影      ├─ mcpServerStatus │ 现在会被 ingestor 丢掉
                         └─ /Updated 等     ┘ → 内存投影 + 设置页 SSE
```

> **`modelProvider/capabilities/read` 不能用来取上下文窗口** —— 0.143 实测只返回 `imageGeneration`／`namespaceTools`／`webSearch`，`model/list` 也没有 context-window 字段。v1.2 写"先读官方能力"是**我的事实错误**（凭方法名推断）。上下文窗口只能保留用户显式输入。

被这条原则判掉的现有实现：正则改写 `config.toml`、直写 `auth.json`、自己 `fetch` provider 的 `/models`、自己 regex 解析 `config.toml` 判断模型配置是否可用——上述四处全部有官方替代（见 §三 D3）。

| 关键原则 | 说明 |
|----------|------|
| 三模式并列 | 顶栏切换不变；三页互不嵌入，各自做到同类工具水准（用户 2026-08-16 拍板） |
| 后端零改动 | 看板、会话分组全部用已有接口；唯一后端新增是 MCP |
| 运行时协议不动 | `event-projection/`、审批链路、`thread/*`、`turn/*` 一行不改（R7） |
| **官方机制优先，不自建替代层** | Codex 能做的事一律用 Codex 的口子（CLI 子命令或 app-server RPC）。禁止自己解析/改写 `config.toml`、自己写 `auth.json`、自建 MCP 客户端、自己拉模型清单 |
| **不抽公共适配层** | 未来若引入 Claude Code CLI 或国产 CLI，做法是**各按各的原生能力接入**，不是先抽一层公共抽象再适配。本期不为多 CLI 付任何抽象成本 |
| 迁移有终点 | 本期交付第一批 + 剩余清单批次，不是无出口的"改到才迁" |

**与现有系统的关系**：

|----------|----------------|------------------|

## 三、关键决策与取舍

### 用户拍板（2026-08-16）

- **U1 信息架构**：维持需求／会话／设置三模式并列，三页都做深。**否决**"会话为主、需求降为上下文"——那是未来选项，本期不做，也不为它预留接口抽象（避免为未定方向付成本）。
- **U2 审批档**：保留 `full` 档能力，**默认不锁**；提供部署侧上限开关，锁定后由**服务端强制**而非仅 UI 置灰。
- **U4 全局事件归属**：`runtime-event-ingestor.ts` 由**本需求承接**，`suduo-token-docs-runtime-noise-001` 的 4.4 避让（已在该需求文档标记移交）。继承其 R3／R4／R5 与双向单测，不得弱化。
- **U3 接入原则**：引入 Codex CLI 而非自建 LLM API harness，目的就是**用它自带的机制**——官方能力最完整最强。MCP、Skills 这类能力**完全基于 CLI 本身的能力接入**。未来可能引入 Claude Code CLI 与国产 CLI，届时**各按各的原生能力接入**；**本期不设计任何兼容层／公共抽象**。

### Claude 自决（依项目定位，非援引旧决策）

- **D1 接入口子的选法**（落实 U3）：**不预设 CLI 优先或 RPC 优先**，逐件事看官方给了哪个口子就用哪个——`codex mcp add/remove`、`codex login --with-api-key`、`codex doctor --json` 走 CLI；`ListMcpServerStatus`、`ConfigRead/Write`、`ModelList`、`McpServerOauthLogin` 走 RPC（这些只有 RPC 有）。两者都是同一个 `codex` 二进制的官方能力，且 RPC 面受 `client/codex-protocol` 的 sha256 基线 + `protocol:diff` 哨兵守着。
  → **R3 措辞按用户意图扩展**为「只走官方 Codex 口子（CLI 子命令或 app-server RPC），禁止自行解析／写入 `config.toml`、`auth.json`，禁止自建 Codex 已有能力的替代实现」。R3 原文写"官方 CLI 子命令"，是需求分析时只勘察了 CLI 面；用户意图是"不碰私有格式、用官方机制"，扩展后的措辞才是它。
- **D2 Codex 版本**：**保持 0.143 精确协议基线不动**。需求「开放问题·版本策略」的前提有误——`@openai/codex@0.143.0` 是 workspace 钉版（`node_modules/.bin/codex` 实测 0.143.0），MCP 六子命令与 `ListMcpServerStatus`／`McpServerOauthLogin`／`ConfigBatchWrite` 在 0.143 基线中**已全部存在**（已核 `baseline-manifest.json`）。doctor 报 fail 是因 `codexBin = SUDUO_CODEX_BIN ?? "codex"` 落到 PATH 撞上开发机全局 0.147——**这是二进制解析缺陷，本期修**，不是版本策略问题。
- **D3 清掉四处自建实现**（v1.1 翻转，落实 U3）：初版把 `ModelProviderService` 的正则改写列为"技术债、本期不迁"，理由是"无官方等价路径"＋"迁后改配置需活跃 codex 连接"。**两条理由都不成立**：
  1. 官方路径全都有（0.143 实测）：`codex login --with-api-key`（stdin 写 `auth.json`）、`ConfigRead`／`ConfigValueWrite`／`ConfigBatchWrite`、`ModelList`、`ModelProviderCapabilitiesRead`、`codex doctor --json`。**"API Key 无官方等价路径"是初版的事实错误**，源自未核实的转述。
  2. app-server 启动**不校验模型配置**（`initialize` 不碰 provider），坏 key 只在 turn 时暴露；真正起不来的场景是 codex 二进制本身坏了，那时改 `config.toml` 也救不回来。所谓"功能倒退"不成立。

  → 本期一并清掉：① 正则改写 `config.toml`、② 直写 `auth.json`、③ 自己 `fetch` provider 的 `/models`（改 `ModelList`）、④ `doctor-service.ts` 自己 regex 解析 `config.toml` 判断模型配置（改 `codex doctor --json`，还白拿官方 `remediation` 修复建议）。
  **代价**：D 块工作量上升，`model-provider-service.ts` 与 `doctor-service.ts` 需重写；`doctor-service.ts` 的 Node/pnpm/better-sqlite3/端口等 **SuDuo 自身检查项保留不动**，只把 Codex 侧检查换掉。

  **D3-a 配置有层级，写入必须承认这件事**（Codex 实测）：`config/read` 返回有效值**与来源层**，但写入默认落 user 层 `config.toml`；`ConfigWriteResponse` 带 `status: ok | okOverridden`、`overriddenMetadata`、`version`。所以：读取一律 `includeLayers:true` 并在每个字段旁显示来源（含"被管控层锁定"）；写入带 `expectedVersion`；**收到 `okOverridden` 绝不能显示"已保存生效"**，要明说"已写入你的配置，但被上层配置覆盖，当前生效值仍是 X"。同一表单的多字段用 `config/batchWrite + reloadUserConfig:true` 一次写完（官方 schema 原文是 hot-reload into all loaded threads），不再 `ValueWrite` 逐字段 + 强制重启 runtime。热重载**不等于**进行中的 turn 会换模型，界面仍按"下回合生效"描述。

- **D3-b 模型测试改为「保存并验证」**（因 `model/list` 不接受草稿凭据）：0.143 `ModelListParams` 只有 `cursor/includeHidden/limit`，**没有 draft base_url/key 入参**。现有"测试连接"是拿表单里未保存的值自己 `fetch` 试的，迁到官方口子后这个交互无法保留。**没选**"起隔离 `CODEX_HOME` 拿临时凭据探测"——那要暂存密钥，与 R4 冲突。
  → 交互改为：点「保存并验证」→ `config/batchWrite`（带 `expectedVersion`）→ `model/list` 验证 → 失败时用保存前读到的旧值**一键还原**。还原能力由 `config/read` 的读值 + `expectedVersion` 保证，不需要额外存储。

- **D7 Codex 全局状态投影**（v1.3 新增，Codex 指出的漏洞）：设置页状态条依赖的 `configWarning`、`skills/changed`、`mcpServerStatus/updated`、MCP OAuth 完成通知，**`threadId` 本就可为 null**，而 `runtime-event-ingestor.ts` 关联不到 session 就丢弃。只给 normalizer 加映射**不够**——状态条、MCP 故障、配置告警会全部静默失效。
  → 新增 `codex-global-state.ts`：订阅无 `threadId` 的官方通知，落**内存投影**（不进 DB，重启重建），设置页经 SSE 或轮询读取。

  **归属已定（用户 2026-08-16「那边避让」）**：`runtime-event-ingestor.ts` 的改动**由本需求承接**，`suduo-token-docs-runtime-noise-001` 的 4.4 已标记移交、不再实施。理由是本需求是严格超集——那边只需"已知全局事件不再抛错"，本需求还要求这些事件**继续向下落进投影**推给状态条；若那边先做，本需求仍要再改同一处。

  **随同继承的约束（来自那边的 R3／R4／R5，不得弱化）**——这三条是 2026-07-24 排查教训的固化：

  | 继承规则 | 内容 |
  |---|---|
  | R3′ | **未知无关联 runtime 事件必须继续抛错**并进 `onError`。保住 codex 进程死因等排查线索 |
  | R4′ | 已知全局事件判定须**同时**满足：`payload.extensions.codex.nativeType` 命中白名单 **且** 无 `threadRef`／`sessionHint`。缺一不可——纯结构性判定会吞掉真正无关联的故障 |
  | R5′ | 白名单**只收已证实项**。继承的两项：`configWarning`、`remoteControl/status/changed`；本需求新增前须逐项实测：`skills/changed`、`mcpServerStatus/updated`、MCP OAuth 完成通知 |

  验收继承那边的**双向单测**：已知全局不报错 ＋ 未知无关联仍报错。本需求再加一条：已知全局事件**到达投影且设置页可见**（不能只是"不报错"就算完）。
- **D4 组件基座**：**改造范围内的控件／overlay／表单原语一律 `components/ui` + Radix；布局 class（`.rail/.center/.main`）保留**。出口条件：`v2-*` 私有 class 在 TSX 中清零 + `styles.css` 对应 39 行删除 + 产出剩余迁移清单。**没选**逐组件重写会话运行时（≈1900 行 TSX），代价是审批／附件／`@`引用／diff 全面回归，撞 R7 且收益仅"代码整洁"。
- **D5 拖拽**：HTML5 原生 DnD，**零新依赖**。本期只需跨列改 status，不需列内排序（无优先级字段，服务端 `ORDER BY updated_at DESC`，前端排序无处可存）。键盘用户走**详情区状态按钮组**，不伪造键盘拖拽。
- **D6 会话页壳**：稳定 `SessionsWorkbench` 外壳 + `key={sessionId}` 的运行时 pane。**没选**给 `SessionRuntime` 加 `railSlot`——slot 内容随 `key` 一起重挂，切会话时左栏状态照样丢。

## 四、核心流程 / 逻辑

### 4.1 看板加载与拖拽改状态

现状缺陷（正确性问题，非观感）：单一 cursor + 前端 `filter(status)`，`limit=50` 的第一页可能全落在 2 列，**其余 4 列显示为空但实际有数据**。

```
进入需求模式
   │
   ├─ 6 列各自请求 listRequirements({status, limit:20})   ← status 过滤 BFF 已白名单放行
   │  并发上限 3，其余排队；每列独立 skeleton
   │  切项目 → AbortController 掐掉在途请求
   ▼
列头计数 = 已加载 N；nextCursor≠null 时显示 "N+"（API 无 count，不伪造总数）
   │
   ▼
拖卡片到目标列
   │  乐观落位；同一卡片只允许一个 pending mutation
   ▼
updateRequirement({status, expectedVersion})
   │
   ├─ 成功 → SSE 广播全组；按 version 去重回声
   │
   └─ 失败（version 冲突/网络）
        └→ getRequirement(id) 取真实 status → 按真实列落位
           （不机械回弹原列：并发下他人可能已移到第三列）
```

**SSE 局部搬移**：`RequirementsEventDto` 只有 `{id,type,projectId,requirementId,requirementVersion}`，**不带 from/to**。客户端从本地 state 知道旧列，`getRequirement` 取新 status，只搬两列——不再像现在那样每个事件都全量 `refresh()`。

### 4.2 端到端走查：小王把"附件预览"从开发中拖到测试中

1. 小王进需求模式。6 列各拉 20 条，"开发中"列头显示 `5`，"测试中"显示 `2+`（还有下一页）。
2. 拖起"附件预览"卡（v7），落到"测试中"。卡片先落位，边框转 pending 态。
3. 前端发 `PATCH /api/v2/requirements/{id}` `{status:"in_testing", expectedVersion:7}`。
4. 同一时刻小李在自己机器上把它改成了"已完成"，version 已是 8 → 服务端返 409。
5. 前端不回弹到"开发中"，而是 `getRequirement(id)` 拿到 `status=completed, version=8`，把卡片放进"已完成"列，Toast 提示"该需求已被李四改为已完成"。
6. 小李那边的改动本来也会经 SSE 到达；按 `requirementVersion=8` 去重，不重复搬移。

### 4.3 MCP 新增服务器

```
设置 › 能力扩展 › + 新增服务器
   │
   ├─ stdio ──→ 命令 + 参数 + 环境变量名
   │              │
   │              ├→ codex mcp add <NAME> -- <CMD>          (CLI，**不带 --env**)
   │              └→ config/batchWrite 写                    (RPC)
   │                 mcp_servers.<name>.env_vars=["TOKEN"]
   │
   └─ HTTP ───→ URL + bearer token 环境变量名
                  └→ codex mcp add <NAME> --url … --bearer-token-env-var …
   │
   ▼
config/mcpServer/reload (RPC) → mcpServerStatus/list (RPC)
   │
   ├─ 已连接 → 列表显示绿灯 + 工具数
   ├─ 启动失败 → 展示 startupFailureReason（可读诊断，非静默）
   └─ 需登录 → McpServerOauthLogin (RPC) → 授权 URL 交前端打开
              → McpServerOauthLoginCompletedNotification 回来后刷新状态
```

**⚠️ v1.2 写错并已更正**：`codex mcp add --env` 收的是 **`KEY=VALUE` 字面值**，会把密钥明文写进 `transport.env`——不是我以为的"变量名"。Codex 隔离实测确认：只有经 `config/batchWrite` 写 `mcp_servers.<name>.env_vars=["LOCAL_TOKEN"]`，`codex mcp get --json` 才返回变量名。所以 **stdio 的 add 一律不带 `--env`**，环境变量引用全部由 RPC 写。HTTP 的 `--bearer-token-env-var` 本来就是变量名，可直接用。

**已知限制**：`codex mcp` 无 `edit` 子命令。编辑 = `config/batchWrite` 原子改写（RPC 可用时），RPC 不可用时降级为 remove+add 并在界面明示"非原子，失败需重建"。

### 4.4 审批档收口（U2）

```

                        =auto → UI 置灰 full + 服务端 clamp

effectiveApprovalMode(session) = min(session.approvalMode, cap)
   │
   ├─ session-service.ts  ├ 创建会话：cap 生效期存**允许的最高档**，不存 full
   │  （v1.3 补，v1.2 漏）└ PATCH approvalMode 超限 → 409

        runtime-supervisor.ts × 3   message-service.ts × 1
```

> v1.2 的清单漏了 `session-service.ts`，还留了个自相矛盾：既说新建会话可能存 `full`，又说 PATCH `full` 会 409。已按"创建时就存允许档"统一。

### 4.5 设置页布局与交互

**设计出发点**：用户来设置页，90% 是因为**某样东西不工作**——"AI 说看不到我的文件"（目录没映射）、"发消息没反应"（模型连不上）、"我的 Skill 没生效"（被停用了或全局开关关了）、"MCP 工具没出现"（没配/没登录/启动失败）。所以设置页的第一职责是**让人看出现在是好是坏**，第二职责才是改配置。现在 doctor 自检被藏在"关于"tab 的一个链接后面，方向是反的。

## 十、迁移影响与风险

- **受影响**：`client/web` 三页全部呈现层、`client/server` 新增 MCP 与审批 clamp、gate-c e2e
- **打法**：**A0（gate-c fixture 与 V2 路径迁移，独立中大型任务）** → A（组件基座） → B（看板）/ C（会话页）并行 → D（设置页，含 D3 官方口子迁移）→ E（MCP，依赖 D7 全局状态投影）/ F（审批档）可与 B/C/D 并行
- **回滚**：纯前端块按 git revert 分块回退；MCP 与审批档各自独立，可单独关停（`SUDUO_MAX_APPROVAL_MODE` 不设即回到现状）

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| gate-c 修复量超预期，本期无回归网 | 中 | 高 | 列为 A 块**最高优先**，先于任何组件迁移；修不动就先补纯函数测试并显式记为缺口 |
| MCP OAuth 在无浏览器的内网机器上不可用 | 中 | 中 | 返回授权 URL 由用户自行打开；失败给可读诊断，不静默 |
| `ConfigBatchWrite` RPC 需活跃 codex 连接，配置时连接不可用 | 中 | 中 | env_vars 写入失败时降级为"仅 CLI 已写入，敏感值需手工配置"并明示 |
| 呈现层迁移引发既有功能回归 | 中 | 高 | `data-testid` 全保留；分块迁移逐块验证；`event-projection/` 与 API 层不动 |
| **全局通知投影漏做** → 状态条／MCP 故障／配置告警全部静默失效 | 中 | 高 | D7 与 E 块绑定验收：MCP 启动失败必须在设置页可见，否则 E 块不算完成 |
| **`okOverridden` 当成保存成功** → 用户以为改了、实际被上层覆盖 | 中 | 高 | 写入一律带 `expectedVersion`；`okOverridden` 走独立文案与来源徽章，禁止复用"已生效"提示 |
| 模型配置迁移后行为漂移 | 低 | 高 | Codex 已在真实 `config.toml`（含嵌套 `model_providers.<id>`）逐字段比对，`providerId/baseUrl/model/reasoningEffort/contextWindow` 全部一致；仍保留一次性回退分支 |
| `codex login --with-api-key` 走 stdin，Windows 上编码/管道行为与 Linux 不同 | 中 | 中 | 复用既有 `decodeWindowsCommandOutput` 范式；Gate C 在 Windows 侧单测这一条 |
