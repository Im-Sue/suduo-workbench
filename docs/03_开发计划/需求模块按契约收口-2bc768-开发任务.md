### pr3 需求模块按契约收口

#### 任务概述

需求模块是三个模块里反馈链路最复杂的一个，也是**唯一已经把并发做对了的地方**。所以这片的重心不是「多改」，而是**在不碰坏已有竞态语义的前提下换掉呈现层**。

改造面：`RequirementsWorkbench.tsx`（1221 行）9 处 `showMessage` + **21 处** `reportError`(14) / `reportErrorMessage`(7)，`RequirementsDetailPage.tsx`（928 行）5 处空态裸文案，`RequirementsBoard.tsx`（207 行）1 处空态。

#### 任务分解

1. **收口失败出口**：`RequirementsWorkbench.tsx:143` 的 `reportError` 与 `:146` 的 `reportErrorMessage` 换成 `reportFailure`。**这不是一次批量替换**——每个调用点都要判定它该落哪个出口，逐项写进走查记录。典型分支见需求十二章：
   - `:936` 409 `VERSION_CONFLICT`（「需求已被他人改动，请刷新」）→ `global` 错误 toast + 自动刷新 + 保留对话框内容
   - 400 校验失败且带字段 → `field`，`InlineError` 贴在对应字段
   - 502 依赖不可用 → `region`，`RegionError` + 重试按钮
   - 409 `AUTH_INVALID` → `page`，`PageFailure` + 去登录（**不能走 409 的自动刷新分支**）。**本片只调 `reportFailure`/`routeFeedback`**，page 层由 pr2 的 `MessageHost` 承载、「去登录」由 pr7 注册——**本片不需要任何新 props，也不碰壳层文件**（详见 outline「勘误」第 3 条）。

2. **并发语义原样保留，只做收编不做改写**。以下全部**不得改变行为**：
   - `:83` `pendingMoves`（写入 single-flight）
   - `:85` `boardAbort` AbortController（读取 latest-wins）
   - `:126` `pendingRequirementId` 与 `selectedRequirementId.current` 的一系列守卫（卸载/切换后不回写）
   - `:177` / `:187` 的 `options.signal?.aborted` 早返回
   
   允许把它们表达为 pr2 的策略函数，但**任何行为差异都算回归**。这里是全仓竞态处理最正确的地方，改坏了会留下比现在更难查的乱序 bug。

3. **已单测的纯函数不动**：`requirements-board.ts` / `requirements-detail.ts` / `requirements-artifacts.ts` / `requirements-events.ts` 里 `resolveConflictPlacement`、`shouldApplyEvent` 等已有测试覆盖的函数保持原样。
