## 二、任务分解

### pr2 反馈契约层与出口组件

#### 任务概述

这片交付的是**标尺本身**，一行页面代码都不改。核心是把一次失败拆成两个互不相干的问题：**「这是什么故障」**（纯数据判断，和界面无关，全局唯一答案）与**「这种故障在这个位置该怎么呈现」**（查表得到，随位置不同）。今天全仓 33 处 `"warning"` 就是这两件事混在一起的产物。

两问都必须做成纯函数——不是审美偏好，是让判定**与界面无关因而可穷举测试**。

> **2026-08-25 更正**：草案原先在此写「没有 jsdom 也没有组件测试环境」，这是错的。`jsdom@^30.0.1`（`client/web/package.json:46`）与 `@vitejs/plugin-react@6.0.3`（`:45`）**都已安装**，`vite.config.ts:7` 已启用 react plugin，唯一缺的是 `vitest.config.ts` 未配 `environment`、include 只匹配 `.test.ts`。因此本片**多承担一项**：把组件测试基建搭起来（见任务分解第 11 条）。这不需要新增依赖。

#### 任务分解

1. **`client/web/src/feedback/classify.ts`** — `classifyFailure(cause) -> Failure`
   - 判定顺序**固定为** `cancelled -> code -> status -> unknown`。
   - **code 优先于 status，这是硬要求**：409 下有 13 种语义不同的 code（`VERSION_CONFLICT` / `AUTH_INVALID` / `IDEMPOTENCY_CONFLICT` / `WORKSPACE_MAPPING_REQUIRED` / `PROJECT_HAS_ACTIVE_SESSIONS` …）。按 status 分类会把「远程地址变更需重新登录」误判成「版本冲突→自动刷新」，用户陷入永远刷不出来的循环。
   - **必须可穿透**：BFF 里存在 4 处运行时变量拼出的 `(status, code)` 组合，枚举不可能穷尽。匹配不到一律落 `unknown`。**禁止写成穷举式 switch**。
   - `AbortError` / `signal.aborted` → `cancelled`，排在判定第一位。切项目、组件卸载、用户主动取消都走这条路，把它当故障报出来是纯噪音。
   - 裸 `TypeError` → `transport_unknown`，**不归因**。仅当请求目标是相对 `/api/*` 时文案可写「无法连接本机工作台」，但不得断言原因，更不得给「去启动 SuDuo」这类误导性动作。
   - `FailureKind` 枚举：`cancelled` / `auth_expired` / `not_configured` / `version_conflict` / `stale_state` / `validation` / `forbidden` / `not_found` / `upstream_unavailable` / `runtime_failed` / `transport_unknown` / `unknown`。`unknown` 是必备兜底，不可省。

2. **`client/web/src/feedback/routes.ts`** — `FEEDBACK_ROUTES` 常量表 + `routeFeedback(failure, context) -> Route`
   - `kind x surface -> 出口 + 停留时长 + politeness`。
   - `FeedbackOutlet`：`silent` / `global` / `field` / `region` / `page` / `boundary`。
   - **路由表是代码，不是文档**。需求十三章第一条风险点名「做成一份没人遵守的风格指南」——常量表 + 纯函数是真相源，markdown 只是它的镜像。

3. **`client/web/src/feedback/report.ts`** — `reportFailure(cause, context)`，上面两者的组合调用，页面级统一出口。
   - **`page` 出口走 host 模式，不走 props**：写入本层的模块级 store，由 `MessageHost` 渲染（见第 7 条）。调用方（pr3~pr6）因此**不需要任何新 props，也不需要碰壳层文件**。
   - 导出 `registerAuthExpiredHandler(handler)`：壳层（pr7）用它注册自己的 `logout`；未注册时 `PageFailure` 的「去登录」降级为不可用并在 dev 下告警，**不得静默失败**。

4. **`client/web/src/feedback/async-action.ts`**
   - `reduceAsyncAction(state, event)` 纯函数状态机：`idle -> pending -> success / failed`。
   - **两个**并发策略函数，不是一个万能 hook：读取用 `latest-wins` + abort，写入用按资源 `single-flight`。看板现在两种都在用且都正确，强推单一 hook 会改坏已有的竞态语义。
   - `useAsyncAction()` 只作**可选** React 壳，非强制。

5. **`client/web/src/feedback/confirm-policy.ts`** — `needsConfirm(action)` 纯函数，按「不可逆性 x 影响范围 x 恢复成本」判定。

6. **`client/web/src/feedback/components/`** — `InlineError` / `RegionError` / `PageFailure` / `EmptyState` / `ConfirmDialog` / `FormDialog`
   - `ConfirmDialog` 与 `FormDialog` **是两个 API**，不再一身二用：前者危险色 + 默认焦点在取消；后者处理未保存内容的关闭拦截（有未保存内容时 Esc 不直接关）。
   - `EmptyState`：说明为什么空 + 引导动作，props 要能覆盖各域片将要接入的全部场景。
   - ARIA 契约在组件内实现：加载区域 `aria-busy`、对话框打开焦点入内 / 关闭归还触发元素、尊重 `prefers-reduced-motion`。**各域片只接入，不各自实现**——这是需求第 6、7 项不单独成片的前提。
   - testid 固定为 `region-error` / `page-failure` / `empty-state` 等，**状态走 `data-feedback-kind` 与 `data-feedback-result` 属性**，不要用随状态变化的 id。

7. **`client/web/src/ui/message.tsx`**（改）
   - **`MessageHost` 扩展为同时承载 page 层**：它已经是零 props 组件、且已挂在 `RequirementsV2App.tsx:278`，扩展它**不需要改任何挂载点**，壳层一个字不动。这是鉴权失效能在不破坏片间边界的前提下落地的关键（详见 outline「勘误」第 3 条）。
   - `MessageType` 加 `error` 档：assertive、停留更久、`message` 可为 `ReactElement` 因而能内嵌重试按钮。
   - 逐条 `ariaProps: {role, aria-live}` 与逐条 `duration`。普通 polite、`error` assertive。
   - `showMessage()` 签名**向后兼容**，`global-message` testid 保留。
   - 以上全部是 react-hot-toast 2.6.0 **原生已有**能力，零新增依赖。

8. **阈值常量**：0 / 0 / 150 / 1000 / 2000 ms 写进契约，不做运行时可配。

9. **单测**（`client/web/test/`）：`classifyFailure` 覆盖 26 种字面量组合 + 运行时变量兜底 + `AbortError` + 裸 `TypeError`；`routeFeedback` 覆盖 kind x surface 全矩阵；`reduceAsyncAction` 覆盖乱序完成 / 卸载后回写 / 重复触发；`needsConfirm` 覆盖判定表。

10. **同提交跑 pr1 的基线再生成命令**（本片新增了 testid）。

11. **组件测试基建**（本片新增职责，2026-08-25 勘误）
   - `client/web/vitest.config.ts`：`include` 放开到 `test/**/*.test.{ts,tsx}`。
   - **不要动全局 `environment`**——改全局会把现有 13 个纯函数测试都拖进 jsdom。组件测试文件各自在顶部写 `// @vitest-environment jsdom` docblock。
   - 交付**第一个组件测试作为样板**，覆盖本片自己的出口组件：`EmptyState` / `RegionError` / `PageFailure` 至少各一条渲染断言，外加一条焦点归还断言（`ConfirmDialog` 关闭后焦点回到触发元素）。
   - **零新增依赖**：用 `react-dom/client` + React 19 自带的 `act` 手写 render helper，不装 `@testing-library/react`。

### 超出验收标准的复核

**`CODE_KINDS` 与契约层双向零差集。** 审查方比对 `client/contracts/src/api.ts` 的 `ErrorCode`(14) ∪ `cloud/contracts/src/errors.ts` 的 `REQUIREMENTS_V2_ERROR_CODES`(15) = **26 个去重码**，`CODE_KINDS` 覆盖恰好这 26 个，两个方向都无差集。回执报的 35 与 spec 写的 26 不矛盾：**26 是码数，35 是 `(status, code)` 对数**（同一个码可带多个状态码，如 `AUTH_INVALID` 同时出现在 401 与 409）。

**「有 code 但不认识 → 直接 unknown，不回落 status」的判定是对的。** 表面上违反「code → status → unknown」的链式读法，但验收原文要求的就是 unknown；且回落 status 会让未来任何新的 409 码重新掉进「版本冲突→自动刷新」的死循环，正是本需求要消灭的 bug。实现里有注释说明该取舍。

**路由表由 `FAILURE_KINDS × FEEDBACK_SURFACES` 笛卡尔积生成**，结构上不可能有空洞，比手写表更强。
