## 二、任务分解

### PR5 · 现状文件持续刷新与降级

#### 任务概述

交付「文件保持新鲜」，以及更重要的——**拿不到数据时不能让模型继续读旧的**。

远程的事件推送（SSE）**没有重放机制**（`event-hub.ts:9-38` 仅内存扇出），断线期间的事件永久丢失。所以 SSE 只能当加速器，不能当可靠通道，必须有兜底的全量收敛。

#### 任务分解

**1. 一条全局 SSE 连接**

远程 `/v2/events` 不带过滤参数，每会话一条连接会重复收全量事件。所以 BFF 维持**一条**连接，按 `requirementId` 去重后扇出刷新多个会话文件。

**2. 四个时机强制 REST 全量收敛**

连接建立时 / 重连后 / 会话激活时 / 超过 TTL 时。这四个时机不依赖 SSE，是丢事件的补偿机制。

**3. 降级：整份替换，而不是加个状态字段**

原设计想在文件头写 `订阅状态: stale`，指望模型看到后改口。**这不可靠**——模型可能忽略字段直接引用内容，而这正是当前 bug 的模式（有信息但不用）。

所以：

- `live` → 文件是完整现状
- `stale` / `unavailable` → **整份替换**为仅含失败原因与最后成功观测时刻的说明，旧内容移出模型可读路径

让模型**物理上读不到**过期数据，比指望它读状态字段可靠。

替换后的文件形如：

```
## 需求现状：当前不可用
远程服务连接失败（最后成功观测 14:02）。
现在**无法确认**是否有新评论或附件，请在 SuDuo 界面核对。
```

#### 验收标准

- [ ] 断线重连后**必定**执行一次 REST 全量收敛（注意：不要写「不丢事件」——无重放时「没丢」不可证明，只能证明做了补偿）
- [ ] 远程不可达时，文件内容只剩降级说明，不含任何过期库存数字
- [ ] 恢复后文件回到完整现状
- [ ] 多个会话绑定同一需求时，一次远程拉取扇出到多个文件，不重复拉

#### 边界

- 不改远程服务
- 不碰 briefing
- 不做附件字节拉取（PR7）
