## 二、任务分解

### T4-1 抽取纯会话运行时组件

#### 任务概述
现在 V2 的会话界面其实是旧界面套了个壳：`RequirementsV2App` 渲染的是 `<SuDuoApp embedded />`。这个 `embedded` 开关只藏起了三块界面元素（`SuDuoApp.tsx` 的 1062、1063、1096 行），**既没有拦住 import，也没有拦住数据加载**——项目加载块里的 `loadWorkItems(projectId)` 和 `api.tapdConfig(projectId)` 照常执行。也就是说，用户每在 V2 里打开一个会话，浏览器都在偷偷请求 `/api/v1/projects/:id/work-items` 和 `/tapd/config`。

所以必须先抽出一个干净的会话运行时，否则后面一删 TAPD，V2 主链路当场断掉。**改成 dynamic import 不算数**——那只改变打包分片，运行时该请求的还是会请求。

#### 任务分解
1. 新建独立会话运行时组件，只保留：消息流、执行步骤、工具调用分组、审批决策行、Composer、模型/审批模式切换、文件与变更面板。
2. 剥离 `workItems` / `workItemCursor` / `workItemGroupCounts` / `tapdConfig` / `tapdWorkspaceId` / `tapdProjection` / `tapdSyncRef` 全部状态与相关请求。
3. 保留**非 TAPD** 的 Codex 设置能力（模型、审批偏好、skills）；`SettingsPanel` 里的 TAPD 区留给 T4-3，本片只解除新组件对它的依赖。
4. `RequirementsV2App` 改为渲染新组件。
5. `/legacy` 与旧 `SuDuoApp` 本片**保持不动**，留给 T4-3。

#### 验收标准
- V2 会话视图的静态依赖图中不含任何 TAPD 模块（用打包分析或 import 图验证）。
- 从 V2 打开一个会话，浏览器网络面板**没有** `/work-items`、`/tapd/` 请求。
- 会话消息收发、审批、工具分组、Composer、模型切换、文件/变更面板全部不回归。
- build / typecheck / lint 通过。

#### 边界
不删任何文件，不动 `/legacy`，不动服务端，不动数据库。
