# SuDuo V2 一致性守卫退役 技术设计

> 一句话：删掉三处「版本对不上就 409」的入口，把 `version` 改成只在正文实变时才动的单一计数器，其余一概不新增。｜最后更新：2026-09-05
>
> **无独立 status** —— 跟随 `requirement_id` 指向的需求；"已确认可开工"等 gate 落需求/任务状态机，不放本文档。

---

## 一、设计概述

**目标对齐**：你要「谁想操作就操作」。今天需求编辑、附件增删、产物发布三条路径各有一道「你手里的版本 ≠ 服务端版本就拒绝」的闸；这三道闸拿掉，不换成任何提示。顺带把 `version` 从"四种操作共用的计数器"改成"只有正文（标题 / 说明 / 状态）真的变了才 +1"，附件与发布只刷"最后更新"时间。删附件确认、产物不可改、评论只增不删、AI 代提交要人点头——这些不可逆保护一处不减。读码后的一个好消息：删字段不需要兼容窗口，旧客户端（含用户机器上已装的发布 skill 副本）带着旧参数照样能跑通。

| 项 | 说明 |
|----|------|
| 名称 | SuDuo V2 一致性守卫退役 |
| 核心职责 | 在 requirements-service / BFF / web / 官方 skill 四层同步删除 `expectedVersion` 入参与 409 分支；`version` 收窄为正文版本；`VERSION_CONFLICT` 三处误用改贴切错误码 |
| 设计原则 | 只删不加（无新表 / 列 / 依赖 / 守卫）；检测留、拒绝去（ADR-0004）；后写生效；行锁与幂等表不属本期 |
| 需求来源 | `docs/02_需求设计/v2-一致性守卫退役-需求.md` |
| 覆盖范围 | 需求 4.1-4.5 五个功能点 + 官方发布 skill + 接口文档同步 |
| 不覆盖 | 项目编辑 `updateProject` 的 `expectedVersion`（项目不是需求协作对象）；AI 侧材料 / 观测路径的全部 `VERSION_CONFLICT`（已交付，不动）；发布幂等表；`ensureSnapshot` v2 死路径 |

## 二、方案与架构

```
改前：一个计数器，四个写入源，三道闸
  正文 PATCH ──┐                                      ┌─ updateRequirement   expectedVersion 必填 → 409
  附件上传  ───┼─► requirements.version + 1 ──比对──► ├─ attachment create/delete  header 可选 → 409
  附件删除  ───┤                                      └─ artifact publish    body 必填 → 409
  产物发布  ───┘

改后：一个计数器，一个写入源，零道闸
  正文 PATCH(实变) ─► version+1 · updated_at/by ─► 审计 requirement.updated ─► SSE requirement.changed(version)
  正文 PATCH(无变) ─► 不写 · 不审计 · 不发 SSE ─► 200 返回当前 DTO
  附件上传 / 删除 ─► touchRequirement（只 updated_at/by）─► 审计 attachment.* ─► SSE attachment.changed
  产物发布        ─► touchRequirement（只 updated_at/by）─► 审计 artifact_version.published ─► SSE artifact.published

  version 剩余消费者（全部只读）：v3 快照目录名 v3-<version> · 会话基线 requirementVersion · 前端 list-vs-detail 读一致性
```

| 关键原则 | 说明 |
|----------|------|
| 只删不加 | 全部改动是删入参、删分支、删函数、改一处 SQL 条件；不新增任何表 / 列 / 依赖 / 锁 / 幂等键（N8） |
| 检测留、拒绝去 | 审计（`before_json`/`after_json`/操作人/时间）一字不动；`version` 继续存在且可比对；只是没有任何地方再用它拒绝人 |
| 保留字段 ≠ 保留守卫 | 响应里的 `requirementVersion` 全部保留（旧 skill 副本硬校验它），但没有任何调用方再拿它去串接 |
| 每条路径的退役与它自己的停增同片落地 | 避免 `incrementRequirementVersion` 被改两次，也避免 skill 去链早于发布校验退役而断（见十、迁移） |

**与现有系统的关系 / 边界**：

| 涉及模块 | 本设计如何动它 | 保留 / 不动什么 |
|----------|----------------|------------------|
| `cloud/server`（远程真相层） | 删三处校验、改 `updateRequirement` SQL、`incrementRequirementVersion` 两份实现合并为一个 `touchRequirement` | 附件 `FOR UPDATE` / 发布 `lockRequirement` 行锁；发布幂等表与 `operationKey` 重放；`versionConflict()` 工厂（`updateProject` 仍用） |
| `client/contracts`、`cloud/contracts` | 删两个请求类型的 `expectedVersion`、schema 属性与 `required`、`REQUIREMENTS_V2_EXPECTED_VERSION_HEADER` 常量；`api.ts ErrorCode` 加两个码 | `REQUIREMENTS_V2_ERROR_CODES` 里的 `VERSION_CONFLICT`（BFF 材料 / 观测路径仍用）；所有响应 DTO 形状 |
| `client/server`（BFF） | 删两处 `validateExpectedVersion` 与两处 header 透传；三处错误码改名 | `:185 updateProject` 校验；`:238/:658/:662` 三道检查的行为 |
| `client/web` | 删版本串接、`requirementEditVersion` 状态、三处 `version_conflict` 分支；`classify.ts` 加两码映射 | `requirements-board.ts` SSE 去重；`:383/:523` 读一致性重试；`VERSION_CONFLICT → version_conflict` 映射 |
| 官方发布 skill | 删串接与 body 字段，`SKILL.md` 改叙述 | 按 SHA-256 复用、`Idempotency-Key`、`Origin`、档位前置 |
| `docs/01_架构设计/v2-系统架构.md` | `:216` 改「仅正文实变递增」 | `:215` 项目 PATCH 的乐观锁描述 |

## 三、关键决策与取舍

- **删字段不设兼容窗口，直接删**：选「schema 直接删属性与 `required`」，因为 Fastify 默认 Ajv 选项 `removeAdditional: true`（`@fastify/ajv-compiler` `default-ajv-options.js:8`），`additionalProperties: false` 的语义是**剥离**未知属性而非拒绝——Codex 用旧 body 内存注入实测 200；header 则本就被忽略。没选「暂留可选字段并忽略一版」，因为 N6 明令不保留忽略语义，且实测证明不需要。
- **正文实变判定放 SQL 端**：选 `UPDATE … WHERE id = $5 AND (title, summary, status) IS DISTINCT FROM (COALESCE($1, title), COALESCE($2, summary), COALESCE($3, status))`，`rowCount = 0` 即无变。没选应用层 `before` 三字段比对，因为两个请求同时读到 A、同时提交 B 时第二笔仍会自增，违反 N2/N4；SQL 条件在 READ COMMITTED 下对最新行重评估，天然去重。**残余**：审计的 `before` 仍是事务内无锁预读（现状如此），两人在毫秒级窗口交错改不同字段时，甲的审计条目可能把乙的字段变更也记进去——乙自己的条目仍完整存在，人可对照恢复。按 ADR-0004 §2 判据（可恢复 → 不做）**不加 `FOR UPDATE`**。**用户 2026-09-05 终端拍板：A 不加锁，接受罕见多记**；Claude 曾建议 B（阻塞式行锁，几毫秒、无拒绝）被否。实施时不得加锁。
- **`touchRequirement` 单函数、单实现**：选把 `attachment-repository.ts:419` 与 `artifact-version-repository.ts:288` 两份 `incrementRequirementVersion` 合并为一个共享 helper（`infrastructure/requirement-touch.ts`，签名 `touchRequirement(executor, requirementId, actorId): Promise<number>`，返回**当前**版本）。没选加 `bumpVersion` 布尔参数，因为收窄后没有任何调用方需要自增（正文 PATCH 内联在自己的 UPDATE 里），永远为 false 的参数是死代码且给后来者"随手传 true"的入口。
- **响应字段全保留**：`ListAttachmentsResponse` / `AttachmentMutationResponse` / `PublishArtifactVersionResult` / SSE `requirementVersion` 一律保留，语义统一为「操作完成时的当前正文版本」。没选删 mutation 响应字段，因为旧 skill 副本 `scripts/publish-artifact-version.mjs:73` 硬校验 `Number.isSafeInteger(uploaded.requirementVersion)`，删了会让附件已传而发布中止（真实兼容断裂）；发布 HTTP 只回 `artifactVersion`（`server.ts:352`），内部字段删之无契约收益。
- **发布幂等摘要去掉 `expectedVersion`，存量行不动**：`publishRequestDigest` 只哈希 `attachmentIds` + `note`。升级前写入的摘要含旧字段，若同一 `operationKey` 在升级后重试会落入既有 `VALIDATION_ERROR`「operationKey 已用于其他发布请求」——但 web（`RequirementsWorkbench.tsx:955` `crypto.randomUUID()`）与 skill（脚本 `:90` `randomUUID()`）都是每次发布生成新 key，**没有任何已发客户端会用旧 key 重试**。没选清表或放宽摘要比较：前者动数据，后者削弱幂等表本身；幂等表的去留归「幂等表转检测」后续需求。
- **错误码命名**：`:238`「只有活动需求会话可以提交评论」与 `:658`「只有活动需求会话可以拉取附件」→ `SESSION_NOT_ACTIVE`（ADR-0004 §3 已点名）；`:662` 比较的是 `session.projectId !== project.id`（本机项目映射）→ `SESSION_PROJECT_MISMATCH`，没选 `SESSION_REQUIREMENT_MISMATCH` 因为它比的不是需求。两码加进 `client/contracts/src/api.ts ErrorCode` 与 `client/web/src/feedback/classify.ts CODE_KINDS → "stale_state"`——不加映射的话会按 `STATUS_KINDS[409]` 兜底成 `version_conflict`，正是要退役的反馈语义。
- **无实变 PATCH 不发 SSE**：`updateRequirement` 返回 `{ requirement, changed }`，HTTP 层 `changed === false` 时跳过 `events.publish`。没选照发，因为看板去重是 `event.requirementVersion > local.version`（`requirements-board.ts:224`），同版本事件会被静默丢弃，发了也是噪音。
- **`updateProject` 不动**：需求拍板的是"三处"（需求编辑 / 附件 / 发布），项目改名归档不是需求协作对象；`versionConflict()` 工厂因此保留。

## 四、核心流程 / 逻辑

```
需求编辑 PATCH /v2/requirements/:id  {title?, summary?, status?}
  ├─ BFF: 删 validateExpectedVersion，其余校验不变
  ├─ requirements-service
  │    ├─ 事务开始
  │    ├─ before = getRequirement(id)                    ← 无锁预读（审计用，现状如此）
  │    ├─ UPDATE … SET title=COALESCE($1,title), summary=…, status=…,
  │    │            updated_by=$4, updated_at=now(), version=version+1
  │    │   WHERE id=$5 AND (title,summary,status) IS DISTINCT FROM (COALESCE($1,title),COALESCE($2,summary),COALESCE($3,status))
  │    ├─ rowCount=0 → 返回 {requirement: before, changed:false}   ← 不审计、不发 SSE
  │    └─ rowCount=1 → after = getRequirement(id) → 审计 requirement.updated / status_changed → {after, changed:true}
  └─ HTTP: changed && events.publish(requirement.changed, version)

附件上传 POST /v2/requirements/:id/attachments（删除同理）
  ├─ 删 X-Requirement-Expected-Version 解析（旧客户端仍带 → 忽略）
  ├─ 事务：SELECT … FOR UPDATE（行锁保留，保附件上限原子）→ 上限检查 → INSERT attachments
  │        → version = touchRequirement()   ← 只刷 updated_at/by，返回当前版本
  │        → 审计 attachment.created(version)
  └─ 201 {attachment, requirementVersion: version}（字段保留）+ SSE attachment.changed

产物发布 POST /v2/requirements/:id/artifact-versions  {operationKey, attachmentIds, note?}
  ├─ BFF: 删 validateExpectedVersion；body 若带 expectedVersion 被 Ajv 剥离
  ├─ 事务：lockRequirement（行锁保留，保产物冻结原子）→ 幂等重放（命中直接返回，不 touch）
  │        → 删 version 比对 → 校验附件归属 → createVersionWithFiles → createPublishComment
  │        → version = touchRequirement() → createPublicationAudit(version) → recordPublishOperation(新摘要)
  └─ 201 artifactVersion + SSE artifact.published(version)
```

**模拟示例**（承接需求十二章 T0-T4，落到代码路径）：

```
T0  需求 R version=7，附件 3 个。PM 小李打开详情开始改描述；开发小王准备传 debug.log

T1  小王 POST /attachments（旧版 skill 副本，仍带 X-Requirement-Expected-Version: 7）
    ├─ server.ts 不再解析该 header → 忽略
    ├─ attachment-repository.create：FOR UPDATE → 上限 OK → INSERT
    ├─ touchRequirement → updated_at=now(), updated_by=小王, RETURNING version → 7
    ├─ audit attachment.created {version: 7}
    └─ 201 {attachment, requirementVersion: 7}   ← 旧 skill 校验 isSafeInteger(7) 通过，续接 expectedVersion=7（无害）

T2  小李 PATCH /requirements/R {summary: "…新描述…"}（新版 web，不带 expectedVersion）
    ├─ before = {summary: 旧, version: 7}
    ├─ UPDATE … WHERE id=R AND (title,summary,status) IS DISTINCT FROM (title, "…新描述…", status) → rowCount=1
    ├─ version → 8；audit requirement.updated {before.summary: 旧, after.summary: 新}
    └─ 200 DTO(version 8) + SSE requirement.changed(8) → 小王的看板 8 > 7 应用

T2' 小李手滑再点一次保存，内容没改
    ├─ UPDATE … IS DISTINCT FROM → rowCount=0
    └─ 200 DTO(version 8)，不审计、不发 SSE、updated_at 不动           ← N4

T3  小李发布产物，勾原 3 个附件；旧 skill 副本此时也在发布，body 带 expectedVersion: 7
    ├─ BFF 不校验；requirements-service Ajv 剥离 expectedVersion → 按 attachmentIds 执行
    ├─ lockRequirement → 幂等未命中 → 附件归属 OK → 建版本 v2 → 系统评论
    ├─ touchRequirement → version 仍 8；audit artifact_version.published {requirementVersion: 8}
    └─ 201 artifactVersion；SSE artifact.published(8)。不提示"debug.log 没带上"       ← 4.3 不告知

T4  小李刷新：附件区 4 个，审计里小王 T1 传了 debug.log。自己决定：不管 / 再发一版 / 找小王
```

| 处理规则 | 说明 |
|----------|------|
| 后写生效 | 三条路径均无版本前置；同一行的并发 UPDATE 由 Postgres 行级串行化，最后提交者的值留下，审计各自记各自的 before/after |
| 实变判定口径 | `title` / `summary` / `status` 三字段同权，任一 `IS DISTINCT FROM` 即算变；`NULL` 与空串按 Postgres 语义区分（现有 schema 三字段均 NOT NULL，不会出现） |
| 无变 PATCH | `version` / `updated_at` / `updated_by` 均不动；不写审计；不发 SSE；HTTP 仍 200 返回当前 DTO |
| `touchRequirement` | `UPDATE requirements SET updated_by=$1, updated_at=now() WHERE id=$2 RETURNING version`；行不存在抛 `notFound("需求")`；附件与发布路径共用同一实现 |
| 幂等重放 | 发布命中 `operationKey` 重放时直接返回存量响应，**不** touch（与今天一致） |
| 审计 `before` | 事务内无锁预读；交错窗口的归属偏差属已知可恢复残余（用户已拍板接受，见三、决策），不引入锁 |
| 可观测性 | 审计表不变；SSE 事件类型与形状不变；无新增日志 |

## 五、测试策略

- [ ] 单元（requirements-service）：`updateRequirement` 三字段各改一处均 `version+1`；三字段全同值 PATCH → `version`/`updated_at` 不变、无审计行、`changed=false`；两个并发同值 PATCH 只自增一次（`IS DISTINCT FROM` 重评估）
- [ ] 单元：`touchRequirement` 只改 `updated_at`/`updated_by`，`RETURNING version` 与之前相等；行不存在 → `NOT_FOUND`
- [ ] 单元：附件 create/delete 不再接受 `expectedVersion`、带过期版本 header 仍成功；上限 409 `ATTACHMENT_INVALID` 与行锁回滚（`attachment-repository.test` 的 stale-409 用例作废，改为「带任意版本头仍成功」）
- [ ] 单元：发布带任意 / 缺省 `expectedVersion` 均成功；`publishRequestDigest` 不含 `expectedVersion`；同 key 同 `attachmentIds+note` 重放返回存量响应、不 touch；同 key 异请求仍 `VALIDATION_ERROR`
- [ ] 单元：HTTP 层 schema——旧 body 带 `expectedVersion` 的 PATCH / 发布返回 200/201（验证 `removeAdditional` 行为，防止未来有人改 Ajv 选项）
- [ ] 单元（BFF）：`requirements-v2-comment-submit.test.ts:31` 与附件拉取用例断言改为 `SESSION_NOT_ACTIVE` / `SESSION_PROJECT_MISMATCH`，行为断言（不调远端）不变
- [ ] 单元（web）：`classify.ts` 两新码 → `stale_state`；`requirements-board.ts` `shouldApplyEvent` 用例不变；删除 `version_conflict` 分支后上传 / 删除 / 发布失败路径的反馈用例改写
- [ ] 专项回归（不可逆保护，需求十三章要求）：删附件确认对话框仍在；被产物版本引用的 blob 删除后不物理清理（`artifact-reference-protection.test`）；产物版本发布后不可改；AI 代提交评论仍需确认门
- [ ] 集成：`official-artifact-skills.test.ts` 用**新脚本**跑多文件发布，夹具不再校验版本、`expectedVersions` 断言删除；另加一条用**旧脚本副本语义**（带 header 与 body 字段）打新夹具仍成功的用例，证明零兼容窗口成立
- [ ] 端到端（Gate-C）：`steps/requirements-board.ts:237-270` 改为「带外正文变化（PATCH 不带 expectedVersion）后，主窗口删附件仍成功，详情回查到 v3 且附件消失」；`:135` `req-conflict` 恒 409 夹具改为「PATCH 成功但回查显示他人已改到另一列，卡片落真实列」；保留 `:135` 段对真实失败（非版本类）回滚的覆盖；`audit-project-id.test` 版本链断言按新语义重写（附件 / 发布不再抬版本）
- [ ] 文档：`SKILL.md` 不再出现「续接 expectedVersion」；`系统架构.md:216` 已改

## 六、数据设计

不新增表 / 列，无 migration（N8）。仅语义变化：

| 实体 / 表 | 关键字段 | 说明 |
|------|----------|------|
| `requirements` | `version` | **仅**正文（`title`/`summary`/`status`）实变时 +1；附件增删与产物发布不再自增 |
| `requirements` | `updated_at` / `updated_by` | 正文实变、附件增删、产物发布均刷新（N3）；无变 PATCH 不刷新（N4） |
| `requirement_publish_operations` | `request_digest` | 新写入的摘要不含 `expectedVersion`；存量行不动 |
| `audit_logs` | `after_json.version` / `requirementVersion` | 附件与发布审计里记录的是操作时的当前正文版本，不再是 +1 后的值 |

## 七、接口设计

| 端点 | 方法 | 变化 | 认证 |
|------|------|------|------|
| `/v2/requirements/:id` | PATCH | body 删 `expectedVersion`（schema 删属性与 `required`）；无变时 200 返回当前 DTO 且不发 SSE | 不变 |
| `/v2/requirements/:id/attachments` | POST | 删 `X-Requirement-Expected-Version` 解析；响应 `requirementVersion` 保留 = 当前正文版本 | 不变 |
| `/v2/attachments/:id/content` | DELETE | 同上 | 不变 |
| `/v2/requirements/:id/artifact-versions` | POST | body 删 `expectedVersion`；响应不变 | 不变 |
| BFF `/api/v2/...` 对应四条 | — | 删 `validateExpectedVersion` 两处与 header 透传两处；`updateProject` 不动 | 不变 |
| BFF 会话评论 / 附件拉取 | — | 409 错误码 `VERSION_CONFLICT` → `SESSION_NOT_ACTIVE`（`:238/:658`）、`SESSION_PROJECT_MISMATCH`（`:662`）；状态码与行为不变 | 不变 |

删除的契约常量：`REQUIREMENTS_V2_EXPECTED_VERSION_HEADER`。新增的错误码：`SESSION_NOT_ACTIVE`、`SESSION_PROJECT_MISMATCH`（`client/contracts/src/api.ts ErrorCode`）。

## 十、迁移影响与风险

- **受影响**：远程 requirements-service（三条写路径）、BFF 四条代理与三处错误码、web 需求工作台、官方发布 skill、Gate-C 与 12 个测试文件。
- **打法**（供任务拆分节点，断裂面按此切）：
  1. **附件片**：附件 `expectedVersion` 退役 + 附件停增（引入 `touchRequirement`）+ BFF / web 附件侧 + `attachment-*.test` + `http.test.ts:440-460` + Gate-C `:237-270` 改写。可独立先行——旧 skill 副本靠响应字段保留继续可用。
  2. **编辑片**：需求编辑 `expectedVersion` 退役 + SQL 实变条件 + 无变不发 SSE + contracts schema + BFF / web 编辑侧 + Gate-C `:135` 改写 + `audit-project-id.test`。
  3. **发布片**：发布 `expectedVersion` 退役 + 发布停增（复用 `touchRequirement`）+ 摘要去字段 + **整套 skill 去链与 `SKILL.md`** + `artifact-version-*.test` + `official-artifact-skills.test` + web 发布侧 + `系统架构.md:216`。skill 去链**必须**与发布校验退役同片：脚本 `:89` 最终发布仍传 `expectedVersion`，校验未退役就去链会断。
  4. **错误码片**：`:238/:658/:662` 改码 + `api.ts` + `classify.ts` + `comment-submit.test` + `feedback-classify.test`。与前三片无耦合，可并行。
  - 不设独立「version 收窄」片：停增与各自路径的退役同批改同一批文件。
- **回滚 / 恢复**：纯代码变更，`git revert` 单片即可；无数据迁移故无需回填；存量幂等摘要行在回滚后重新匹配旧格式。

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
