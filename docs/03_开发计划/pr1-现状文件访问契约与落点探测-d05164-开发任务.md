## 二、任务分解

### PR1 · 现状文件访问契约与落点探测

#### 任务概述

后面所有片都要往一个文件里写「需求现状」，模型再去读它。**这一片先把这个文件放哪、谁能改它定死**，否则后面写出来的东西可能模型读不到，或者模型自己就能改。

实测结论（生产版本 codex 0.143.0）：文件放在工作区**外**时模型只能读不能写（沙箱直接报 `Read-only file system`，连 `chmod` 都被拒）；放在工作区**内**则模型可写、可删、可先 `chmod 0644` 再改——文件权限位完全挡不住，因为 BFF 和 Codex 是同一个用户。沙箱的路径级保护只覆盖 `.git` / `.agents` / `.codex`。

但工作区外的路径在**原生 Windows 上未验证**（官方文档提示可能拒绝工作区外读取），所以不能写死。

#### 任务分解

**1. 落点探测**

- BFF 启动时执行 `codex sandbox -c sandbox_mode=read-only -- cat <探针文件>`，复用既有 `codexBin` 配置
- 这是纯命令行调用，**不发起 LLM 回合**，不产生 token 成本
- 探测结果缓存，不必每次会话都探

**2. 两个落点的路径解析**

- 探测通过 → `<dataDir>/observations/<sessionId>/`（模型只读，BFF 单向维护天然成立）
- 探测失败 → `<projectRoot>/.suduo/observations/<sessionId>/`，目录内写 `.gitignore`（内容 `*`），不改用户自己的 gitignore
- 当前生效落点要能被 briefing 读到（PR6 会用）

**3. 降级路径的防篡改兜底**

工作区内无法强制保护，改为：BFF 每次刷新前比对上次写入的 hash，发现被改则记录一条日志并直接重写。这是「尽力防改」，不是保证。

**4. 顺带修 materials 的 ACL 既有缺口**

`material-service.ts:635` 的 `ensurePrivateDirectory()` 在 Windows 上直接跳过 chmod，而 `mkdir` 的 `mode: 0o700` 在 Windows 被 Node 忽略——**现有快照在 Windows 上没有任何私有保护**。而 `local-json-store.ts:75` 早就有 `repairPrivateFile()` 用 icacls 做 ACL，只是没被复用。把两边接上。

#### 验收标准

- [ ] 探测在 Linux/WSL2 下返回「可读」，落点解析到 dataDir
- [ ] 人为让探测失败时，落点自动降到项目目录且 `.gitignore` 就位
- [ ] dataDir 落点下，`workspace-write` 沙箱内写入该文件失败
- [ ] 项目目录落点下，hash 比对能检出被改并触发重写
- [ ] materials 与 observations 在 POSIX 下为 0700/0600，在 Windows 下走 icacls
- [ ] 探测过程不产生任何 LLM 调用

#### 边界

- 不写现状文件的**内容**（那是 PR3）
- 不碰 briefing、不碰 SSE、不碰生命周期
- 不改远程服务

## 七、已知遗留问题

以下问题经 PR1 review 确认，不纳入本片返工范围：

1. `WorkspaceObservationWriter` 的 hash 防篡改仅为组件级保障：尚未接入生产服务，`onTampered` 默认不记录，且 hash 仅存在内存中，重启后的首次写入无法识别此前篡改。运行态闭环归属 resolver 接入任务。
2. 拒读控制探针仍创建在项目根目录；进程异常终止时可能留下随机隐藏文件。改到 `.suduo/` 前需处理提前创建目录的副作用，归属 resolver 接入任务，不能假定由 PR3 顺带处理。
3. 未覆盖真实 `runObservationSandbox()` 的端到端 CLI 调用、原生 Windows 的 ACL 实效与 stdio 捕获；hash 防篡改在重启、多 writer 与并发 TOCTOU 下未验证；输出上限在子进程退出后读取，不能限制其先写满临时盘。
