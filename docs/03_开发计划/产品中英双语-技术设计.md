# SuDuo 产品中英双语 技术设计

> 一句话：前端与本机后端各用一套「以中文为样板、英文必须同形」的类型化字典，语言随每个请求传给本机后端；云端只出英文与错误码；会被别人看到或会留存的系统文字一律存「类型 + 参数」。先改掉靠中文字符串运行的逻辑、固定测试语言，再按功能区分批迁移。｜最后更新：2026-10-03（S0 已实施，见 §十一）
>
> 需求：[产品中英双语](../02_需求设计/产品中英双语-需求.md)（现状盘点见需求 §二）。

---

## 一、设计概述

**目标对齐**：使用者在设置里选语言（默认跟随浏览器），前端立即切换。之后每个发往本机后端的请求都带上语言，本机后端按它生成错误和提示。新建会话时把语言记在会话上，交给 Codex 的工具说明和需求卡按这个语言出。房间里别人也会看到的系统文字（自动评论、共享 Agent 的原因和进度）存成类型 + 参数，每个人的前端各自按自己的语言渲染。字典用 TypeScript 写：中文版是样板，英文版必须结构相同，少一条就类型检查失败。迁移期用 lint 白名单「只减不增」，最终界面代码里不允许出现写死的中文。

| 项 | 说明 |
|----|------|
| 名称 | 产品中英双语（zh-CN / en） |
| 核心职责 | 语言选择与传递；三处字典（前端、本机后端、共享标签）；系统文字结构化；防回归检查 |
| 设计原则 | ① 缺译文就编译失败；② 留存或跨人可见的系统文字不存成句文本；③ 逻辑判断不依赖任何语言的文字；④ 零新增运行时依赖 |
| 需求来源 | [产品中英双语 需求](../02_需求设计/产品中英双语-需求.md) |
| 覆盖范围 | `client/web`、`client/server`、`client/contracts`、`cloud/contracts`、`cloud/server`、`client/scripts` 的面向使用者输出、对外文档 |
| 不覆盖 | Windows 安装器与启动器、`docs/` 内部文档、代码注释、开发联调脚本（`dev-local.sh`、`gate-c-vm.sh`）、服务端日志 |

## 二、方案与架构

```
                    设置：跟随系统 / 中文 / English
                                │
          ┌─────────────────────┴───────────────────────┐
          ▼                                             ▼
  client/web（浏览器）                           client/server（本机后端）
  ┌─────────────────────────────┐   X-SuDuo-Locale  ┌────────────────────────────────┐
  │ i18n/locale.ts 偏好与解析     │ ───每个请求────▶ │ request.locale（头 → 已存偏好    │
  │ i18n/messages/zh-CN/*  样板   │                   │   → Accept-Language → en）      │
  │ i18n/messages/en/*  satisfies │ ◀──已本地化的──── │ i18n/messages/{zh-CN,en}/*      │
  │ useT() / 统一 format.ts       │   错误与提示      │ settings.locale.json（请求头记下）│
  │ 渲染「类型 + 参数」的记录      │                   │ sessions.locale（建会话时定）   │
  └─────────────────────────────┘                   │ 给 Codex 的文字按会话语言        │
          ▲  类型 + 参数                             └───────────────┬────────────────┘
          │                                                          │ 只取错误码
          │                                                          ▼
          │                                         cloud/server（英文 message + 错误码）
          └──── 自动评论 system、Agent 任务 reasonCode/进度 code ─────┘
                                （云端存类型 + 参数，各人前端渲染）

  共享：cloud/contracts/i18n.ts（Locale 类型、解析、单复数助手、按语言的状态标签）
        client/contracts 只重新导出，依赖方向仍是 客户端 → 云端
```

| 关键原则 | 说明 |
|----------|------|
| 中文字典是样板 | `en` 字典用 `satisfies Messages<typeof zhCN>` 约束：少键、多键、参数签名不一致都是类型错误，满足需求 R2 |
| 语言跟请求走 | 本机后端不猜语言：前端每个请求带 `X-SuDuo-Locale`，本机后端顺手把它记进数据目录的 `settings.locale.json`；后台任务（共享 Agent）与带不了头的请求（EventSource）用最近一次记下的语言 |
| 留存文字结构化 | 会留存、会被别人看到的系统文字存 `code + params`，渲染时翻译；旧数据能识别的回填、识别不了的原样显示 |
| 逻辑不看文字 | 先把按中文比较的逻辑改成按类型 / 常量判断，再动任何文案 |

**与现有系统的关系 / 边界**：

| 涉及模块 | 本设计如何动它 | 保留 / 不动什么 |
|----------|----------------|------------------|
| `cloud/contracts` | 新增 `i18n.ts`；`REQUIREMENT_STATUS_LABELS`、`AGENT_RUN_STATUS_LABELS` 改为按语言取值（实施时：前端改由字典取，`AGENT_RUN_STATUS_LABELS` 已删，`REQUIREMENT_STATUS_LABELS` 只剩本机服务在用）；评论与 Agent 任务 DTO 加结构化字段 | 状态枚举值、接口路径不变 |
| `client/contracts` | 重新导出 `Locale`；`SUDUO_TOOL_LABELS` 改为按语言；新增 `LOCALE_HEADER` 常量；账本警告事件加 `code` / `params` | 工具名 `suduo_*`、错误码枚举不变 |
| `client/web` | 新增 `src/i18n/`；约 2,200 处文案迁入字典；4 套日期工具合并；去掉对服务端文字的正则改写 | 组件结构、路由、data-testid 不变 |
| `client/server` | 新增 `src/i18n/`；`ApiError` 改为传文案键与参数；展示文字、自检、提示词、工具回包迁入字典；`sessions` 加 `locale` 列；git 检查点加标记行 | 错误码、HTTP 状态码不变 |
| `cloud/server` | 错误 `message` 改英文；评论与 Agent 任务存类型 + 参数（增量迁移，ADR-0001） | 审计与活动流已是结构化，不动 |
| 测试 / gate-c | 固定默认测试语言为 zh-CN；新增英文冒烟；视觉基线按语言分文件 | 现有断言大部分保持中文不变 |
| ESLint | 现有 `no-restricted-syntax` 数组里并入中文检测选择器；迁移期白名单 | 旧品牌名拦截规则保留 |

## 三、关键决策与取舍

- **字典实现：自建类型化字典，不引入 i18next / Lingui / react-intl**。只有两种语言、译者就是项目自己，最需要的是「缺译文编译失败」与重构安全。用 TS 对象加函数：参数有类型，单复数用 `Intl.PluralRules`，带组件的句子由函数接收渲染好的节点。零运行时依赖，与前端「不引入新依赖」的惯例一致。没选 i18next：它要靠额外工具才能检查缺键，键是字符串、改名不安全，而它的翻译平台对接、按需加载对两种语言用处不大。代价：将来要接社区翻译或第三种语言时，需要把字典导出成 JSON 目录（届时另立 ADR）。
- **字典按「属性访问」而非字符串键**：`t.requirements.board.empty` 而不是 `t("requirements.board.empty")`，编辑器能补全与跳转，删除未使用条目也容易发现。
- **错误文字由本机后端按请求语言生成，前端照常显示 `message`**：本机后端是每人一个、天然知道请求者语言；前端现有「显示服务端 message、按 code 分类」的链路不用改，只是 message 变成对的语言。没选「前端按错误码翻译」：147 处 `VALIDATION_ERROR` 各是不同句子，要在契约里加子码再在前端维护一份同样大的错误字典，工作量翻倍。云端的 message 本来就到不了用户（`remote-client.ts` 只取 code），改英文即可。
- **语言切换后刷新服务端文字**：切换时前端让所有查询失效重取，已经显示的服务端文字随之更新；账本与记录类数据本来就是前端渲染，立即生效。
- **给 Codex 的文字跟会话走**：`sessions.locale` 在建会话时按请求语言写入，之后不变（需求 R6）。线程的说明和工具定义只在建线程时下发，这样同一会话前后一致。共享 Agent 的线程用所有者 `settings.json` 里的语言。
- **git 检查点：提交说明按语言写，识别靠标记行**：提交正文末尾加 `SuDuo-Checkpoint: turn-start | manual`。识别时先看这一行，再兼容旧的中文前缀「SuDuo 自动存档」「SuDuo 检查点」；两种前缀常量放在 `client/contracts`，前端与后端共用，不再各写一份。
- **测试默认固定 zh-CN**：jsdom 的 `navigator.language` 默认是英文，Playwright 也没设语言。不固定的话，改造一上来就会大面积变红，或者让反向断言（`not.toMatch(/中文/)`）悄悄失效。现有约 670 处中文断言保持不动；另加英文冒烟与英文专属断言。
- **lint 白名单只减不增**：中文检测选择器并进现有拦截旧品牌名的同一个数组（flat config 中同名规则后者整体覆盖前者，分开写会把品牌规则冲掉）。迁移期用一个「待迁移文件清单」配置块，对清单里的文件使用不含中文选择器的数组；每批迁移从清单里删文件，最后删掉整个配置块。字典目录、测试、`src/dev/`、显式标注的旧数据兼容常量不受此规则约束。

## 四、核心流程 / 逻辑

### 4.1 语言解析与传递

```
页面加载 ─ theme-init.js（渲染前）读 localStorage 的偏好
          → resolveLocale(偏好, navigator.language) → <html lang> 与首屏语言
React 启动 ─ LocaleProvider 提供 locale 与 t
每个请求 ─ api client 加头 X-SuDuo-Locale: zh-CN | en
本机后端 ─ request.locale = 头 ?? settings.locale ?? 解析 Accept-Language ?? "en"
          头里是合法语言时记进 settings.locale.json（变化才写；写失败只记日志，不影响请求）
用户切换 ─ 写 localStorage → 更新 <html lang> → 按新语言重建界面
          → queryClient.invalidateQueries() → 重取请求带上新语言头，服务端文字与记下的语言一起变
别的标签页 ─ 监听 storage 事件跟着切
```

`resolveLocale` 规则：偏好为 `zh-CN` / `en` 时直接用；为「跟随系统」时，语言标签以 `zh` 开头取 `zh-CN`，否则取 `en`，且只落在界面已经做完的语言里（`client/web/src/i18n/locale.ts` 的 `UI_LOCALES`，迁移期只有 zh-CN）。

### 4.2 字典形态

```ts
// client/web/src/i18n/messages/zh-CN/requirements.ts（样板）
export const requirements = {
  board: {
    empty: "还没有需求",
    count: (n: number) => `${n} 条需求`,
    movedBy: (p: { who: ReactNode; status: string }) => [p.who, " 把状态改为 ", p.status],
  },
};
// client/web/src/i18n/messages/en/requirements.ts
export const requirements = {
  board: {
    empty: "No requirements yet",
    count: (n: number) => plural("en", n, { one: "1 requirement", other: `${n} requirements` }),
    movedBy: (p) => [p.who, " changed status to ", p.status],
  },
} satisfies Messages<typeof zhRequirements>;
```

### 4.3 留存文字的结构化

| 对象 | 现在 | 改为 | 旧数据 |
|------|------|------|------|
| 发布产物自动评论 | `body` 存「发布了产物 vN，含 M 个文件。」，活动流用相等比较判断有无说明 | 新增 `system_kind = 'artifact_published'` + `system_params {versionNumber, fileCount}`；`body` 存英文兜底句（该列非空约束不变）；判断改为看 `system_kind` | 迁移时回填挂在该版本上、正文逐字等于旧句式的评论 |
| @ 提及 | DTO 已有 `kind: user / agent / all`，`label` 存中文「所有人」与 Agent 标签 | 渲染与高亮按 `kind`（`all` 按看的人的语言显示）；正文里的 `@所有人` / `@everyone` 都认 | 不迁移，`kind` 已足够 |
| 共享 Agent 任务 | `reason`、`progress`、`events` 存所有者本机生成的中文 | 新增 `reason_code` + `reason_params`；进度与事件条目带 `code` + `params`；文字列存英文兜底 | 旧行没有 code，原样显示文字 |
| 本机账本警告 / 审批撤回 | `runtime.warning` 的 `payload.message` 存中文，部分无 code | 一律带 `code` + `params`；前端按 code 渲染 | 无 code 的旧事件原样显示 |
| git 检查点 | 中文前缀识别 | 见 §三 | 旧前缀继续识别 |
| 默认名称 | 「新会话」「REQ-n 讨论」「房间任务」 | 按创建者语言生成 | 用户数据，不动 |

**模拟示例**：Alice（en）在 REQ-128 发布产物 v3、没写说明。她的本机后端调用云端发布接口，云端写评论：`body = "Published confirmed version 3 with 2 files."`、`system_kind = 'artifact_published'`、`system_params = {"versionNumber":3,"fileCount":2}`。张三（zh-CN）打开活动流：前端看到评论的 `system`，用中文字典渲染「发布了产物 v3，含 2 个文件。」，并判定「无发布说明」。一年前的旧评论 `body = "发布了产物 v1，含 5 个文件。"` 已被迁移回填了 `system_kind`，Alice 看到的是英文。

| 处理规则 | 说明 |
|----------|------|
| 缺译文 | 编译期发现（类型检查），运行时不存在缺键回退 |
| 未知 code | 前端显示通用文字 + 兜底文本（`body` / `reason` / `message`），不吞 |
| 日期与数字 | 一律走 `ui/format.ts`：`Intl.DateTimeFormat`、`Intl.RelativeTimeFormat`、`Intl.NumberFormat`；仍用 date-fns 格式串的地方传入 `zhCN` / `enUS` locale |
| 排序 | 服务端保持 `zh-CN` 排序规则（对拉丁字母同样正常） |
| 设置搜索与命令面板 | 索引同时包含两种语言的关键词，显示用当前语言 |

## 五、测试策略

- [ ] **单元**：`resolveLocale`、单复数助手、字典同形（类型检查即覆盖）；`git-service` 新旧前缀与标记行识别；云端评论回填正则与活动流判断；账本警告按 code 渲染；`request.locale` 的回退链。
- [ ] **组件**：语言切换后界面、`<html lang>`、服务端文字刷新；英文下关键页面渲染（长文本不截断的检查点）。
- [ ] **测试环境**：`client/web/test/setup-dom.ts` 固定 `navigator.language = "zh-CN"`；gate-c 的 Playwright 上下文设 `locale: "zh-CN"`；新增 `SUDUO_GATE_LOCALE=en` 跑英文冒烟（登录、看板、需求详情、开工、会话一轮、房间、设置）。
- [ ] **视觉基线**：`gate-c/visual-baseline` 按语言分文件；中文全量照旧，英文覆盖 7 个关键页的亮色 × 宽视口。
- [ ] **反向断言**：把 `not.toMatch(/中文/)` 一类改写成明确的正向断言，避免换语言后悄悄失效。
- [ ] **提示词**：中英两版逐条对照；用真实会话回放各跑一轮「从需求开工 → 调用需求工具 → 结论笔记」，比对工具调用是否一致。
- [ ] **lint**：中文检测规则对白名单外文件生效；白名单只减不增（加一条检查：清单不得新增条目）。
- [ ] **全量**：每个分片在改动的端跑 `pnpm typecheck` / `pnpm lint` / `pnpm test`；改契约时两端都跑；S0、S4、S7、S9 结束各跑一次 gate-c。

## 六、数据设计

| 实体 / 表 | 关键字段 | 说明 |
|------|----------|------|
| 本机 SQLite `sessions` | `locale TEXT NOT NULL DEFAULT 'zh-CN'` | 新增迁移；存量会话都是中文提示词建的，默认值正确 |
| 本机 `settings.locale.json`（与 `settings.json` 同目录） | `{ "locale": "zh-CN" \| "en" }` | 前端最近一次使用的界面语言，由本机后端从请求头记下（先写临时文件再改名）；后台任务读取，经 `SettingsDto.locale` 只读给出。单独成文件，是为了请求路径上的被动写入永远不碰 `settings.json`。界面偏好（含「跟随系统」）只存在浏览器 localStorage |
| 云端 `requirement_comments` | `system_kind varchar(32) NULL`（取值 `artifact_published`）、`system_params jsonb NULL` | 增量迁移 + 旧句式回填 |
| 云端 `agent_runs` | `reason_code text NULL`、`reason_params jsonb NULL`；`events` 条目增加 `code` / `params` | 增量迁移；旧行不回填 |
| 本机账本 `runtime.warning` 等 | `payload.code`、`payload.params` | 只改新写入事件的形状；读取兼容旧形状 |

**枚举（示例，实施时以代码为准）**：`AgentRunReasonCode`（如 `owner_offline`、`share_expired`、`share_closed`、`turn_failed`、`answer_truncated`）、`RuntimeWarningCode`（如 `thread-rebuilt`、`unsupported-request`、`connection-rebuilt`）、`CommentSystemKind`（`artifact_published`）。

## 七、接口设计

| 端点 / 约定 | 方法 | 作用 | 认证 |
|------|------|------|------|
| 请求头 `X-SuDuo-Locale` | — | 前端每个发往本机后端的请求都带；本机后端据此生成错误与提示 | 同现状 |
| 本机设置接口（沿用现有设置读写） | GET / PUT | 增加 `locale` 字段 | 同现状 |
| `/doctor` 纯文本自检页 | GET | 按 `?lang=` → 已存偏好 → `Accept-Language` 选语言 | 同现状 |
| 云端评论 DTO | — | 增加 `system?: { kind, params }`（判别联合，以后加类型往里加） | 同现状 |
| 云端 Agent 任务 DTO | — | 增加 `reasonCode?`、`reasonParams?`；进度事件带 `code` / `params` | 同现状 |
| 错误响应 | — | 结构不变：`{ error: { code, message, requestId, details? } }`；本机后端的 `message` 按请求语言生成，云端的 `message` 为英文 | 同现状 |

## 九、迁移影响与风险

| 风险 | 影响 | 应对 |
|------|------|------|

**英文写法**

- 句首大写（sentence case）：按钮、标题、菜单都是 “Start session”，不是 “Start Session”。
- 简短直接，用 you；不用感叹号，不用 “Please” 开头的客套，不用 “Oops”。
- 按钮用动词：Save、Create requirement、Restore；确认对话框的按钮与标题里的动作一致。
- 错误说明发生了什么、你能做什么，不堆叠技术细节；技术细节放在可展开的详情里。
- 单复数用 `plural()`（`@suduo/client-contracts`），不写 “file(s)”。
- 标识符不翻译：`suduo_*` 工具名、API 路径、错误码、配置项、环境变量、文件名、Git 分支名。
- 用户写的内容（需求标题、评论、消息、项目名、文件名）原样显示。
- 输入框示例统一写成 “e.g. …”，示例名用英文场景（e.g. Checkout、e.g. Alex Chen）；引用名字用弯引号 “ ”。

**字典写法（前端）**

- 按功能区分文件：`client/web/src/i18n/messages/zh-CN/<分区>.ts` 导出同名对象，英文同名文件 `satisfies Messages["<分区>"]`。
- 组件里 `const t = useT()`；React 之外的代码按调用时的语言取 `messagesFor(currentLocale())`，或由调用方传入 `t`；不要在模块加载时取文字（常量列表改成函数）。
- 带参数的句子写成函数；句子里要嵌组件（链接、加粗）时，函数接收渲染好的节点、返回节点数组。
- `aria-label`、`title`、`placeholder`、空状态、加载与失败提示、确认对话框都要进字典。
