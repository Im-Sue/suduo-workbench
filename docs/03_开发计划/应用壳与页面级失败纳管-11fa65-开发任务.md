## 二、任务分解

### pr7 应用壳与页面级失败纳管

#### 任务概述

这片管的是**壳**：全局 toast 宿主、崩溃兜底、鉴权失效后的整页出路、以及模式切换时在途请求的处理规则。需求「八、拆分预览」把「故障分级与页面级失败 / 崩溃兜底纳管」列为独立第 6 项——它在代码上落到的就是这一层，与三个域片没有文件重叠。

**`RequirementsV2App.tsx` 是全局壳，不是需求模块壳**：它渲染全局 `MessageHost`（`:278`，2026-08-25 实测行号），并分发 `SettingsMode`（`:295` / `:339`）与 `SessionsMode`（`:327`）。所以它归本片而不是 pr3。

#### 任务分解

1. **`RequirementsV2App.tsx` 4 处 `showMessage` 逐项定路由**（`:89` / `:212` / `:239` 三处 `messageOf(cause)` + `:220` 「请先选择远程项目」）。注意 `:220` 不是失败而是**前置条件未满足**，很可能该落 `field` 或行内提示而非 toast。

2. **鉴权失效走页面级失败**（需求 4.6）：401 / 登录态失效 → `PageFailure` 占内容区 + 明确「去登录」动作。
   - **本片负责注册，不负责渲染**：调 pr2 的 `registerAuthExpiredHandler(logout)`，把已有的 `logout`（`RequirementsV2App.tsx:242`）接进契约层。`PageFailure` 由 pr2 的 `MessageHost` 承载，**挂载点 `:278` 一个字不改**。
   - 因此 pr3~pr6 只需调 `reportFailure` 即可触发整页失败，**不需要本片为它们提供任何 props**——这是 2026-08-25 勘误解除 pr3↔pr7 死锁的落点（详见 outline「勘误」第 3 条）。
   - **端到端链路由本片验收**：pr3~pr6 只验「判定正确 + 选对出口」，「触发 → PageFailure → 去登录 → 登录页」这条完整链路归本片证明。
   - 与 `RequirementsLogin.tsx` 打通：该文件 `:16` / `:31` / `:51` 已有一套自己的 inline error（`setError(messageOf(cause))`），本片把它接到契约的 `InlineError`，并保证「PageFailure 去登录 → 登录页失败 → InlineError」这条链完整。
   - 409 `AUTH_INVALID`（远程地址变更需重新登录）必须走到这条路径，**不能走版本冲突的自动刷新分支**——否则用户永远刷不出来。

3. **`AppErrorBoundary.tsx` 纳入统一语言**（69 行，2026-07-23 白屏事故的产物）
   - 只统一文案、可操作项、以及它与其他错误层（`PageFailure` / `RegionError`）的关系与边界。
   - **不重写恢复机制**，「清缓存重载」保持原样（需求六章明确不做项）。
   - 它由 `main.tsx:21` 在全局入口包裹，层级关系写进契约文档的镜像表。

4. **四类故障分级落地**（需求 4.6）：鉴权失效 / 浏览器→本机 BFF 不通 / BFF→远端不通 / SSE 断连，各自的判定方式、打扰级别与文案在壳层收口。
   - 「浏览器→本机 BFF 不通」的文案**不得断言原因**——裸 `TypeError` 无法区分本机未启动、CORS、超时、DNS。不给「去启动 SuDuo」这类误导性动作。

5. **模式切换与详情进出的在途请求规则**（需求 4.5）：取消还是允许完成但不回写，在壳层给出统一规则。
   - **`RequirementsV2App.tsx:160` 「退出详情用 `back()` 避免历史死循环」的设计必须保留，不得被新契约推翻**（需求 4.5 明确点名）。

6. **`RequirementsWorkspaceMappingDialog.tsx`**（77 行）按 `ConfirmDialog` / `FormDialog` 的区分归位——它是表单类还是确认类，给出结论。

7. **同提交跑 pr1 的基线再生成命令**。

### 第 1 轮为什么没过：契约层缺陷被修在壳层

执行方在实施中发现裸 `TypeError` 会泄漏浏览器原始文案，自行加了防护并写了注释说明理由。**判断完全正确，但位置不对。**

审查方跑一次性探针取证（跑完即删）：

```
IN=[Failed to fetch]                                  KIND=transport_unknown  MSG=[Failed to fetch]
IN=[NetworkError when attempting to fetch resource.]  KIND=transport_unknown  MSG=[NetworkError when attempting to fetch resource.]
IN=[空]                                                KIND=transport_unknown  MSG=[暂时无法连接工作台，请稍后重试]
```

`classify.ts` 的 `message: details.message?.trim() || fallbackMessage(kind)` **优先采用浏览器给的原始 message**，中性兜底只在 message 为空时生效。后果：

- 本机 BFF 未启动是**最常见的失败场景**。Chrome 显示英文 `Failed to fetch`；**Firefox 显示 `NetworkError when attempting to fetch resource.`——明确的网络归因，直接违反 spec「裸 `TypeError` 不归因」的硬规则**，且中文界面蹦英文。
- pr7 在壳层挡住了，**但 pr3~pr6 五个模块全都没挡**。契约的「不归因」承诺当时只在记得手动 normalize 的地方成立——**这恰是本需求要消灭的「每页各自发明一套」**。

顺带查出 pr2 有一条**假绿用例**：`classifyFailure(new TypeError("fetch failed"))` 断言 `not.toContain("启动")`——message 本就是 "fetch failed"，不含「启动」，所以该用例一直绿，却从未真正验证兜底生效。

**Claude 裁决**：特批解除 `feedback/**` 冻结，**仅限 `classify.ts` 一处**——`transport_unknown` 始终用中性兜底、忽略 `cause.message`；其余 kind 保持（服务端给的中文 message 有价值）。同时要求删除壳层的局部补丁，避免留下第二套逻辑。
理由：宁可晚一轮，也不发一个已知的、一行可修的 spec 违反；局部补丁修在壳层等于把契约层的承诺变成各模块的自觉，与需求目标相反。
