### 🔴 本次验收发现的缺陷（需另开返工）

**缺陷：PostgreSQL 连接中断导致 requirements-service 进程崩溃退出**

- **复现**：服务正常运行时停止 PostgreSQL（`pg_ctl -m fast stop`）→ 进程立即退出，4100 端口消失，后续请求返回 `HTTP 000`（连接失败）而非 503。
- **根因**：`cloud/server/src/infrastructure/database.ts:44` 创建 `new Pool({...})` 后**未注册 `pool.on("error", ...)`**。全代码库无该监听器。空闲连接被服务端断开时（`error: terminating connection due to administrator command`），`pg` 触发 Node 的 `Unhandled 'error' event`，进程终止。
- **与文档冲突**：T5-1 交付的 `cloud/server/DEPLOYMENT.md:27` 声称「数据库不可达时它返回 HTTP 503」。实测无法返回 503——进程已不存在。该表述需修正或随代码修复而成立。
- **影响**：PG 重启、主从切换、网络抖动、连接超时均会导致服务崩溃。compose 的 `restart: unless-stopped` 可自动拉起，属缓解而非修复；PG 长时间不可用时会陷入崩溃—重启循环。
- **归属**：该 Pool 代码属 T1 期既有实现，非 T4/T5 引入；但按 spec「验收发现缺陷，缺陷另开返工」，应在发行前修复。
- **建议修复**：注册 pool 级 error 监听并记录日志，使空闲连接错误不上升为未捕获异常；同时确认 `/v2/health` 在 DB 不可达时确实返回 503。修复成本低。

**说明**：此缺陷仅能由实机运行发现——typecheck、lint、单元测试与静态扫描均无法覆盖。这正是 T5-3 存在的价值。

## 九、缺陷修复与本地环境固化（2026-08-15）

### 缺陷修复：PG 连接中断不再导致进程崩溃

**提交** `c36884d`，改动 3 个文件、85 增 8 删，边界未越界（`client/server`、`client/web`、`packages`、`migrations` diff 均为空）。

**修复实现**（`cloud/server/src/infrastructure/database.ts:49-56`）——**双层监听**：

```ts
pool.on("error", (error) => { console.error("... idle connection error", error); });
pool.on("connect", (client) => {
  client.on("error", (error) => { console.error("... connection error", error); });
});
```

值得记录的是：执行方**首次仅加 Pool 级监听后实测仍然崩溃**，据此定位到第二层原因——附件所有权使用的是从 pool 长期 checkout 的 client，其 `error` 事件不经 Pool 冒泡，必须在 `connect` 时逐个挂载。若只做第一层，缺陷会以更低频率残留，且更难复现。

**Claude 独立实测复验**（非采信回执自述）：

| 步骤 | 操作 | 结果 |
|---|---|---|
| ① | 正常态 | `/v2/health` 200，服务 pid=4142984 |
| ② | `systemctl --user stop suduo-postgres.service` | PG `inactive`；**服务存活且 pid 未变（4142984）**；`/v2/health` **503**，响应 `{"error":{"code":"DEPENDENCY_UNAVAILABLE","message":"数据库依赖不可用"}}` |
| ③ | `systemctl --user start suduo-postgres.service` | **不重启服务**即自愈；`/v2/health` 200；pid 仍为 4142984，`uptimeMs` 连续（106438ms） |

pid 全程未变是关键证据：排除了「崩溃后被 systemd/compose 拉起」的假通过。

**业务错误语义未被吞掉**（error 监听最易改坏之处）：不存在资源 404、无 token 401、参数校验 400、乐观锁冲突 409，均正确返回；PG 恢复后读写正常。

### 本地 PostgreSQL 固化

用户要求本地安装 PostgreSQL。因 `apt` 需 sudo 密码（AI 无法提供），采用便携二进制 + systemd user 服务方案，为完整的 PostgreSQL 18.4 而非嵌入式替代品：

| 项 | 值 |
|---|---|
| 服务单元 | `~/.config/systemd/user/suduo-postgres.service`（已 `enable --now`，开机自启） |
| 二进制 | `~/.local/share/suduo-postgres/pgsql`（源自 `@embedded-postgres/linux-x64` 18.4） |
| 数据目录 | `~/.local/share/suduo-postgres/data` |
| 监听 | 127.0.0.1:15432（非标准端口，避免与将来的系统级 PG 冲突） |
| 日志 | `~/.local/share/suduo-postgres/postgres.log` |

实施记录：`Type=notify` 启动会卡满超时——经 `ldd` 查证该便携 `postgres` 的 libsystemd 链接数为 0，不支持 sd_notify 协议；改用 `Type=forking` + `pg_ctl -w` 后正常。临时实例数据已整体迁入，迁移后 users/projects/requirements/attachments 各 1 行完整保留。

若日后改用系统级 PG，安装后将 `REQUIREMENTS_DATABASE_URL` 指向新实例，再 `systemctl --user disable --now suduo-postgres.service` 即可退役本方案。
