# SuDuo 客户端桌面应用 技术设计

> 一句话：新增 `client/desktop`（Electron 外壳）。它用捆绑的官方 Node 24 拉起原样的本机服务，在自己的窗口里显示 `http://127.0.0.1:<端口>/`，并负责托盘常驻、退出确认、更新和开机自启。用 electron-builder 产出 Mac（Apple 芯片 / Intel）和 Windows x64 安装包，首版不签名，作为试用版发布。｜最后更新：2026-10-06
>
> 需求：[客户端桌面应用安装包-需求](../02_需求设计/客户端桌面应用安装包-需求.md)｜决策：[ADR-0013](../06_决策记录/ADR-0013-客户端桌面外壳采用Electron-本机服务跑在捆绑的官方Node上.md)

## 一、设计概述

**做什么**：把现有客户端（本机服务 + 前端 + 锁定的 Codex）装进桌面外壳，打成三个安装包。

**不改什么**：
- 本机服务与前端的形态：仍是只监听 127.0.0.1 的 Web 服务加它托管的页面。
- 业务逻辑、数据库结构、云端，以及源码运行（`pnpm start`）和 gate-c。

**版本基线**（2026-10-06 核实，实施时取当时最新的小版本）：

| 组件 | 版本 | 说明 |
|---|---|---|
| Electron | 44.5.1（Chromium 152） | 当前最新稳定版，Electron 只维护最近三个大版本 |
| 捆绑的 Node | 24.21.0（官方二进制） | 满足 `engines >=24.10`，只用来跑本机服务 |
| better-sqlite3 | 12.11.1，官方 Node 预编译包（ABI 137） | 与源码运行同一个包 |
| Codex | 0.159.2，各平台 vendor 目录 | 与 `client/codex-protocol/VERSION` 一致 |

**体积估算**（按 2026-10-06 下载到的各组件实测压缩大小）：

| 组成 | 压缩后 | 解压后 |
|---|---|---|
| Electron 外壳 | 约 130 MB | 约 280 MB |
| Codex（单平台） | 约 130 MB | 约 305 MB |
| Node | 约 30–40 MB | 约 110 MB |
| 本机服务 + 前端 | 约 5 MB | 约 15 MB |
| **合计** | **约 280–300 MB 下载** | **约 700 MB 安装后** |

Windows 安装包用 LZMA 压缩，应该会小一些。以上都以 D1 实测为准。

## 二、方案与架构

```
SuDuo.app / SuDuo.exe —— Electron 主进程（client/desktop）
 │  单实例锁 · 菜单 · 托盘 · 窗口 · 更新 · 开机自启 · 退出确认
 │
 │  启动：读取登录 shell 环境（Mac）→ 选端口 → 拉起本机服务 → 等 /healthz → 窗口载入本机地址
 │
 ├─ 子进程：resources/node/node  resources/suduo/server/dist/main.mjs      ← 捆绑的官方 Node 24
 │     本机服务（与源码运行同一份代码，用 esbuild 打成单文件）
 │     ├─ 托管 resources/suduo/web/dist（前端产物）
 │     ├─ SQLite：resources/suduo/node_modules/better-sqlite3（官方 Node 预编译包）
 │     └─ 拉起 resources/codex/<平台>/bin/codex（锁定 0.159.2，目录原样保留）
 │
 └─ 窗口：BrowserWindow（contextIsolation + sandbox，不开 nodeIntegration）
       载入 http://127.0.0.1:<端口>/；preload 只暴露 window.suDuoDesktop（见 §七）
```

**原则**：
1. 外壳不承载业务逻辑。外壳需要的数据都通过本机服务现有或新增的 HTTP 接口取得，前端照常调用本机服务。
2. 本机服务在安装版里的运行方式和源码运行一样：同样是官方 Node、同样的代码和 SQLite 模块。区别只在环境变量。
3. 浏览器访问本机地址照样可用。

**安装包内布局**（沿用旧 Windows 安装器已经跑通的相对布局，本机服务按 `../../web/dist/` 找前端，不用改代码；目录名用 `suduo/` 而不是旧安装器的 `app/`，因为 `resources/app` 是 Electron 自己找应用代码的位置）：

```
resources/
├── app.asar                      外壳：主进程、preload、启动页
├── suduo/
│   ├── server/dist/main.mjs      本机服务（esbuild 单文件）
│   ├── server/dist/doctor.mjs    自检（启动失败时用）
│   ├── server/dist/migrations/
│   ├── web/dist/                 前端产物
│   └── node_modules/better-sqlite3（+ bindings、file-uri-to-path）
├── node/node | node.exe          官方 Node 24
├── codex/<目标三元组>/            Codex vendor 目录原样（bin/codex、codex-path/rg、codex-resources）
└── licenses/                     LICENSE、THIRD_PARTY_NOTICES 与各组件许可
```

**数据与端口**：

| | Mac | Windows |
|---|---|---|
| 安装位置 | `/Applications/SuDuo.app` | `%LOCALAPPDATA%\Programs\SuDuo` |
| 外壳数据（偏好、窗口位置、网页缓存） | `~/Library/Application Support/SuDuo Desktop/` | `%LOCALAPPDATA%\SuDuo Desktop\` |
| 本机服务数据（SQLite 等） | `…/SuDuo Desktop/data/` | `…\SuDuo Desktop\data\` |
| 日志 | `…/data/logs/suduo.log`（服务）、`desktop.log`（外壳） | 同左 |
| Codex 配置 | `~/.codex` | `%USERPROFILE%\.codex` |
| 端口 | 首选 8790；被别的程序占用时依次试 8791–8799，选中后记住 | 同左 |
| 源码运行（对照，不变） | `~/Library/Application Support/SuDuo/`，8787 | `%LOCALAPPDATA%\SuDuo\`，8787 |

Electron 默认的外壳数据目录是 `<系统应用数据目录>/SuDuo`，在 Mac 上正好就是源码运行的数据目录，Windows 上则落在漫游目录。所以主进程在 `ready` 之前用 `app.setPath("userData", …)` 改到上表的位置。端口记住后不再变动：网页的本地存储按「地址 + 端口」区分，端口一变，界面偏好和草稿就丢了。

## 三、关键决策与取舍

| # | 决策 | 否决的方案与理由 |
|---|---|---|
| 1 | 外壳用 **Electron**（[ADR-0013](../06_决策记录/ADR-0013-客户端桌面外壳采用Electron-本机服务跑在捆绑的官方Node上.md)） | Tauri：Mac 上换成 WebKit，界面验收要重做，前端要改通知、下载、外链，还要多一套 Rust。启动器 + 浏览器：没有常驻，共享 Agent 会掉线。详见需求「讨论 1」 |
| 2 | **本机服务跑在捆绑的官方 Node 上**，不用 Electron 内置的 Node | 用内置 Node（utilityProcess）能省约 35 MB，但 better-sqlite3 12.11.1 的 Electron 预编译包只到 ABI 146（Electron 42），Electron 43 / 44 必须在每台构建机上现场编译；13.x 的发布已不再附带预编译包。另外，内置 Node 和源码运行、CI 测试用的官方 Node 不是同一个构建。改用捆绑 Node 后，Electron 升级不再牵动 SQLite 模块，本机服务的运行环境也和测试过的完全一致 |
| 3 | 打包用 **electron-builder + 暂存目录** | 不让 electron-builder 直接读 pnpm 工作区：符号链接布局容易出问题。由自己的 `stage.mjs` 把产物、Node、Codex、SQLite 模块放进暂存目录，并关闭 electron-builder 的依赖重编译 |
| 4 | **捆绑资产按版本和 SHA256 锁定**，带离线缓存 | 沿用旧 Windows 安装器 `assets.mjs` / `fetch-assets.mjs` 的做法。Mac 两种芯片和 Windows 三个平台的 Node、Codex、SQLite 模块都锁定，任何一台机器都能暂存任意目标；冒烟测试仍须在对应平台上跑 |
| 5 | **Mac 用临时签名**（ad-hoc），Codex 和 Node 保留各自原有的 Developer ID 签名 | 完全不签名的话，Apple 芯片会报「已损坏」；临时签名下系统通知也能正常弹出（Electron 文档写明 ad-hoc 签名足够） |
| 6 | **Windows 用 NSIS 按当前用户一键安装**（`oneClick`，`perMachine: false`） | 带向导的安装界面对试用没有价值，还会让后台自动更新变复杂。卸载时询问是否删除数据，用自定义 NSIS 宏实现，自动更新触发的卸载跳过这一步 |
| 7 | **更新用 electron-updater + GitHub Releases** | Windows 走完整流程：下载、校验 sha512、退出时静默安装。Mac 未签名时只检查版本、打开下载页（Squirrel.Mac 要求已签名）。不自己写检查逻辑 |
| 8 | **用健康检查区分运行形态**：`/healthz` 增加 `runMode` 字段 | 源码运行的 `pnpm start` 把 `runMode` 不是 `source` 的服务当成「别的程序」，提示换端口，不会接管安装版；安装版只认 `runMode: desktop` 且实例标识（外壳生成、存在 `desktop.json`，经 `SUDUO_INSTANCE_ID` 交给本机服务，随 `/healthz` 带出）与自己一致的服务。用实例标识而不是数据目录，是为了不在健康检查里暴露本机路径 |
| 9 | **外壳和前端通过 preload 桥通信**，接口最小化，每次调用都校验发送方是本机地址 | 不在页面里开 Node 能力 |
| 10 | **退役旧 Windows 安装器** | 它从未发布。其中有用的部分搬进新外壳：探测与拉起逻辑、资产锁定、esbuild 打包、安装后冒烟 |
| 11 | **Electron 的 npm 安装脚本不放行**，用到时再下载 | 源码运行的 `pnpm install` 不因此多下载约 100 MB 的 Electron。`desktop:dev` 首次运行时再执行 Electron 的安装脚本；electron-builder 打包时会自己下载并缓存 Electron |

**ADR-0004 自查**：本设计没有新增锁、版本校验、幂等表或 409 一类拒绝式守卫。单实例只是把已有窗口带到前面；退出前有进行中的会话时只确认一次，确认后照常退出（需求 R9 和「保真差异」已过三问）。更新不强制。

## 四、核心流程

### 4.1 启动

```
双击图标
 ├─ requestSingleInstanceLock() 失败 → 通知已运行的实例把窗口带到前面 → 退出
 ├─ setPath(userData) → 读 desktop.json（端口、偏好、窗口位置）
 ├─ 窗口先载入内置启动页（中英文按 §4.7 选），显示「正在启动本机服务…」
 ├─ Mac：读取登录 shell 环境（§4.4），最多等 10 秒
 ├─ 选端口：
 │     按「上次用的 → 8790 → 8791…8799」逐个看：先试绑定，能绑上就用它
 │     绑不上、但 /healthz 是 runMode=desktop 且实例标识相同（上次外壳异常退出留下的服务）
 │       → 里面没有进行中的会话：调用 /api/v1/admin/shutdown 停掉它，等端口释放后重新拉起，保证服务由当前外壳管理
 │       → 里面还有进行中的会话：先问使用者（ADR-0004：告知并给选项）——「停掉并重新启动」或「等会话结束再启动」（每 5 秒看一次）
 │     desktop.json 记下的服务 pid 还活着、端口却一时认不出它（还在迁移、没回应）：最多多等 10 秒再判断
 │     绑不上、也不是自己的 → 试下一个；选中后写回 desktop.json
 │     全部被占用 → 失败页
 ├─ 拉起：spawn(resources/node/node, [main.mjs])，env 由三部分合成：
 │     ① 登录 shell 环境（Mac）或继承的环境（Windows）
 │     ② SUDUO_RUN_MODE=desktop、SUDUO_INSTANCE_ID、SUDUO_PORT、SUDUO_DATA_DIR、SUDUO_PID_FILE、
 │        SUDUO_CODEX_BIN=<resources/codex/…/codex>、SUDUO_IDLE_EXIT_MS=0、SUDUO_LOG_LEVEL=info
 │     ③ 不设 CODEX_HOME，用默认的 ~/.codex
 │     stdout / stderr 写入 data/logs/suduo.log（超过 20 MB 轮转，沿用 start.mjs 的做法）
 ├─ 每 300 ms 轮询 /healthz，最长 60 秒（首次启动要跑迁移）
 │     就绪 → 窗口载入 http://127.0.0.1:<端口>/
 │     超时或子进程退出 → 失败页：原因摘要、日志路径，以及「重试」「运行自检」「打开日志目录」三个按钮
 └─ 带 --hidden 参数启动时（开机自启）不显示窗口，只出托盘图标
```

**运行中服务意外退出**：5 分钟内自动重启最多 3 次，间隔依次为 1 秒、5 秒、15 秒。仍然失败时，窗口切到失败页，托盘的提示文字改为「没能启动」（Mac 的模板图标没法着色）。

### 4.2 关窗与退出

```
关窗（窗口的 close 事件）
 └─ 不是「正在退出」状态 → 拦下默认关闭，只隐藏窗口
      首次关窗 → 发一条系统通知「SuDuo 仍在后台运行，可从菜单栏 / 通知区域图标打开或退出」
                 （desktop.json 记下 closeHintShown，之后不再提示）
      Mac：点 Dock 图标（activate 事件）重新显示窗口

退出（托盘「退出」、⌘Q、菜单「退出」、更新安装）
 ├─ before-quit：拦下默认动作
 ├─ GET /api/v1/system/activity → runningSessions > 0？
 │     是 → 弹框「有 N 个会话正在进行，退出会中断它们」[退出] [取消]
 │          选「取消」→ 放弃退出
 ├─ POST /api/v1/admin/shutdown → 等子进程退出，最多 15 秒，超时强制结束
 └─ app.exit(0)

系统关机 / 注销：不弹框（无法阻止），尽力完成第 3、4 步
```

### 4.3 更新

```
启动 30 秒后检查一次，之后每 24 小时一次（设置里关闭了自动检查就跳过）；也可以手动「检查更新」
 └─ electron-updater.checkForUpdates()（autoDownload=false，读 Release 里的 latest.yml / latest-mac.yml）
      没有新版 → 手动检查时提示「已是最新」，自动检查时不打扰
      检查失败（内网、GitHub 不通） → 自动检查时静默记日志，手动检查时显示原因
      有新版 → 通过桥通知前端显示顶部横幅「SuDuo x.y.z 可用 · 更新说明 · 更新」，托盘菜单加一项
         Windows 点「更新」→ 有进行中的会话先确认 → downloadUpdate()（显示进度）
                 → quitAndInstall()：先走 4.2 的退出流程停掉服务，再静默安装、重启
         Mac（未签名）点「更新」→ 用系统浏览器打开该版本的 Release 页面
```

Release 不标成「预发布」：标了的话 `latest` 取不到它，electron-updater 也会跳过。试用的意思写在发布说明和下载页上。

### 4.4 登录 shell 环境（Mac）

- 运行 `"$SHELL" -ilc '<打印标记>; /usr/bin/env -0; <打印标记>'`，超时 10 秒，取两个标记之间的内容解析。用标记是为了避开 oh-my-zsh 一类的欢迎信息。
- `SHELL` 为空时用 `/bin/zsh`。fish 等 shell 同样支持 `-ilc`，实施时实测。
- 去掉 `PWD`、`SHLVL`、`_`、`OLDPWD` 后，与外壳自身的环境合并，交给本机服务。本机服务启动的 Codex 和 Codex 在项目里执行的命令都会继承这份环境。
- 失败或超时时，用外壳自身的环境，PATH 后面补上 `/opt/homebrew/bin`、`/usr/local/bin`，并在 `desktop.log` 和「设置 → 诊断」里提示。
- Windows 不做这一步。常见问题里写明：装了新工具之后要重启 SuDuo，个别情况需要注销重登。

**本机服务不再把自己用的 Node 目录加进 PATH**：`withNodeOnPath` 在 `SUDUO_RUN_MODE=desktop` 时跳过。否则使用者项目里的 `node` 会变成 SuDuo 自带的 Node 24，而不是他自己装的版本。安装版直接运行 Codex 的二进制，不经过需要 PATH 里有 node 的 npm 包装脚本，所以也用不着这一步。

### 4.5 用 ChatGPT 账号登录 Codex

```
设置 → 模型服务 →「用 ChatGPT 账号登录」
 └─ POST /api/v1/codex/account/login
      本机服务为这次登录单独起一个 `codex app-server`（CODEX_HOME 与会话一致）
      → account/login/start（type: chatgpt）→ 返回 { loginId, authUrl }
 ├─ 前端打开 authUrl：安装版经 setWindowOpenHandler 交给系统浏览器，源码运行就是新标签页
 ├─ 用户在浏览器里完成授权；回调由 Codex 自己的本地回调服务处理（Codex 内部逻辑，SuDuo 不经手）
 ├─ 前端每 2 秒轮询 GET /api/v1/codex/account/login/:loginId，直到收到 account/login/completed（成功或失败）
 │     成功 → 刷新 GET /api/v1/codex/account，显示登录方式和账号
 │     10 分钟没完成，或用户点「取消」→ account/login/cancel，结束这个临时进程
 └─「退出登录」→ POST /api/v1/codex/account/logout（account/logout）
```

符合需求 R4：凭据由 Codex 自己写进 `~/.codex`，SuDuo 只拿到 `authUrl` 和登录结果。源码运行同样能用这个功能。

### 4.6 Git 检查

- 「设置 → 诊断」和启动失败页的自检新增 Git 检查，所有运行形态都有。
- Mac 上先用 `xcode-select -p` 判断是否装了命令行工具，装了才执行 `git --version`。没装命令行工具时，`/usr/bin/git` 会直接弹出系统的安装对话框，不能在启动时意外触发。
- 缺 Git 时显示引导：Mac 执行 `xcode-select --install`，Windows 安装 Git for Windows。不阻止启动。

### 4.7 外壳文字的语言

外壳自己的文字（菜单、托盘、提示框、启动页和失败页）用一份很小的中英字典，与现有字典规则一样：中文为样板，英文同形，由测试检查。

语言按以下顺序确定：
1. 前端在语言变化时通过桥调用 `setLocale` 告知外壳；
2. 外壳启动时读取本机服务记下的 `data/settings.locale.json`；
3. 都没有时用 `app.getLocale()`，以 `zh` 开头取中文，其他取英文。

## 五、测试策略

| 层 | 内容 |
|---|---|
| 外壳单元测试（vitest，`client/desktop/test`） | 登录 shell 输出解析（标记、欢迎信息、空值）、端口选择、孤儿服务判定、退出决策、更新状态机、语言选择、IPC 发送方校验、`desktop.json` 读写与损坏恢复、中英字典同形 |
| 本机服务 | `/healthz` 带 `runMode`；`/api/v1/system/activity` 计数（含房间任务会话）；desktop 模式跳过 `withNodeOnPath`；自检的 Git 项（命令行工具缺失与存在两种情况）；Codex 账号接口用假 Codex 夹具覆盖开始、完成、取消、超时 |

## 七、接口设计

### 7.1 本机服务（新增或修改）

| 端点 | 作用 |
|---|---|
| `GET /healthz`（修改） | 增加 `runMode: "source" \| "desktop"`。只有外壳设置 `SUDUO_RUN_MODE=desktop` 时为 `desktop`，其余情况都是 `source`，包括 `pnpm start`、联调栈和 Linux 的 `install:m1`。设置了 `SUDUO_INSTANCE_ID` 时另带 `instanceId` |
| `GET /api/v1/system/activity` | `{ runningSessions: number }`：本次启动以来开始、至今没结束的回合分布在几个会话里（含房间任务会话），用于退出确认。只看本次启动以来的事件，上次异常退出时停在半路的回合不算 |
| `GET /api/v1/codex/account` | 当前登录方式与账号（经 Codex `account/read`）：`{ mode: "chatgpt" \| "apiKey" \| "none", email?: string, plan?: string }` |
| `POST /api/v1/codex/account/login` | 开始 ChatGPT 登录，返回 `{ loginId, authUrl }` |
| `GET /api/v1/codex/account/login/:loginId` | `{ status: "pending" \| "succeeded" \| "failed", error?: string }` |
| `POST /api/v1/codex/account/login/:loginId/cancel` | 取消登录 |
| `POST /api/v1/codex/account/logout` | 退出登录 |

所有写接口都沿用 LoopbackGuard、`Idempotency-Key` 和语言参数的现有约定。

## 十二、实施记录

### D0 外壳骨架（2026-10-06）

**交付**：`client/desktop`（`@suduo/desktop`）；本机服务的 `SUDUO_RUN_MODE` / `SUDUO_INSTANCE_ID`、`/healthz` 的 `runMode` 与 `instanceId`、`GET /api/v1/system/activity`；`start.mjs` 不接管桌面版；`client/contracts/src/desktop.ts`。开发态用 `pnpm desktop:dev`（先 `pnpm build`），说明见 `client/desktop/README.md`。

**验证**：
- client 质量门全过：contracts 12、desktop 30、server 658、web 873，以及 lint 和 testid 基线。
- Apple 芯片 Mac 上用 Playwright 驱动开发态外壳，33 项全过（脚本后来提交为 `client/desktop/scripts/verify-dev.mjs`，修正后扩到 39 项），包括：
  - 首次启动走首选端口，读到登录 shell 环境；
  - 页面拿到桥、没有 Node 能力，外链交给系统浏览器；
  - 菜单随前端告知的语言切换；
  - 关窗隐藏、服务不停，首次提示只出一次；
  - 第二个实例自行退出并唤起已有窗口；
  - `pnpm start` 把桌面版端口当成被占用；
  - 服务被杀后自动重启回到原端口；
  - 有进行中的会话时退出先确认，取消不退、确认后服务停止、端口空出；
  - 外壳被强杀后留下的服务，下次启动时被停掉并在原端口重新拉起；
  - 8790 被占用时换到 8791 并记住；
  - Node 不存在时显示失败页，三个按钮可用、自检有输出。
- 本机服务的 PATH 保持登录 shell 的原顺序，没有把 Node 目录放到最前（§4.4）。
- 以上是初版的验证结果，审查修正后的复验见下方「独立审查」一段。
- gate-c 本片没跑：本机服务只多了只读接口和健康检查字段，前端没改。D2 改前端时再跑。

**与设计的偏差**：
- 桥的全局名按品牌写法规则（ADR-0010）改为 `window.suDuoDesktop`，启动页的是 `window.suDuoStartup`。
- 活动接口返回 `runningSessions`（会话数），不是回合数。它只看本次启动以来的事件，上次异常退出时停在半路的回合不算。
- 认「自己留下的服务」用实例标识，不用数据目录（决策 8）。
- 外壳读取 Codex 位置时，开发态直接用 `client/node_modules/.pnpm/@openai+codex@<版本>-<平台>/…/bin/codex` 二进制，不经过需要 PATH 里有 node 的包装脚本。本机服务的工作目录设为数据目录，这样它不会去找工作区里的 Codex，而是用 `SUDUO_CODEX_BIN`。
- 开发态的外壳数据默认放在「SuDuo Desktop Dev」，可以用 `SUDUO_DESKTOP_HOME` 覆盖，不碰安装版的数据。
- 菜单栏与通知区域图标由 `client/desktop/scripts/icons.mjs` 从品牌标志渲染，结果提交在 `client/desktop/assets/`。

**踩到的坑**：
- 从基于 Electron 的编辑器（如 VS Code 扩展宿主）里启动时，环境里带着 `ELECTRON_RUN_AS_NODE=1`，Electron 会直接当 Node 跑。`dev.mjs` 启动 Electron 前会删掉它；外壳交给本机服务的环境也会去掉所有 `ELECTRON_*`。
- Electron 二进制默认缓存在 `~/Library/Caches/electron`。本机已改到 SSD：在不提交的 `client/mise.local.toml` 里设置 `electron_config_cache` 和 `ELECTRON_BUILDER_CACHE`。
- 实测 Electron 44 的 Mac arm64 外壳解压后约 325 MB，比 §一的估算（约 280 MB）大。D1 实测安装包体积时一并更新。

**独立审查（subagent，只读）与修正**：共 14 条，按严重程度逐条处理：
1. 外壳设置的 `SUDUO_*` 经本机服务漏给 Codex 及其在项目里执行的命令。已修：`runtimeEnvironment` 去掉全部 `SUDUO_*`（只留 `SUDUO_LOCALE`），有测试。
2. 旧服务迟到的退出事件会抹掉新服务的引用；页面载入失败被当成服务启动失败，重试时把自己活着的服务当孤儿停掉。已修：
   - 崩溃回调核对是不是当前服务；
   - boot 开始时先按「自己要求的停止」停掉手里的服务；
   - 页面载入单独处理：`ERR_ABORTED` 忽略，其余记日志、稍后重试一次。
3. 生命周期竞态。已修：
   - boot 在每个等待之后检查是否正在退出；
   - 退出流程先停服务、等启动收尾、再停一次，并包在 try/finally 里；
   - 确认框开着时服务崩了，取消后补一次重启；

**交付**：

- `dist.mjs`：electron-builder 26.15.3 的配置。
- 冒烟模式 `--smoke-report` 与 `smoke.mjs`。
- `--quit`：供安装器调用。
- `build/installer.nsh`：覆盖安装或卸载前先请 SuDuo 自己退出；卸载时询问是否删除数据，自动更新时不问。
- 打包图标：icns 由 `iconutil` 生成，ico 自己写。
- `.github/workflows/desktop.yml`：三个平台各在自己的构建机上构建并冒烟，打版本标签时挂到 Release。这一项原定在 D3，因 0.9.0 发布提前做了。
- 本地命令：`pnpm dist:desktop`、`pnpm dist:desktop:smoke`。

**待实测项的结果**：
1. **隔离标记**：用户 2026-10-06 在本机用浏览器下载 dmg，按「仍要打开」放行后，本机服务正常启动，SQLite 原生模块能加载，连接云端和登录都正常。结论：「仍要打开」覆盖到了包里的原生模块，不需要改用 `node:sqlite`。另外，`spctl` 显示 Node 与 Codex 都是「已公证的 Developer ID」。
2. **签名**：用 `signIgnore` 保留了 Node（HX7739G8FX）与 Codex（2DC432GLL2）的原签名；`better_sqlite3.node` 与外壳都是临时签名；`codesign --verify --deep --strict` 通过。
5. **登录 shell**：zsh 下正常读取。
6. **体积**：Mac Apple 芯片的 dmg 约 274 MB，安装后约 711 MB（外壳 239 MB、Codex 331 MB、Node 128 MB、本机服务与前端 12 MB）。
- 第 3、4 项（Mac 开机自启、Windows 全量更新）留给 D2 / D3。

**踩到的坑**：
- **electron-builder 丢掉 `node_modules`**：extraResources 源目录下直接的 `node_modules` 一律会被丢掉（app-builder-lib 的 `util/filter.js`），本机服务因此起不来。改为把整个 `resources/` 作为一条 extraResources 拷贝。
- **Cookie 加密 fuse 卡住网络请求**：这个 fuse 的密钥放在钥匙串里，临时签名每次构建都不同，钥匙串会反复要授权，网络请求在授权前一直卡着。首页载入从 8–24 秒（一次卡死）降到约 0.1–0.4 秒，是关掉这个 fuse 之后的结果。
- **icns 显示成噪点**：electron-builder 转换出的 icns 把 64 px 的图放进了 48 px 的 `icp6` 槽位，拷贝对话框里的小图标显示成噪点。改用 `iconutil`。
- **自检的 Node 版本要求过严**：原先要求逐字等于 24.10.0，捆绑的 24.21.0 不通过，源码运行装了较新 24.x 的使用者也一样。改为「24.x 且不低于 24.10.0」，与 `engines` 一致。
- **服务的目录名**：不能用 `resources/app`，那是 Electron 找应用代码的位置。改为 `resources/suduo`。

**验证**：
- client 质量门全过：desktop 36、server 661、web 873。
- 开发态端到端检查 39 项全过。
- 安装包冒烟连续多次通过：窗口、健康检查，以及自检中 Node、SQLite、Codex 三项。
- `--quit`：正在运行时退出并停掉服务；没在运行时什么也不启动。
- 用户在本机完成了真实的下载、放行、配置向导（连接云端、登录）。
- 三平台构建机上的构建与冒烟见 desktop.yml 的运行记录。

### D2 体验（2026-10-09，分支 `feat/desktop-d2`，基于 `feat/multi-agent`）

分支基于多 Agent 的分支：D2 改的自检、设置分组、首启向导、模型服务刚被多 Agent 大改过，分开做合并时冲突面大。D2 的合并排在多 Agent 之后。

**交付**：
- **ChatGPT 登录**（§4.5）：`CodexAccountService` 每次登录单独起一个 `codex app-server`（环境与会话同一份，含 CODEX_HOME 与代理设置），`account/login/start`（chatgpt）拿授权地址（只认 https），等 `account/login/completed`；取消、10 分钟超时、退出登录（`account/logout`）、读登录方式（`account/read`，带 `requiresOpenaiAuth`）。同一时间只留一次登录：再点「登录」先取消上一次（不是拒绝）。接口见 §7.1。前端在「设置 → 模型服务」里加「ChatGPT 账号」一行：即点即生效、不进保存表单；授权页用 `window.open` 打开（桌面版交给系统浏览器，浏览器里是新标签页，被拦了可以点「重新打开授权页」），每 2 秒问一次结果；用自定义模型服务时说明 ChatGPT 登录对它不起作用。
- **Git 检查**（§4.6）：所有运行形态都查；Mac 先 `xcode-select -p`，没装命令行工具不去碰 `/usr/bin/git`；缺 Git 只提醒并给安装引导，算进「本机运行环境」的结论（首启向导没过的项照常留到「我的工作」）。
- **开机自启**：桥的 `getPreferences / setPreferences`；只在安装版改系统登录项（Windows 带 `--hidden`；Mac 13+ 走 SMAppService，状态 `requires-approval` 时说明要在系统设置里允许）；开机拉起时不弹窗口（`--hidden` 或 Mac 的 `wasOpenedAtLogin`）；启动时以系统的登录项为准同步偏好（使用者在系统设置里关掉的不再重新登记）。
- **中英菜单与外链**：Mac 菜单加「帮助」（官网、使用说明、报告问题，交给系统浏览器；打开日志目录），Windows 的日志目录在托盘菜单里。网页的语言变化时由 `LocaleBoundary` 告诉外壳（D0 只有桥，前端之前没调）。
- **原生通知**：安装版里网页通知不用另外授权（权限处理只放行通知与剪贴板写入，`Notification.permission` 为 granted）；点通知时请外壳把窗口带到前面（窗口可能关到了菜单栏 / 通知区域），再聚焦页面。「设置 → 通知」在桌面版里改说明。规则沿用现状（打开着的会话在后台时提醒）。
- **「桌面应用」设置分组**：只在安装版列出：开机自启、本机地址（可在浏览器中打开）、打开数据 / 日志目录、版本。更新相关的设置随 D3。
- 桥新增 `getPreferences`、`setPreferences`、`openDirectory`（只接受 data / logs）、`showWindow`，都按发送方地址校验。

**验证**：
- client 质量门（审查修正后）：contracts 12、desktop 40、server 900、web 960，lint、testid 基线（447 个静态）通过。
- gate-c（Lima 虚拟机）：中文全量 20 步、英文冒烟 8 步均通过；审查修正后中文全量再跑一轮，通过。
- 开发态外壳端到端审查修正后再跑一轮，49/49。
- 开发态外壳端到端（`verify-dev.mjs`）49/49：原有 39 项，加上 D2 的帮助菜单与「报告问题」走系统浏览器、开机自启偏好（开发态不改系统登录项）、通知权限为 granted、`showWindow` 唤出隐藏的窗口、自检有 Git 一项、空 Codex 配置下账号为没登录、真实 Codex 0.159.2 给出 `auth.openai.com` 的授权地址并能取消。

**独立审查（subagent，只读）与修正**：没有高危问题，没有新增拒绝式守卫（「再点登录先取消上一次」是替换：Codex 的登录回调占固定本地端口，两次登录本来不能并存）。处理：
1. 临时 Codex 进程握手失败时没关，每读一次账号可能留下一个 → 握手失败也关掉；读完不等进程退出就回包。
2. 登录成功、退出登录后，会话用的共享 Codex 进程不一定用上新的登录 → 本机服务在没有进行中的 Codex 回合时重连它（同改代理设置的做法），有回合在跑就等最后一个结束。
3. Windows 在「设置 → 启动应用」里停用后 `openAtLogin` 仍为 true → 再看 `executableWillLaunchAtLogin`。
4. 等待中这次登录已不在（本机服务重启过）时界面一直等 → 收到 404 就收起。
5. 登录完成后账号读两次、从浏览器回来聚焦窗口又读一次（每次起一个 Codex）→ 只失效一个前缀、聚焦不重取。
6. 失败原因「timeout」「codex exited」英文原样显示 → 换成界面文字。
7. 文案：桌面版通知改为「不用在浏览器里授权（系统第一次可能会问一下）」；在 API Key 登录时点 ChatGPT 登录，说明会替换它。
8. 未改：组件卸载或切换语言后等待状态不保留（服务端的登录照常进行，再点登录会替换上一次）。

**CI 里发现**（PR #42）：Intel Mac 构建机上安装包冒烟一次卡死 240 秒（连外壳自己的冒烟超时都没触发，说明主线程被同步调用堵住）。启动时查系统登录项（`app.getLoginItemSettings`，Mac 上经 SMAppService 问系统服务）是同步调用，在构建机上会卡住 → 只有使用者开过开机自启才在启动时查（没开过就不会是开机拉起的，也没有要同步的）；设置页里的状态仍在使用者打开时查。

**待人工验收**（安装包上做，列进 D3 的验收清单）：Mac 临时签名应用的开机自启（待实测 3：是否 `requires-approval`、开机后是否只出菜单栏图标）、系统通知真弹出与点击、用真实 ChatGPT 账号走完登录（授权后会话能用上新登录）。
