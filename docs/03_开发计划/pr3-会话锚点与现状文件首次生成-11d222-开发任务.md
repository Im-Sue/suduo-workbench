## 二、任务分解

### PR3 · 会话锚点与现状文件首次生成

#### 任务概述

这一片交付「新建会话后，磁盘上有一份内容正确的现状文件」。

要解决的核心问题是**怎么分清「你开工前就有的」和「你开工后新增的」**。不能靠比时间——会话创建时刻取自本机时钟，审计时间来自远程数据库时钟，两台机器对不齐，会**永久性**把新旧算错。所以要在会话创建时记一个「书签」：远程审计当时走到哪一条了。

#### 任务分解

**1. 本机 SQLite migration（用户已批准）**

`v2_requirement_session_refs` 增加审计锚点游标列（`createdAt` + `id`）。迁移链当前 `[1, 2, 10]`，新增一版。不动远程 schema，不动 manifest v3。

**2. 调整会话创建顺序（易错点）**

```
先：拉一次审计最新有效条目 → 写入锚点
后：生成 v3 快照
```

**顺序不可颠倒**。现有创建流恰好是相反的，实施时要调整 `requirements-v2-service.ts` 的 `createRequirementSession`。落在锚点与快照之间的事件标记为 bootstrap 窗口，**宁可多报不可漏报**。

**3. 首次收敛**

| 要什么 | 从哪来 | 承诺 |
|---|---|---|
| 库存：现在几条评论、几个附件、正文是什么 | `listComments` / `listAttachments` / `getRequirement` | **必须准确** |
| 时间线：锚点之后谁做了什么 | `GET /api/v2/audit?resourceId=<reqId>&projectId=<pid>` | 尽力而为，可截断 |

审计查询**绝不能传 `resourceType`**——它是精确匹配，会把评论、附件、产物事件全过滤掉。`resourceId` 过滤已内建 `before_json`/`after_json` 的 `requirementId` 匹配。带 `projectId` 是为了走索引。

**不要为了发现既有评论/附件去翻审计到需求创建**——权威清单端点直接给出完整库存，翻审计又慢又没必要。翻页设上限，超限时标注「更早的时间线未列出」，**库存数字不受影响**。

**4. 原子写入**

临时文件 → fsync → rename。落点与权限复用 PR1 的契约。

#### 验收标准

- [ ] 新会话创建后现状文件存在，库存数字与远程一致
- [ ] 锚点记录时刻早于快照生成时刻
- [ ] 存量场景：需求已有 5 条评论、会话刚建（锚点后无事件）→ 文件显示「5 条，其中 0 条在你开工后」
- [ ] 审计查询不带 `resourceType`，且能取到评论/附件/产物事件
- [ ] 翻页超上限时有明确截断标注，库存仍准确
- [ ] 写入过程被中断不产生半截文件

#### 边界

- 不做生命周期与清理（PR4）
