# 优化：对话界面的交互设计 技术设计

> 一句话：不新增任何协议调用，把 `clientUserMessageId` 这条**已经躺在事件流里没人捡**的关联链接起来，让对话栏能如实说出「这条话进了哪一轮」，并用同一个机制驱动运行态、队列节拍和动作卡 ｜ 最后更新：2026-09-05

---

## 一、设计概述

**目标对齐**：你要的是对话栏自己会说话。这份设计的做法是——**不加新接口、不问 Codex 多余的话**，只是把它本来就在事件里告诉我们、而我们一直扔掉的一条信息捡回来：每条用户消息发出去时我们都带了一个自己的编号，Codex 会在事件里把这个编号连同**它真正落进的那一轮**一起报回来。捡回这条信息，四件事同时成立：气泡能如实标注去向、排队能按真实回合节拍出队、附件/评论动作卡不再静默失效、运行态有了可靠的锚点。

**同时钉死一条底线**：我们能证明的是「这条话被**记进**了哪一轮」，**不能**证明「模型在那一轮里**读到**了它」。协商中 Codex 给出了源码级证据（见 §三-1），证明这两件事在 Codex 收尾窗口里会分叉。所以文案只说前者，且明令禁止任何「下一步一定送到」的表述。

| 项 | 说明 |
|----|------|
| 名称 | 会话对话栏运行态与归属表达 |
| 核心职责 | 让用户在输入框附近就能知道：跑没跑、跑到哪、跑了多久、怎么停、我这会儿再发一条会去哪 |
| 设计原则 | 只说能证实的；证据来自权威事件流而非本机推断；一个机制服务多个症状；不引入任何拒绝用户发送的守卫 |
| 需求来源 | [优化：对话界面的交互设计](../02_需求设计/优化-对话界面的交互设计-3af281-需求.md) |
| 覆盖范围 | 运行态表达与中断中间态、归属判定与表达、前端队列、两张卡片重构、运行态消费面收口、`busy` 拆分、4.7 缺陷修复 |
| 不覆盖 | 关页/跨标签页/跨设备队列、Codex 协议版本变更、远程需求服务接口、视觉主题与国际化、需求详情页与我的工作台 |

## 二、方案与架构

### 2.1 关联链：一条已经通了的链路

黑话先解释：**归属**（= 这条用户消息最终被记进了哪一个回合）；**回合 / turn**（= Codex 一次「收到输入 → 干活 → 出结论」的完整过程）；**投影 / projection**（= 把事件流算成界面要显示的样子的那个纯函数）。

```
用户点发送
  │
  ▼
MessageService.send()                              client/server/src/application/message-service.ts
  ├─ clientTurnId = stableClientTurnId(...)                                        【已有】
  ├─ ledger.append(message.submitted { payload.clientTurnId })                     【已有】
  └─ runtimes.startTurn({ clientTurnId })
        └─ codex-runtime: turn/start { clientUserMessageId }                       【已有】
              │
              │  ⚠ 运行中调用时，返回的 turn.id 是一个**永不出现在事件流里的幽灵 id**
              │
              ▼
        Codex 发出通知：item/started + item/completed
              item.type = "userMessage"
              item.clientId = 我们传的 clientUserMessageId      ← 关联键
              turnId        = **真正收下它的那一轮**            ← 答案
              │
              ▼
        codex-event-normalizer：normalizePayload 原样保留 params                    【已有】
              → payload.item.clientId + turnRef.turnId 完整透出
              │
              ▼
        EventRepository.listBackfill 只过滤 message.delta / command.output-delta    【已有】
              → item.* 在历史补齐里同样保留
              │
              ▼
        event-projection/reducer.ts
              ✗ 当前：if (/^usermessage$/i.test(rawType)) continue;   ← 唯一的断点
              ✓ 本设计：在这里建立 clientId → 真实 turnId 的映射
```

**整条链除最后一格外全部已存在。**本设计的核心改动就是把 reducer 里那一行 `continue` 换成解析。

### 2.2 一个机制，四个出口

```
                  ┌─────────────────────────────────────┐
                  │  归属解析（reducer 内，纯函数）      │
                  │  clientId → 真实 turnId + 三态标记   │
                  └──────────────┬──────────────────────┘
                                 │
        ┌────────────────┬───────┴────────┬────────────────────┐
        ▼                ▼                ▼                    ▼
   气泡归属标记      队列出队节拍      动作卡追踪          运行态锚点
   （4.2 R3/R4）    （4.3 真实回合）  （4.7 缺陷修复）    （4.1 计时/步骤）
```

| 关键原则 | 为什么 |
|----------|--------|
| 证据只取自权威事件流 | 本机入账先后、HTTP 响应先后都不能证明「谁创建了回合」；Codex 自己发的 item 在回合内的先后可以 |
| 记录归属 ≠ 消费证明 | 两者在收尾窗口分叉，混为一谈就是撒谎（§三-1） |
| 无法证实就退回「已提交」 | 失败形态是「说不出来」，不是「说错」——这是本方案相对 `turn/steer` 路径最重要的性质 |
| 不新增任何协议调用 | 不用 `turn/steer`，`client/codex-protocol` 基线不动 |
| 不引入任何拒绝用户发送的守卫 | R7 / ADR-0004；输入框永不禁用，运行中永远有可点的发送控件 |

## 三、关键决策与取舍

### 1. 归属判定选 B（事件流关联回填），否决 A（`turn/steer`）与 C（前端反查）

需求第七章把这条移交技术设计。我用 pinned `codex-cli 0.143.0` 起隔离 `CODEX_HOME` 跑了三个真实协议探针，拿到以下事实：

| # | 实测事实 | 证据 |
|---|----------|------|
| F1 | 回合运行中再调 `turn/start`，返回一个全新 turn id 且谎称 `status:"inProgress"`，**该 id 此后再不出现在任何事件里** | 探针 1：返回 `01a070bc-021c-…`，全日志仅出现在那一条 response 里；`turn/started` / `turn/completed` 通知只有真实回合 `01a070bb-dedd-…` 各一条 |
| F2 | 输入确实进了正在跑的那一轮 | 探针 1：`clientId:"CLIENT-B"` 的 userMessage item 落在 `turnId=01a070bb-dedd-…` |
| F3 | **userMessage item 同时携带真实 `turnId` 与我们传入的 `clientId`** | 探针 1：三条 `clientId` = CLIENT-A / CLIENT-B / CLIENT-C 全部命中，`item/started` 与 `item/completed` 都带 |
| F4 | `turn/steer`（`expectedTurnId` 正确）返回真实 turn id | 探针 1：`{"turnId":"01a070bb-dedd-…"}` |
| F5 | `turn/steer` / `turn/interrupt` 失配时报 `-32600`，**错误文案直接带出当前真实活跃回合 id** | 探针 3：`expected active turn id 01a00000-… but found 01a070bd-c745-…` |
| F6 | 无活跃回合时：`no active turn to steer` / `no active turn to interrupt` | 探针 2 |
| F7 | 中断的终态是 `turn/completed` + `status:"interrupted"`，**没有独立通知** | 探针 3 lifecycle |

- **选 B**：F3 意味着答案本来就在事件里。整条链除 reducer 那一行 `continue` 外全部已通，改动面最小，且**失败形态是「说不出来」而不是「说错」**——恰好落进 R3 的第三态。
- **否决 A（后端调 `turn/steer`）**：它把一次今天不会失败的发送变成一次可能失败的发送（F5/F6 两种 `-32600`），而 R7 明令不得让用户白发一次。要安全使用就必须再实现「失配 → 回退 `turn/start` → 去重」的二次投递链路，两个 RPC 换来的信息与 B 等价。唯一优势是同步拿到归属，但实测中 userMessage 的 `item/started` 在提交后同一秒即到（它先于任何模型工作发出），该优势不成立。
- **否决 C（前端反查）**：反查是推断不是证据，直接违反 R3。

### 2. 记录归属 与 消费证明 必须拆开（Codex 协商推翻了我的初版）

我初版提了一条「防御性收紧」：要求回合在收下这条输入之后**还继续产生过 item 事件**，才允许标「已并入当前工作」。**Codex 用源码把它推翻了**，我采纳：

| Codex 给出的源码链路（`rust-v0.143.0`） | 说明 |
|---|---|
| `core/src/tasks/mod.rs:563` | `on_task_finished` 取出剩余输入，**以原 `turn_context`** 调 `record_pending_input` |
| `core/src/hook_runtime.rs:539` | 继续把该 context 传给 `record_user_prompt_and_emit_turn_item` |
| `core/src/session/mod.rs:3794`（`turn_id` 取自 `turn_context.sub_id`，1962–1985 行） | 记录历史后**立即**发 userMessage started/completed；**这条路径没有再次推理** |

结论：**收尾窗口里注入的输入，userMessage item 报的就是旧回合 X**，而模型并不会在 X 里读到它。
Codex 同时给出我那条规则的最短反例：`start(X) → submitted(B) → user.started(B) → user.completed(B) → terminal(X)`——**B 自己的 `item/completed` 就满足了「后续还有 item 事件」**；即使排除自身，收尾循环记录 C 也能让未消费的 B 拿到标记。规则无效，整体撤回。

**最终决策**：把两件事在代码与文案两层都拆开。

- 我们**证明**的是：这条话被**记进**了哪一轮（F3 + 上述源码链路）。
- 我们**不能证明**的是：模型在那一轮里读到了它。Codex 进一步确认，更强的消费证据需要关联「实际模型请求包含的输入与 clientId」再关联响应，**0.143.0 协议不提供这种确认**。
- 因此：`已并入当前工作` 的语义严格限定为「**已记入当前正在跑的这一轮**」，其说明文案必须原样这么写；**禁止**出现「模型正在处理它」「下一步一定送到」或任何等价表述（R4）。

**这里我与 Codex 保留了一处分歧，并按需求裁决**：Codex 主张「未证实消费时一律保留『已提交』」，那会让 4.2 的 `已并入当前工作` 永不出现。需求第三章在**已经引用同一段源码**（`tasks/mod.rs:603-623`「记进历史但不保证触发推理」）的前提下，明确裁定「能确定**归属**就说『已并入当前工作』，确定不了就说『已提交』」。归属是可确定的，所以按需求执行；Codex 是在对一条需求已裁定的产品口径提更严标准，不构成新的技术事实。**代价我如实写在这里，并已在用户可见输出中点名，用户若认为仍不够诚实可以推翻本条。**

**附加的诚实限定**：中断会清掉未消费的 pending input（`tasks/mod.rs:603-623`）。因此当回合 T 以 `interrupted` 终止时，归属到 T 的**插入型**消息追加一行限定语「这一轮被中断，这条可能没被处理到」。这是既有协议事实的告知，不是第四种状态，不违反 R3。

### 3. 三态判据改用「回合内 item 次序」，不用本机入账次序

Codex 指出我初版判据的独立错误：`submitted(A) < submitted(B) < started(X)`（A 开启 X、B 插入 X）时，「`turn.started(X).seq < message.submitted.seq` 才算 merged、否则 new-turn」会把 B 误判成「已作为新一轮」；而且缺失 `start` 时不能走 `else → new-turn`。**本机入账先后不能证明谁创建了回合。**

改用只依赖 Codex 自身事件次序的判据（按序求值，命中即停）：

| 序 | 条件 | 结果 |
|---|------|------|
| 1 | 找不到 `clientId` 对应的 userMessage item | **已提交** |
| 2 | 该 item 所属回合 T 在本投影里没见过 `turn.started`（`truncatedHead`） | **已提交** |
| 3 | 该 item 是 T 内 **seq 最小**的 userMessage item | **已作为新一轮** |
| 4 | 其余（T 内已有更早的 userMessage item） | **已并入当前工作** |

对 Codex 反例的复核：A 创建 X，A 的 userMessage item 是 X 内第一条 → 规则 3 → 新一轮；B 的在其后 → 规则 4 → 并入。判对。
该判据对历史回放同样成立，且**不需要**任何 HTTP 响应参与，因此也不受「SSE 先于 HTTP」影响。

### 4. 契约只加一个字段，中断不加字段（此处我与 Codex 的方案不同）

- **加**：`SendMessageAccepted.clientTurnId?: string`。可选、加法式、本机 loopback BFF、同仓唯一消费者。需求第十章已预授权「本机 BFF 的会话消息接口与共享契约中的发送响应结构」。作用是让前端在发送那一刻就拿到关联键，不必再用 `messageEventSeq` 反查事件。
- **不加**：Codex 建议给中断响应加字段以表达「目标已非活跃、另一轮仍在跑」。我改用更省的做法——前端从自己的投影里读同一份权威事实即可，不需要服务端再回传一遍：
  1. 前端中断时**传显式 `turnId`**（当前是 `api.interrupt(sessionId)` 不传，由服务端从账本猜唯一运行回合）。
  2. 服务端**永不覆盖已有终态**：`InterruptService` 在 `alreadyStopped` 分支补写 `turn.interrupted` 前，先确认该回合在账本里尚无终态事件——否则一次对已自然完成回合的中断会把 `completed` 改写成 `interrupted`（Codex 发现的既有隐患，投影是后写覆盖语义）。
  3. F5 的 `expected active turn id X but found Y` 与 F6 的 `no active turn` 一并纳入「目标已非活跃」的幂等语义，不再抛 `IndeterminateOperationError`。
  4. 前端据投影自行判断：若目标回合已终态而另有回合在跑 → 显示告知 +「停止当前这一轮」按钮，**不自动中断 Y**。

### 5. `busy` 拆分排在第一片，不是收尾清理

`SessionRuntime.busy` 一个布尔被发送、上传、预览、diff、审批提交五个互不相干的动作共用，并向下 `disabled={!session || busy}` **禁掉整个输入框**——打开一个 diff 就让用户不能打字，直接违反 R1。拆掉它，R1/R2 是白送的，所以它是第一片的前置而非 4.5 的附属清理。

### 6. 检查点两个守卫按 ADR-0004 分开裁决（Codex 提出）

`EnvPanel.tsx` 现有两处「回合进行中不可…」：

| 位置 | 判据（仲裁者是谁 / 拿掉最坏结果 / 人能否恢复） | 裁决 |
|------|------------------------------------------------|------|
| `:133` 保存检查点 | 仲裁者是人；最坏是快照时点不理想；人可重存 | **拿掉拒绝**，改为告知后继续：「这一轮还在跑，现在存的快照可能不包含正在写入的改动」 |
| `:177` 还原到检查点 | 会在 agent 正在写文件时覆盖工作区 → **不可逆字节损失红线** | **保留禁用**，但把裸 tooltip 换成说明原因的文案 |

### 7. 被否决的其它选项

- **服务端新增 `message.attributed` 事件做回填**：要加事件类型、要迁移、投影还得再消费一次；而同样的信息已在 `item.*` 里，纯属多一层。
- **队列落后端常驻**：需求已明确否决（关页继续替用户说话是新的能力承诺，不属对话界面交互）。
- **给归属加第四种状态**：违反 R3「只表达能证实的三态之一」；改用「中断限定语」表达同一信息。

## 四、核心流程 / 逻辑

### 4.1 运行中发一条消息：从点击到标记落定

```
用户在回合 X 运行中按发送
  │
  ├─ 立刻：消息进入本地待定表，气泡标「已提交」，输入框保留焦点、不禁用
  │
  ├─ HTTP POST /sessions/:id/messages
  │     └─ 响应 { clientTurnId, turnRef.turnId(可能是幽灵 id), messageEventSeq }
  │           ⚠ 响应里的 turnRef.turnId 只用于诊断，**不参与任何归属判定**
  │
  └─ SSE 事件流（与 HTTP 响应无先后保证）
        ├─ message.submitted { payload.clientTurnId }        → 气泡正文来源
        └─ item.started/completed { item.type="userMessage",
                                     item.clientId = clientTurnId,
                                     turnRef.turnId = T }     → 归属证据
              │
              ▼
        reducer 按 §三-3 四条规则求值
              ├─ T 内首条 userMessage      → 已作为新一轮
              ├─ T 内非首条                → 已并入当前工作
              └─ 无 item / T 未见 start    → 已提交（保持）
                    │
                    └─ 若 T 最终以 interrupted 终止，且本条为插入型
                          → 追加限定语「这一轮被中断，这条可能没被处理到」
```

**模拟示例**（端到端走一遍，对齐需求第二章的场景）：

你发「把测试跑一遍」。当时没有回合在跑，`turn/start` 创建回合 `T1` 并返回 `T1`；Codex 发出 `item/started{userMessage, clientId:c1, turnId:T1}`，它是 `T1` 内第一条 userMessage → 规则 3 → 气泡标「已作为新一轮」。发送按钮旁出现停止控件，输入框上方出现 `● Codex 正在工作 · 正在执行 pnpm test · 12s`。

跑到第 12 秒你补一句「顺便看下覆盖率」。这次 `turn/start` 返回幽灵 id `G1`（F1），我们**不看它**；Codex 发出 `item/started{userMessage, clientId:c2, turnId:T1}` —— 还是 `T1`，且不是首条 → 规则 4 → 气泡标「已并入当前工作」，说明文案写「已记入当前正在跑的这一轮」。同时 `T1` 进入本页的 watchedTurns，`T1` 完成时才解析动作卡（4.7 缺陷由此消失：过去这里等的是永不出现的 `G1`）。

你又想到第三件事但不想打断，按排队键。它进入队列列在输入框上方，可编辑可删除可取回。`T1` 正常结束后队列取队首发出，等**那一条**落进的真实回合终态，才取下一条。

中途若你点了停止：`stopping` 立刻置位、停止控件禁用；队列**从点击那一刻**暂停（不等完成事件）；收到 `T1` 的任一终态即收口停止控件。若 `T1` 是被中断的，你补的那句「顺便看下覆盖率」会带上「这一轮被中断，这条可能没被处理到」。

### 4.2 队列状态机

```
        ┌────────┐  用户排队   ┌─────────┐
        │  idle  │───────────▶│ waiting │
        └────────┘            └────┬────┘
             ▲                     │ 无回合在跑 且 awaitingTurnId=null
             │ 队列空              ▼
             │                ┌──────────┐  发送 → 解析归属
             │                │ dispatch │─────────────┐
             │                └──────────┘             ▼
             │                                  awaitingTurnId = 真实 turnId
             │                                         │
             │      该 turnId 终态且 seq > 出队时水位   │
             └─────────────────────────────────────────┤
                                                       │
        ┌────────┐◀────────────────────────────────────┘
        │ paused │  ← 用户点停止(点击瞬间) / 回合 failed|interrupted
        └────────┘    / 发送失败或不确定 / 归属超时未证实 / 页面刷新恢复
             │
             └─ 队列项保持可编辑·可删除·可取回输入框；提供「恢复」动作
```

| 处理规则 | 怎么保证 |
|----------|----------|
| 一个真实回合终态只取一项 | 出队时记录 `awaitingTurnId` + 当时的投影水位；只有**该 turnId** 的终态事件 `endedSeq > 水位` 才前进（`turnMeta` 记终态 seq，不用投影全局 `lastSeq` 代替） |
| 不以 HTTP 受理为节拍 | 出队后不看 HTTP 响应的 turnId（幽灵 id），只等归属解析出的真实 turnId |
| 刷新/历史补齐不得触发出队 | 恢复后队列强制进入 `paused`；水位比较天然屏蔽回放的旧终态 |
| 等待审批不算结束 | 审批不产生回合终态事件，自动满足 |
| 不确定就停，不重试 | 归属在限定窗口内未证实 → `paused`，理由如实写「这一条去了哪儿还没确认」 |
| HTTP 失败 ≠ 未发送 | `message-service` 先入账 `message.submitted` 再启动 turn，失败抛「结果不确定」：只有证实未受理（明确拒绝且未入账）才回队首重发；断网 / 超时 / 结果不确定一律 `paused`、在途内容留给人核对、不自动重发（r2 物化前协商修正） |
| 切会话不丢草稿 | 队列按 `sessionId` 存 `sessionStorage`；切走保留，切回恢复为 `paused`（**不清空**——需求未要求清空，清空等于毁掉用户已写的字） |
| 排队入口不只有键盘 | 次级按钮「排队」为主入口；`Tab` 仅在补全面板关闭且有回合在跑时生效（补全面板打开时 `Tab` 仍是接受候选，既有行为优先） |

### 4.3 停止的中间态

```
用户点停止
  │
  ├─ 立即：stopping=true，停止控件禁用（不等远程返回）
  ├─ 立即：队列 paused（从点击瞬间起算，避免完成事件先到而自动发下一条）
  │
  ├─ POST interrupt { turnId: 前端投影认定的运行回合 }
  │     ├─ 成功 / 目标已非活跃（F5·F6 幂等）→ 不视为错误
  │     └─ 请求本身失败 → **解除 stopping 并如实报错**，绝不无限等终态
  │
  └─ 收到该回合任一终态（completed / interrupted / start-failed）
        └─ 收口停止控件，恢复发送形态
             ⚠ 自然完成同样收口（4.6）
             ⚠ 迟到的 turn.interrupt-requested 不得把已终态的回合拉回 stopping
                （该事件是远程调用返回后才入账的，必然可能迟到）

若投影显示目标回合已终态、而另有回合 Y 在跑：
  └─ 告知「刚才那一轮已经结束，现在在跑的是新的一轮」+ 提供「停止当前这一轮」
     绝不自动中断 Y
```

### 4.4 两张卡片分家

```
消息流内（一次性动作卡）              右栏「关联需求」tab（常驻材料）
┌──────────────────────────┐         ┌───────────────────────────┐
│ Codex：<评论全文 / 附件>  │         │ 改动 │ 文件 │ 关联需求    │
│  ┌────────────────────┐  │         ├───────────────────────────┤
│  │ 发表这条评论？      │  │         │ 优化：对话界面的交互设计  │
│  │ [逐字预览并确认]    │  │         │ 基线 v2                   │
│  └────────────────────┘  │         │ 附件                      │
│  处理完即消失            │         │  · 素材.zip  未拉取 ⤓     │
└──────────────────────────┘         │ [发表评论]                │
                                     └───────────────────────────┘
锚点 = 产出该内容的那条 assistant 消息   右栏被 Drawer 占用或折叠时，
（不是用户消息 —— 见下）                 头部保留一个「关联需求」入口兜底
```

**动作卡锚点为什么改挂 assistant 消息**：Codex 指出 `actionTurnId` 是单值、连发会覆盖，且「不能把 X 已生成的旧全文绑定给收尾输入」。改为——本页每次发送把解析出的真实 turnId 记入 `watchedTurns: Map<turnId, …>`；某个 watched 回合终态且拿到完整 assistant 正文时，就在**那条 assistant 消息**下方渲染卡片。卡片描述的是「这段正文里的东西要不要执行」，锚在正文旁天然正确，也天然支持并发多回合。历史回放的回合永远不进 `watchedTurns`，因此历史不出卡（4.4 保留项）。

**R8 守住**：只有用户先在对话里提出评论诉求、模型据此给出全文，输出里才会有可解析的评论全文；模型不得主动建议发评论。解析逻辑不变，只改锚点与追踪结构。

**回显宿主（r2 物化前协商修正）**：`SessionsWorkbench` 以 `key=sessionId` 重挂 `SessionRuntime`，切会话即卸载，回显结果不能只存在 Runtime 里。提交结果（全文、评论标识、拉取状态）存在 Runtime 之上的 sessionId 级宿主，按回合关联；右栏材料区手动发表的评论回显在材料区「本会话已发表」列表；「历史回放不出卡」不清除已有结果；页面刷新后不保证回显（需求未要求）。

### 4.5 运行态消费面一次对齐

| 面 | 现状问题 | 本设计 |
|----|----------|--------|
| 发送按钮 | 运行中无变化 | 运行中与停止控件并存，二者都可点（R2） |
| 状态行 | 不存在 | 输入框上方新增：当前步骤 + 已耗时；审批时整行换审批提示 + 跳转 |
| 顶栏徽章与中断入口 | 中断按钮离手最远 | 停止控件下移到 composer（`interrupt-turn` testid 跟控件走），顶栏只留徽章 |
| 顶栏徽章判定 | `SessionRuntime.runtimeStatus()` 与 `ui/session-status.ts:sessionUiStatus()` **是同一判定的两份实现**，前者不看 `lastTurnOutcome`，永远不显示「已完成/异常」 | 删除前者，统一走 `sessionUiStatus` |
| 侧栏会话状态灯 | `SessionsRail` 对**选中会话也传 `0, 0`**，注释却写「选中会话用 SSE 实时值」，实际走 10s 轮询 | 选中会话传入实时 `running` / `pendingApprovals` |
| 模型切换器 | 「回合进行中，切换会中断当前工作」**无代码依据** | 见 §五-实测项；实测通过后改为准确表述 |
| 改动面板与检查点 | 保存/还原都在运行中禁用 | 按 §三-6 分开裁决 |
| 审批区 | 与全局 `busy` 耦合 | 只用自身 `deciding` |
| 断线与恢复 / 历史补齐 / 切会话清理 | — | 计时锚点丢失时不显示时长；`watchedTurns`、队列、`stopping` 按 sessionId 清理 |

**计时基准**（需求第七章移交项）：`turn.started` 事件的 `ts` 是 normalizer 的 `Date.now()`，即 **BFF 时钟**，既不是浏览器也不是 Codex 时钟。规则：**本标签页亲眼见过该回合 `turn.started` 的**，用本地锚点计时；没见过的（开页前就在跑、缓存截断补齐的），**不显示时长**，只显示「运行中」。不显示，好过显示一个跨时钟算出来的错数字。「亲眼见过」的判据（r2 物化前协商修正）：SSE 一条连接先回放账本再转实时（`event-stream.ts`），客户端分不出历史与实时，光排除 HTTP 回填路径挡不住回放阶段的历史 `turn.started`。因此由服务端在回放结束时向本连接发一条 `stream.live` 控制事件作实时边界：边界之后经实时入口收到的 `turn.started` 才建本地锚点；SSE 回放阶段与 HTTP 回填得知的 start 一律不建；重连后边界复位。不用 `Date.now() - ts` 阈值判断（跨时钟）。

### 4.6 `busy` 拆分与草稿保全

拆分后：`SessionRuntime.busy` 删除；`drawerLoading`（预览/diff，只影响右侧抽屉）、`sending`（Composer 自有，仅发送按钮 0ms 忙碌态）、`uploading`（Composer 自有，仅图片按钮）、`deciding`（Stream 审批卡自有）。**textarea 的 `disabled` 收窄为 `!session`，与回合运行态、与任何其它动作彻底解耦（R1）。**

**顺带必须修的一个 bug（Codex 发现）**：`Composer.send()` 成功后无条件 `setText("")` / 清空附件与 skill。今天因为发送期间输入框是禁用的，这个 bug 打不到；**一旦按 R1 解除禁用，用户在等响应期间新写的草稿就会被清掉**。改为：发送前对 `{text, skillPath, attachments}` 取快照，成功后**只移除快照那一份**（文本若已被改动则保留用户的新草稿；附件只移除本次提交的 id；期间完成的上传不受影响）；会话切换时在途回调不得作用于新会话。

## 十、迁移影响与风险

**受影响**：会话页整条对话栏链路（投影 → Composer → Stream → 右栏）、中断服务、gate-c 端到端与 testid 基线。

**回滚**：纯前端为主 + 一个加法式可选字段，按片 `git revert` 即可；无数据迁移、无持久化结构变更、无远程副作用。

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 收尾窗口里「已并入当前工作」实际未被模型读到 | 中 | 用户以为补充已生效 | 语义严格限定为「已记入这一轮」；中断终态追加限定语；禁止一切「会送到」表述。**残余风险已知且如实记录，Codex 主张更严口径，需求裁定按三态执行** |
| 队列重复执行同一条消息 | 中 | 重复模型调用与重复副作用 | 一个真实回合终态只取一项 + 出队水位比较 + 不确定就暂停不重试 |
| 刷新后队列自动跑起来 | 中 | 用户没预期地被代发 | 恢复强制 `paused`，必须人工恢复 |
| 端到端大面积变红 | 高 | 交付被测试拖住 | 基线分摊到各片；`final-interrupt` 的 testid 跟控件走以最小化改动 |
| 关联需求入口被 Drawer 抢占或折叠藏死 | 中 | **手动兜底能力事实消失＝静默回退上一需求已交付的保证** | 头部保留兜底入口，作为第 4 片的验收硬条件 |
| 中断把自然完成改写成 interrupted | 中 | 历史被伪造 | `InterruptService` 补写终态前先查账本已有终态 |
| 解除输入禁用后草稿被清空 | 高 | 用户刚打的字丢失 | 发送快照 + 只清快照那一份，与第 1 片同片交付 |
| 模型切换器换成另一句仍不准的话 | 低 | 又一句没依据的提示 | 第 1 片强制实测，覆盖当前轮与下一轮 |
