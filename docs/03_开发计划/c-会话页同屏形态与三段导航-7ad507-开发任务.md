## 二、任务分解

### C · 会话页同屏形态与三段导航

#### 任务概述

会话页现在是「先在一个 118 行的列表页选会话 → 跳到另一个页面打开」。用户要的是 Codex／Claude Code 桌面端那样的形态：**左边一直有列表，右边直接开会话**。

好消息是运行时侧其实相当完整（`Stream` 的 per-turn 聚合投影、`Composer` 的附件/拖拽/`/`Skills/`@`文件引用、审批流、`Drawer` 的 diff 与 Monaco 预览都在），`LeftRail`(400) 更是现成的会话侧栏——它在 T4 清 `/legacy` 旧壳时被连带断了线，代码还在仓库里。所以本片主体是**接线与形态改造**，真正新建的只有需求-会话分组。

外壳要**稳定**：`SessionsWorkbench` 常驻，运行时 pane 用 `key={sessionId}`。否决了给 `SessionRuntime` 加 `railSlot` 的做法——slot 内容会随 `key` 一起重挂，切会话时左栏状态照样丢。

#### 任务分解

1. 新增 `app/SessionsWorkbench.tsx`：稳定外壳 + `key={sessionId}` 的运行时 pane；替换 pr2 建的 `SessionsMode` 槽内实现。
2. 新增 `components/sessions/SessionsRail`（三段）与 `SessionRow`（自 `LeftRail` 接回重构）：
   - ① 新建会话（项目会话 / 从需求发起）
   - ② **需求-会话列表**（按需求分组，组内列该需求下的会话）
   - ③ 会话列表（当前项目全部会话，含项目级会话）
3. 数据来源用已有接口，**后端零改动**：`GET /api/v2/projects/:projectId/sessions`、`GET /api/v2/requirements/:requirementId/sessions`。
4. **需求-会话分组的标题来源**：`RequirementsSessionReferenceDto.requirement` 只有 `{remoteRequirementId, requirementVersion, materialPath}`，**没有标题**。做法是 join 已加载的需求列表，未命中时 `getRequirement(id)` 懒补并缓存。**不新增 BFF 聚合接口**（守 R2）。
5. 提取 `ui/session-status.ts`（`sessionUiStatus` + 标签），并**迁移既有 `client/web/test/session-status.test.ts`**。（归本片而非基座片：它是会话域逻辑，不是 UI 原语。）
6. `SessionRuntime.tsx`(787)：移除 stub `.rail`；`showRuntimeSettings` 改为跳设置页。
7. **`RuntimeFileTree` 的去处**（技术设计自相矛盾处，本片负责收口）：它定义在 `SessionRuntime.tsx:697`，唯一挂载点就是要被移除的 `.rail`（:484）。设计里既写「移除 rail 挂载点」又写「保留在役的 RuntimeFileTree」，两句冲突。按需求 4.4「已具备能力保持不减」，**把它迁到右侧改动面板作为一个标签页**，与 diff／检查点并列——那本就是「文件/改动」域。不塞进 SessionsRail 第四段（会破坏 4.3 规定的三段形态）。
8. **深链接双向同步**：`/sessions?projectId=&sessionId=` 契约保留。本片负责**首次加载读 query** 与 **popstate 双向同步**——当前顶层 `projectId` 不读 query（已核实），是缺口。
9. 会话操作：重命名、归档、删除；按标题搜索/过滤；当前会话高亮；运行中会话有状态指示；默认只展开有活跃会话的需求。
10. `ApprovalModeSwitcher` 会话头置灰：读 pr6 加的 `SettingsDto.approvalModeLocked`，锁定时禁用 `full` 并用 Tooltip 写明锁来源（`SUDUO_MAX_APPROVAL_MODE`）与「请联系管理员」。
11. 删除 `RequirementsSessions.tsx`(118)（空态并入 rail）与 `LeftRail.tsx`(400)（在替代物挂上之后再删）。

#### 验收标准

## 审查纠正 · 2026-08-24（ccb_claude）—— 会话删除豁免的理由不成立

**本片上面记的验收豁免理由是假的。** 状态不变（本片交付的代码是好的，且本片自己就写了「补齐需另立任务」），但记录必须纠正，不能让一条与事实相反的"查证"结论留在归档里。

### 原记录（第 157 行）

> spec 任务 9 写「重命名、归档、**删除**」。查证：**服务端无会话 DELETE 路由**，`UpdateSessionRequest.state` 只有 `active | archived`……补删除需动服务端与契约，超出本片「后端零改动」边界。

### 实核结果

| 断言 | 判定 | 证据 |
|---|---|---|
| 服务端无会话 DELETE 路由 | **假** | `client/server/src/infrastructure/http/http-server.ts:558` 就是 `server.delete("/api/v1/sessions/:sessionId")` |
| 补删除需动服务端 | **假** | `session-service.ts:307` `remove()` 已把状态置为 `deleted`，逻辑完整 |
| 该能力属本片新增成本 | **假** | `git blame` 指向 `60b6069 chore: import SuDuo code and documentation`——**基线导入就有**，远早于本片 `7175f9e` |

`UpdateSessionRequest.state` 只有 `active | archived` 这句本身没错，但它管的是**更新**接口，与**删除**接口是两回事，被错误地当成了删除不可行的旁证。

**真实缺口只在 web 端**：`client/web/src/api/client.ts` 没有任何 `sessions/${...}` 的 DELETE 封装（现有三处 DELETE 分别是需求附件、工作区映射、MCP server）。所以这从来不是"后端零改动边界"问题，而是一个纯前端接线缺口。

### 影响
