## 二、任务分解

### pr4 会话模块按契约收口

#### 任务概述

会话模块有一个**容易被做错的地方**：`SessionRuntime.tsx:648` 那个自研的 `<div className="toast" role="alert">`。它手动关闭、不自动消失——看起来像「第二套 toast 要被消灭」，实际上它是**一个本就不该长成 toast 的持久错误块**。

需求业务规则 N4 写得很明确：会话终态错误保留在上下文中，**不并入自动消失的全局 toast**。把它并进去会丢关键信息，这正是本需求刻意避免的失败模式。所以本片的动作是**改定性**（重新表达为 `RegionError`），不是**改归属**。

改造面：`SessionRuntime.tsx`（753 行）、`SessionsWorkbench.tsx`（270 行）、`SessionsRail.tsx`。

#### 任务分解

1. **`SessionRuntime.tsx:648` 自研 toast → `RegionError`**
   - 保留「不自动消失、留在出错位置、可手动关闭」的全部语义。
   - `:173` 的 `reportError`（`setError(messageOf(cause))`）改为经 `classifyFailure` + `routeFeedback` 得到出口；`cancelled` 必须静默返回。
   - **8 处** `reportError` 调用点（直接调用 `:396` / `:423` / `:452` / `:469` / `:543`，`.catch(reportError)` `:199` / `:430` / `:551`）**逐项定路由**，不是统一替换。（`:173` 是定义、`:250` 是依赖数组，均不计入）
   - politeness 冲突随之消除：现在它是显式 `role="alert"`（assertive）而全局 toast 是 polite，两套并存无规则；收口后由 `error` 档统一决定。

2. **`SessionsWorkbench.tsx` 两处 `window.confirm` 逐个按 `needsConfirm` 判定**
   - **`:203` 归档会话**（「确认归档会话「…」？」）：是否可逆？影响范围多大？恢复成本多高？**该确认就迁 `ConfirmDialog`（危险色 + 默认焦点在取消），本不该确认的直接去掉**。需求业务规则 N6 明确：确认与否由策略判定，不由历史实现决定。
   - **`:206` 删除会话**（「删除会话「…」后无法恢复，确认删除？」）：**不可逆、且文案自陈不可恢复，几乎必然保留并迁 `ConfirmDialog`**，危险色 + 默认焦点在取消。
     **这一处是草案初稿漏掉的**——它来自 2026-08-24 commit `92434dc` 新增的会话删除能力。漏掉它，本片做完会话页仍留着一个裸 `window.confirm`，而本需求的目标正是消灭它们。
   - `:100` 与 `:215` 两处 `showMessage(..., "warning")` 按分类结果重定档——它们现在被降级成 warning，很可能实际是 `error`。

3. **空态收编**：`SessionsRail.tsx:125`（当前项目还没有从需求发起的会话）、`:152`（当前项目还没有项目级会话）→ `EmptyState` + 引导动作。

4. **SSE 断连保持静默**（业务规则 N2）：判为可自愈，**不发 toast**，只更新角落持久状态标识（沿用现有 `RealtimeState`）。
   - 同时落实业务规则 N5：同一告警短时间重复必须传 `MessageOptions.id`。这个去重能力**建好了但全仓 0 处使用**，正是给「断连风暴」准备的，本片把它变成强制规则以防刷屏。

5. **`TablePreview.tsx`** 自带的 `"loading" | "ready" | "error"` 局部状态机与全局契约对齐（该文件经 `Drawer.tsx:10` 挂载）。若改动面超出「接入出口组件」，**先停下来确认范围**。

6. **同提交跑 pr1 的基线再生成命令**。
