# 需求附件回归本义、评论可带文件、需求优先级 技术设计

> 一句话：优先级是需求上的一个元数据列，排序纳入游标；附件区只改客户端（云端确认版接口原样保留给旧客户端），三个确认版工具撤下；评论文件复用房间文件的存储与上传模式，文件行挂在评论上。｜最后更新：2026-10-07
>
> 需求：[需求附件评论文件与优先级-需求](../02_需求设计/需求附件评论文件与优先级-需求.md)

---

## 一、设计概述

**目标对齐**：三项改动分三片交付，互不阻塞，按 S1 → S2 → S3 的顺序做。S1 给需求加优先级：云端加一列、一个审计动作、列表的筛选与排序，客户端加图标、菜单、筛选、排序切换。S2 把附件区改成按时间倒序的一张列表，停用确认版：云端几乎不动（只放宽附件允许的文件类型），客户端删掉发布入口，历史确认版只读，Codex 撤下三个确认版工具。S3 让评论带文件：云端新建评论文件表，存储复用房间文件那一份，接口照房间文件写；客户端评论框照房间输入框接上传，评论下面照房间消息显示文件，再加「存为附件」。

| 项 | 说明 |
|----|------|
| 名称 | 需求附件回归本义、评论可带文件、需求优先级 |
| 核心职责 | 需求优先级（存储、筛选、排序、展示）；附件区平铺与确认版停用；评论文件（上传、关联、展示、下载、存为附件、Codex 查看） |
| 设计原则 | 新字段对旧版本一律可选；云端接口默认行为不变（新行为要显式参数开启）；不新增拒绝式守卫；存储只增不删 |
| 需求来源 | [需求附件评论文件与优先级-需求](../02_需求设计/需求附件评论文件与优先级-需求.md) |
| 覆盖范围 | cloud/contracts、cloud/server、client/contracts、client/server、client/web、gate-c 夹具 |
| 不覆盖 | 房间文件；我的工作、概览、命令面板的排序；Codex 发带文件的评论；任何数据清理 |

## 二、方案与架构

```
                 cloud/contracts（两端共用）
   RequirementDto.priority? ─ CommentDto.files? ─ CommentFileDto ─ RequirementsHealthDto.features?
                 │
   ┌─────────────┴───────────────── cloud/server ─────────────────────────────┐
   │ requirements.priority (smallint 0..4)   requirement_comment_files（新表） │
   │ 列表：priority 筛选 + sort=priority     评论文件：上传 / 关联 / 下载 / 存为附件 │
   │ 游标：{timestamp,id,rank?}             存储：复用房间文件的 BlobStore（room-files 目录）│
   │ 确认版：接口与数据原样保留（只读 + 旧客户端发布）                           │
   └─────────────┬────────────────────────────────────────────────────────────┘
                 │  /v2
   ┌─────────────┴───────────── client/server（本机服务）───────────────────────┐
   │ /api/v2 透传 priority / sort；评论文件上传下载代理（照房间文件）            │
   │ 会话工具：撤下 3 个确认版工具（保留「已停用」回复）；附件最新在前；            │
   │          评论工具列出文件；suduo_attachment_view 也认评论文件编号           │
   └─────────────┬────────────────────────────────────────────────────────────┘
                 │  /api/v2
   ┌─────────────┴───────────────── client/web ─────────────────────────────────┐
   │ 优先级图标 / 菜单 / 筛选 / 排序切换     附件区平铺 + 历史确认版（只读）         │
   │ 评论框附文件（复用房间的草稿与文件组件） 评论下显示文件 + 存为附件             │
   │ 云端能力判断：/v2/health 的 features                                        │
   └────────────────────────────────────────────────────────────────────────────┘
```

| 关键原则 | 说明 |
|----------|------|
| 云端默认行为不变 | 列表不带 `sort` 时仍按最近更新排，游标格式不变；我的工作、命令面板、旧客户端都不受影响 |
| 新字段可选 | `priority?`、`files?`、`features?` 都标「旧版需求服务不返回」，客户端按缺失处理 |
| 云端能力显式声明 | `/v2/health` 新增 `features` 列表，客户端据此显示或隐藏入口，不靠猜版本号 |
| 确认版云端不动 | 旧客户端（0.8.x）仍能发布；新界面在「历史确认版」里看得到 |
| 排序在客户端补齐 | 附件「最新在前」在客户端排（旧云端仍是升序） |

**与现有系统的关系 / 边界**：

| 涉及模块 | 本设计如何动它 | 保留 / 不动什么 |
|----------|----------------|------------------|
| 需求列表与游标 | 加 `priority` 筛选、`sort`；需求列表的游标多一个可选 `rank` | 项目、评论、审计、活动的游标不动 |
| 确认版（云端） | 不动 | 读写接口、幂等表、版本文件的存储保护（`referencedStorageKeys` 与启动对账的并集）全部保留 |
| 附件（云端） | 默认允许的扩展名放宽到与房间文件一致 | 列表顺序（升序）、100 个上限、300 MB、删除逻辑不动 |
| 房间文件存储 | 评论文件放进同一个 `BlobStore` 实例 | 只增不删的约定不变；房间模块的逻辑不动 |
| 会话工具 | 撤下三个确认版工具；改附件、评论、查看三个工具 | 写工具确认流程不动；工具名常量保留完整名单 |

## 三、关键决策与取舍

- **优先级存成 smallint 0..4，不存字符串**：`0` 无、`1` 低、`2` 中、`3` 高、`4` 紧急，`NOT NULL DEFAULT 0`。数值越急越大，排序三个键都是降序，可以用一条行值比较翻页并直接用索引。没选「varchar 可空 + 生成列」：多一列，且可空值不能参与行值比较。契约里仍用字符串 `urgent | high | medium | low`，`null` 表示无，数值只在云端内部出现。
- **按优先级排序要显式开启**：`GET /v2/requirements?sort=priority`。默认仍是 `updated`，因为我的工作（`assignee=me, limit 100` 被截断时依赖「最近更新在前」）和命令面板都依赖默认顺序。
- **游标不匹配排序方式时返回 400**：`sort=priority` 的游标里有 `rank`，`sort=updated` 的没有；换了排序还拿旧游标就是 `VALIDATION_ERROR "Invalid pagination cursor"`，与现有的游标格式错误同一种处理。这是输入格式校验，不是一致性守卫。
- **改优先级不递增正文版本**：照抄 `changeAssignee`，先 `FOR NO KEY UPDATE` 读旧值（用于审计的「从 → 到」，不拒绝任何请求），同值不写，UPDATE 只改 `updated_by / updated_at`。
- **新审计动作不进 `AUDIT_ACTIONS`**：照 `REQUIREMENT_ASSIGNEE_CHANGED_ACTION`，进 `RECORDED_AUDIT_ACTIONS` 与 `REQUIREMENT_ACTIVITY_ACTIONS`。概览的文案表按 `AuditAction` 穷举，加进去旧界面会编译失败；`/v2/audit` 也就不会把它返回给旧版概览。
- **云端能力用 `/v2/health` 的 `features` 声明**：S1 加 `requirement_priority`，S3 加 `comment_files`。没选「看列表条目里有没有 `priority` 键」：空项目判断不了，也把两项功能绑在一个字段上。网页已经有 `serviceHealthQuery`（设置页用它比对版本），复用即可。
- **确认版云端一行不改**：保留发布接口，旧客户端照常能用。没选「删路由」：Fastify 默认 404 的响应体旧客户端认不出，会报「远程需求服务返回了无法识别的响应」，旧版 Codex 工具还会提示「结果未确认，不要直接重发」，误导用户。
- **撤下的工具名保留在常量里**：`SUDUO_TOOL_NAMES` 不删，新增 `RETIRED_SUDUO_TOOL_NAMES`，派生在用工具名类型。旧会话时间线里的工具步骤还要显示中文标题（`timeline.ts` 的标题表按 `SuDuoToolName` 穷举）。Codex 续接旧线程时不会重新下发工具清单（`codex-runtime.ts` 只在新建线程时带 `dynamicTools`），旧会话里模型仍可能调用这三个工具；分发时对它们（含旧前缀 `zjwork_`）先回复「确认版已停用，附件请用 suduo_requirement_attachments 查看」，放在房间只读检查之前（否则房间里会误报「只能用只读工具」）。
- **附件「最新在前」在客户端排**：网页详情、速览、会话右栏，Codex 的附件工具与需求卡，都在拿到列表后按 `createdAt` 降序排。云端列表保持升序：新客户端连旧云端时也要对。
- **评论文件复用房间文件的存储实例**：同一个 `LocalDiskBlobStore`（`room-files` 目录，启动时只清半截上传，不对账、不删对象）。备份、恢复、部署脚本已经覆盖这个目录，不用加卷。不能放附件目录：附件存储启动时会物理删除「活跃附件 ∪ 版本引用」之外的一切对象。
- **评论文件挂在评论上用一列 `comment_id`，不用关联表**：「只属于这条评论」的语义更直接，未发送就是 `comment_id IS NULL`。
- **发评论时文件只能挂到「本需求、还没发出」的文件上**：条件是 `id = ANY($ids) AND requirement_id = $r AND comment_id IS NULL`，行数对不上返回 400 `VALIDATION_ERROR { field: "fileIds" }`。三问：仲裁者是发评论的人；拿掉 `comment_id IS NULL` 的最坏结果是文件被悄悄从评论 A 挪到评论 B，A 永久少了文件，而评论不可变（ADR-0004 第 5 条「不可变优先」，改挂等于不可逆地改写已发出的评论）；人无法恢复 A。所以保留，并配上「告知」：被拒后网页查文件状态，若已挂在评论上就说明「刚才这条评论其实已经发出」（见 4.2）。`requirement_id = $r` 是引用校验：拿掉的最坏结果是文件显示在别的需求的评论下（可恢复），保留它只为防止张冠李戴，不属于一致性守卫。不校验上传人（与房间一致）。
- **只有文件的评论**：正文约束（1..4000 字）不动。正文为空时云端写一条英文兜底正文（`Attached 2 files: a.png, b.pdf`，超长截断），并记 `system_kind = 'comment_files'`、`system_params = { fileCount }`，沿用迁移 012 的「类型 + 参数 + 兜底」机制。新客户端认出这个类型就只显示文件；旧客户端对不认识的类型显示兜底正文，不会出现空气泡。没选「放宽约束允许空正文」：旧客户端会显示空白评论。
- **点发送时才上传，遗留的不清理**：需求 R7。选中文件只放进评论框的待发列表（浏览器内存里的 `File`，图片用本机地址预览），点发送才逐个上传、再发评论；上传成功的文件编号留在评论框状态里，重发时复用。遗留只出现在「上传成功、评论发送失败且用户放弃」时。存储接口不加 `remove`。没选「正文和文件一个请求发出」：做不了逐个进度与单独重试，云端 `singleMultipartFile` 也要改成多文件解析。
- **「存为附件」在云端复制字节**：打开评论文件的流，交给 `AttachmentService.upload`（新附件编号、重算 sha256、100 个上限、审计 `attachment.created`、推 `attachment.changed`）。没选「共用存储键」：两份存储在不同目录、不同卷；`attachments.storage_key` 有唯一约束，同一文件第二次存就会冲突；附件删除与启动对账也要再加一层引用保护。代价是每存一次多占一份磁盘。
- **评论文件允许的类型 = 附件允许的类型**：类型按扩展名定（复用房间的 `file-types.ts`），允许列表取 `config.allowedAttachmentExtensions`，保证「存为附件」一定成功。S2 已把附件默认列表放宽到与房间一致，两者默认相同；部署时用环境变量收窄附件列表，评论文件跟着收窄。
- **历史确认版不显示发布说明**：`ArtifactVersionDto` 没有 `note`，说明只在活动时间线里。为它改云端 DTO 不值得，需求文档已同步。
- **ApprovalDock 里的发布确认卡删除**：本机服务重启时会把挂起的确认卡全部作废（`orphanPersistedPending`），升级后不会再有发布卡，这段是死代码。旧会话时间线里「发布确认版到 REQ-…」的投影保留。

## 四、核心流程 / 逻辑

### 4.1 按优先级翻页

```
web 列 「待开发」 → GET /api/v2/requirements?projectId&status=ready&sort=priority&priority=urgent,high&limit=50
  → BFF 白名单透传 → 云端解析：ranks=[4,3]，sort=priority
  → SELECT … WHERE project_id=$p AND status=$s AND priority = ANY($ranks)
       [AND (priority, updated_at, id) < ($rank, $ts, $id)]       ← 第二页起
     ORDER BY priority DESC, updated_at DESC, id DESC LIMIT 51
  → nextCursor = base64url({ timestamp: cursor_at, id, rank })
```

| 处理规则 | 说明 |
|----------|------|
| 时间精度 | 沿用 `cursorTimestampColumn()` 的微秒字符串 |
| 游标与排序方式 | `rank` 有无必须与 `sort` 一致，否则 400 |
| 翻页时被改 | 与现在一样：实时事件让整列失效，重新算每页；前端把各页 `flatMap` 后按 id 去重（看板、列表都补上） |
| 乐观插入 | `placeInColumns` 按当前排序方式找位置：`priority` 时按 (rank, updatedAt, id) 降序插入；落在已加载的最后一条之后、且还有下一页时不插，等重新拉取 |
| 并发 | 两人同时改优先级，后写的生效；活动时间线各记一条（ADR-0004，不拒绝） |

### 4.2 发一条带文件的评论

```
评论框：粘贴 / 拖入 / 点选 → 进待发列表（不上传）
  → 点发送：还没上传的文件逐个 POST /api/v2/requirements/:id/comment-files（multipart，XHR 带进度）
  → BFF 流式转发 → 云端：查需求存在 → 按扩展名定类型（允许列表 = 附件列表）
     → BlobStore.put（边写边算 sha256，超 300 MB 返回 413）→ INSERT comment_id=NULL → 201 CommentFileDto
  → 全部传完，接着 POST /api/v2/requirements/:id/comments { body, fileIds }
  → 云端一个事务：确认需求存在 → INSERT 评论（正文为空时写兜底正文 + system_kind）
     → UPDATE requirement_comment_files SET comment_id, position
          WHERE id = ANY($ids) AND requirement_id=$r AND comment_id IS NULL  （行数不符 → 400，整个事务回滚）
     → 审计 comment.created（after 带 files: [{ id, fileName }]）→ 推 comment.created
  → 评论出现在时间线，文件在正文下方
```

**模拟示例**：小李在 REQ-42 的评论框里粘贴一张 120 KB 的截图、拖入 `日志.txt`，写「导出按钮点了没反应」。点发送：两个文件各自上传，拿到 `f1`、`f2`；接着发评论，云端插入评论 `c9`，把 `f1`、`f2` 的 `comment_id` 设为 `c9`、`position` 为 1、2，写审计，推送事件。小王的详情页收到 `comment.created`，重取活动；评论 `c9` 下面是截图缩略图和日志文件卡片。小王点截图的「存为附件」：云端打开 `f1` 的字节流，按新附件写入附件存储，附件区最上面出现「报错截图.png（上传人：小王）」，时间线多一条「上传了附件」。

| 处理规则 | 说明 |
|----------|------|
| 发送时上传失败 | 评论不发出；失败的文件可单独重试或移除，已传好的保留编号，再点发送只补传没传好的 |
| 评论发送失败 | 正文与待发文件留在评论框（文件已在云端，编号仍有效，重发复用） |
| 发出后响应丢失再点发送 | 文件已挂到前一条评论，返回 400；网页查文件元数据（`GET /comment-files/:id`），全部已挂上就说明「刚才这条评论其实已经发出」、不放回正文；部分挂上就拿掉那些、其余留着 |
| 粘贴归属 | 评论框的 `onPaste` 收下文件并 `preventDefault`；附件区注册在 window 上的粘贴监听先判断 `event.defaultPrevented`，已被处理就跳过（同时核对房间悬浮窗口的输入框） |
| 能力判断 | `/v2/health` 的 `features` 不含 `comment_files` 时，不显示「添加文件」按钮，也不接收粘贴、拖入的文件 |

### 4.3 Codex 查看评论文件

```
suduo_requirement_comments → 每条评论下追加文件行：- f1 · 报错截图.png · image/png · 120 KB
suduo_attachment_view(attachmentId=f1)
  → 先在附件列表里找；找不到就 GET /v2/comment-files/f1，确认 requirementId 是本需求
  → 以 inline 方式下载（云端按扩展名给出真实类型）→ 复用图片 / 文本 / 落盘三条分支
```

### 4.4 撤下确认版工具后的旧会话

```
旧会话（线程续接，没有新工具清单）里模型调用 suduo_artifact_fetch
  → session-tool-service 分发：名字在 RETIRED_SUDUO_TOOL_NAMES（或旧前缀 zjwork_ 对应项）
  → 回复「确认版已停用，附件请用 suduo_requirement_attachments 查看」（按会话语言），不进房间只读检查
```

## 五、测试策略

- [ ] cloud/contracts：DTO 与 schema（priority、sort、fileIds、可空正文）；`RECORDED_AUDIT_ACTIONS` 精确列表；`features` 常量
- [ ] cloud/server 单元与集成：
  - 优先级设置、更换、清空：不递增版本、写审计、推送事件、同值不写；创建时带优先级；审计 after 带 `priority`
  - 筛选（含 `none`）；`sort=priority` 翻页：同档同时间戳多行、`limit=1` 连翻不重不漏（照 `expectStablePaging`）；游标与排序方式不符返回 400；不带 `sort` 时结果与游标格式不变
  - 活动时间线出现 `priority_changed`；`/v2/audit` 不返回它；`audit-project-id.test.ts` 穷举表加一项
  - 评论文件：上传（类型、大小上限 413）、关联（别的需求、已发出、不存在 → 400 且整体回滚）、只有文件的评论（兜底正文 + system 类型）、评论列表 / 详情 / 活动带出文件、下载（inline、Range、ETag）、存为附件（成功、到 100 个上限、审计与事件）
  - 附件允许扩展名放宽后 rar / mp4 能传

CREATE TABLE requirement_comment_files (
  id uuid PRIMARY KEY,

**已知限制（未改）**

- 健康检查还没回来或失败时，看板仍按优先级排，但排序切换入口隐藏，用户暂时切不回「最近更新」。
- 云端刚升级的那一刻，拿着旧游标的「加载更多」会 400 一次，重取后恢复。
- 复核顺带发现：`.env.example` 还写死了 `REQUIREMENTS_MAX_ATTACHMENTS_PER_REQUIREMENT=20`（注释称「唯一允许值」，与代码缺省 100 不符），脚本部署的服务器每个需求实际只能有 20 个附件。用户 2026-10-07 同意按推荐一并改：模板改为注释（缺省 100），部署脚本在 install / upgrade 时把一字未改的 20 注释掉，改过的保留。
