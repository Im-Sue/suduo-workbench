# SuDuo V2 工程实施技术设计

> 一句话：先稳定远程协作契约，再接本机 BFF/UI，随后补附件和实时协作；T4 清理旧数据与旧运行时能力，T5 完成部署发行和完整环境验收。｜最后更新：2026-08-15
>
> 📊 **当前进度：T1～T4 已交付，T5 暂缓（T5-1/T5-2 已交付，T5-3 挂起于外部环境与授权）** —— 见 [十一、实施进度总览](#实施进度总览2026-08-15-按分支代码校对)。代码在 `ccb/req-suduo-v2-requirements-workbench-001` 分支，尚未合并 `main`。

## 一、设计概述

V2 在 `suduo` monorepo 中新增独立远程应用 `cloud/server`。现有 `client/server` 保持本机 localhost 服务和 Codex 运行时职责，`client/web` 以 `/` 为唯一工作台壳，在壳内提供需求、会话、设置模式；共享类型统一放到 `client/contracts`、`cloud/contracts`。

| 项 | 说明 |
|---|---|
| 核心职责 | 将共享需求协作从本地 SQLite/TAPD 拆到远程服务，并把需求快照安全送到本机 Codex 会话。 |
| 设计原则 | 契约先行、服务端/本机职责隔离、浏览器仅访问 localhost、需求快照可复现、V2 不兼容旧数据。 |
| 需求来源 | [SuDuo V2 需求协作工作台](../02_需求设计/v2-需求协作工作台-需求.md) |
| 覆盖范围 | T1～T5 的应用、数据、接口、页面、旧能力清理、部署、发行和切换实施。 |
| 不覆盖 | 自动化测试新增、TAPD 兼容、权限后台、密码找回、服务端 Codex。 |

## 二、方案与架构

```
client/contracts 与 cloud/contracts
  └── requirements-v2 DTO / 枚举 / 错误码
        ▲                         ▲
        │                         │
requirements-service          client/server（localhost BFF）
Fastify + PostgreSQL + 受控附件目录   ├─ 本机登录态 / 远程 API 代理
  ├─ auth / projects               ├─ 文件流 / SSE 转发
  ├─ requirements / comments       ├─ 项目→工作目录映射
  ├─ attachments / audit           └─ 需求快照→本机材料→Codex 会话
  └─ events                                      ▲
                                                  │
client/web ───── localhost API ─────────────────────┘
统一 `/` 工作台壳：需求 / 会话 / 设置模式
```

| 关键原则 | 说明 |
|---|---|
| 新旧契约隔离 | 新增 V2 DTO，不继续扩展旧 `WorkItemDto` 或 TAPD 模型。 |
| 远程服务单一真相 | 共享项目/需求/评论/附件元数据只在 PostgreSQL；本机只存必要配置、token、会话和材料缓存。 |
| BFF 代理 | UI 不处理远程 token/CORS/服务器文件流，所有远程请求经本机 `client/server`。 |
| 复用而不误用 | 复用现有 Codex 会话运行时、审批、Skill、Composer；不把现有仅支持会话图片的 `attachment-store` 当成远程需求附件仓库。 |

### 与现有系统的关系

| 现有模块 | V2 如何改 | 保留 / 不动 |
|---|---|---|
| `client/server` | 新增远程服务客户端、本机认证态、目录映射、需求快照/材料同步与 BFF 路由。 | localhost 安全边界、Codex runtime、会话/审批基本能力。 |
| `client/web` | 重构为统一 `/` 工作台壳，在同一顶部栏和左栏框架内切换需求、会话、设置模式，接入 BFF。 | 现有深色视觉基调、会话运行态、消息、审批、工具调用与 Composer。 |
| `client/contracts`、`cloud/contracts` | 新增 V2 需求域 DTO、状态、错误码。 | 其他现有契约不因 V2 被隐式破坏。 |
| 本地 WorkItem/TAPD | T4 在精确清单、预览和用户确认后删除 V2 不再使用的路由、服务、迁移、对话框和数据。 | 不改 Codex runtime、技能、Composer 的独立能力。 |

## 三、关键决策与取舍

- **需求服务独立部署**：选 `cloud/server` + PostgreSQL + 服务器受控附件目录；不把远程协作塞进本机 `client/server`，避免共享数据和本机 Codex 边界混杂。
- **浏览器只访问 BFF**：选本机 `client/server` 持有远程 token 并代理；不让 Web 直连远程 API、服务器文件或静态附件目录，避免 token、CORS 和文件流边界分散。
- **需求与会话分别持久化**：远程服务只保存需求协作；本机服务继续保存会话/线程，避免把本地源码路径与 Codex 对话上传。
- **材料按快照拉取**：新会话下载明确版本的需求与附件；不让运行中会话自动追逐远程更新，保证上下文可解释。
- **先基础协作、后附件实时**：先令账号/项目/需求/评论/审计可独立验收，再接受控硬盘附件、SSE，降低第一阶段联调面。
- **清理与发行分阶段**：T4 只在受控、可回滚的清理清单内退出旧 SQLite/TAPD 数据及旧运行时能力；T5 再提供部署发行资产并完成完整环境验收，避免把破坏性清理和部署环境问题混为同一批次。

## 四、核心流程 / 逻辑

### 4.1 需求创建与审计

```
本机需求页 → BFF → requirements-service
  → 验证 Bearer token、项目活动状态、输入
  → 数据库事务：写 requirement / comment / audit（或状态前后值）
  → 提交后发布 requirement.changed 事件
  → BFF 转发 SSE 给本机页面
```

处理规则：需求的 `version` 在每次更新时递增；写操作要求携带期望版本或等价并发控制字段，冲突返回明确的版本冲突错误，页面提示刷新后再编辑。状态变更不受前置状态限制。

### 4.2 T2：从项目或需求创建本机会话

```
项目上下文「新建会话」或需求详情「在本机开始对话」
  → BFF 验证本机登录态与 remoteProjectId→localProjectId 映射
  → realpath + stat + R/W/X 校验本机绝对目录
  ├─ 映射无效：返回可处理的映射缺失/失效结果；Web 在当前上下文打开映射配置，保存并校验成功后带原请求续办
  ├─ 项目级：在映射目录创建既有 Codex primary thread，不写 requirement ref、需求版本或材料快照
  └─ 需求级：读取远程 RequirementDetailDto，校验其 projectId 与 URL/映射一致
       → 原子生成无附件快照 material/<project>/<requirement>/<version>/
       → SessionService.createFromRequirement 创建既有 Codex primary thread
           developer instructions = 需求标识 + 状态 + 快照版本 + 材料路径
       → 同一 SQLite 事务写 thread、active 状态、会话—需求快照引用
  → 返回本机会话；统一工作台切换为会话模式并选中该 sessionId
```

会话创建不区分产品、开发、测试等角色：任何已登录用户都受同一映射预检约束，且会话工作目录只能是当前电脑上该远程项目的有效映射目录。映射缺失、目录不存在或无 R/W/X 权限时绝不创建会话；“配置当前项目工作目录”是原操作上下文中的抽屉/对话框，而不是跳到另一套应用页面后要求用户重新发起。

本阶段 `attachments` 固定为空数组，不读写服务器硬盘，也不实现附件流和 SSE。需求快照建立失败时绝不创建需求会话；同版本目录已存在时只能完整校验后复用，校验不通过即失败，绝不覆写。`SessionService.createFromRequirement()` 必须令 `taskId = null`，不能把远程 requirement 伪装成旧 WorkItem，也不能调用 `workItemBriefing()`。项目级会话复用现有无 WorkItem 的创建能力，但创建参数必须使用映射得出的本机项目/目录，不能允许任意客户端路径覆盖它。

`v2_requirement_session_refs` 是需求会话重建简报的权威来源。`MessageService` 在 V2 会话恢复失败并重建 thread 时，从该引用重新生成 developer instructions；普通会话仍沿用既有 WorkItem 或自由会话路径。

#### 4.2.2 统一工作台模式、深链接与续办状态

`SuDuoApp` 是 V2 的唯一壳组件。它持有远程登录态、当前远程项目、当前会话和工作台模式；`RequirementsV2App` 不再作为路由根或独立壳保留。首个已登录的 `/` 默认进入需求模式；`/requirements`、`/sessions`、`/settings` 只是对 `WorkbenchMode` 的深链接恢复。四个 URL 都必须挂载同一个顶部栏、同一个左栏框架以及同一份会话 runtime 状态。

```text
WorkbenchMode = requirements | sessions | settings

/             → 壳 + requirements（首次默认）
/requirements → 壳 + requirements
/sessions     → 壳 + sessions
/settings     → 壳 + settings
```

- 未登录时不切换到独立登录页：统一壳主区显示 `RequirementsLogin`，成功后恢复进入前的 `WorkbenchMode` 和已选择项目。
- 需求模式只负责远程项目/需求/评论/审计内容；会话模式直接使用已有 session sidebar、消息、审批、工具调用和 Composer，不能复制一份运行时 UI。
- 顶部的远程项目选择器负责项目切换、创建项目、管理项目和发起项目级会话；需求详情负责发起需求级会话。
- 前端保存 `pendingSessionCreation = { kind: "project", remoteProjectId } | { kind: "requirement", remoteProjectId, requirementId }`。若 BFF 返回 `WORKSPACE_MAPPING_REQUIRED`，在当前壳打开映射配置对话框；成功保存后只重放一次该原请求，仍由 BFF 实时复验目录和需求归属。取消或保存失败时清除 pending 状态，不创建会话。

#### 4.2.3 项目级会话与列表口径

项目级会话不增加远程实体，也不增加 SQLite 表：它是映射得到的本机项目上的既有 `sessions` 记录，`task_id = null`、无 `v2_requirement_session_refs` 记录、工作目录由映射得到。`POST /api/v2/projects/:projectId/sessions` 不接收客户端目录、`taskId` 或远程 token；BFF 先调用与需求会话相同的映射预检，再以该本机项目 ID 调用既有 `SessionService.create()`。

`GET /api/v2/projects/:projectId/sessions` 只在当前映射有效时读取对应本机项目的会话，返回 `{ session, requirement: null | { remoteRequirementId, requirementVersion, materialPath, createdAt } }`。需求会话由引用补充 `requirement`，项目级会话为 `null`；切换阶段暂时同目录下的历史一般会话也按其现有 session 数据返回，不将其伪装为需求会话。删除映射不删除会话或快照，只使其不再属于当前远程项目的可列出范围，直至重新建立有效映射。

#### 4.2.1 原子快照顺序与失败边界

```text
远程详情已读取且项目一致
  → mkdir <data>/materials/<project>/<requirement>/.staging/<uuid> (0700)
  → requirement.json / requirement.md / manifest.json 写入、fsync (0600)
  → rename staging → <version>/，fsync 父目录
  → 创建 runtime thread
  → SQLite 事务：thread 映射 + 会话 active + v2_requirement_session_refs
```

- 快照目录固定为 `<SUDUO_V2_DATA_DIR>/materials/<remoteProjectId>/<requirementId>/<version>/`；`manifest.json` 记录 `requirement.json`、`requirement.md` 的 SHA-256、需求 ID、项目 ID、版本、`attachments: []` 与捕获时间。会话引用保存 manifest 文件 SHA-256。
- 目标目录不存在才允许 rename；已存在的同版本目录必须按 manifest 校验 ID、版本、文件清单和摘要后复用。任何缺失、额外可执行步骤或摘要不符均中止，不清空历史版本。
- runtime 创建失败将本地 session 标记 `error`，不会写 V2 会话引用；SQLite 持久化失败按现有不确定性语义报错并保留错误 session，不能宣称会话创建成功。
- T3 才把附件清单和受控硬盘下载加入此顺序；T2 的快照语义保持“需求正文的无附件版本”。

### 4.3 附件上传/下载与实时事件

```
浏览器 ──multipart/下载流──► 本机 BFF ──认证流──► 远程服务
                                                    │
                                        PostgreSQL（元数据/审计）
                                                    │
                                  受控附件根目录（专用持久卷）

远程服务 SSE ──Bearer──► 本机 BFF ──同源 SSE──► 浏览器
```

附件上传先写入 `REQUIREMENTS_ATTACHMENT_ROOT/.staging` 下的服务生成临时名，在 300 MiB（314,572,800 字节）默认限额内流式计算 SHA-256；校验成功后 fsync 文件，以服务生成的相对存储键原子移动到同一专用卷并同步父目录，再以数据库事务写附件元数据、递增需求版本并审计。每需求默认最多 20 个未删除附件。数据库写入失败时服务立即补偿删除已落盘文件，并通过启动清理重试已逻辑删除但仍在磁盘上的文件；未完成、逻辑删除或孤儿文件不得经下载 API 可见。删除操作先在事务内撤销元数据可见性、递增需求版本并留审计，再删除对应受控文件，失败由启动清理重试。下载在已鉴权且开始读取后记录审计。附件 DTO 返回 SHA-256，不返回存储键或服务器路径。

创建需求会话时先拉取需求详情和附件清单，把正文与附件流写入本机同版本 staging，逐个校验大小与 SHA-256，并在发布前再次读取需求详情复验版本；只有文件集、摘要和版本均一致时才原子发布快照并创建会话。任一下载、空间、校验或版本复验失败均不创建会话，也不覆写已有版本快照。SSE 事件只携带事件 ID、资源标识、需求版本和变更类型，UI 再按需读取最新详情；事件不承载正文且不作为持久日志，断线重连后以补拉当前状态恢复一致性。

## 五、验证策略

用户已明确本期不安排自动化测试，因此不新增单元、集成或端到端测试任务。每个阶段仍须执行以下非测试性验证：

- 构建：`pnpm build`。
- 类型检查：`pnpm typecheck`。
- 静态规范：`pnpm lint`。
- 人工闭环：按阶段验收路径在本机和内网服务环境手动走通。

未包含自动化测试不等于跳过验收；每个阶段的人工验收项见第十一节。

## 六、数据设计

### 6.1 PostgreSQL（远程服务）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | `id`、`login_name`、`display_name`、`password_hash`、时间戳 | 唯一登录名；密码只存摘要。 |
| `projects` | `id`、`name`、`is_archived`、创建/更新人、时间戳、`version` | 项目归档不删除历史需求。 |
| `requirements` | `id`、`project_id`、`title`、`summary`、`status`、`version`、创建/更新人、时间戳 | `status` 只允许固定六值。 |
| `requirement_comments` | `id`、`requirement_id`、`body`、`author_id`、时间戳 | 需求评论。 |
| `attachments` | `id`、`requirement_id`、`storage_key`、`file_name`、`content_type`、`size_bytes`、`sha256`、上传人、时间戳 | T3 启用服务器受控硬盘目录。`storage_key` 只能是服务生成的相对路径，不向 API 响应暴露。 |
| `audit_logs` | `id`、`actor_id`、`resource_type`、`resource_id`、`action`、`before_json`、`after_json`、时间戳 | 仅保存可审计摘要，敏感字段脱敏。 |

索引至少覆盖：项目下需求按状态/更新时间查询、需求下评论/附件按时间查询、资源审计按时间查询、用户登录名唯一查询。

### 6.2 本机 V2 数据目录

| 数据 | 用途 | 处理规则 |
|---|---|---|
| 远程登录态 | BFF 调用远程服务 | 仅本机保存，不发给浏览器。 |
| 项目目录映射 | `remoteProjectId → absolutePath` | 每次创建会话前校验；不上传。 |
| 需求材料缓存 | 需求 ID + 快照版本下的说明、manifest、附件 | 可按会话引用清理，不能覆盖已被会话引用的版本。 |
| 本机会话映射 | 会话 ID、远程需求 ID、快照版本 | 用于 UI 回显与复现。 |

V2 使用新的本机数据目录。最终切换后仅删除已解析的旧 SuDuo SQLite/TAPD 数据；用户源代码工作目录与 Codex 配置不在清理目标内。

### 6.3 T2 本机 SQLite 009

目标数据库是本机 `client/server` 已有的 better-sqlite3 数据库。新增 migration `009_v2_requirements_local_state.sql`，由既有 migration runner 顺序加载；不改写旧 `projects`、`sessions`、`work_items` 或 TAPD 表。

| 表 | 字段 / 约束 | 用途 |
|---|---|---|
| `v2_project_workspace_mappings` | `remote_project_id TEXT PRIMARY KEY`、`local_project_id TEXT NOT NULL UNIQUE REFERENCES projects(id)`、`created_at`、`updated_at`、`last_validated_at` | 强制一个远程项目只映射一个本机项目，且一个本机项目不被两个远程项目共用。目录路径仍以既有 `projects.root_path/root_path_key` 为唯一真相。 |
| `v2_requirement_session_refs` | `session_id TEXT PRIMARY KEY REFERENCES sessions(id)`、`remote_project_id`、`remote_requirement_id`、`requirement_version INTEGER CHECK (> 0)`、`material_path`、`manifest_sha256`、`created_at` | 将成功创建的本机会话绑定到不可变远程需求快照。 |

索引：`v2_requirement_session_refs(remote_requirement_id, requirement_version)`，以及按远程项目查询会话所需的 `(remote_project_id, created_at DESC)`。表、字段和索引均为新增，无历史回填、无生产共享数据库写入。

映射保存遵循以下次序：先请求远程项目确认当前用户可见，再校验输入为无 NUL 的绝对路径（POSIX 与 Windows 均检查）、`realpath`、目录 `stat` 与 `access(R_OK|W_OK|X_OK)`；随后按现有 `root_path_key` 查询或创建本机项目记录；最后在 SQLite 事务内检查双向唯一映射并写入。若已被另一个远程项目占用，返回 `WORKSPACE_MAPPING_CONFLICT`；删除映射只删除该表记录，不删除本机项目、会话或材料目录。

**兼容与回滚**：009 仅加表，停止 T2 时可撤回 `/api/v2` 和 Web 路由而不删表、不删快照。禁止为回滚删除 `projects/sessions` 或用户工作目录；若确有完全卸载需求，留到 T4 的用户确认清单中逐项预览后处理。（本段为 T2 期约束；T4 起本机 SQLite 按 D4 视为可丢弃运行态，迁移链目标形态见 T4 小节，但「不删用户工作目录」仍然有效。）SQLite 文件为本机运行态，沿用现有 migration 机制，不新增服务根 `sql/`、回滚 SQL 或 `EXECUTED.md`；项目 SQL 增量规则面向本项目的 MySQL 服务不适用于此 SQLite 内嵌 migration。

### 7.3 BFF 共通约定

本机路由保持 `LoopbackGuard` 的 loopback Host 与写请求同源 Origin 约束，并以 `/api/v2/` 命名，与旧 WorkItem/TAPD 路由隔离。所有浏览器请求均为相对 localhost 路径；BFF 只允许下表列出的远程调用，不实现“任意远程 URL/方法/请求头”透传。

### 9.2 T2 本机认证与远程客户端

`SUDUO_REQUIREMENTS_SERVICE_URL` 是首次启动的默认值；用户可在统一工作台的设置模式保存覆盖值。`SUDUO_V2_DATA_DIR` 默认落在既有本机数据目录下的独立 `requirements-v2/` 子目录，目录权限为 0700。配置和 token 使用不同原子 JSON 文件，写入顺序均为临时文件（0600）→ fsync 文件 → rename → fsync 父目录；读取时修复为 0600。Windows 沿用现有凭证存储的用户 ACL 修复策略。

### 9.3 T3 附件与事件安全边界

- 浏览器只访问 localhost；BFF 只代理固定附件和 SSE 路径，远程 token 只进入 BFF 发出的 `Authorization` 请求头，响应、事件和日志均不得包含 token。
- 上传、下载、会话材料同步与 SSE 全链路流式处理。300 MiB 附件不得在浏览器或 BFF 聚合为 Blob/Buffer；远程附件卷和本机材料目录在写入前按声明大小预检可用空间，并以实际流量上限兜底。
- 文件名只作为经过控制字符清理的展示名和 `Content-Disposition` 下载名；存储键、staging 名和本机附件文件名均由服务生成，任何原始文件名都不能参与路径拼接。
- HTML/HTM 与 SVG 允许保存，但与其他附件一样视为不可信输入：不提供在线预览，下载固定 `Content-Disposition: attachment`、`X-Content-Type-Options: nosniff`、`Content-Type: application/octet-stream`。本机会话简报明确不得把附件内容当系统指令、不得自动执行其中脚本或命令。
- SSE 连接必须完成远程 Bearer 鉴权；BFF 对浏览器保持同源并在断开时中止远程连接。服务发送心跳，浏览器使用 `EventSource` 自动重连；重连成功后补拉当前项目/需求/评论/附件状态，不依赖事件回放。

| 文件 | 内容 | 浏览器可见性 |
|---|---|---|
| `requirements-service.json` | `schemaVersion`、规范化 `baseUrl` | 仅 GET settings 的脱敏地址可见。 |
| `auth-session.json` | `schemaVersion`、绑定的 `baseUrl`、`accessToken`、`expiresAt` | access token 永不可见；只返回用户和过期时间。 |
| `materials/**` | 版本化无附件需求快照 | 仅经需求会话元数据展示；不提供文件读取 API。 |

远程客户端只接受无用户名/密码、无 query/fragment、根路径为 `/` 的 `http:`/`https:` URL，并持久化规范化 origin。每次请求采用固定超时、`redirect: "error"` 和显式 `Authorization: Bearer`；不跟随跳转，不把 token 发给新主机。更换 URL 必须先清旧 token 再保存新地址；token 的 `baseUrl` 与当前配置不相等也必须视为无效。远程返回 401、`AUTH_REQUIRED` 或 `AUTH_INVALID` 时立即清 token，再向浏览器返回 `AUTH_INVALID`。网络失败统一映射为无敏感详情的 `DEPENDENCY_UNAVAILABLE`。

## 十、迁移影响与风险

| 风险 | 影响 | 缓解 / 恢复 |
|---|---|---|
| 契约未稳定就同时改三端 | 联调反复、页面与服务不一致 | T1 先稳定 contracts 和远程 API；T2 只消费已确认版本。 |
| 需求材料下载半成 | Codex 读到不完整材料 | manifest 标明完整性；下载失败不创建会话或标为失败后重试。 |

| 更改远程地址后携带旧 token | token 被误发给非预期服务 | URL 变更先清 token，token 文件绑定规范化 baseUrl，客户端禁重定向。 |
| 两个远程项目映射同一本机目录 | 会话在错误源码目录执行 | 映射表双向唯一；保存前按 `root_path_key` 复用/冲突检查，创建会话再实时校验。 |

| 旧流程残留 | 用户继续使用 TAPD 或本地需求 | T4 统一移除已确认入口、配置、运行时代码和数据；清理前人工核对范围。 |

| 误删本机用户数据 | 丢失源码或 Codex 设置 | 清理脚本仅接收已解析的旧 SQLite/TAPD 目标；绝不使用宽泛目录/通配符，先预览再执行。 |
