# SuDuo V2 会话需求上下文闭环 技术设计

> 一句话：BFF 代模型访问远程，把「现状」维护成一份会话可读的文件；模型只读文件，不联网。｜最后更新：2026-08-30
>
> **无独立 status** —— 跟随 `suduo-v2-session-context-closure-001`。

---

## 一、设计概述

先说清楚这个方案为什么长这样。

会话里的模型跑在 Codex 沙箱中，而沙箱**关死了网络**——`ask` 和 `auto` 两档都访问不了 `127.0.0.1`（pr1 实测，`network_access` 是唯一决定因素，无 loopback 例外）。所以「让模型自己去查远程」这条路，除非把会话开成 `full` 档（不设限、不询问），否则走不通。而出厂默认档是 `ask`。

但沙箱管的是**写和网络，不是读**。BFF 是宿主进程，根本不在沙箱里，它想访问远程随时可以。

于是方案就一句话：**BFF 去查，把结果写成文件；模型只读文件。** 模型一次网络都不用发，三个档位全都能用。

| 目标 | 做法 |
|---|---|
| 模型知道远程现在什么样 | BFF 维护 `current.md`，模型直接读 |
| 「查不到」不能说成「没有」 | 文件头带观测时刻与订阅状态；失败时**整份替换**为降级说明 |
| 基线可追溯性不受损 | 现状文件与 `materials/v3-*` 完全隔离，永不回写 |
| 变更检测有唯一信号源 | 远程审计日志 + 会话锚点书签 |

**验收北极星**：模型能说出「你的基线是 v2；远程现在 v5，有 3 条评论、1 个附件，差异是……要我拉下来吗？」

## 二、方案与架构

```
远程需求服务
   │  SSE /v2/events（无 replay，仅内存扇出）
   │  REST：audit / comments / attachments / requirements
   ▼
BFF · RequirementObservationService（宿主进程，不受沙箱约束）
   │  写：临时文件 → fsync → rename（原子）
   ▼
<projectRoot>/.suduo/observations/<sessionId>/current.md
   ▲
   │  只读（ask / auto / full 三档均可）
Codex 会话
```

### 2.1 现状文件落在哪：运行时探测，两个落点

落点直接决定一件事：**模型能不能改这份文件**。实测（生产版本 codex 0.143.0）：

| 落点 | 模型可读 | 模型可篡改 |
|---|---|---|
| `<dataDir>/observations/`（工作区**外**） | Linux/WSL2 ✅，原生 Windows 未验证 | ❌ 沙箱报 `Read-only file system`，`chmod` 也绕不过 |
| `<projectRoot>/.suduo/observations/`（工作区**内**） | 全平台必然可读 | ✅ 可写、可删、`chmod 0644` 后可改 |

工作区内**没有任何机制**能阻止模型改这份文件：文件权限位挡不住（BFF 与 Codex 同 UID，所有者总能 `chmod`），删掉父目录里的文件重建也能绕过。沙箱的路径级保护只覆盖 `.git` / `.agents` / `.codex`，`.suduo` 不在其中（实测 `.git/config` 写入被拒、`.suduo` 下写入成功）。

因此采用**运行时探测 + 自动降级**：

1. BFF 启动时用 `codex sandbox -c sandbox_mode=read-only -- cat <探针>` 探测数据目录可读性。这是纯命令行调用，**不发起 LLM 回合**，成本可忽略；`codexBin` 已是既有配置。
2. 探测通过 → 用 `<dataDir>/observations/`，模型只读不可写，BFF 单向维护天然成立。
3. 探测失败（如原生 Windows 拒绝工作区外读取）→ 降级到 `<projectRoot>/.suduo/observations/`，目录内自带 `.gitignore`（内容 `*`）。此路径下**放弃强防篡改**，改为 BFF 每次刷新前比对上次写入的 hash，发现被改则记录并重写。
4. 当前生效落点写进 briefing，模型只认这一个路径。

### 2.2 库存与时间线分层

这是本设计最重要的一条分层，它决定了降级时哪些信息仍然可信。

| 信息 | 来源 | 承诺 |
|---|---|---|
| **库存**：现在有几条评论、几个附件、正文是什么 | `listComments` / `listAttachments` / `getRequirement` 权威端点 | **必须准确** |
| **时间线**：锚点之后谁做了什么 | `/api/v2/audit?resourceId=<reqId>&projectId=<pid>` | 尽力而为，可截断 |

**不为了发现既有评论/附件去翻审计到需求创建**——那既慢又没必要，权威清单本来就给出完整库存。审计只负责表达「自你开工以来发生了什么」。

翻页设上限；超限时在文件里标注「更早的时间线未列出」，但**库存数字不受影响**。这样降级是优雅的：时间线不完整不会污染库存的可信度。

### 2.3 变更检测

- **L1（有没有变）**：`?resourceId=<reqId>&projectId=<pid>&limit=1`，比对最新条目游标与锚点。
  **不过滤 action** —— L1 只判断「审计游标有没有前进」。最新一条即使是 `attachment.downloaded`（他人下载，无实质变更）也照样触发 L2，误报的代价仅是多做一次 L2。这样就不需要远程提供 action 过滤参数。
- **L2（变了什么）**：翻页到锚点，此时才做语义过滤（剔除 `attachment.downloaded` 等只读事件），聚合成人话。

`resourceId` 过滤已内建 `before_json`/`after_json` 的 `requirementId` 匹配（`collaboration-repository.ts:643-649`），**不能传 `resourceType`**——它是精确匹配，会把评论、附件、产物事件全部过滤掉。

### 2.4 刷新触发（SSE 不能是唯一机制）

远程 `RequirementsEventHub` 仅内存扇出、**无 replay**（`event-hub.ts:9-38`），断线区间的事件永久丢失。因此 SSE 只是「加速器」，不是可靠通道。

BFF 维持**一条全局 SSE 连接**（远程 `/v2/events` 不带过滤参数，每会话一条会重复收全量），按 `requirementId` 去重后扇出刷新多个会话文件。

四个时机必须做 REST 全量收敛，不依赖 SSE：连接建立时、重连后、会话激活时、超过 TTL 时。

## 三、关键决策与取舍

| 决策 | 结论与理由 |
|---|---|
| 模型联网还是 BFF 代劳 | **BFF 代劳**。沙箱关网是硬约束，让模型联网只能靠 full 档（不设限不询问），代价不成比例 |
| 现状文件落点 | **项目工作目录**。用户决定不做 Windows 平台验证，直接取全平台必然可读的路径 |
| 改不改远程 API | **不改**（用户拍板）。库存走权威端点、时间线深度可控，现有端点已够用 |
| 时钟偏移 | **本机 SQLite 加锚点书签**（用户批准）。不用容差——两台机器时钟对不齐会**永久性**误分类「开工前/开工后」 |
| 评论发送超时 | **不重试**，自动查证一次后明确告知。远程 POST 无幂等，重试可能重复发不可撤回的评论 |
| 降级表达 | **整份替换**文件，而非只加状态字段 |

### 被拒绝的方案

| 方案 | 拒绝理由 |
|---|---|
| 要求切 `full` 档 + skill 直连 BFF | 出厂默认 `ask`，等于默认不可用；`full` = `danger-full-access` + 不询问 |
| 放宽 `assertM1SecurityPolicy` 增加第四档（`workspace-write` + 开网） | pr1 实测该组合确实可达 loopback，但要引入非标准档位、改变既有安全模型，用户还要多理解一个档位 |
| 一次性预取、不接 SSE | 会话中途的变更看不到，部分退回原问题 |
| 现状写入 `materials/v3-*` 或 manifest | 污染基线；快照按 `v3-${version}` 复用，评论不递增版本会造成伪基线 |
| 翻审计到需求创建以发现既有评论/附件 | 慢且无必要，权威清单端点直接给出完整库存 |

## 四、核心流程 / 逻辑

### 4.1 会话创建（建立锚点）

1. **先**拉一次审计最新有效条目，把 `(createdAt, id)` 游标写入 session ref 作为锚点书签
2. **再**生成 v3 快照（现有逻辑不变）
3. 首次全量收敛：拉库存 + 锚点后时间线，写 `current.md`
4. briefing 告知模型：基线在哪、现状文件在哪、失败时怎么说

**顺序不可颠倒**：锚点必须早于快照，否则两者之间发生的变更会被永久漏掉。现有创建流恰好是相反顺序，实施时需调整。宁可多报（落在锚点与快照之间的事件标记为 bootstrap 窗口），不可漏报。

### 4.2 端到端走查示例

> PM 昨天在需求下留了 2 条评论、传了 1 个附件；开发今天从需求进入对话。

1. 会话创建 → 锚点记为今天此刻 → 首次收敛拉到：库存 5 条评论 / 1 个附件，锚点后时间线为空
2. `current.md` 写入：`基线 v2 ｜ 远程当前 v5 ｜ 评论 5 条（0 条在你开工后）｜ 附件 1 个`
3. 开发问「有什么补充说明吗」→ 模型读文件 → 答「需求下共 5 条评论，都在你开工前，其中 PM 说……」
   —— 注意这里**不是**「没有变动」。存量靠库存回答，不靠时间线。
4. 会话进行中 PM 又加 1 条评论 → SSE 推 `comment.created` → BFF 刷新 → 文件变为 `6 条（1 条在你开工后）`
5. 若此时远程掉线 → BFF 收敛失败 → `current.md` 被**整份替换**为：「现状暂不可用：远程服务连接失败（最后成功观测 14:02）。当前无法确认是否有新评论，请在 SuDuo 界面核对。」
   —— 模型读到的就是这段话，**读不到过期库存**，因此无法「自信地报旧数据」

### 4.3 降级为什么要整份替换

原设计是在文件头写 `订阅状态: stale`，指望模型看到后按三态作答。Codex 指出这不可靠——**模型可能忽略状态字段直接引用内容**，而这正是当前 bug 的模式（有信息但不用）。

所以：`live` 时文件是完整现状；`stale`/`unavailable` 时**整份替换**为仅含失败原因与最后成功观测时刻的说明，旧内容移出模型可读路径。让模型**物理上读不到**过期数据，比指望它读状态字段可靠。

### 4.4 评论提交（UI 执行，模型不发）

1. 模型在对话里写出完整评论文本（结构化标记，仅是**建议**）
2. UI 严格解析，解析失败就不出卡片；操作绑定**当前会话的 requirement**，不信任模型给出的 ID
3. 用户看到全文后点发送 → BFF 执行 `POST /comments`
4. 成功 → 立即回显内容与评论 id
5. **超时/结果不明** → 不重试；自动 `GET listComments` 查证一次；仍不确定则提示：「发送结果未确认，请在需求页核对是否已存在，**不要直接重发**」

模型不得自主发起，也不得主动建议发评论。UI 另提供不依赖模型输出的通用入口作兜底。

### 4.5 生命周期

| 会话状态 | 现状文件 |
|---|---|
| `active` | 持续刷新 |
| `archived` | 停止刷新，保留（可恢复），超过 TTL（30 天）自动清理 |
| `deleted` | 立即删除 |
| `error` | 不刷新 |

`archived` 会话可以恢复成 `active`（`session-service.ts:279-282` 会重建 thread），所以不能一归档就删。`deleted` 是软删、session ref 仍保留，但现状文件应即时清理。

## 五、测试策略

| 层 | 覆盖 |
|---|---|
| 单元 | 锚点比对（含 bootstrap 窗口）；只读 action 过滤；翻页上限与截断标注；降级文件生成 |
| 集成 | SSE 断线 → 重连 → REST 收敛不丢事件；会话状态流转对应的文件生命周期 |
| 契约 | **每个变更类远程 API 调用后断言审计有对应新增**（防未来静默漏写，见需求 R-1） |
| 端到端 | 4.2 的走查全流程；存量评论场景（锚点后无事件但库存非空）必须答「有」而非「没有」 |
| 平台 | 只读位在 POSIX 与 Windows 下均阻止模型写入现状文件 |

**关键反例测试**（对应需求 BR-2 / BR-3）：

1. 只加评论不改正文 → 远程版本号不变 → 必须仍能检测到变更
2. 锚点后无任何事件、但库存有 5 条评论 → 必须答「有 5 条（都在你开工前）」，不得答「没有变动」
3. 最新审计条目是 `attachment.downloaded` → L1 触发、L2 过滤 → 不得报「有实质变更」

## 六、数据设计

**本机 SQLite（用户已批准）**：`v2_requirement_session_refs` 增加审计锚点书签列（游标 `createdAt` + `id`）。迁移链当前为 `[1, 2, 10]`，新增一版。

不改远程 schema。不改 manifest schema（v3 保持原样）。

**文件**：`<projectRoot>/.suduo/observations/<sessionId>/current.md`，同目录写入 `.gitignore`（内容 `*`）。

---

## 七、接口设计

不新增远程 API，全部复用既有端点（详见需求文档「十、接口（草案）」）。

本机 BFF 新增：现状文件刷新的内部触发，以及 UI 侧评论发送与附件拉取的执行入口。

---

## 九、依赖与配置

不引入新依赖——Node 原生 `fetch` + `ReadableStream` 足以消费 SSE。

配置项：现状刷新 TTL、审计翻页上限、`archived` 保留天数（默认 30）。

## 十、迁移影响与风险

| 风险 | 缓解 |
|---|---|
| **模型忽略降级状态引用过期数据** | 整份替换文件，让它物理上读不到（4.3） |
| **SSE 断线丢事件** | SSE 仅作加速器；四个时机强制 REST 收敛（2.4） |
| **审计漏写导致静默失效** | PR1 补漏 + 收口 + 契约测试；这是唯一信号源 |
| **评论重复发送** | 不重试 + 自动查证 + 明确禁止用户盲目重发（4.4） |
| **模型改动现状文件** | 探测优先落工作区外（沙箱天然只读）；降级到项目目录时无法强防，改为刷新前 hash 比对并重写（2.1） |
| **他人评论正文留存本机** | `archived` 30 天 TTL；`deleted` 即时清理；复用 `repairPrivateFile()` 做 Windows ACL |
| **Windows ACL 既有缺口** | `material-service.ts:635` 在 Windows 跳过 chmod，而 `local-json-store.ts:75` 已有 icacls 实现未被复用。本期顺带接上（用户已批准） |
| 长会话翻页深度退化 | 翻页上限 + 截断标注；库存不受影响 |
